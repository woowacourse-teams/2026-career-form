# DOM Snapshot Collection

모델이나 이전 대화의 메모리에 의존하지 않는 수집 절차다. 브라우저 도구는 현재
환경의 도구 설명과 스킬을 읽고 선택한다. 특정 REPL 전역 변수, 실행 파일 경로,
회사 주소, Issue 번호를 이전 세션에서 가져오지 않는다.

## 시작 전에 읽을 파일

이 파일을 `.agents/skills/cf-dom-snapshot-collection/SKILL.md`에 설치한 기준이다.

- `../../../harness/policies/dom-snapshot-fixtures.md`
- `../../../harness/templates/dom-snapshot-review.md`
- 현재 Issue 본문과 저장소의 `AGENTS.md`
- 대상 어댑터 문서와 실제 수집·반복 행·쓰기 코드 중 이번 단계에 필요한 부분

정책이 정본이다. 정책을 완화하는 범용 정제기를 만들지 않는다. 이 절차의 코드는
대상별로 사람이 검토하는 일회성 추출 코드다.

## 재개 가능한 체크포인트

`git rev-parse --git-path cf-workflow`로 실제 worktree 메타데이터 경로를 구한다.
그 아래에 검토용 파일과 체크포인트를 둔다. 실행 전 현재 상태를 읽고 이어서 한다.

체크포인트에는 다음만 기록한다.

- Issue, 공개 site_id, 범위, 기대 결과와 비식별 관찰 결과
- 준비 상태와 반복 행 종류별 예상 개수
- 승인받은 추출 규칙과 코드 경로, 승인 후 코드 변경 유무
- 정제본 경로, 정제 전후 구조 통계, 합성 상태, 누락 동작
- 개인정보 검토 / 구조 보존 검토 / 외부 요청 검사 / 재현 / 변이 검사 각각의 상태
- 실행 명령, 종료 코드, 제품 코드 revision, 다음 단계

원본 DOM, 실제 지원서 값·URL, 계정·세션 정보, 식별자 대응표는 기록하지 않는다.
설치본 revision은 별도로 증명하지 못하면 `UNVERIFIED`다.

## 1. 범위와 준비 상태 확인

1. 사람이 지정한 대상만 조사한다. 같은 플랫폼의 다른 회사로 대체하지 않는다.
   후보 탭이 둘 이상이면 대상부터 확정한다.
2. 실패 영역에 필요한 최소 범위를 정한다. 사용자가 전체 폼을 명시한 경우에도
   헤더·푸터·다른 폼·폼 밖 템플릿까지 자동으로 포함하지 않는다.
3. 브라우저 연결 전 자동 DOM·접근성 트리·스크린샷·Console·네트워크 저장이
   차단되는지 확인한다. 보장하지 못하면 연결하거나 추출하지 않고 중단한다.
4. 허용된 읽기 작업으로 원본을 브라우저 안에서만 검사하고 구조 통계만 반환한다.
   영역별 control 종류·개수, 반복 행 종류·개수, 옵션 수, 참조 누락·중복 ID 수를 센다.
5. 추가 버튼의 존재와 반복 행의 존재를 구분한다. 고등학교·대학·대학원처럼
   다른 행 종류는 각각 센다. 사람이 행을 열었다고 해도 DOM에 있는지 확인한다.
6. 필요한 행이나 상태가 없으면 사람이 준비하도록 요청한다. 준비 후 다시 센다.
   AI가 추가·삭제·선택·저장·제출·이동·미리보기를 실행하지 않는다.

이 단계의 산출물은 원본 전문이 아니라 범위와 상태의 비식별 확인 결과다.

## 2. 허용 목록과 추출 코드 검토

현재 어댑터가 실제로 읽는 속성을 조사한 뒤 대상별 허용 목록과 코드를 제시한다.
사람 승인을 받은 코드만 실행한다. 규칙을 바꾸면 변경 부분을 다시 검토받는다.

- `id`, `name`, `class`는 전부 제거하지 않는다. 필요한 공통 토큰인지 검토하고
  불명확하면 일관되게 치환한다. 짧은 영숫자라는 이유만으로 비개인정보라고 단정하지 않는다.
- `for`와 ARIA 참조는 같은 치환표를 사용한다. ID 자체와 공백으로 구분되는
  ARIA ID 목록을 구분한다. `for`를 임의로 공백 분리하지 않는다.
- 원본의 끊긴 참조와 중복 ID를 몰래 고치지 않는다. 정제로 새 오류가 생겼는지 따로 센다.
- 값·기본값·선택·체크·편집 본문, 숨김 데이터, 개인화 문구는 정책대로 제거한다.
  정규식이나 입력값 반향 제거만으로 공통 텍스트 검토를 대신하지 않는다.
- 선택지 표시명과 value 코드를 따로 검토한다. 이메일 도메인 같은 공통 선택지를
  일괄 치환하면 의미가 사라질 수 있으므로 보존 여부와 한계를 명시한다.
- `data-*`는 기본 제외하고 필요한 키·값만 검토한다. Greeting의 `data-scope`,
  `data-part`, 상태 속성도 자동 허용하지 않는다.
- 원본 CSS는 제거한다. 필요한 숨김 상태는 합성 `hidden` 등으로 명시하고 기록한다.
  CSS 숨김, `aria-hidden`, viewport 밖, native input을 대신하는 custom control을
  같은 의미로 세지 않는다. 전후 통계에는 동일한 판정 함수를 적용한다.
- 값이 있던 칸을 비워도 동적 빈 상태 표시가 자동 복원되지는 않는다.
  체크 상태만 비우고 다른 상태가 남으면 불일치로 기록한다.
- 포털 선택지, Shadow DOM, iframe, 폼 밖 템플릿은 포함 여부를 명시한다.
  닫힌 메뉴에 옵션이 없다는 관찰만으로 모든 동적 동작을 확정하지 않는다.

새 비활성 문서로 허용 정보만 옮긴다. 원본을 변경하거나 먼저 반환해 정제하지 않는다.
검증 실패 시 문제 문자열이나 예외 객체 대신 실패 종류만 반환한다.
통과한 정제본만 비추적 파일로 저장하고 사용자에게는 구조 통계와 경로를 전달한다.

## 3. 정제 전후 구조와 사람 검토

원본은 저장하지 않고 브라우저 내부에서 다음을 대조한다.

- control 종류·수와 섹션 소유 관계
- 반복 행 종류·수·순서와 행별 control 수
- 라벨 연결, 주변 문맥, 선택지 개수·순서
- 참조 대상 누락·중복, 팝업 소유 관계
- 숨김·읽기 전용·비활성 상태

총수 일치만으로 구조 보존 통과를 선언하지 않는다. 달라진 항목은 정제 영향,
원본 결함, 의도된 제외로 구분한다.

사람의 개인정보 검토와 구조 검토를 별도로 받는다. 개인정보 “통과”를 구조
승인으로 해석하지 않는다. 원본 화면과 정제본의 DOM 구조 대조표를 먼저 제공하고,
제품 수집 결과 표는 별도로 표시한다. 제품 수집기의 누락을 정제본 누락과 혼동하지 않는다.
표시용 합성 CSS를 쓰더라도 원본 화면과 같은 디자인이라고 주장하지 않는다.

## 4. 제품 수집 결과 검증

현재 코드의 타입과 직렬화 구조를 먼저 읽는다. 임의의 속성명을 추정한 타입 단언으로
검사를 작성하지 않는다. 현 계약의 후보는 일반 필드와 반복 행 필드를 모두 포함한다.

```ts
const fields = snapshot.request.sections.flatMap((section) => [
  ...section.fields,
  ...(section.items ?? []).flatMap((item) => item.fields),
]);
```

총수뿐 아니라 섹션별 일반 후보 수, 반복 묶음 수, 묶음별 후보 수를 기록한다.
`fields`만 읽어 학력·경력 등이 없다고 결론 내리지 않는다. DOM control 수와
제품 후보 수는 radio 묶음·custom control·제외 규칙 때문에 다를 수 있다.

대조표는 섹션과 반복 행 소속을 보존한다. 일반 필드 뒤에 행 필드를 붙인 순서는
DOM 순서와 같다고 보장되지 않는다. 화면 순서라고 표시하려면 registry의 실제
노드 순서와 대조한다. 구조 검토에는 추가 버튼과 제외 컨트롤도 별도로 기재한다.

테스트의 문서 URL은 필요한 어댑터 선택에 맞게 설정하고 테스트 종료 시 복원한다.
수집 어댑터 판정 자체도 확인한다. localhost에서 범용 경로로 실행한 결과를
회사 전용 어댑터 결과라고 쓰지 않는다.

## 5. 오프라인 재현과 테스트

1. 네트워크가 차단된 로컬 브라우저에서 외부 요청 시도 0건을 확인한다.
   HTML에 script가 없거나 jsdom 테스트가 통과한 것으로 이 검사를 대신하지 않는다.
2. 실패 단계의 기존 제품 함수로 실행한다. 수집 → 검토 → 쓰기 중 실제 실행한
   단계와 mock한 경계를 구분한다. 이메일 문자열을 포함한 동의 칸을 이메일
   입력란으로 간주하지 말고 실제 control과 의미를 확인한다.
3. 고정 API 응답·편집 mock은 실제 LLM 매핑이나 사이트 값 수락을 입증하지 않는다.
   정제본에서 성공해도 원인이 반드시 사이트 JS라는 결론은 내리지 않는다.
   제거된 상태·관계나 mock 차이도 남은 가설이다.
4. 관찰 실패 재현과 구조 기준선 검사를 구분한다. 구조 기준선만 확보했다면
   실패를 재현했다고 쓰지 않는다. 정책상 별도 승인이 필요한 등록은 보류한다.
5. 테스트는 실제 구조 관계와 동작을 검증한다. 제품 버그를 이 작업에서 고치지
   않는다. 현재 실패를 고정하는 검사가 통과해도 기능 수정 완료가 아니다.
6. 원인 후보 구조를 메모리상의 정제 DOM에서 바꿔 결과가 달라지는지 검사한다.
   변이를 실제 픽스처에 섞지 않는다. HTML 전체나 문서 문구를 고정하지 않는다.
7. 관련 테스트·타입 검사·형식 검사와 저장소 필수 검증의 종료 코드를 확인한다.
   파이프로 출력만 거르고 원래 실패를 잃지 않는다. 무조건 참인 assertion은 쓰지 않는다.
   고정 sleep이나 우연한 타이밍으로 통과시키지 않는다.

재현하지 못했다면 보류한다. 대조표나 집계 오류를 발견하면 같은 방식을 사용한
다른 픽스처 기록도 확인하되 관계없는 제품 수정은 하지 않는다.

## 6. 등록과 전달

개인정보 검토, 구조 검토, 외부 요청 검사와 필요한 재현을 모두 통과한 자료만
정식 fixture 경로에 등록한다. 미완료 자료를 “조건부 등록”으로 우회하지 않는다.
메타데이터는 정책의 계약을 사용하고 실제 실행한 명령·revision·변이 근거를 남긴다.

정적 파일의 `file://` 접근은 확장 실행을 보장하지 않는다. manifest의 주입 대상과
런처 조건을 별도로 확인한다. 실제 브라우저에서 픽스처를 열어도 제거한 사이트
스크립트가 돌아오지는 않는다. 최종 보고에는 다음 경계를 구분한다.

- 정제본의 구조 보존
- 기존 제품 함수의 오프라인 처리
- 확장을 로드한 브라우저 통합 실행
- 실제 사이트의 상태·이벤트·서버 반응

작업 소유 임시 참조·프로브·서버만 정리하고 사용자의 페이지는 변경하지 않는다.
수집 중단 / 보류 / 등록 가능 중 하나를 근거와 함께 보고한다.
커밋·push·PR·Wiki 반영은 각각 기존 승인 범위를 따른다.
