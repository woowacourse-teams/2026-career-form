# 자동 기입 패널 비교 실험 — CF-132

## 실행과 배포

- Node.js 22 이상. 저장소의 기존 frontend 의존성을 사용한다.
- 로컬: `npm --prefix frontend run dev:site`, `/experiment/`에 접속한다. 포트 충돌 시 `npm --prefix frontend run dev:site -- --port 4176`을 사용한다.
- Vercel 설정: Root Directory `frontend`, Build Command `npm run build:site`, Output Directory `dist-site`, Framework Preset `Other`.
- `dist-site/experiment/index.html`을 포함한 기존 사이트의 다중 HTML 진입점을 배포한다. SPA catch-all rewrite를 추가하지 않는다.
- 운영자가 Vercel에서 저장소·브랜치를 선택해 배포하고 `/experiment/` 직접 접속과 새로고침을 확인한다. 계정·도메인 설정과 실제 배포는 사람이 수행한다.
- 확장 설치·로그인·실제 프로필·API·수집 서버 없이 동작한다. `/demo/`와 제품 확장 기본 동작은 그대로 유지한다.

## 실험 진행

1. 취업 준비 또는 채용 지원서 작성 경험이 있는 참가자 10명을 모집한다. 경험은 비식별 요약으로 별도 기록한다.
2. 참가자마다 별도의 새 브라우저 세션을 사용한다. 같은 탭의 새로고침은 이전 순서와 저장한 평가를 복원한다. 탭 복제는 세션이 복사될 수 있으므로 새 참가자에게 사용하지 않는다. 이미 끝난 페이지는 새 브라우저 세션에서 연다.
3. 한 참가자는 A-B-D, A-D-B, B-A-D, B-D-A, D-A-B, D-B-A 중 무작위로 배정된 순서에서 세 버전을 한 번씩 체험한다. 무작위 배정이므로 10명의 순서별 인원은 균등하지 않을 수 있다. 실제 분포를 기록한다.
4. 모든 버전은 같은 예제 지원서 19개 필드에 0.667초마다 한 항목씩 입력한다. 기입 구간은 12.673초이며, 마지막 입력 후 공통 400ms 전환 시간을 둔다. B의 100%를 마지막 DOM 입력 후 표시한다. 전환 시간은 `durationMs`에 포함하지 않는다.
5. 완료 뒤 ‘평가하기’를 누르고 세 문항에 1~5점을 응답한다. 1=전혀 그렇지 않다, 5=매우 그렇다. `comfort`는 편안함, `trust`는 잘 진행된다는 느낌, `wait`는 시간이 길게 느껴진 정도다. `wait`가 높을수록 더 길게 느낀 것이다.
6. 마지막 화면에서 체험 순서와 정지 예시를 대조해 선호한 체험 또는 차이 없음을 선택한다. 선택 이유는 선택 사항이다. 이름·연락처 등 개인정보를 적지 않는다.
7. JSON을 내려받아 운영자에게 전달한다. 페이지는 외부로 전송하지 않는다. 저장소 접근이 차단되면 메모리에서 계속할 수 있지만 새로고침 시 평가가 사라진다.

탭 숨김·돌아가기·닫기는 현재 입력을 취소한다. 같은 순서의 체험을 처음부터 재시작하며 저장한 이전 평가는 유지한다. 진행 중 새로고침도 미평가 체험을 다시 시작한다. 앱을 앞에 유지하고 같은 기기·브라우저·화면 크기·움직임 설정에서 세 버전을 진행한다. 타이머 지연과 기기 부하로 실제 간격은 달라질 수 있으므로 `durationMs`와 관찰한 오류를 비교해 공정성을 확인한다. 움직임 줄이기 설정은 각 체험 시작 시 기록한다.

이번 조건은 `panel-study-v3`다. 이전 4종 실험(v1/v2) 평가와 섞지 않으며 기존 세션은 복원하지 않는다. 캐릭터 전용 C는 제거하고 A/B/D 모두 정지 카피바라 아이콘을 배치한다.

## 결과 스키마

`version`, `order`, `trials`, `preference`, `reason`만 내보낸다. 각 trial은 `variant`, `ratings`(comfort/trust/wait), `durationMs`, `reducedMotion`을 포함한다. `preference`는 A/B/D 또는 `none`이다. 예제 입력값·지원서 DOM·참가자 식별자·인증 정보는 포함하지 않는다. 자유서술의 개인정보는 운영자가 수집 전 확인한다. 코드 변경이 비교 조건을 바꾸면 새 실험 버전으로 별도 운영한다.

## 10명 탐색 실험의 가설 사이클

| 항목      | 사전 계획 / 실험 후 기록                                                                                                                      |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 가설      | 자동입력 패널 표현을 바꾸면 작업 내역형보다 편안하게 기다리며 신뢰도 유지할 수 있다. 현재 방식이 최선이라는 사용자 근거가 없어 선택했다.      |
| 실험      | 관련 경험이 있는 참가자 10명이 동일 조건에서 세 버전을 모두 체험·평가한다. 아래 성공 기준을 사전에 고정한다.                                  |
| 관측      | 현재 미실험. 참여·완료 인원, 지원서 작성 경험 요약, 순서별 인원, 버전별 점수·선호 인원, 실제 기입 간격·오류, 주요 의견을 실험 후 기록한다.    |
| 결론      | 아래 기준으로 검증·기각·판정 불가와 이유를 기록한다.                                                                                          |
| 러닝      | 작업 정보, 완료 예측, 진행 표시, 단순함 중 중요하게 여긴 요소를 관측으로 설명한다.                                                            |
| 다음 액션 | 성공하면 다음 스프린트 실제 자동입력 환경에서 재검증한다. 실패하면 이유를 반영해 대안을 수정한다. 판정 불가면 참가 인원·비교 조건을 보완한다. |
| 자신감    | 실험 전 낮음. 실험 후 점수 차이와 의견의 일관성으로 갱신한다.                                                                                 |

A는 작업 내역형, B는 진행률형, D는 최소 표시형이다. B/D 중 **동일 대안 하나**가 세 조건을 모두 충족해야 한다.

- 편안함: 참가자별 `(대안 comfort − 자신의 A comfort)`를 계산한 뒤 10명 평균이 **+0.5점 이상**.
- 신뢰감: 참가자별 `(대안 trust − 자신의 A trust)`의 10명 평균이 **0점 이상**.
- 최종 선호: 전체 **10명 중 5명 이상**이 해당 대안을 선택. `none` 응답도 분모에 포함.

다른 대안의 좋은 지표를 조합하지 않는다. 체감 대기와 자유서술은 해석용이며 성공 필수 조건이 아니다.

- **검증**: 같은 조건에서 10명이 세 체험·평가를 마쳤고 한 대안이 세 조건 모두 충족.
- **기각**: 같은 조건에서 10명이 완료했지만 충족한 대안이 없음.
- **판정 불가**: 완료자가 10명 미만이거나 타임라인 차이·오류 등으로 공정한 비교가 어려움.

검증은 이번 10명과 조건에서 가설을 지지한다는 뜻이며 통계적 유의성·전체 사용자 일반화가 아니다. 결과를 본 뒤 기준과 포함 조건을 바꾸지 않는다. 다음 사이클의 변경으로 기록한다. 실제 참가자 실험과 가설의 성공은 페이지 구현 완료와 별개다.

## 확인 절차

- `npm --prefix frontend test -- site/experiment`로 타임라인, 중단, 표시 격리, 순서와 복원, 필수 평가 및 JSON을 검사한다.
- 세 체험을 끝까지 진행하고 다운로드 파일과 순서·값을 비교한다. 예제 값과 DOM이 내보내기에 없는지 확인한다.
- 돌아가기·닫기·탭 이탈·재시작, 시작 연타, 새로고침 복원을 확인한다.
- 키보드 Tab/Enter/방향키, 320px 폭·확대, 움직임 줄이기를 확인한다. 자동 기입 중 본문 외 패널 chrome·지원서·시작·완료를 비교한다.
- `typecheck`, `lint`, `format:check`, `test`, `coverage`, `build:site`, `build`, `zip`과 `.venv/bin/python harness/scripts/verify.py`를 실행한다. 기존 실패와 신규 실패를 구분해 기록하며 실패를 통과로 간주하지 않는다.

## SK Careers 형태의 체험 화면

SK Careers 공개 헤더(https://www.skcareers.com/)와 저장소의 SK 지원 항목 정의를 참고해 기본정보·학력정보·자격/면허로 나눈 실험용 화면이다. 로그인 후 실제 지원서를 그대로 복제한 화면은 아니다. 실제 지원·저장·제출 동작과 외부 호출을 연결하지 않는다. 세 가지 패널 모두 같은 SK 형식 지원서와 동일한 19개 예제 필드를 사용한다. 카피바라 크기는 작업 내역형 36px, 진행률형 80px, 최소 표시형 48px이다.
