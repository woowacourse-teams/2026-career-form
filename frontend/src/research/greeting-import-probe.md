# Greeting 지원서에서 프로필 가져오기

Issue: [CF-192](https://github.com/woowacourse-teams/2026-career-form/issues/192)

현재 구현은 초기 6종 제한을 제거했다. [정확한 Greeting 필드 경로](../profile/page-import/greeting-import-mappings.ts)를 기존 프로필 필드에 대응시키고, [reader](../profile/page-import/reader.ts)가 현재 페이지의 각 필드를 독립적으로 읽는다. 회사별 미지원 필드와 잘못된 값은 제외하고 나머지 후보를 계속 보여 준다. 기존 Greeting 정적 매핑과 프로필 목적지가 있는 항목을 지원하며, 임의의 회사별 추가 질문을 프로필 필드로 추측하지 않는다.

## 사용 흐름

지원서 패널의 **지원서에서 가져오기**를 누르면 범주별로 기존 값과 가져올 값을 비교한다. 처음에는 모두 미선택이다. 개별 선택 또는 **전체 선택** 후 반복 항목마다 새 추가/기존 항목 연결을 지정하고 **선택한 정보 저장**을 누른다. 민감 범주는 표시하며 전체 선택에도 포함됨을 안내한다. 저장 성공 후 패널이 갱신되어 자동 기입으로 이어진다.

국문·영문 전체 이름은 원문을 참고해 성과 이름을 직접 확인한다. 월 단위 날짜는 정확한 전체 날짜를 입력하거나 선택에서 제외한다. 학교·시험·자격증 등 카탈로그 항목은 확인되지 않은 ID를 만들지 않고 직접 입력한 정체성으로 저장한다.

## 부분 실패와 읽기 경계

- 비연속 인덱스, 다른 반복 개수·순서, 알 수 없는 추가 질문은 정상 필드 수집을 막지 않는다.
- 중복 필드·여러 원본이 같은 목적지를 가리키는 충돌·서로 섞인 행 소유권은 해당 필드/행만 제외한다.
- 읽기 예외, 빈 값·선택 안내문·잘못된 날짜·미지원 옵션은 값을 반환하지 않는다.
- 보이는 disabled/readonly는 읽는다. hidden, inert, aria-hidden, 숨김 스타일과 접힌 영역은 열지 않고 제외한다.
- Greeting 지문을 확인하고 정확한 경로·행 소유권으로 읽는다. 기존 자동 기입의 더 엄격한 수집 동작은 변경하지 않는다.
- 현재 페이지 밖, 렌더링되지 않은 다음 단계의 존재나 지원서 전체의 완전성은 보장하지 않는다.
- 페이지 DOM·이동·저장·제출·인증·업로드를 실행하지 않고 읽은 값을 외부 서버·분석·로그로 보내지 않는다.

## 병합과 저장

[PageImport](../profile/page-import/PageImport.tsx)는 프로필 필드 정의로 범주와 비교 화면을 구성한다. [mergeImportSelection](../profile/page-import/merge.ts)은 허용된 선택 필드만 검증해 복제 프로필에 반영한다. 미선택 기존 필드와 다른 항목을 보존한다.

반복 항목은 페이지 인덱스로 기존 데이터에 자동 연결하지 않는다. 같은 범주·종류의 ID를 사용자가 고르거나 대표 이름과 새 ID로 추가한다. 범주별 대표 이름·날짜·등록번호 등 식별 필드가 같은 새 항목 재추가를 거부한다. 복수·부전공명은 결과 상태가 해당 전공 있음일 때만 저장한다. 날짜·표준 옵션을 검증하고 알 수 없는 필드를 임의 저장하지 않는다.

production 저장은 기존 [background 단일 큐](../storage/profile-write-handler.ts)에서 기준 프로필과 현재값을 비교해 기록한다. 충돌 시 재검토하고 미저장 편집을 임의로 버리지 않는다. 취소·읽기 실패·저장 실패·중복 클릭 처리도 유지한다.

## 빈 반복 행 처리

Greeting이 빈 대학원에 표시하는 `주전공`과 빈 경력의 미체크 재직 여부(`퇴사`)는 다른 읽을 수 있는 값이 없으면 빈 값으로 제외한다. 전체 선택이 이 기본값만 있는 행의 저장 대상이나 이름을 요구하지 않게 한다. 학교명·회사명이 없더라도 날짜·담당업무 등 정상 형제 필드가 있으면 해당 행의 후보는 보존하며, 새 항목의 대표 이름 확인과 저장 충돌 검증은 유지한다.

[merge tests](../profile/page-import/merge.expanded.test.ts)는 선택값만 저장하는 계약·표준값·중복·조건부 필드를 검사한다. [Chromium 통합 테스트](../profile/page-import/PageImport.browser.test.tsx)는 실제 reader→그림자 DOM 검토 UI→다중 범주 저장 및 취소를 검증하고 원본 지원서 변경이나 이벤트가 없음을 확인한다.

## 실사이트 관찰과 남은 한계

초기 6종 빌드는 사용자가 설치한 Aside에서 실제 LF 공개 지원서의 합성 입력으로 읽기·검토·저장했고, HLB의 다른 Greeting 지원서에서는 기본정보 3종과 이메일만 선택 저장 시 다른 값 보존을 확인했다. 이 검증에서 나머지 필드가 누락되는 제한을 발견해 현재 확장을 진행했다.

LF의 실제 DOM 경로와 제어 종류를 읽기 전용으로 대조하여 연봉 경로 등을 확인했다. 최신 확장 빌드를 재로딩한 Aside의 LF 지원서에서 56개 원본 후보를 확인했다. 국문·영문 이름을 각각 성·이름으로 직접 확인하여 총 58개 프로필 필드를 선택·저장했고, 별도 프로필 관리 화면의 저장값 58개를 대조했다. 월 단위 날짜 8개에는 검증용 전체 날짜를 명시적으로 입력했다. 기존 대학교는 기존 ID에 연결했으며 고등학교·대학원·경력·어학시험·자격증은 새 항목으로 추가했다. 대응하는 프로필 항목이 없는 21개 제어는 제외 안내를 표시했고 저장을 막지 않았다.

같은 최신 빌드로 HLB 지원서의 이름·이메일·전화번호 3종을 읽었다. 이메일만 저장한 뒤 LF에서 저장한 이름·전화번호, 학력 3건, 어학·자격증 2건이 보존됨을 확인했다. 지원서 제출·동의·인증·파일 업로드는 실행하지 않았다. 이 결과는 해당 두 페이지에서 관측한 구조에 한정되며, 다른 모든 Greeting 회사와 클릭률 개선 효과는 입증하지 않았다.

최종 자동 검증: 전체 Vitest 3,522개 통과·19개 건너뜀(317개 파일 통과·1개 건너뜀), 관련 단위 테스트 158개와 Chromium 가져오기 통합 3개 통과. 타입 검사·저장소 lint·변경 파일 포맷·빌드·가상환경 하네스 검증 통과. 독립 리뷰에서 지적한 상속 속성 alias 및 읽기 실패 진단 누락을 수정하고 관련 회귀를 재검증했다. 저장소 ESLint 설정은 TS 파일을 직접 검사하지 않으므로 TypeScript 검사를 별도로 수행했다.

## 2026-10-14 수정 및 재검증

기존 Greeting 정적 정책의 88개 원본 규칙을 독립적인 경로·목적지·값 기대값으로 대조했다. 82개 direct/lookup 경로의 reader→merge, 이름 2종의 확인 요구, 추가전공 4개 경로의 복수·부전공 변형을 검증했다. 기존 매핑의 목적지 누락은 발견하지 않았다. 이 테스트가 모든 DOM 제어 종류·선택지·실사이트 변형을 증명하는 것은 아니다.

빈 반복 행 회귀는 수정 전 2개 실패를 확인한 뒤 통과했다. Chromium에서는 정상 경력·빈 대학원·빈 경력·알 수 없는 제어가 함께 있을 때 전체 선택으로 정상 값만 저장하고 기존 주소를 보존했다.

Aside의 기존 확장을 끄고 분리된 `Career Form CF-192 검증` 확장만 사용했다. 새로고침 전 탭에는 이전 콘텐츠 스크립트가 남아 있었으므로, 합성 입력을 사용하는 테스트 페이지를 새로고침한 뒤 다시 입력했다. 실사이트 검증 빌드는 `4085bfc` / `CLEAN`이며 이후 품질 관측 테스트의 mock 타입만 보정했다. 가져오기 production 소스는 동일하다.

### 의도적으로 유도한 통신 실패

DevTools의 테스트 탭 Offline 조건에서 자격증 검색을 실행했다. 검증 확장 활성 탭과 비활성 새 탭 모두 검색 POST가 `net::ERR_INTERNET_DISCONNECTED`로 실패한 뒤 지원서 전체가 “페이지를 찾을 수 없습니다” 화면으로 바뀌었다. 공개 검색 소스는 loader 예외를 잡지 않고, Next 서버 액션 실패가 React transition을 거쳐 전역 오류 화면으로 전달된다. 이 오류 화면은 오류 종류를 구분하지 않는 fallback이므로 실제 404나 권한 오류의 증거가 아니다.

**이는 의도적인 통신 실패 실험이며 최초의 지속 로딩과 다른 현상이다.** 통신 실패 처리 경로가 Greeting 자체에 있다는 점은 확장 없이도 재현했지만, 이를 최초 로딩 멈춤의 원인으로 연결하지 않는다. 테스트 후 정상 통신 조건과 검증 확장 활성 상태를 복구했다.

### 코드 경로와 진단 한계

확장 reader와 수집 보조 함수는 지원서 DOM을 조회하고 값을 읽는다. 가져오기 진입은 자동 기입을 실행하지 않는다. Shadow DOM 키 이벤트 격리는 패널 내부에만 적용되며 지원서 검색 입력 이벤트나 fetch/XHR을 차단하는 경로를 발견하지 못했다. 설치한 빌드는 `4085bfc` / `CLEAN`이고 이후 production 가져오기 소스 차이는 없다.

공개 Greeting 소스에서 학교·전공·회사·시험·자격 검색은 공통 검색 훅과 서버 액션을 사용한다. 확인한 Next 클라이언트의 서버 액션 큐는 요청을 순차 처리하며 React의 동시 async transition은 완료 상태를 공유한다. 앞선 작업이 계속 pending이면 후속 검색도 기다릴 가능성은 있으나, 이번 조사에서 실제 미완료 작업이나 자연 조작으로 이를 만드는 조건을 확보하지 못했다. 날짜·반복 행 추가·로컬 onBlur 검증에서 별도의 검색 요청 경로도 발견하지 못했다.

### 최신 온보딩과 저장 충돌 통합

필수 검증 시 기준 브랜치에 새로 병합된 CF-193 온보딩 변경을 통합했다. fixture 탐색은 양쪽에서 같은 15개 profile-export JSON만 포함하는 기준으로 맞췄고 품질 관측 mock의 인자 타입을 보존했다. 새 QuickStart에는 CF-192가 추가한 동시 저장 conflict 상태의 안내·복구가 빠져 있었다. 이것은 Greeting 검색 멈춤과 별개의 확장 UI 통합 결함이다.

QuickStart는 충돌 뒤 미저장 편집을 유지하며, 사용자가 확인한 경우에만 최신 프로필을 다시 불러온다. 확인 취소나 재조회 실패 시 편집을 보존하고 재조회 중에는 입력·단계 이동·가이드 복귀를 막는다. 성공 후에만 오래된 반복 행 선택·탐색 기록을 초기화해 저장된 정보 화면으로 이동한다. 네 회귀를 수정 전에 실패시켰고 수정 후 QuickStart 60개 테스트가 통과했다. 독립 검토에서 추가 수정 권고는 없었다. 기존 Greeting reader·매핑·검색에는 이 통합 수정을 적용하지 않았다.

최종 통합본에서 전체 Vitest **3,724 통과·19 건너뜀**(323개 파일 통과·1개 건너뜀), 타입 검사·lint·변경 파일 Prettier·확장 빌드·차이 검사·Python 3.12 하네스 검증을 확인했다. 전체 테스트에는 Chromium 12개와 QuickStart 60개가 포함된다. 저장소 lint 설정은 TS/TSX를 제외하므로 해당 소스의 정적 검증은 별도 타입 검사 결과로 구분한다. 하네스 386개 및 infra 159개(40개 건너뜀), Wiki·셸·execpolicy 검증도 통과했다. 검색 A/B 관측은 분리 빌드4085bfc에서 수행했고, 최종 통합의 Greeting reader·매핑 소스는 그 빌드와 동일하다.
