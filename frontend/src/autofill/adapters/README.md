# 프론트 회사 어댑터

백엔드 정책은 **어떤 프로필 항목을 연결하고 어떤 입력 명령을 허용할지** 결정한다.
프론트 회사 어댑터는 **해당 회사 화면을 수집하고 특수한 입력을 실행하는 방법**을 제공한다.
실제 프로필 값은 브라우저 안에서 결합한다.

## 코드 읽는 순서

1. `company.ts`: 정확한 host로 회사 식별. 미등록 host는 generic이다.
2. `collection.ts`: 회사별 DOM 수집 규칙 선택. `hyundai/collection.ts`와 `sk/collection.ts`가 회사 예외를 소유한다.
3. `workflow.ts`: 준비 후 필요한 선택과 재분석 대상 판별. 현재 SK 조건부 필드 규칙은 `sk/workflow.ts`에 있다.
4. `write.ts`: 특수 입력의 처리 여부와 실패를 공통 writer에 전달. 현대 버튼 선택과 입력 후 라벨 보정은 `hyundai/write.ts`에 있다.

공통 `dom/collect.ts`는 snapshot과 후보 registry를 만들고, `workflow/AutofillWorkflow.tsx`는 API 호출과 실행 순서를 관리한다.
프로필 값 해석, 기존 값 보호, 승인 상태 검사, stale 후보 검사, 일반 text/select/radio/checkbox 입력은 공통 계층의 책임이다.

## 새 회사 추가

- 사람이 확정한 Issue에서 대상 화면과 인수 조건을 먼저 정한다.
- `company.ts`에 확인된 host를 등록하고 회사 식별 테스트를 추가한다.
- 일반 DOM 수집으로 충분하지 않을 때만 회사 `collection.ts`를 추가하고 수집 선택기에 연결한다.
- 선행 선택 때문에 다른 필드가 나타나거나 초기화될 때만 workflow 기능을 구현한다. API 호출·프로필 저장·React 상태 전체를 회사 구현으로 옮기지 않는다.
- 표준 명령으로 입력할 수 없는 검증된 위젯에만 회사 write 구현을 추가한다. 구현한 기능의 선택기에만 연결한다.
- 백엔드에는 별도로 회사 경로, fingerprint, 준비 규칙, 필드 매핑을 등록한다. 프론트 어댑터 등록만으로 서버 정책이 생기지는 않는다.
- 비식별 fixture로 회사 범위, 반복 행, 실패, 재수집, 기존 값 보호를 검증하고 회사 문서와 지원 현황 갱신은 지식 승인 절차를 따른다.

## 특수 입력의 실패

`CompanyWriteAttempt`의 `handled: true, written: false`는 해당 회사 입력을 인식했지만 실행에 실패했다는 뜻이다.
이 결과에 일반 writer를 다시 적용하면 안 된다. 미등록 회사에서 특수 명령을 받는 경우에도 입력하지 않는다.

현재 현대 버튼 선택은 기존 동기 메뉴 동작을 이동한 구현이다. 검색 결과를 기다리거나 최종 선택 코드를 검증하는 범용 검색 기능은 아니다.
LG 학교 검색을 추가하려면 별도 계약에서 비동기 대기·취소·같은 학력 행의 대상 식별·후보의 유일성·선택 반영 확인을 정의하고 검증해야 한다.
학교명만 같은 결과 중 첫 번째를 임의로 선택하거나 검색 실패를 text 입력으로 우회하지 않는다.

## 유지한 동작과 제한

이번 분리는 기존 자동 실행 및 승인 화면 정책을 재설계하지 않는다. SK의 기존 선행 라디오 탐색과 현대 메뉴의 검색 범위·재실행 방식도 별도 개선 대상이다.
학교 검색, LG 실제 지원, 실제 페이지 수동 검증이 완료된 것으로 해석하지 않는다.

## 회귀 검증

`frontend/`에서 실행한다.

```sh
npm test -- src/autofill src/autofill-demo/AutofillOverlay.test.tsx
npm run typecheck
npm run coverage
npm run build
```

전체 검증과 최신 기록은 Issue 작업 계획을 따른다. 실제 지원서 값, 계정, 세션 및 시크릿은 테스트와 진단 로그에 넣지 않는다.
