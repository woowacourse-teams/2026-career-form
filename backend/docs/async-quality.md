# 비동기 품질 처리

CF-288의 분석 응답은 품질 DB 저장, 작업 큐 공간과 집계를 기다리지 않는다. 값 없는 관측 이벤트 구성과 접수 비용은 남는다. Servlet 요청, 응답, QualityScope나 원문 본문은 작업자에게 넘기지 않는다. 실제 배포와 부하 측정은 사람이 수행한다.

## 등록과 보고

확장 background는 첫 분석과 병렬로 실행별 등록 POST를 한 번 보낸다. 임의 연결 키는 분석을 같은 실행에 연결하는 능력이며, 공개 실행 식별자나 보고 토큰과 구분한다. 서버는 연결 키와 보고 토큰의 해시만 문맥에 보관하고, 등록 응답으로 실행 번호와 무작위 보고 토큰을 반환한다. 토큰 원문은 서버 영속 데이터나 로그에 기록하지 않는다.

| 요청 또는 상황 | HTTP | 계약 |
|---|---|---|
| `POST /api/v1/quality/executions` | 201 | 메모리 문맥과 저장 작업 접수, DB 저장 완료 아님 |
| 기존 `POST /api/v1/quality/executions/{runId}/report` | 202 | 접수 완료. 이미 접수한 동일 이벤트도 202 |
| 잘못된 형식 / 본문 크기 초과 | 400 / 413 | 해당 품질 요청 제외 |
| 문맥 소실, 무효 또는 만료 토큰 | 401 | 해당 실행의 추가 보고 중단 |
| 동일 연결 키의 중복 등록 | 409 | 토큰 재발급 없음 |
| 문맥 또는 작업 예산 포화 | 429 | 새 작업 제외, 즉시 재시도 없음 |
| 품질 비활성 / 등록 미지원 | 404 | 분석과 입력은 유지 |

보고 토큰은 등록 후 24시간까지 유효하다. 관리 API 권한으로 사용할 수 없다. 등록과 보고 POST만 관리 인증 예외이며 나머지 경로의 비밀번호, 조회 자격과 Origin 검사는 유지한다. 상세 30일과 일별 집계 90일의 보존 기간은 유지한다.

입력 결과가 먼저 준비되면 등록 시작 후 최대 30초까지 보관한다. 등록 실패 또는 시간 초과 시 품질 보고만 포기하고 늦은 응답을 새 실행에 연결하지 않는다. 등록 응답이 먼저 오면 기존 입력 종료 시점까지 기다린다. snapshot 구분과 300 필드 분할은 유지한다. 자동 입력과 완료 표시는 등록, 보고 전송이나 보고 큐 drain을 await하지 않는다. 네트워크 오류에는 기존처럼 같은 이벤트 ID로 보고를 한 번 재전송하며 주기적 보고와 등록 재시도는 추가하지 않는다.

실행, 탭, frame, document의 메시지 소유 검증을 유지한다. 보고는 서버가 분석한 snapshot과 필드 대응만 사용한다. 등록, 분석과 보고의 순서가 바뀌면 준비 상태를 제한된 메모리에서 기다리며 MongoDB를 폴링하지 않는다. 최대 30초 안에 선행 정보가 준비되지 않으면 제외한다. 실행당 보고 이벤트와 snapshot은 각각 최대 200개이며 snapshot당 2000개 후보, 보고 본문 128KiB를 검사한다.

## 저장과 집계

원본 저장, Registry 처리, 집계, 점진 보정과 품질 배치는 하나의 전용 작업자에서 수행한다. 원본 변경 후 집계할 원본 ID를 표시하고 약 60초마다 최신 저장 상태를 반영한다. 집계 도중 추가 변경은 다음 대상으로 남는다. 실패 재처리는 제한한다. 기존 보정은 큰 문서 여러 개가 동시에 쌓이지 않게 원본을 한 건씩 읽고, 회당 제한된 범위를 이어서 처리하며 정상 집계와 동시에 DB를 점유하지 않는다.

| Spring property (`career-form.quality.` 접두사) | 시험 기본값 | 범위 |
|---|---|---|
| `queue-capacity` | 64 | 실행 중, 큐 대기, 선행 정보 대기를 합친 작업 수 |
| `retained-bytes` / `event-bytes` | 4194304 / 131072 | 보관 이벤트 직렬화 바이트 총량 / 이벤트당 바이트 |
| `dependency-ttl-ms` | 30000 | 실행 시작 전과 선행 정보 재대기 수명 |
| `registration-capacity` | 256 | 실행 문맥 수, 최대 24시간 유지 |
| `aggregate-capacity` / `aggregate-ttl-ms` | 1024 / 86400000 | 변경된 원본 ID 수 / 보관 수명 |
| `aggregate-attempts` / `aggregate-batch-size` | 3 / 64 | 집계 재처리 횟수 / 회당 대상 수 |
| `aggregate-poll-ms` / `repair-poll-ms` | 60000 / 60000 | 집계 / 보정 제출 주기. 보정 첫 제출은 5분 후 |
| `repair-batch-size` / `repair-budget-ms` | 16 / 1000 | 보정 회당 건수 / 다음 DB 작업 시작 예산 |
| `db-timeout-ms` | 2000 | 품질 Mongo 작업별 CSOT 제한시간 |

이는 초기 시험값이며 143 RPS의 처리량이나 메모리 안전성을 실측한 결과가 아니다. 설정은 Spring property이고 Compose 전달과 실제 서버 적용은 사람이 확인한다. 품질용 MongoTemplate은 기존 클라이언트와 풀을 공유하며 품질 작업에만 제한시간을 적용한다. 분석용 Mongo 설정은 변경하지 않는다.

4MiB는 JVM 힙/RSS 상한이 아니다. 객체, 실행 문맥, snapshot 준비 상태, 집계 ID, DB 응답과 실행 중 작업의 메모리는 별도다. 확장 background의 등록 문맥은 128개/24시간, 대기 보고는 64개/4MiB로 제한한다. content 보고 큐도 보관과 전송 대기에 개수 및 바이트 상한을 둔다.

포화 시 새 이벤트를 즉시 제외한다. 요청 스레드가 대신 저장하거나 큐 공간을 기다리지 않는다. 실행 중 Java 처리는 TTL이나 취소 요청만으로 종료했다고 간주하지 않으며 실제 종료 전까지 보관 예산과 처리 중 수를 유지한다. 회당 시간 예산은 이미 시작한 DB 호출의 제한시간과 다르다.

## 유실과 버전 전환

서버 재시작, 페이지 또는 확장 background 종료, 포화, 만료와 저장 실패로 일부 기록이 유실될 수 있다. 접수는 저장 보장이 아니며 통계를 완전한 모집단으로 해석하지 않는다. 재시작 뒤에는 DB를 동기 조회해 보고 권한을 복구하지 않는다. 이때 기존 토큰은 401로 제외한다.

새 확장과 구형 서버는 등록 404를 품질 제외로 처리한다. 구형 확장과 새 서버의 분석 JSON과 자동 입력은 유지하지만 이전 Receipt 응답 헤더를 제공하지 않아 품질 보고는 누락될 수 있다. 양쪽 버전을 함께 배포하고 복구 때에도 분석 성공, 품질 접수와 저장 성공을 구분한다. 새 확장은 구형 보고 응답 204도 접수 성공으로 인식한다. 별도 큐 서버, 영속 큐와 데이터 마이그레이션은 도입하지 않는다.

## 검증과 관측

`quality.tasks`의 `outcome`으로 거절, 처리 실패, 만료와 종료 제외를 센다. `quality.tasks.queue.wait`는 최초 실행 전 대기, `quality.tasks.execution`은 실행 시도별 실제 소요시간이다. `quality.tasks.active`, `quality.tasks.waiting`, `quality.tasks.retained.bytes`는 실제 처리 중 수, 선행 정보 대기를 포함한 대기 수와 보관량이다. `quality.registration`과 `quality.registrations`는 문맥 거절/만료와 개수, `quality.aggregate`와 pending/oldest 지표는 집계 결과와 지연을 나타낸다. 식별자와 토큰은 라벨로 사용하지 않는다. HTTP, Mongo와 GC는 기존 계측을 사용한다.

사람이 dev에서 같은 합성 시나리오와 실제 도달 RPS로 품질 on/off의 HTTP P95, 실패율, JVM 힙/RSS, CPU, swap 입출력, DB 연결과 드롭률을 비교한다. Controller 이후 품질 작업이 원래 요청 trace에 연결되는지는 실제 Java agent에서 확인한다. 필요하면 기존 계측 설정을 보존하며 `QualityAsyncService.collect`, `QualityCollectionService.observeRegistered`, `reportRegistered`, `QualitySchedule.aggregate`의 메서드 span을 검토한다. 예약 집계는 별도 작업이므로 원래 HTTP 시간에 더하지 않는다. CPU, 객체 할당과 GC 원인은 JFR로 대조한다. 기존 400ms 전부가 절감됐다고 가정하지 않는다.
