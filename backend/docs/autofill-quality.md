# 자동 입력 품질 관측과 필드 수 확인

CF-164는 기존 분석 API의 schemaVersion 2 응답을 유지하면서 요청 관측, 브라우저 결과 보고, 사람 확인 목록과 일별 집계를 추가한다. 기능은 기본으로 꺼져 있다. 운영 설정과 배포는 사람이 수행한다.

## 수집과 해석

서버는 실제 라우터 선택을 STATIC, GREETING, GENERIC과 차단 사유로 기록한다. 실제 외부 호출은 별도로 센다. 범용 경로를 선택했지만 AI를 호출하지 못한 요청은 AI 호출 수를 증가시키지 않는다.

요청 수집 후보와 실행의 고유 칸 수를 구분한다. 재분석 후보는 브라우저가 같은 DOM 제어에 부여한 실행 내 임의 식별자를 보고한 경우에만 합친다. 서버는 이미 분석한 snapshot과 candidate 소속을 검사하고 식별자는 해시로 저장한다. 여러 snapshot의 대응이 미확인인 실행은 `DEDUPLICATION_UNOBSERVED`로 표시하고 고유 칸 비율에서 제외한다. 클라이언트 보고는 실제 입력이나 정답을 인증하는 증거가 아니다.

| 지표 | 분자와 분모 |
|---|---|
| 매핑률 | 서버 매핑 후보 / 요청 수집 후보 |
| 값 준비율 | 보고된 값 준비 칸 / 보고된 매핑 칸 |
| 입력 성공률 | 값 반영 확인 칸 / 입력 시도 칸 |
| 1초 유지율 | 1초 뒤 유지 확인 칸 / 값 반영 확인 칸 |
| 수집 대비 유지율 | 유지 확인 칸 / 보고된 수집 칸 |
| 사람 기준 커버리지 | 범위가 대응되는 실행의 각 단계 칸 수 / 사람 확인 분모 합 |

비율은 건수를 합산해서 계산한다. 분모가 0이면 null이다. 필요한 입력, 유지 결과나 중복 제거 대응이 미관측이면 전체 비율은 null이며, 실제 관측 결과만의 비율을 별도로 제공한다. 결과 보고가 없는 실행은 마지막 관측 후 30분까지 진행 중이고 이후 미관측으로 판정한다. 늦은 보고는 이전 실행 기여분을 교체한다.

원문 라벨, DOM ID와 name, 분석의 원본 경로, 입력값과 프로필 값은 품질 집계에 저장하지 않는다. 검증된 공개 작성 링크만 확인 후보의 별도 메타데이터로 보관한다. 화면 구조는 제어 종류, 제한, 반복 관계와 정제된 의미 구조의 해시다. 버전은 백엔드, 확장, 정책, 실제 관측된 모델과 관측 계약 정보를 포함한다. 없는 정보는 UNKNOWN으로 남는다.

## 관리 화면

기존 HTTP 백엔드의 `/quality/`에서 고정 공용 비밀번호를 입력한다. 회원가입과 개인 계정은 없다. 관리 API는 요청마다 같은 비밀번호를 Basic 자격으로 확인한다. 비밀번호 설정이 없으면 관리 화면과 관리 API를 공개하지 않는다.

- 로그인 세션, 인증 쿠키와 CSRF 토큰을 발급하지 않는다. 비밀번호와 담당 식별자는 페이지 모듈 메모리에만 유지하며 localStorage와 sessionStorage에 저장하지 않는다. 새로고침과 새 탭에서는 다시 로그인한다. 로그아웃은 메모리를 비우고 로그인 화면으로 이동한다.
- 담당 식별자는 후보의 동시 수정 소유권만 구분하고 관리 API 접근 권한으로 쓰지 않는다. 담당 상태는 24시간 유지되므로 페이지를 새로고침하거나 닫기 전에 맡은 후보를 완료하거나 담당을 해제한다. 새 로그인은 이전 담당 식별자를 복구하지 않는다. 별칭은 개인 인증을 뜻하지 않는다.
- 잘못된 비밀번호는 출처별 10분 동안 5회까지 허용한다. 읽기와 쓰기에 모두 비밀번호를 요구하며 다른 Origin의 관리 요청을 거부한다. Grafana 읽기 전용 자격은 집계 조회만 허용한다.
- HTTP는 비밀번호, 실행 보고 자격과 조회 자격을 암호화하지 않는다. HTTPS 설정 없이 기존 HTTP 연결을 사용하는 것은 사용자 확정 운영 정책이다. 실제 비밀번호 원문은 저장소에 넣지 않고 기존 PBKDF2 검증 설정으로 확인한다.
- 전체 미확인 목록에서 오늘 선정 외 후보도 완료할 수 있다. 완료 목록에는 필드 수, 확인일과 수정 이력이 남는다. Discord의 후보 링크는 목록 페이지 밖의 후보도 직접 연다.
- `/site-groups` 관리 조회는 같은 환경의 사이트를 묶은 뒤 페이지를 나눈다. 알려진 회사 정책은 company 경계를 유지한다. 미확인 공유 호스트는 한 사이트 카드에 표시하되 각 실행과 화면의 후보 ID, 담당, 보류, 완료 이력과 사람 분모는 합치지 않는다. 기존 `/sites` API는 유지한다.
- 카드에 미완료 화면이 하나라도 있으면 미확인 목록에 나타나며 완료한 화면의 이력도 카드 안에서 볼 수 있다. 모두 완료한 사이트는 완료 목록으로 이동한다. 구조가 다른 후보는 별도 화면 범위와 재확인 대상으로 표시한다.
- 확장 백그라운드는 Chrome runtime sender URL 중 분석 host와 같은 HTTPS Greeting tenant의 `/ko/o/<공고번호>/apply`와 `/en/o/<공고번호>/apply`만 품질 전용 `X-Career-Form-Public-Application` 헤더에 전달한다. 공고번호는 1~12자리 양의 정수, 주소는 최대 512자다. BE가 같은 규칙을 반복 검증한다. query, fragment, 계정 정보, port, 인코딩 및 다른 경로를 거부하며 주소 일부를 잘라 정상 링크로 바꾸지 않는다. 이 헤더는 분석 body, AI 공급자 요청, 일반 로그와 품질 요청 기록에 포함하지 않는다.
- 필드 수를 등록하기 전에도 공개 링크를 얻는다. 같은 URL은 최근 관측 시점만 갱신하고 서로 다른 공고는 보존한다. 후보와 사이트 카드에서 최근 20개 관측 링크를 유지하며 한도 초과를 표시한다. 기존 후보와 구형 확장은 새 관측으로 보완할 수 있고 새 저장 필드가 없으면 빈 목록으로 읽는다. 데이터 마이그레이션은 필요하지 않다.
- 여러 관측 공고가 같은 후보 구조로 대응되는 경우 사람이 기록한 수를 다른 공고의 분모로 추정하지 않는다. 해당 시점까지 서로 다른 링크가 두 개 이상이면 자동 분모 적용을 중단한다. 사람 확인 링크와 새 관측 링크가 다르거나, 링크 없이 완료한 뒤 처음 다른 주소가 관측되면 기존 분모를 적용하지 않고 다시 확인한다. 링크 한도를 넘은 후보도 자동 적용을 중단한다. 이미 명시적으로 확인한 전용 호스트와 구조의 기준은 기존 승인 범위를 유지한다.
- 사람이 등록한 기존 공개 링크는 별도로 보존한다. 정확한 링크가 없으면 `작성 링크 미확보`를 표시하며 사이트 홈은 보조 링크로만 제공한다. 만료 또는 폐쇄된 링크는 해당 화면에서 `LINK_UNAVAILABLE` 보류로 처리한다. 실제 지원서 이동과 접근 성공 확인은 사람이 수행한다.

같은 화면에서 프로필 값이 준비되어 있고 자동 입력을 허용할 수 있는 칸을 센다. 잠긴 칸, 파일 업로드와 동의 항목은 제외한다. 연, 월, 일 제어는 각각 센다. 한 답을 받는 radio 또는 checkbox 그룹은 한 칸이다. 반복 행의 현재 개수도 같아야 한다.

사람 등록은 필드 수만 확인하므로 **사람 확인 분모, 정확도 미검증**으로 표시한다. 정답 매핑, 정확도, 재현율이나 오입력률로 해석하지 않는다. 100%를 넘거나 화면 범위가 다르면 범위 불일치다. 같은 구조에서 확인 이후 시작한 실행에만 분모를 적용하며 과거 실행을 소급 평가하지 않는다. 앱 버전만 바뀌고 구조가 같으면 재사용할 수 있다.

공유 ATS 호스트의 기업 소속이 미확인인 요청은 임의로 합치지 않는다. 회사 정책이나 Greeting tenant로 구분하거나, 사람이 해당 호스트와 화면 구조가 한 기업을 구분한다고 확인한 이후 재사용한다. 구조가 바뀌면 새 재확인 후보를 만들고 완료 이력을 보존한다.

## 평일 확인 요청

Asia/Seoul 평일 09:20에 당일 batch를 저장한다. 재시작 시 당일 09:20 이후의 미처리 batch만 복구하고 주말이나 지난날 알림을 따라 보내지 않는다. 공휴일 달력은 적용하지 않는다.

동일 사이트의 여러 실행과 구조는 당일 Discord 목록에 한 번만 선정한다. 후보 대표는 담당 중, 기존 확인 요청, 선택 가능한 대기, 보류 순으로 고르며 각 상태와 이력은 유지한다. Discord의 후보 링크는 전체 사이트 카드와 해당 화면 범위로 연결한다. 이미 발송한 과거 batch는 변경하거나 다시 발송하지 않는다.

활성 미완료와 자발적 담당 화면을 포함해 신규 선정 여력은 최대 5개다. 같은 사이트에 이미 맡은 화면이 여러 개여도 기존 작업 수를 그대로 차감한다. 사이트 카드 수로 줄여 새 일감을 추가하지 않는다. 오래된 대기를 최대 2개 먼저 배정하면서 STATIC → GREETING → GENERIC 순환 위치를 보존한다. 나머지는 최근 데이터에서 낮은 입력 성공률, 낮은 매핑률, 사용량 순으로 고른다. 미관측 입력 결과를 실패율 선정 근거로 쓰지 않는다. 동률은 관련 표본 수 내림차순, 첫 대기일과 후보 ID 오름차순이다.

새 후보가 없어도 미완료 목록을 안내한다. 처리 가능한 후보가 없으면 `오늘 확인할 사이트가 없습니다.`와 전체 목록 링크를 보낸다. 보류 후보는 따로 표시하며 기본 보류는 7일이다.

전용 Discord 웹훅만 사용한다. `wait=true`의 성공 응답에서 메시지 ID를 받은 경우만 SENT다. 명확한 429는 최대 3회 재시도하며 개별 대기는 최대 10초다. timeout, 전송 결과가 불명확한 오류와 전송 중 중단은 UNKNOWN이며 자동 재전송하지 않는다. 정확히 한 번 전달됐다고 보장하지 않는다. 미설정과 전송 거부는 성공이나 후보 완료로 처리하지 않는다.

일반 메시지 2000자를 넘으면 한 개의 embed 설명으로 동일한 목록을 보낸다. 최대 4096자를 넘는 메시지는 거부하고 모든 알림에서 자동 멘션을 끈다. 잘못된 웹훅 설정 오류에는 원본 URL을 포함하지 않는다.

## 사람이 설정할 값

| 환경변수 | 기본값과 역할 |
|---|---|
| `CAREER_FORM_QUALITY_ENABLED` | false, 수집, 관리 기능 활성화 |
| `CAREER_FORM_QUALITY_VERSION` | 직접 실행은 UNKNOWN, 배포 Compose는 실제 `BACKEND_IMAGE` 자동 전달 |
| `CAREER_FORM_QUALITY_PASSWORD_HASH` | 공용 비밀번호 검증용 PBKDF2 설정 |
| `CAREER_FORM_QUALITY_QUERY_TOKEN_HASH` | Grafana 전용 조회 토큰의 SHA-256 hex |
| `CAREER_FORM_QUALITY_MANAGEMENT_URL` | 외부 HTTP 관리 화면의 `/quality/` 주소 |
| `CAREER_FORM_QUALITY_DISCORD_ENABLED` | false, 전용 확인 요청 활성화 |
| `CAREER_FORM_QUALITY_DISCORD_ENVIRONMENT` | prod, 알림을 보내는 환경 하나 |
| `CAREER_FORM_QUALITY_DISCORD_WEBHOOK` | 새 채널의 전용 Discord 웹훅 |
| `CAREER_FORM_QUALITY_SELECTION_DAYS` | 7, 후보 선정에 사용하는 최근 일수 |
| `CAREER_FORM_QUALITY_SELECTION_MINIMUM_SAMPLE` | 20, 비율 선정의 최소 분모 |

비밀번호 검증 형식은 `pbkdf2-sha256$반복수$base64 salt$base64 digest`다. PBKDF2-HMAC-SHA256, 반복수 600000~2000000, salt 16~64바이트, digest 32바이트를 사용한다. 실제 비밀번호, 검증 설정, 조회 토큰과 웹훅은 저장소와 문서에 적지 않는다. 확장에는 관리 비밀번호나 Grafana 조회 토큰을 넣지 않는다.

확장은 분석 헤더의 `quality-v1` 기능 협상을 사용한다. 서버가 발급한 보고 토큰은 백그라운드의 해당 문서, 실행에만 보관하며 관리 API에 사용할 수 없다. 유효 기간은 24시간이고 원문은 저장하지 않는다. 실행당 200개 이벤트, snapshot당 최대 2000개 후보와 보고당 128KiB를 검사한다. 보고는 여러 칸을 묶어서 보내며 같은 이벤트 재전송은 멱등이다. 구형 서버, 확장과 계측 실패는 기존 입력 흐름을 유지한다. 분석 응답의 품질 저장 대기는 최대 250ms이며 시간 초과나 대기열 포화 시 관측 실패로 처리하고 기존 응답을 반환한다. 관측 작업은 최대 2개 스레드와 64개 대기열로 제한하며 응답 헤더의 보고 토큰은 제한 시간 내 관측이 끝난 경우에만 발급한다.

## 배포 환경 설정 연결

GitHub Environment `development`, `staging`, `production`에서 해당 환경의 설정을 등록한다. 품질 설정은 각 workflow의 `deploy` job에만 전달하며 이미지 빌드와 검증 job에는 전달하지 않는다. 미등록 또는 빈 설정은 Compose의 기본값을 사용하므로 기존 배포는 유지하고 품질 기능은 비활성이다.

| 종류 | 설정 | 사람이 준비하는 값 |
|---|---|---|
| Variable | `CAREER_FORM_QUALITY_ENABLED` | 사용 환경만 true |
| Variable | `SERVER_FORWARD_HEADERS_STRATEGY` | 기존 서비스의 프록시 전달 헤더 전략, 기본값 none이며 품질 기능의 필수 설정 아님 |
| Secret | `CAREER_FORM_QUALITY_PASSWORD_HASH` | 공용 비밀번호의 PBKDF2 검증 문자열 |
| Secret | `CAREER_FORM_QUALITY_QUERY_TOKEN_HASH` | Grafana 전용 임의 토큰의 SHA-256 hex |
| Variable | `CAREER_FORM_QUALITY_MANAGEMENT_URL` | 외부 HTTP 관리 화면의 `/quality/` 주소 |
| Variable | `CAREER_FORM_QUALITY_DISCORD_ENABLED` | 실제 수신 준비 뒤 true |
| Secret | `CAREER_FORM_QUALITY_DISCORD_WEBHOOK` | 새 채널의 전용 웹훅 |

`CAREER_FORM_QUALITY_DISCORD_ENVIRONMENT`, `CAREER_FORM_QUALITY_SELECTION_DAYS`, `CAREER_FORM_QUALITY_SELECTION_MINIMUM_SAMPLE`은 필요할 때만 Variable로 등록한다. 미등록 시 prod, 7일, 20개를 사용한다.

운영 주소는 `http://운영IP/quality/`이며 품질 기능을 위해 새 도메인, TLS 인증서와 Nginx HTTPS 구성을 준비하지 않는다. 기존 HTTP 프록시 연결을 유지한다. `SERVER_FORWARD_HEADERS_STRATEGY`는 기존 서비스의 프록시 요구에 따라 설정하고, 품질 기능 활성화만을 위해 framework로 변경하지 않는다. 관리 요청의 Origin 검사에서 실제 HTTP Host와 포트가 일치해야 한다.

배포 버전은 사람이 등록하지 않는다. Compose가 현재 `BACKEND_IMAGE`의 digest 고정 이미지 식별자를 `CAREER_FORM_QUALITY_VERSION`으로 전달한다. 운영에서 스테이징 이미지를 재사용하거나 이전 이미지로 롤백해도 실제 이미지 식별자를 기록한다. GitHub Variable의 수동 품질 버전은 사용하지 않는다.

Grafana 서버의 `/etc/career-form-monitoring/secrets/grafana.env`에는 환경별 `QUALITY_*_API_ORIGIN`과 `QUALITY_*_QUERY_TOKEN`을 등록한다. 조회 토큰 원문은 Grafana에만, 동일 토큰의 해시는 해당 백엔드 Environment Secret에 등록한다. 기존 운영 알림의 `DISCORD_WEBHOOK_URL`을 유지하며 품질 확인용 웹훅과 구분한다. 환경 파일 수정 뒤 Grafana 컨테이너를 재생성해야 환경변수가 반영된다.

## 보존과 집계 조회

상세 요청, 실행은 생성 후 30일, KST 일별 집계는 기준일 후 90일까지만 조회한다. TTL 정리가 늦어져도 만료 자료는 조회에서 제외한다. 사람 확인과 후보 및 발송 이력은 자동 만료하지 않는다. 상세가 남아 있는 동안 시간별 복구 작업이 누락된 후보, 집계를 멱등 반영한다. 기존 Loki 7일과 Prometheus 14일 설정은 유지한다.

`GET /api/v1/quality/stats`는 관리 세션 또는 집계 전용 Bearer 토큰으로 조회한다. `site`, `structure`, `route`, `version`, `from`, `to`와 `groupBy=ROUTE|FULL|SITE_ROUTE_VERSION|VERSION_TREND|SITE_VERSION_TREND|SITE`를 지원한다. 기간은 KST 일별 범위로 반올림하고 최대 90일이다. 500개 그룹을 넘으면 필터를 좁히라는 오류를 반환한다. 상세 실행과 보고 토큰은 제공하지 않는다.

P95는 고정 버킷의 근사 상한값이다. 버킷은 50, 100, 250, 500, 1000, 2500, 5000, 10000, 20000, 30000, 60000, 120000ms와 상한 초과다. 시간 표본과 상한 초과 수를 함께 제공하며 P95 위치가 상한을 넘으면 null이다.

## 검증 범위

자동 검증은 합성 MongoDB, 합성 페이지, 통제된 시계와 모의 응답을 사용한다. 실제 지원서나 운영 Discord를 호출하지 않는다. 운영 담당자는 기존 HTTP 연결과 요청별 비밀번호 검사, 새 채널의 메시지 수신, 링크 접근과 없음 안내를 실제 환경에서 별도로 확인한다.

수정 확장과 백엔드 반영 후 같은 Greeting tenant의 두 공고를 다른 팀원과 시간에 분석하고 카드 한 개, 정확한 링크 두 개 및 Discord 진입을 확인한다. 지원서 제출과 임시저장은 수행하지 않는다.


## 공고 단위 사람 확인

환경과 검증된 공개 Greeting 작성 URL마다 확인 기록을 하나 둔다. 사이트 카드는 정책 회사 경계를 유지하며 공고별 기록을 표시한다. 구조 해시와 과거 화면 상태는 접힌 관측 이력으로 보존하고 별도 확인 작업을 다시 만들지 않는다. 완료한 공고는 사람의 명시적 재확인 전까지 완료로 남는다. 링크 없는 과거 후보는 별도 접힌 목록에 두며, 공고가 있는 사이트의 완료 판단과 새 Discord 선정은 공고 기록을 기준으로 한다.

전체 입력 가능 칸 수는 조건부 항목을 펼치고 학력, 경력 등 반복 항목을 각 1행 둔 기준으로 확인한다. 확인일과 팀 별칭을 기록하며 별칭은 개인 인증이 아니다. 기존 확인에는 이 기준이 저장되어 있지 않아 자동 승계하지 않고 과거 숫자와 이력을 보존한 채 공고에서 한 번 재확인한다. 기존 담당이 남아 있으면 다른 팀원의 변경을 거부하며 공고 담당 해제는 연결된 기존 담당도 해제한다.

공고 확인 완료와 실행의 분모 적용은 분리한다. 실행 snapshot에는 서버에서 검증한 공고 식별 해시와 비민감 범위 증거만 연결한다. 같은 공고임을 확인할 수 있고 모든 snapshot의 수집 칸 수가 확인값과 같으며 전체 후보가 표시되고 비활성 또는 inert가 없고 반복 행이 각 1개일 때만 호환 범위로 인정한다. 기존 실행 고유 칸 중복 제거와 구조 범위 검사도 유지한다. 링크가 없는 실행, 다른 공고가 섞인 실행, 증거가 없거나 기준과 다른 실행에는 공고 확인값을 자동 적용하지 않는다. 호환 범위가 아니면 참고 커버리지는 빈 값으로 남으며 기존 범위 불일치 또는 미등록 상태를 제공한다.

관측 후보와 과거 집계를 삭제하거나 실제 데이터 마이그레이션을 실행하지 않는다. 기존 후보의 안전한 링크는 조회 또는 새 관측 시 공고 기록에 연결한다. 링크 없는 기존 관리 API와 구형 보고 요청은 유지한다. 사이트 및 공고 조회는 각각 최대 10000개 범위에서 처리하고 초과 시 오류를 반환한다. Discord는 사이트 중복 안내 제한과 하루 여력 5개를 유지하며 이전 담당과 새 공고 담당을 실제로 연결된 공고 범위에서만 중복 차감하지 않는다. 같은 사이트의 독립 공고 담당은 별도로 차감한다. 공고 확인이 끝난 기존 담당은 새 여력을 계속 차지하지 않는다. 과거 batch는 수정하거나 재발송하지 않는다.

배포 후 같은 공고를 다른 시간과 조건부 표시 상태에서 분석하고 등록 입력이 하나인지 확인한다. 한 번 완료한 뒤 새 구조가 나와도 완료가 유지되어야 한다. 다른 공고의 확인값과 담당은 독립이어야 하며 정확한 링크, 과거 이력과 새 Discord 진입을 함께 확인한다. 배포와 실제 지원서 이동, 제출 및 임시저장은 사람 담당이다.


## 자동 입력 결과 대시보드 (CF-184)

화면 이름은 "자동 입력 결과"다. 입력 방식은 회사 전용(STATIC), 그리팅 전용(GREETING), 범용(GENERIC)으로 표시한다. 방식은 사이트 구성과 분석 경로를 구분하며 AI 정확도나 공정한 우열을 나타내지 않는다.

기존 `bindingRate`, `inputSuccessRate`, `retentionRate`, `collectedRetentionRate`와 관측 결과만의 기존 두 비율 필드는 의미를 유지한다. 새 주요 표와 그래프는 `observed`를 사용한다. 이 비율은 결과를 받은 항목 기준이다.

| 화면 이름 | 응답 | 계산 기준 |
| --- | --- | --- |
| 프로필 연결률 | `observed.mapping` | 분석 요청의 연결 후보 합 / 수집 후보 합 |
| 입력값 준비율 | `observed.binding` | 필드 보고가 있는 실행에서 보고된 값 준비 칸 합 / 보고된 연결 칸 합 |
| 입력 성공률 | `observed.inputSuccess` | 성공 칸 합 / 입력 결과를 받은 시도 칸 합 |
| 입력 후 1초 유지율 | `observed.retention` | 유지 칸 합 / 유지 결과를 받은 성공 칸 합 |
| 전체 칸 대비 입력 유지율 | `observed.collectedRetention` | 필요한 결과와 중복 대응이 확인된 실행의 유지 칸 합 / 같은 실행의 수집 칸 합 |

각 지표는 `numerator`, `denominator`, `rate`, `sampleCount`, `excludedSamples`, `excludedFields`, `unavailableReason`을 제공한다. 비율의 평균을 사용하지 않는다. 프로필 연결률의 표본은 분석 요청이며 나머지 표본은 실행이다. 실행 수는 해당 그룹의 실행 식별자를 중복 없이 센다. 한 실행이 여러 구조에 걸치면 포함된 부분과 제외된 부분 양쪽에 나타날 수 있다. 칸 수는 조회한 그룹의 보고 범위 기준이다.

값 준비율에서 아직 보고되지 않은 연결 칸은 제외한다. 입력 성공률은 성공 또는 명시적 입력 실패가 관측된 시도 칸을 분모로 사용하며, 결과 없는 시도 칸은 제외량이다. 유지율은 유지 성공 또는 유지 실패가 관측된 성공 칸을 분모로 사용하며 결과 없는 성공 칸을 제외한다. 수집 대비 유지율은 필드 보고, 입력 결과, 유지 결과, 중복 대응 중 하나라도 부족한 실행의 수집 칸 전체를 제외한다. 이 지표의 전체 칸은 유효한 실행 안의 전체 칸이다.

`observed.fieldUnobserved`는 알고 있는 고유 수집 칸 중 필드 보고가 없는 칸 수다. 중복 대응 자체가 불명확한 실행의 칸 수는 임의로 추정하지 않고 `observed.deduplicationUnknown` 실행 수로 따로 표시한다. 보고 여부가 아니라 입력 또는 유지 단계의 미관측량은 기존 `inputResultUnobserved`, `retentionUnobserved`를 사용한다. 미관측 결과를 실패나 성공으로 계산하지 않는다. 계산 기준이 없으면 rate는 null이며 `NO_VALID_SAMPLES` 또는 `ZERO_DENOMINATOR`로 원인을 안내한다.

보고율은 일부 필드 결과 또는 완료, 취소 보고를 받은 실행의 비율이다. 부분 보고 실행은 보고된 실행이면서 결과가 부족한 실행일 수 있다. `reportedExecutions`와 `unobserved`는 서로 보완하는 건수가 아니며 보고율을 전체 필드 관측률로 해석하지 않는다.

채용 사이트 필터는 `GET /api/v1/quality/stats/sites`의 `value`(기존 사이트 식별값), `text`(도메인과 기존 회사 구분 정보)로 선택한다. 집계 전용 Bearer 토큰 또는 기존 관리 자격으로 읽을 수 있으며 관리용 `/api/v1/quality/sites` 권한은 열지 않는다. 환경은 서버 설정을 따르고 `from`, `to`, `structure`, `route`, `version` 필터와 기존 조회 제한을 적용한다. 날짜, 입력 방식, 버전, 구조, 환경을 바꾸면 선택 목록도 갱신한다. 기존 회사 식별, 그리팅 회사별 사이트와 미확인 사이트를 임의로 합치지 않는다. 새로운 회사명을 수집하거나 외부 사이트를 조회하지 않는다.

사이트별 표는 `SITE_ROUTE_VERSION`, 사이트별 일별 표와 그래프는 `SITE_VERSION_TREND`를 사용한다. 기존 `VERSION_TREND`는 사이트를 합산하는 계약을 유지한다. `time`은 KST 자정을 UTC ISO 시각으로 표현하고 `series`는 사이트, 입력 방식, 버전을 표시한다. `siteLabel`은 도메인과 기존 회사 구분 정보다. 미확인 사이트에는 구별용 식별값 일부를 함께 표시한다.

일별 그래프는 조회한 사이트, 경로, 버전 조합에 대해 기간 내 없는 날짜를 빈 집계로 채운다. 비율은 null, 실행 건수는 0이며 Grafana는 null을 0으로 대체하거나 선으로 연결하지 않는다. 날짜를 채운 뒤에도 최대 500개 행 제한을 검사하므로 기간이나 사이트 수가 크면 필터를 좁혀야 한다. 실제 한 실행이라도 있는 날짜는 기존 집계에 따라 계산한다. `human`에는 사람 기준 단계별 분자(`collected`, `mapped`, `written`, `retained`), 분모(`denominator`)와 포함 실행 수(`executions`)를 제공한다. 계산할 수 없는 단계의 분자는 null이다. 사람이 확인한 입력 가능 칸 수 기준 표와 일별 그래프는 클라이언트 관측 비율과 구분하며 미등록, 범위 불일치, 필요한 보고 부족은 기존 커버리지 계약을 유지한다.

스테이징에서 사이트 선택, 사이트별 비교, 일별 표와 그래프의 같은 날짜 건수, 빈 날짜, 사람 확인값 등록 전후를 사람이 확인한다. 자동 검증은 합성 Contribution과 격리 Grafana의 합성 API 응답을 사용하며 실제 지원서와 운영 서버를 호출하지 않는다.
