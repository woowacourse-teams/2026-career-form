# 범용 매칭 모델 평가

범용 자동기입이 서버로 보내는 AI 호출(준비 단계 버튼 결정, 섹션 분류, 필드 매핑)을 고정 입력과 사람이 검토한 정답으로
반복 측정한다. 관련 Issue: #356.

## 켜는 방법

development 서버에서만 켠다. 평가 호출은 사용자 요청과 서버 동시 호출 상한(`career-form.analysis.jev.max-concurrent`)을
나눠 쓴다. 운영 환경에서는 켜지 않는다.

| 키 | 기본값 | 의미 |
| --- | --- | --- |
| `CAREER_FORM_EVALUATION_ENABLED` | false | 평가 API·작업자·화면. `CAREER_FORM_QUALITY_ENABLED=true`일 때만 뜬다(비밀번호 보호 없이 열리지 않음) |
| `CAREER_FORM_EVALUATION_MAX_MODEL_CALLS` | 500 | 실행당 모델 호출 한도. 등록 때 예상치로, 실행 중 관측치로 확인 |
| `CAREER_FORM_EVALUATION_MAX_REPETITIONS` | 20 | 반복 수 상한 |
| `CAREER_FORM_EVALUATION_POLL_INTERVAL` | 10s | 작업자 확인 주기 |
| `CAREER_FORM_EVALUATION_LEASE` | 5m | 실행 임대. 끝나면 다른 작업자가 이어받는다 |
| `CAREER_FORM_EVALUATION_OPENAI_ENABLED` | false | 평가 공급자 목록에 OpenAI를 넣는다 |
| `CAREER_FORM_EVALUATION_OPENAI_API_KEY` | `OPENAI_API_KEY` | OpenAI 키. 사람이 서버 환경에 넣는다 |
| `CAREER_FORM_EVALUATION_OPENAI_MODELS` | gpt-6-luna | 쉼표로 구분한 허용 모델. 첫 모델이 기본값 |
| `CAREER_FORM_EVALUATION_OPENAI_REASONING_EFFORT` | none | 추론 강도. 실행 설정과 지문에 남는다 |

API와 화면은 품질 확인 공용 비밀번호(`CAREER_FORM_QUALITY_PASSWORD_HASH`)로 보호한다. 실행자는
`X-Evaluation-Requester` 헤더(영문·숫자·한글 32자)로 기록하고 없으면 `quality-admin`이다.

## 공급자

범용 매칭(섹션 분류, 필드 매핑, 버튼·선택지 결정)의 질문과 선택지는 공급자와 무관한 공통 코드(`ChoiceSectionClassifier`, `ChoiceFieldResolver`, `ChoiceInteractionDecisions`)가 만든다. 공급자는 `ChoiceModel` 하나만 구현한다.

- `answer`: 질문마다 고른 선택지와 확신도를 그대로 돌려준다(섹션 분류, 필드 매핑).
- `choose`: 확신도 기준을 넘은 답만 돌려주고 나머지는 ABSTAIN이다(버튼·선택지 결정).

| 공급자 | 구현 | 확신도 | 등록 조건 |
| --- | --- | --- | --- |
| `jev` | `JevChoiceModel`(제품 `JevClient` 그대로) | 선택지별 확률. 단일 최고 확률이고 0.8 이상일 때만 선택 | 제품 JEV 연결이 있을 때 |
| `openai` | `OpenAiChoiceModel`(Chat Completions, 질문별 선택지 enum 엄격 JSON) | 모델 자기 보고(0~1). 0.8 이상일 때만 선택 | `CAREER_FORM_EVALUATION_OPENAI_ENABLED=true`이고 키가 있을 때 |

확신도 산출 방식이 달라 버튼·선택지 결정의 기권 비율이 공급자마다 다를 수 있다. 이 차이는 비교 범위로 적는다. 프롬프트 해시는 공통 질문 문구에 공급자 연결부 문구(OpenAI 시스템 문구)를 더해 만든다. 제품 사용자 요청은 계속 `career-form.analysis.provider`를 쓴다.

새 공급자는 `ChoiceModel` 구현(따로 보내는 고정 문구가 있으면 `PromptSource`)과 `EvaluationConfiguration.evaluationProviders`의 항목 하나로 추가한다. 실행 등록 본문의 `provider`, `model`로 고르고(없으면 기본값), `GET /api/v1/evaluations/providers`가 고를 수 있는 목록(첫 항목이 기본값)을 준다.

## API

| 요청 | 결과 |
| --- | --- |
| `POST /api/v1/evaluations/runs` | 202 `{runId}`. 진행 중 실행이 있으면 409와 기존 실행 ID, 같은 조건인지 여부 |
| `GET /api/v1/evaluations/runs` | 최근 실행과 보고 |
| `GET /api/v1/evaluations/runs/{id}` | 상태, 처리 건수, 원자료에서 다시 계산한 보고(진행 중이면 부분 결과) |
| `GET /api/v1/evaluations/runs/{id}/results` | 호출별 답, 점수, 실패 원인, 시간, 모델 시도 |
| `POST /api/v1/evaluations/runs/{id}/cancel` | 대기 중이면 즉시 취소, 실행 중이면 다음 호출 경계에서 취소 |
| `POST /api/v1/evaluations/runs/{id}/scorings` | 재채점. 새 기록을 추가하고 이전 기록과 호출 결과는 그대로 둔다 |
| `GET /api/v1/evaluations/datasets/{id}/v{N}` | 데이터셋 사례, 화면 칸, 준비 동작, 검토 상태, 합성 프로필 |
| `GET /api/v1/evaluations/prompts/{digest}` | 프롬프트 버전 전문 |
| `GET /api/v1/evaluations/providers` | 고를 수 있는 공급자와 모델(첫 항목이 기본값) |
| `GET /api/v1/evaluations/comparisons/{id}` | 비교에 속한 모델별 실행과 보고(등록 순서) |
| `GET /api/v1/evaluations/runs/{id}/items` | 채점 항목별 답(칸 매핑·섹션 분류·선택 결정)과 반복별 판정 |
| `DELETE /api/v1/evaluations/records/{key}` | 비교 묶음(비교 ID, 단독 실행이면 실행 ID)의 실행·호출 결과·재채점 이력 삭제. 끝나지 않은 실행이 있으면 409. 프롬프트 원문은 남기고 삭제 사실은 서버 로그(`EVALUATION_RECORD_DELETED`)에 남긴다 |

등록 본문: `datasetId`, `datasetVersion`, `split`(tuning|final), `repetitions`, `promptVersion`(선택),
`overrides`(`field-batch-size` 1~128, `section-concurrency` 1~16만 허용), `provider`·`model`(선택, 없으면 기본값).
여러 모델 비교는 `targets`(`[{provider, model}]`, 1~5개, 중복 불가)로 보낸다. 모델마다 같은 조건의 실행을 만들어 한 비교(`comparisonId`)로 묶고, 첫 실행만 QUEUED, 나머지는 WAITING으로 두어 앞 실행이 끝나면 작업자가 차례로 돌린다. 비교 실행 하나를 취소하면 같은 비교의 남은 실행도 취소된다. 화면은 비교 묶음을 골라 모델별 결과를 나란히 보여 준다.

상태: `WAITING →` (비교의 두 번째 이후 실행) `QUEUED → RUNNING → COMPLETED | PARTIAL | FAILED | CANCELLED`. 모든 호출을 채점했으면 COMPLETED, 실패 호출이 있거나
예산에 닿아 멈추면 PARTIAL, 등록 뒤 데이터셋·프롬프트가 바뀌었거나 예외가 나면 FAILED다.

## 채점

### 대표 점수: 자동기입 점수 (2026-11-02 사용자 결정)

- 모델 비교의 대표 점수는 자동기입 점수다. 칸 매핑 답을 확장프로그램처럼 확신도 0.8 이상만 넣은 것으로 보고,
  칸마다 맞게 넣음, 맞게 비움, 놓침(비움·확인 필요·막음인데 정답이 있음), 잘못 넣음(다른 항목, 넣지 말아야 할 칸)으로 나눈다.
- 정밀도 = 맞게 넣음 ÷ 넣은 칸, 채움률 = 맞게 넣음 ÷ 정답이 있는 칸, 자동기입 점수 = 정밀도와 채움률의 F0.5.
  잘못 넣은 칸은 사용자가 찾아 고쳐야 하고 그대로 제출될 위험이 있지만 놓친 칸은 직접 입력하면 되므로, 정밀도를 2배 중시한다.
  아무것도 넣지 않으면 채움률 0이라 0점이다.
- 항목 단위 정확도는 모든 오류를 같은 무게로 세서, 많이 채우는 대신 잘못 넣는 모델이 높게 나왔다(v2 기준 JEV 81.9%,
  GPT 85.7%). 같은 실행의 자동기입 점수는 JEV 93.6%(정밀도 100%, 채움률 74.5%), GPT 86.9%(87.3%, 85.4%)다.
- 같은 식으로 단계 점수도 낸다(`report.scores`의 TOTAL·PREPARATION·MAPPING). 준비 점수는 섹션 분류·학력 구분 선택, 매핑
  점수는 섹션 분류·칸 매핑, 자동기입 점수(TOTAL)는 둘을 합친 모든 질문이다. 칸 매핑은 확신도 0.8 이상만 답한 것으로 보고,
  나머지 질문은 답 그대로 답함/비움으로 나눈다(2026-11-03 사용자 결정). 화면의 전체 흐름·준비·매핑 탭이 각 점수를 보인다.
- 보고 조회 때 저장한 답을 실행 때의 데이터셋 정답(해시 일치)과 다시 비교해 계산하므로 다시 실행하지 않아도 된다.
  확신도를 기록하기 전 실행은 측정 불가다. 반복마다 따로 계산해 범위를 보인다.
- 아래 항목 단위 정확도는 확신도와 무관한 진단 지표로 남긴다.

### 실행 조건과 구조 변경 비교

- 실행마다 코드 버전(`codeVersion`, 커밋), 서버 설정(칸 묶음, 섹션 동시, 최대 동시 호출, 재시도, 시간 제한, 확신도 기준,
  추론 강도), 프롬프트 지문, 모델을 `versions`에 남긴다. 병렬·호출 구조처럼 프롬프트가 아닌 변경도 코드 버전이나 설정 차이로
  구분된다.
- 화면은 비교 정보에 코드 버전과 칸 묶음·섹션 동시를 보이고, 항목별 비교에서 기준 실행을 고르면 모델마다 "달라진 조건"(코드,
  프롬프트, 모델, 설정)을 개선·악화 수와 함께 보인다. 실행 이름에는 무엇을 바꿨는지 짧게 적는다(예: `batch10`).
- 보고의 `itemsByCall`은 항목 판정을 "단계/호출 종류"별로 나눈 합계다. 화면은 전체 흐름·준비·매핑 전환으로 품질과 성능을 함께
  나눠 본다. 전체 흐름은 자동기입 점수(합산)와 단계별 점수 요약·자동기입 단위 성능, 준비는 준비 점수와 준비 결과, 매핑은
  매핑 점수·칸별 결과·섹션 분류 결과이고, 준비·매핑의 성능은 요청·AI 질문 단위다. 탭별 화면 동작은
  `frontend/src/evaluation/page/evaluation-page.test.ts`가 실제로 그려 확인한다. 평가는 다음 요청을 정답으로 만들어 앞 단계 오답이 자동기입 점수에 반영되지
  않으므로 준비·매핑 탭에서 따로 본다.

### 항목별 비교

- 화면의 "항목별 비교"는 `GET /api/v1/evaluations/runs/{runId}/items`로 답을 채점 항목마다 받는다. 이름은 데이터셋에 기록한
  제품 요청에서 읽는다(칸 이름·섹션, 섹션 제목, 학력 구분 대상과 선택지 글자). 칸 매핑은 자동기입 점수와 같은 분류(확신도 0.8),
  섹션 분류와 학력 구분 선택은 모델 답 그대로 채점한다. 종류를 바꿔 가며 항목×모델 표로 보고, 모델끼리 다른 항목, 틀린 항목,
  놓친 항목을 거른다. 행을 펼치면 반복별 답과 확신도가 보인다.
- 같은 데이터셋 버전의 다른 비교 묶음을 기준 실행으로 고르면 같은 모델끼리 항목마다 맞음 +1, 놓침·누락 0, 틀림 −1의 반복
  평균을 비교해 개선·악화 수를 보인다. 프롬프트·코드 변경 전후 비교에 쓴다.

### 진단 지표: 항목 단위 정확도

- 채점은 제품 API 호출 1건의 항목별로 한다. 서버가 그 안에서 모델을 몇 번 불렀는지는 비중에 쓰지 않는다.
- 호출 점수 = 맞힌 항목 수 ÷ 정답 항목 수. 정답에는 매핑 불가·기권도 들어간다. 누락, 다른 키, 불필요 제안은 그 항목의 오답이다.
- 공급자 사용 불가 항목은 채점에서 빼고, 모든 항목이 빠진 호출은 채점 불가 실패다.
- 모델 시도가 있었는데 하나도 성공하지 못한 호출은 응답 내용과 관계없이 실패(타임아웃, API 오류, 응답 형식 오류)다.
- 최종 정확도 = 채점 가능한 호출의 맞힌 항목 수 합 ÷ 채점한 항목 수 합(항목 단위, 채점식 `item-weighted-exact-v2`).
  준비·매핑 정확도는 호출이 일어난 단계로 나눠 같은 방식으로 계산한다(준비 루프 안의 섹션 분류는 준비).
- 이전 채점식 `call-unit-item-exact-v1`은 호출 점수의 평균이었다. 섹션 4개짜리 분류 호출과 칸 40여 개짜리 매핑 호출이
  같은 비중이라 매핑 품질 차이가 가려지고 모델 순위가 바뀔 수 있어 항목 단위로 바꿨다(2026-11-02 사용자 결정).
- 실행 보고는 원자료에서 현재 채점식으로 다시 계산하고 `report.scoringVersion`에 그 채점식을 적는다. 실행 등록 때의
  채점식은 `versions.scoringVersion`에 남는다.
- 채점식을 바꾸면 `RunService.SCORING_VERSION`을 올리고 재채점으로 새 기록을 만든다.
- 실제 자동기입 결과: 칸 매핑 답을 확장프로그램(`field-grading.ts`)과 같은 확신도 구간으로 나눈다. 0.8 이상은 자동기입이라
  정답·오답을 따지고, 0.5~0.8은 사용자 확인, 0.5 미만은 막음, 답이 없으면 비움이다. 이름 칸 보정과 정확히 일치하는 값
  올림 규칙은 반영하지 않는다. 칸별 확신도는 2026-11-02 이후 실행부터 저장하므로 그 전 실행은 측정 불가다. OpenAI
  확신도는 모델 자기 보고 값이라, 이 결과는 그 모델을 제품에 쓸 때 잘못 자동기입할 정도를 보여 준다.
- 0.8 기준은 공급자와 무관한 제품 규칙이다. 버튼·선택지 결정(`choose`)은 서버에서, 칸 매핑의 자동기입 구간은
  확장프로그램에서 같은 값을 쓴다.

## 측정 범위

| 값 | 시작 | 끝 | 포함 | 제외 |
| --- | --- | --- | --- | --- |
| 제품 호출 시간 | 작업자가 제품 서비스 호출 | 서비스 반환 | 서버 내부 배치, 동시 호출 상한 대기, 모델 대기, 429 재시도 대기 | HTTP 전송, 확장·페이지 조작 |
| 모델 시도 시간 | 모델 HTTP 전송 직전 | 전체 응답 수신 | 네트워크, 공급자 대기 | 응답 해석 |
| 흐름 시간(자동기입 1번) | 같은 반복에서 처음 화면 준비 호출 + 펼쳐진 화면 하나의 호출 시간 합(이전 데이터셋은 사례 하나). 토큰·실패도 같은 단위 | | 준비·매핑 호출 | 호출 사이 작업자 처리 |
| 처리량 | 완료 호출 수 ÷ 실행 경과 초 | | | |
| 큐 대기 | 등록 | 작업자 시작 | | |

토큰은 공급자가 응답에 준 값이다. 응답을 받지 못한 시도는 `null`이며 평균에서 빼고 미관측 수로 따로 센다. 비용은 서버가
계산하지 않는다. 화면에서 사용자가 넣은 단가로만 계산한다. 첫 반복과 나머지 반복의 평균 호출 시간을 따로 보고해 공급자 쪽
캐시 영향을 구분한다. 동시 호출 상한을 사용자 요청과 나눠 쓰므로 그 시간대의 사용자 요청이 대기 시간에 섞일 수 있다.

## 입력 동일성과 한계

- `SOURCE_PIPELINE_VERIFIED`: `woowahan-dataset.test.ts`가 현재 제품 코드로 fixture에서 요청을 다시 만들어 저장본의
  정규화 digest(생성 ID 제외)와 같은지 확인한다. 제품 요청 코드가 바뀌면 이 테스트가 실패한다.
- 백엔드 컨텍스트 테스트가 저장본의 모든 요청을 엄격 JSON 매퍼와 Bean Validation으로 읽어 제품 서비스에 넣는다.
- 설치 확장이 실사이트에서 보낸 요청과는 대조하지 않았다. 기본정보 섹션 제목(인사말)은 `[비식별]`이라 실제 입력과 다르다.
- 검색 팝업(주소·학교·전공)의 SEARCH_* 결정 호출과 기입 성공은 평가하지 않는다.
- 공급자 비교는 같은 데이터셋·요청·질문 문구로 모델 응답만 바꾼다. 공급자 연결부 문구와 확신도 산출 방식은 공급자마다 다르다.
- 공고 하나(화면 상태 3개)와 합성 프로필 하나라 일반화 성능을 주장하지 않는다.
- 튜닝용(initial)과 최종 평가용(high-school, university)은 같은 지원서 양식의 다른 상태다. 튜닝용으로 고친 내용이 최종
  평가용 점수에 그대로 반영될 수 있어 독립된 검증 세트로 보지 않는다.

### 실행 범위

평가 화면은 항상 현재 데이터셋(최신 버전)의 모든 화면(`split: all`)으로 실행한다. 튜닝용·최종 평가용 분할은 데이터셋
파일에 남지만 화면에서는 고르지 않는다. 개선 전후는 같은 데이터셋으로 개선 전 코드와 개선 후 코드를 각각 실행해
비교한다. 데이터셋 버전과 해시는 실행·재채점 때 입력이 바뀌지 않았는지 확인하는 데만 쓴다.

### 데이터셋 버전

| 버전 | 화면 | 바뀐 점 |
| --- | --- | --- |
| v1 | 처음(튜닝용), 고등학교·대학교(최종 평가용) | 첫 버전 |
| v2 | v1 + 검정고시(최종 평가용) | 검정고시에서만 나타나는 합격연월 칸. 프로필의 합격일자는 지원 필드 목록에 없어 정답은 매핑 불가다. 기존 3개 사례는 v1과 같은 파일이다 |
| v3 | v2와 같은 4개 | 처음 화면(학력 구분을 고르기 전)은 준비 단계(섹션 분류·학력 구분 선택)만 채점한다. 실제 제품은 고른 뒤 펼쳐진 화면에서 칸을 채우므로 고르기 전 화면의 칸 매핑은 실제 흐름과 다르고, 기본정보·병역·경력 같은 공통 칸을 중복 채점했다(2026-11-03 사용자 결정). 나머지 3개 사례는 v2와 같은 파일이다. 사례당 호출은 처음 2개 + 나머지 3개씩, 반복 1회에 11개 |

같은 공고에서 학력 '전문대학'·'대학원(석사)'은 '대학교'와 칸 구성이 같고(두 정제본이 바이트까지 같음), 병역
'병역필_현역(병)'은 새 칸 없이 면제사유 칸만 사라져 새 사례로 쓰지 않았다(2026-11-02). 이 공고에서 새로 나오는 화면은
더 없으므로 표본을 더 늘리려면 다른 회사 지원서를 수집한다. 합성 프로필을 바꾸는 확대는 매핑 요청에 프로필 값이
들어가지 않아 요청이 거의 같으므로 하지 않는다.

v2 검정고시 화면은 사용자가 승인한 예외로 에이전트가 사용자 Chrome에서 선택만 바꾸고 수집 지침 스크립트를
실행해 모았다(저장·제출·미리보기·스크린샷 없음, 끝난 뒤 선택을 처음대로 되돌림). 기록은 fixture의 `review.md`에 있다.

### 최종 평가용 화면의 전제 (2026-11-02 확인)

- 사용자가 학력 구분(고등학교·대학교)과 보훈·장애 "대상"을 미리 고른 뒤 자동기입을 실행한 화면이다. 제품이 처음 화면에서
  학력 구분을 직접 고르는 흐름은 튜닝용(initial)의 준비 단계 결정 호출로만 잰다.
- 정제본은 선택 상태를 지우고, 이미 펼쳐진 학력 행은 제품 준비 단계가 학력 구분 선택 대상으로 보지 않는다. 그래서 최종
  평가용에는 준비 단계 결정 호출이 없고 매핑 요청에 학력 기록 힌트(`recordSectionId`)가 없다.
- 제품이 처음 화면에서 "대학교"를 고르고 페이지가 칸을 펼치는 흐름을 jsdom으로 흉내 내 대학교 화면 요청과 비교했다.
  학력 칸 10개 중 8개(학교명·입학연월·졸업연월·입학구분·졸업구분·주전공·전공추가·복수/부전공)의 요청이 같았다.
  학력 구분 선택 칸에만 단계 표시("대학교")가 더 붙었고, 야간 체크박스의 라벨 차이는 흉내 방식 때문일 수 있어 확정하지
  않았다. 학력 칸의 학력 기록 모호성은 녹화 방식이 아니라 제품 요청의 성질이다.

### 단계별 채점 범위

- 최종 평가용의 준비 단계는 섹션 분류 호출 1건(병역·학력·첨부자료·지원경로 4개 항목)뿐이다. 준비 정확도는 이 4개
  항목으로 정해지며, 두 화면의 섹션 구성이 같아 사실상 같은 질문을 반복해 잰다.
- 항목 단위 집계에서 최종 평가용 사례 하나의 준비 단계 비중은 약 7%(4 ÷ 55~57 항목)다.
- 판단 보류(ABSTAIN)는 누락으로 센다. 제품은 보류한 섹션의 후보를 전체로 넓히고 확인을 요구하므로, 다른 키를 고른 오답과
  위험이 다르다. 정확도와 함께 보고의 `quality.items`(오답·누락·불필요 제안 수)를 본다.
