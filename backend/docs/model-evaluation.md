# 범용 매칭 모델 평가

범용 자동기입이 서버로 보내는 AI 호출(준비 단계 버튼 결정, 섹션 분류, 필드 매핑)을 고정 입력과 사람이 검토한 정답으로
반복 측정한다. 관련 Issue: #356.

## 구성

| 부분 | 위치 | 역할 |
| --- | --- | --- |
| 화면 fixture | `frontend/fixtures/dom-snapshots/woowahan-r2605009-*` | 사람이 준비한 지원서 화면의 비식별 정제본 |
| 요청 기록 | `frontend/src/evaluation/capture/` | 제품 범용 흐름을 fixture에 실행해 제품 요청을 호출 순서대로 기록. 후속 요청은 정답으로 만든다 |
| 데이터셋 | `src/main/resources/evaluation/datasets/<id>/v<N>/` | manifest(파일 sha256, 검토 상태), 사례(요청과 정답), 정답 원본 |
| 합성 프로필 | `src/main/resources/evaluation/profiles/v1/` | 가상 인물 3명. 실제 지원자 자료가 아니다 |
| 등록 검사 | `evaluation/dataset/DatasetLoader` | 해시, 사람 검토, 입력 동일성, 형식, 분할을 통과한 데이터셋만 실행에 쓴다 |
| 실행 | `evaluation/run/` | 등록(`RunService`), 작업자(`EvaluationWorker`), 제품 서비스 호출(`ServiceProductCallGateway`), 결과·재채점 저장 |
| 채점 | `evaluation/scoring/` | 항목 채점(`CallScorer`), 항목 단위 집계(`RunAggregator`) |
| 공급자 | `formanalysis/application/port/ChoiceModel`, `evaluation/run/EvaluationProviders` | 범용 매칭이 모델에 묻는 유일한 포트와 평가에서 고를 수 있는 공급자 목록 |
| 모델 호출 기록 | `monitoring/ModelCallRecording`, `JevClient`, `OpenAiChoiceModel` | 평가 실행 범위 안의 모델 HTTP 시도별 시간·상태·토큰 |
| 프롬프트 버전 | `formanalysis/application/PromptSource`, `evaluation/prompt/` | 프롬프트 고정 문구 조각과 sha256 해시, 버전별 전문 |
| 화면 | `src/main/resources/static/evaluations/` (`/evaluations/`) | 결과 비교, 데이터셋·정답 기준·프롬프트 보기, 실행 등록, 수집 지침 내려받기 |

## 쓰는 방법

| 환경 | 용도 | 기록 |
| --- | --- | --- |
| 로컬 | 프롬프트·호출 구조·설정을 고칠 때마다 개선됐는지 잰다. 전후 비교 탭에서 고치기 전과 후 실행을 비교한다 | 로컬 MongoDB 볼륨에만 |
| 개발서버 | 평가에 영향을 주는 변경이 머지되면 자동으로 한 번 재서 팀이 변경별 결과를 본다 | 개발서버 MongoDB에 계속 쌓임 |

화면 위쪽 **사용 가이드**에 두 환경의 순서와 명령을 적어 두었다. 지금 서버가 로컬 주소면 로컬 탭이 먼저 열린다.

### 로컬에서 돌리기

```bash
python3 scripts/evaluation_local.py          # 이 체크아웃 코드로 빌드해 http://127.0.0.1:18090/evaluations/ 에 띄움
python3 scripts/evaluation_local.py stop     # 끄기(기록은 남음)
python3 scripts/evaluation_local.py reset-password
```

- 키(JEV·OpenAI)는 `.env.local`에서 읽는다(이 체크아웃, 없으면 메인 체크아웃). 처음 실행 때 정한 로그인 비밀번호는 해시만
  Git 메타데이터 폴더(`cf-workflow/evaluation-password.hash`, 저장소 밖)에 둔다.
- 코드 버전은 커밋 번호이고, 커밋하지 않은 `backend/` 변경이 있으면 `-dirty-<지문>`을 붙여 실행 조건에서 구분한다.
  프롬프트 원문 지문과 서버 설정도 실행마다 남는다.
- 고치기 전과 고친 뒤에 각각 평가를 돌리고 **전후 비교** 탭에서 이전·이후 실행을 고른다. 모델마다 지표(자동기입·준비·매핑
  점수, 정밀도, 채움률, 자동기입 시간, AI 응답 시간, 실패율)의 이전·이후·변화, 달라진 조건, 판정이 바뀐 항목(악화 먼저)이
  나온다. 메인 화면(품질·성능, 항목별 비교)은 실행 하나만 보인다. 복사 버튼은 PR 본문용 요약을 복사한다.
- 어느 한쪽이 반복 1회이거나 두 실행의 반복별 점수 범위가 겹치면 변화는 색 없이 `구분 불가`로 붙는다(시간·비율은 반복 수만
  본다). 프롬프트·모델·설정이 같은 두 실행에서도 OpenAI 자동기입 점수가 4.7%p 움직였으므로(2026-11-03, 이전 반복 1회),
  개선 판단은 둘 다 반복 3회 이상으로 한다.
- 포트·볼륨·프로젝트 이름은 `CF_EVAL_PORT`, `CF_EVAL_DATA_VOLUME`, `CF_EVAL_PROJECT`로 바꾼다.
- `CF_EVAL_AUTO_RUN=true`면 로컬에서도 개발서버와 같은 자동 평가 판단이 돈다(실제 모델 호출 비용이 든다).

### 개발서버 자동 평가

`CAREER_FORM_EVALUATION_AUTO_RUN_ENABLED=true`면 서버가 뜬 뒤 평가 입력을 계산해 지난 자동 평가의 입력과 비교하고, 다를 때만
공급자마다 기본 모델로 비교 하나(반복 3회)를 등록한다. 판단에는 AI를 쓰지 않는다.

| 입력 | 잡아내는 변경 | 만드는 방법 |
| --- | --- | --- |
| `behavior` | 질문 구성, 칸 묶음, 후보 좁히기, 응답 후처리 | 데이터셋 요청을 제품 코드에 넣고 가짜 모델(첫 선택지, 판단 보류 두 벌)로 돌려 AI에 간 질문과 최종 응답을 해시(`BehaviorFingerprint`). 측정 시간은 뺀다 |
| `prompt` | 공통·공급자 프롬프트 문구 | 프롬프트 스냅샷 지문 |
| `settings` | 기본 모델, 동시 호출, 재시도, 시간 제한, 추론 강도 | 공급자별 실효 설정 |
| `provider` | JEV·OpenAI 연결 코드 | 빌드 때 넣는 adapter 폴더의 Git 트리 지문(`CAREER_FORM_ADAPTER_DIGEST`) |
| `dataset` | 화면 추가, 정답 변경 | 데이터셋 지문 |

입력은 실행 기록(`versions.inputs`)에 남고 코드 버전은 표시용으로 따로 남는다. 변수명만 바꾸면 입력이 같아 돌지 않고, 서버 로그에
`EVALUATION_AUTO_RUN_UNCHANGED`가 남는다. 단 adapter 폴더는 소스 지문이라 변수명 변경에도 돈다. 진행 중인 평가가 있으면 건너뛰고, 다음
서버 시작 때 다시 비교한다. 실패·취소된 자동 평가도 그 입력으로는 다시 돌지 않는다(비용 반복 방지).

이름은 바뀐 입력과 커밋 앞 7자다: `prompt-391fbd8`, `call-391fbd8`(프롬프트·설정·데이터셋이 같은데 동작 지문만 바뀜), `settings-…`,
`provider-…`, `dataset-…`, 여러 개면 이어 붙이고(`settings-dataset-…`), 32자를 넘으면 `multi-…`, 지난 기록이 없으면 `first-…`다. 실행자는
`auto-deploy`로 남고 화면 실행 조건에 "자동(배포)"로 보인다.

알 수 없는 변경: 공급자가 같은 이름으로 모델을 바꾼 경우(`jev-latest`), 질문과 응답이 같고 속도만 바뀐 변경, 가짜 답이 지나가지 않는
후처리 분기. 이런 변경은 평가 실행으로 직접 돌린다. 데이터셋 버전은 평가 화면과 같은 `catalog.json`의 현재 버전이다. 데이터셋 v4·반복 3회 기준 실행당 두 모델 합 약 $0.2(GPT 약 $0.13, JEV 약 $0.07)가 든다. 코드 버전은 이미지에 담긴 커밋 번호(짧은 SHA)다.
개발 배포 워크플로가 이미지 빌드 때 `CAREER_FORM_COMMIT`을 넘기므로 롤백해도 그 이미지의 커밋으로 보이고, 커밋이 없는 빌드는 `CAREER_FORM_QUALITY_VERSION`을 쓴다.

개발서버에서 켜는 값은 GitHub `development` Environment에 사람이 넣는다. 배포 워크플로와 `infra/compose.deploy.yaml`이
이 값을 백엔드로 넘기고, 값이 없으면 모두 꺼진다. staging·production 워크플로는 평가 값을 넘기지 않는다.

| 종류 | 이름 | 값 |
| --- | --- | --- |
| 변수 | `CAREER_FORM_QUALITY_ENABLED` | true (평가 화면 비밀번호 보호에 필요) |
| 시크릿 | `CAREER_FORM_QUALITY_PASSWORD_HASH` | 팀 공용 비밀번호 해시(`pbkdf2-sha256$600000$...`) |
| 변수 | `CAREER_FORM_EVALUATION_ENABLED` | true |
| 변수 | `CAREER_FORM_EVALUATION_AUTO_RUN_ENABLED` | true (평가에 영향을 주는 머지가 배포될 때 평가 1회) |
| 변수 | `CAREER_FORM_EVALUATION_OPENAI_ENABLED` | OpenAI와 비교할 때 true. 키는 기존 `OPENAI_API_KEY` 시크릿 |
| 시크릿 | `CAREER_FORM_EVALUATION_PROVIDER_KEYS` | 화면에서 등록하는 공급자의 키 묶음(필요할 때만) |

값을 넣거나 바꾼 뒤에는 다음 develop 머지(또는 개발 배포 워크플로 재실행) 때 반영된다.

### 저장소에 담은 기준 기록

평가를 켠 서버는 뜰 때 `evaluation/seed-records/*.jsonl`의 기록 중 없는 것만 넣는다(`EvaluationSeedRecords`). 모델을 호출하지 않고, 있는 기록은 건드리지 않으며, 입력(`versions.inputs`)이 없어 첫 자동 평가를 막지 않는다. 그래서 개발서버는 이후 개선과 비교할 기준 세 건을 갖고 시작한다. 모두 2026-11-05 로컬 측정이다.

| 이름 | 모델 | 묻는 방식 | 보려는 것 |
|---|---|---|---|
| `initial-openai` | OpenAI `gpt-5.6-luna`, `gpt-6-luna` | 초기 구조: 화면 전체 칸을 지원 키 전부와 한 번에(`whole-form=1`, 칸 묶음 128) | OpenAI만 쓰던 때의 호출 방식. 당시 기본 모델은 `gpt-5.6-luna`이고 `gpt-6-luna`는 비교용이다 |
| `token-limit` | JEV `jev-latest` | 같은 초기 구조 | JEV 도입 직후의 입력 토큰 초과와 반으로 나눠 다시 묻는 동작 |
| `current` | JEV `jev-latest`, OpenAI `gpt-5.6-luna`, `gpt-6-luna` | 현재 구조(섹션별, 5칸씩) | 구조 개선 뒤. 같은 모델로 구조만 바꾼 효과와 모델 차이를 가른다 |

화면은 기준 기록을 측정한 시각이 아니라 파일 순서(`순번-이름.jsonl`, `capabilities.baselineOrder`)대로 다른 실행보다 오래된 쪽에 놓는다. 다시 측정해 시각이 뒤섞여도 초기 → 이후 순서가 유지된다.

호출 구조만 재현한 측정이고 당시 결과가 아니다. 프롬프트, 후처리, 데이터셋(v4)은 측정 시점의 것이고, 초기에는 없던 섹션 분류·준비 호출도 그대로 돌므로 초기 구조 기록은 칸 매핑(자동기입 점수)만 본다. 초기 코드는 답을 목록으로 받아 모르는 칸을 뺄 수 있었지만 지금은 모든 칸에 답한다.

초기 코드는 선택지 목록을 응답 스키마에 한 번만 넣었고, 지금 연결 코드는 질문마다 넣는다. 그래서 화면 전체를 한 번에 물으면 OpenAI 구조화 출력의 enum 한도(1,000개)를 넘어 enum 없이 답을 받게 되고, 답 하나가 목록에 없으면 응답 전체가 버려져 요청의 절반 이상이 실패했다(초기에는 없던 실패). 한도를 넘으면 같은 선택지를 쓰는 질문이 정의 하나를 공유하도록 고친 뒤(`OpenAiChoiceModel`) 다시 측정한 것이 이 기록이다. JEV는 입력 토큰 초과로 거절되면 나눠 다시 물어 실패 없이 끝나며, 거절 횟수는 `performance.*.tokenLimitAttempts`(화면의 입력 토큰 초과)로 본다.

다시 측정할 때는 기준 기록이 먼저 들어가 이름이 겹치지 않도록 `CF_EVAL_SEED_RECORDS=false`로 로컬 서버를 띄우고, 형식을 보존하도록 `mongoexport --jsonFormat=canonical`로 내보낸다.

## 켜는 방법

development 서버에서만 켠다. 평가 호출은 사용자 요청과 서버 동시 호출 상한(`career-form.analysis.jev.max-concurrent`)을
나눠 쓴다. 운영 환경에서는 켜지 않는다.

| 키 | 기본값 | 의미 |
| --- | --- | --- |
| `CAREER_FORM_EVALUATION_ENABLED` | false | 평가 API·작업자·화면. `CAREER_FORM_QUALITY_ENABLED=true`일 때만 뜬다(비밀번호 보호 없이 열리지 않음) |
| `CAREER_FORM_EVALUATION_MAX_MODEL_CALLS` | 500 | 실행당 모델 호출 한도. 등록 때 예상치로, 실행 중 관측치로 확인 |
| `CAREER_FORM_EVALUATION_MAX_REPETITIONS` | 20 | 반복 수 상한 |
| `CAREER_FORM_EVALUATION_POLL_INTERVAL` | 10s | 작업자 확인 주기 |
| `CAREER_FORM_EVALUATION_LEASE` | 5m | 실행 임대. 끝나면 다른 작업자가 이어받는다 |
| `CAREER_FORM_EVALUATION_OPENAI_ENABLED` | false | 평가 공급자 목록에 OpenAI를 넣는다 |
| `CAREER_FORM_EVALUATION_OPENAI_API_KEY` | `OPENAI_API_KEY` | OpenAI 키. 사람이 서버 환경에 넣는다 |
| `CAREER_FORM_EVALUATION_OPENAI_MODELS` | gpt-6-luna | 쉼표로 구분한 허용 모델. 첫 모델이 기본값 |
| `CAREER_FORM_EVALUATION_OPENAI_REASONING_EFFORT` | none | 추론 강도. 실행 설정과 지문에 남는다 |
| `CAREER_FORM_EVALUATION_AUTO_RUN_ENABLED` | false | 평가 입력이 바뀐 배포 뒤 평가 1회 자동 실행 |
| `CAREER_FORM_EVALUATION_RECORD_DELETE_ENABLED` | false | 평가 기록 삭제와 휴지통 버튼. 로컬 실행기만 켠다. 개발서버 기록은 팀의 변경 이력이라 지우지 않는다 |
| `CAREER_FORM_EVALUATION_AUTO_RUN_REPETITIONS` | 3 | 자동 실행 반복 수 |
| `CAREER_FORM_EVALUATION_AUTO_RUN_DATASET_VERSION` | 0 | 자동 실행 데이터셋 버전. 0이면 `catalog.json`의 현재 버전 |
| `CAREER_FORM_ADAPTER_DIGEST` | 빈 값 | 공급자 연결 코드의 Git 트리 지문. 개발 배포 이미지 빌드 인자로 넣고 자동 평가 입력에 쓴다 |
| `CAREER_FORM_COMMIT` | 빈 값 | 이미지가 만들어진 커밋. 개발 배포 이미지 빌드 인자로 넣고, 코드 버전에 앞 7자를 쓴다 |

API와 화면은 품질 확인 공용 비밀번호(`CAREER_FORM_QUALITY_PASSWORD_HASH`)로 보호한다. 실행자는
`X-Evaluation-Requester` 헤더(영문·숫자·한글 32자)로 기록하고 없으면 `quality-admin`이다.

## 공급자

범용 매칭(섹션 분류, 필드 매핑, 버튼·선택지 결정)의 질문과 선택지는 공급자와 무관한 공통 코드(`ChoiceSectionClassifier`, `ChoiceFieldResolver`, `ChoiceInteractionDecisions`)가 만든다. 공급자는 `ChoiceModel` 하나만 구현한다.

- `answer`: 질문마다 고른 선택지와 확신도를 그대로 돌려준다(섹션 분류, 필드 매핑).
- `choose`: 확신도 기준을 넘은 답만 돌려주고 나머지는 ABSTAIN이다(버튼·선택지 결정).

| 공급자 | 구현 | 확신도 | 등록 조건 |
| --- | --- | --- | --- |
| `jev` | `JevChoiceModel`(제품 `JevClient` 그대로) | 선택지별 확률. 단일 최고 확률이고 0.8 이상일 때만 선택 | 제품 JEV 연결이 있을 때 |
| `openai` | `OpenAiChoiceModel`(Chat Completions, 질문별 선택지 enum 엄격 JSON) | 모델 자기 보고(0~1). 0.8 이상일 때만 선택 | `CAREER_FORM_EVALUATION_OPENAI_ENABLED=true`이고 키가 있을 때 |

확신도 산출 방식이 달라 버튼·선택지 결정의 기권 비율이 공급자마다 다를 수 있다. 이 차이는 비교 범위로 적는다. 프롬프트 해시는 공통 질문 문구에 공급자 연결부 문구(OpenAI 시스템 문구)를 더해 만든다. 제품 사용자 요청은 계속 `career-form.analysis.provider`를 쓴다.

새 공급자는 `ChoiceModel` 구현(따로 보내는 고정 문구가 있으면 `PromptSource`)과 `EvaluationConfiguration.evaluationProviders`의 항목 하나로 추가한다. 실행 등록 본문의 `provider`, `model`로 고르고(없으면 기본값), `GET /api/v1/evaluations/providers`가 고를 수 있는 목록(첫 항목이 기본값)을 준다.

## API

| 요청 | 결과 |
| --- | --- |
| `POST /api/v1/evaluations/runs` | 202 `{runId}`. 진행 중 실행이 있으면 409와 기존 실행 ID, 같은 조건인지 여부 |
| `GET /api/v1/evaluations/runs` | 최근 실행과 보고 |
| `GET /api/v1/evaluations/runs/{id}` | 상태, 처리 건수, 원자료에서 다시 계산한 보고(진행 중이면 부분 결과) |
| `GET /api/v1/evaluations/runs/{id}/results` | 호출별 답, 점수, 실패 원인, 시간, 모델 시도 |
| `POST /api/v1/evaluations/runs/{id}/cancel` | 대기 중이면 즉시 취소, 실행 중이면 다음 호출 경계에서 취소 |
| `POST /api/v1/evaluations/runs/{id}/scorings` | 재채점. 새 기록을 추가하고 이전 기록과 호출 결과는 그대로 둔다 |
| `GET /api/v1/evaluations/datasets/{id}/v{N}` | 데이터셋 사례, 화면 칸, 준비 동작, 검토 상태, 합성 프로필 |
| `GET /api/v1/evaluations/prompts/{digest}` | 프롬프트 버전 전문 |
| `GET /api/v1/evaluations/providers` | 고를 수 있는 공급자와 모델(첫 항목이 기본값) |
| `GET /api/v1/evaluations/comparisons/{id}` | 비교에 속한 모델별 실행과 보고(등록 순서) |
| `GET /api/v1/evaluations/runs/{id}/items` | 채점 항목별 답(칸 매핑·섹션 분류·선택 결정)과 반복별 판정 |
| `GET /api/v1/evaluations/capabilities` | 화면이 켜고 끌 기능(`recordDelete`)과 기준 기록의 표시 순서(`baselineOrder`) |
| `DELETE /api/v1/evaluations/records/{key}` | 비교 묶음(비교 ID, 단독 실행이면 실행 ID)의 실행·호출 결과·재채점 이력 삭제. 기록 삭제를 켠 서버(로컬)가 아니면 403, 끝나지 않은 실행이 있으면 409. 프롬프트 원문은 남기고 삭제 사실은 서버 로그(`EVALUATION_RECORD_DELETED`)에 남긴다 |

등록 본문: `datasetId`, `datasetVersion`, `split`(tuning|final), `repetitions`, `promptVersion`(선택),
`overrides`(`field-batch-size` 1~128, `section-concurrency` 1~16만 허용), `provider`·`model`(선택, 없으면 기본값).
여러 모델 비교는 `targets`(`[{provider, model}]`, 1~5개, 중복 불가)로 보낸다. 모델마다 같은 조건의 실행을 만들어 한 비교(`comparisonId`)로 묶고, 첫 실행만 QUEUED, 나머지는 WAITING으로 두어 앞 실행이 끝나면 작업자가 차례로 돌린다. 비교 실행 하나를 취소하면 같은 비교의 남은 실행도 취소된다. 화면은 비교 묶음을 골라 모델별 결과를 나란히 보여 준다.

상태: `WAITING →` (비교의 두 번째 이후 실행) `QUEUED → RUNNING → COMPLETED | PARTIAL | FAILED | CANCELLED`. 모든 호출을 채점했으면 COMPLETED, 실패 호출이 있거나
예산에 닿아 멈추면 PARTIAL, 등록 뒤 데이터셋·프롬프트가 바뀌었거나 예외가 나면 FAILED다.

## 채점

### 대표 점수: 자동기입 점수 (2026-11-02 사용자 결정)

- 모델 비교의 대표 점수는 자동기입 점수다. 칸 매핑 답을 확장프로그램처럼 확신도 0.8 이상만 넣은 것으로 보고,
  칸마다 맞게 넣음, 맞게 비움, 놓침(비움·확인 필요·막음인데 정답이 있음), 잘못 넣음(다른 항목, 넣지 말아야 할 칸)으로 나눈다.
- 정밀도 = 맞게 넣음 ÷ 넣은 칸, 채움률 = 맞게 넣음 ÷ 정답이 있는 칸, 자동기입 점수 = 정밀도와 채움률의 F0.5.
  잘못 넣은 칸은 사용자가 찾아 고쳐야 하고 그대로 제출될 위험이 있지만 놓친 칸은 직접 입력하면 되므로, 정밀도를 더 중시한다.
  아무것도 넣지 않으면 채움률 0이라 0점이다.
- 항목 단위 정확도는 모든 오류를 같은 무게로 세서, 많이 채우는 대신 잘못 넣는 모델이 높게 나왔다(v2 기준 JEV 81.9%,
  GPT 85.7%). 같은 실행의 자동기입 점수는 JEV 93.6%(정밀도 100%, 채움률 74.5%), GPT 86.9%(87.3%, 85.4%)다.
- 점수는 질문 종류를 섞지 않고 따로 낸다(`report.scores`, 2026-11-05 사용자 결정). 자동기입 점수(`TOTAL`, `MAPPING`과 같음)는 값을
  실제로 넣는 칸 매핑만이고, 준비 점수(`PREPARATION`)는 준비 단계의 섹션 고르기·버튼·선택 결정, 섹션 분류 점수(`SECTION`)는
  매핑 단계의 섹션 분류다. 2026-11-03에는 모든 질문을 합쳐 자동기입 점수를 냈는데, 섹션 분류 오답이 "잘못 넣은 칸"처럼 정밀도를
  깎아(칸 매핑 정밀도 100%인 JEV가 92.8%로 보임) 나눴다. 칸 매핑은 확신도 0.8 이상만 넣은 것으로 보고, 나머지 질문은 답 그대로
  답함/비움으로 나눈다.
- 가중치는 F0.5를 유지한다. F0.5는 점수식 분모에서 잘못 넣은 칸 1개를 놓친 칸 4개(1/β²)와 같게 친다. 제품의 자동 입력 기준과
  같은 비율이다: 확신도 p인 칸을 넣는 것이 이득이려면 (1−p)×(잘못 넣은 비용) < p×(놓친 비용)이어야 하고, 제품의 경계
  `AUTO_CONFIDENCE_MIN` 0.8에서 두 비용의 비가 4가 된다. 버튼·선택 결정도 0.8 미만을 보류로 돌리므로 같은 비율을 쓴다. 섹션 분류는
  제품에 기준이 없어 같은 식을 준용한 것이고, 분류 오답이 칸에 미치는 영향은 재지 않는다. 이 비율이 모델 순위를 가른다: 현재
  구조의 칸 매핑은 4칸에서 JEV 88.1%, OpenAI 88.3%로 같고, 2칸이면 OpenAI(81.6% 대 87.4%), 10칸이면 JEV(94.2% 대 89.1%)가 앞선다.
- 요청이 실패해 답하지 못한 칸도 사용자에게는 빈 칸이므로 빼지 않고, 정답이 있으면 놓침, 없으면 맞게 비움으로 센다(2026-11-05 사용자 결정). 빼면 실패가 많은 모델이 쉬운 칸만 채점받아 점수가 오른다.
- 확신도 0.8 기준은 제품 등급 규칙(`frontend/src/autofill/generic/field-grading.ts`)을 단순화한 것이다. 제품은 범주가 확정된 칸이면 0.35 이상도 조건이 맞을 때 자동 입력으로 올리고, 범주 미확정(`MIXED`, `ABSTAIN`) 칸은 확인 필요 등급이지만 기본으로 입력 목록에 넣으며, 값·선택지 검사로 막는 칸도 있다. 그래서 자동기입 점수는 프롬프트·모델·구조를 같은 기준으로 비교하는 값이고 실제 자동 입력률이 아니다. 등급 규칙을 채점에 옮기면 같은 규칙이 두 곳에 생기므로 옮기지 않았다(2026-11-05 확인).
- 같은 0.8이라도 JEV는 확률, OpenAI는 모델이 적은 값이라 뜻이 다르다. `report.confidence`(화면의 매핑 탭)는 칸 매핑 답을 기준 0.5~0.9로 다시 나눠 기준이 결과를 얼마나 바꾸는지 보인다. 같은 데이터로 본 값이고 제품은 0.8 아래 칸도 조건이 맞으면 넣으므로, 제품 기준을 바꾸는 근거가 아니라 모델의 확신도가 오답을 거르는지 보는 진단으로 쓴다.
- 보고 조회 때 저장한 답을 실행 때의 데이터셋 정답(해시 일치)과 다시 비교해 계산하므로 다시 실행하지 않아도 된다.
  확신도를 기록하기 전 실행은 측정 불가다. 반복마다 따로 계산해 범위를 보인다.
- 아래 항목 단위 정확도는 확신도와 무관한 진단 지표로 남긴다.

### 실행 조건과 구조 변경 비교

- 실행마다 코드 버전(`codeVersion`, 커밋), 서버 설정(칸 묶음, 섹션 동시, 최대 동시 호출, 재시도, 시간 제한, 확신도 기준,
  추론 강도), 프롬프트 지문, 모델을 `versions`에 남긴다. 병렬·호출 구조처럼 프롬프트가 아닌 변경도 코드 버전이나 설정 차이로
  구분된다.
- 화면은 실행 조건에 코드 버전과 칸 묶음·섹션 동시를 보이고, 전후 비교 탭은 모델마다 "달라진 조건"(코드, 프롬프트, 모델,
  설정)을 개선·악화 수와 함께 보인다. 실행 이름에는 무엇을 바꿨는지 짧게 적는다(예: `batch10`).
- 보고의 `itemsByCall`은 항목 판정을 "단계/호출 종류"별로 나눈 합계다. 화면은 전체 흐름·준비·매핑 전환으로 품질과 성능을 함께
  나눠 본다. 전체 흐름은 자동기입 점수(합산)와 단계별 점수 요약·자동기입 단위 성능, 준비는 준비 점수와 준비 결과, 매핑은
  매핑 점수·칸별 결과·섹션 분류 결과이고, 준비·매핑의 성능은 요청·AI 질문 단위다. 탭별 화면 동작은
  `frontend/src/evaluation/page/evaluation-page.test.ts`가 실제로 그려 확인한다. 평가는 다음 요청을 정답으로 만들어 앞 단계 오답이 자동기입 점수에 반영되지
  않으므로 준비·매핑 탭에서 따로 본다.

### 항목별 비교

- 화면의 "항목별 비교"는 `GET /api/v1/evaluations/runs/{runId}/items`로 답을 채점 항목마다 받는다. 이름은 데이터셋에 기록한
  제품 요청에서 읽는다(칸 이름·섹션, 섹션 제목, 학력 구분 대상과 선택지 글자). 칸 매핑은 자동기입 점수와 같은 분류(확신도 0.8),
  섹션 분류와 학력 구분 선택은 모델 답 그대로 채점한다. 종류를 바꿔 가며 항목×모델 표로 보고, 모델끼리 다른 항목, 틀린 항목,
  놓친 항목을 거른다. 행을 펼치면 반복별 답과 확신도가 보인다.
- 같은 모델의 실행 사이 비교는 전후 비교 탭이 맡는다. 항목마다 맞음 +1, 놓침·누락 0, 틀림 −1의 반복 평균을 비교해 판정이
  바뀐 항목과 개선·악화 수를 보인다.

### 진단 지표: 항목 단위 정확도

- 채점은 제품 API 호출 1건의 항목별로 한다. 서버가 그 안에서 모델을 몇 번 불렀는지는 비중에 쓰지 않는다.
- 호출 점수 = 맞힌 항목 수 ÷ 정답 항목 수. 정답에는 매핑 불가·기권도 들어간다. 누락, 다른 키, 불필요 제안은 그 항목의 오답이다.
- 공급자 사용 불가 항목은 채점에서 빼고, 모든 항목이 빠진 호출은 채점 불가 실패다.
- 모델 시도가 있었는데 하나도 성공하지 못한 호출은 응답 내용과 관계없이 실패(타임아웃, API 오류, 응답 형식 오류)다.
- 최종 정확도 = 채점 가능한 호출의 맞힌 항목 수 합 ÷ 채점한 항목 수 합(항목 단위, 채점식 `item-weighted-exact-v2`).
  준비·매핑 정확도는 호출이 일어난 단계로 나눠 같은 방식으로 계산한다(준비 루프 안의 섹션 분류는 준비).
- 이전 채점식 `call-unit-item-exact-v1`은 호출 점수의 평균이었다. 섹션 4개짜리 분류 호출과 칸 40여 개짜리 매핑 호출이
  같은 비중이라 매핑 품질 차이가 가려지고 모델 순위가 바뀔 수 있어 항목 단위로 바꿨다(2026-11-02 사용자 결정).
- 실행 보고는 원자료에서 현재 채점식으로 다시 계산하고 `report.scoringVersion`에 그 채점식을 적는다. 실행 등록 때의
  채점식은 `versions.scoringVersion`에 남는다.
- 채점식을 바꾸면 `RunService.SCORING_VERSION`을 올리고 재채점으로 새 기록을 만든다.
- 실제 자동기입 결과: 칸 매핑 답을 확장프로그램(`field-grading.ts`)과 같은 확신도 구간으로 나눈다. 0.8 이상은 자동기입이라
  정답·오답을 따지고, 0.5~0.8은 사용자 확인, 0.5 미만은 막음, 답이 없으면 비움이다. 이름 칸 보정과 정확히 일치하는 값
  올림 규칙은 반영하지 않는다. 칸별 확신도는 2026-11-02 이후 실행부터 저장하므로 그 전 실행은 측정 불가다. OpenAI
  확신도는 모델 자기 보고 값이라, 이 결과는 그 모델을 제품에 쓸 때 잘못 자동기입할 정도를 보여 준다.
- 0.8 기준은 공급자와 무관한 제품 규칙이다. 버튼·선택지 결정(`choose`)은 서버에서, 칸 매핑의 자동기입 구간은
  확장프로그램에서 같은 값을 쓴다.

## 측정 범위

| 값 | 시작 | 끝 | 포함 | 제외 |
| --- | --- | --- | --- | --- |

| 모델 시도 시간 | 모델 HTTP 전송 직전 | 전체 응답 수신 | 네트워크, 공급자 대기 | 응답 해석 |

| 큐 대기 | 등록 | 작업자 시작 | | |

토큰은 공급자가 응답에 준 값이다. 응답을 받지 못한 시도는 `null`이며 평균에서 빼고 미관측 수로 따로 센다. 비용은 서버가
계산하지 않는다. 화면에서 사용자가 넣은 단가로만 계산한다. 첫 반복과 나머지 반복의 평균 호출 시간을 따로 보고해 공급자 쪽
캐시 영향을 구분한다. 동시 호출 상한을 사용자 요청과 나눠 쓰므로 그 시간대의 사용자 요청이 대기 시간에 섞일 수 있다.

## 입력 동일성과 한계

- `SOURCE_PIPELINE_VERIFIED`: `woowahan-dataset.test.ts`(v3)와 `nhn-dataset.test.ts`(v4)가 현재 제품 코드로 fixture에서 요청을 다시 만들어 저장본의
  정규화 digest(생성 ID 제외)와 같은지 확인한다. 제품 요청 코드가 바뀌면 이 테스트가 실패한다.
- 백엔드 컨텍스트 테스트가 저장본의 모든 요청을 엄격 JSON 매퍼와 Bean Validation으로 읽어 제품 서비스에 넣는다.
- 설치 확장이 실사이트에서 보낸 요청과는 대조하지 않았다. 기본정보 섹션 제목(인사말)은 `[비식별]`이라 실제 입력과 다르다.
- 검색 팝업(주소·학교·전공)의 SEARCH_* 결정 호출과 기입 성공은 평가하지 않는다.
- 공급자 비교는 같은 데이터셋·요청·질문 문구로 모델 응답만 바꾼다. 공급자 연결부 문구와 확신도 산출 방식은 공급자마다 다르다.
- 공고 하나(화면 상태 3개)와 합성 프로필 하나라 일반화 성능을 주장하지 않는다.
- 튜닝용(initial)과 최종 평가용(high-school, university)은 같은 지원서 양식의 다른 상태다. 튜닝용으로 고친 내용이 최종
  평가용 점수에 그대로 반영될 수 있어 독립된 검증 세트로 보지 않는다.

### 실행 범위

평가 화면은 항상 현재 데이터셋(최신 버전)의 모든 화면(`split: all`)으로 실행한다. 튜닝용·최종 평가용 분할은 데이터셋
파일에 남지만 화면에서는 고르지 않는다. 개선 전후는 같은 데이터셋으로 개선 전 코드와 개선 후 코드를 각각 실행해
비교한다. 데이터셋 버전과 해시는 실행·재채점 때 입력이 바뀌지 않았는지 확인하는 데만 쓴다.

### 데이터셋 목록 파일

`evaluation/datasets/<id>/catalog.json`이 현재 버전(`currentVersion`)과 공고(`sites`)·화면(`states`)의 이름·설명을 가진다. 평가 화면은
`GET /api/v1/evaluations/datasets/{id}/catalog`로 읽고, 자동 평가도 같은 현재 버전을 쓴다. 공고나 화면을 더할 때 이 파일과 새 버전 폴더만
고치면 실행 조건, 사이트 수, 공고 드롭다운, 데이터셋 창, 흐름도 요청 수에 반영된다. 칸·화면·요청 수는 데이터셋에서 계산한다. 이름을
빠뜨리거나 새 버전을 만들고 `currentVersion`을 안 올리면 `DatasetLoaderTest`가 실패한다. 버전 폴더 밖에 있어 이름을 고쳐도 이전 실행의 데이터셋
지문은 그대로다.

### 데이터셋 버전

| 버전 | 화면 | 바뀐 점 |
| --- | --- | --- |
| v1 | 처음(튜닝용), 고등학교·대학교(최종 평가용) | 첫 버전 |
| v2 | v1 + 검정고시(최종 평가용) | 검정고시에서만 나타나는 합격연월 칸. 프로필의 합격일자는 지원 필드 목록에 없어 정답은 매핑 불가다. 기존 3개 사례는 v1과 같은 파일이다 |
| v3 | v2와 같은 4개 | 처음 화면(학력 구분을 고르기 전)은 준비 단계(섹션 분류·학력 구분 선택)만 채점한다. 실제 제품은 고른 뒤 펼쳐진 화면에서 칸을 채우므로 고르기 전 화면의 칸 매핑은 실제 흐름과 다르고, 기본정보·병역·경력 같은 공통 칸을 중복 채점했다(2026-11-03 사용자 결정). 나머지 3개 사례는 v2와 같은 파일이다. 사례당 호출은 처음 2개 + 나머지 3개씩, 반복 1회에 11개 |
| v4 | v3 + NHN Careers 지원서 1단계 최초 화면(최종 평가용) | 처음 보는 양식에서의 일반화를 잰다. 드롭다운이 읽기 전용 칸 + 목록 버튼이라 선택지가 없고, 제품이 섹션 제목을 거의 못 읽어 여러 항목이 한 섹션으로 묶인다. 준비 단계는 섹션 분류와 학력 행 추가 결정(+ 버튼), 매핑은 섹션 7개·칸 52개. 학력 구분을 고르지 않은 첫 학력 행은 최종 학력(대학교) 기준, 장애사항 선택칸은 정제로 placeholder가 가려졌지만 disabilityStatus, 부서명/직책은 department로 정답을 뒀다(2026-11-03 사용자 결정). 자동 임시 저장이 있는 지원서라 선택을 바꾼 상태는 수집하지 않았다. 우아한형제들 사례·정답은 v3와 같은 파일이다. 반복 1회에 15개 호출 |

같은 공고에서 학력 '전문대학'·'대학원(석사)'은 '대학교'와 칸 구성이 같고(두 정제본이 바이트까지 같음), 병역
'병역필_현역(병)'은 새 칸 없이 면제사유 칸만 사라져 새 사례로 쓰지 않았다(2026-11-02). 이 공고에서 새로 나오는 화면은
더 없으므로 표본을 더 늘리려면 다른 회사 지원서를 수집한다. 합성 프로필을 바꾸는 확대는 매핑 요청에 프로필 값이
들어가지 않아 요청이 거의 같으므로 하지 않는다.

v2 검정고시 화면은 사용자가 승인한 예외로 에이전트가 사용자 Chrome에서 선택만 바꾸고 수집 지침 스크립트를
실행해 모았다(저장·제출·미리보기·스크린샷 없음, 끝난 뒤 선택을 처음대로 되돌림). 기록은 fixture의 `review.md`에 있다.

### 우아한형제들 최종 평가용 화면의 전제 (2026-11-02 확인)

이 절과 다음 절은 우아한형제들 화면 기준이다. NHN 화면은 아무것도 고르지 않은 최초 화면이고, 선택지가 DOM에 없어 학력 구분 선택
질문이 없다. 준비 단계는 섹션 분류 4개와 학력 행 추가 결정 1개, 매핑 단계는 섹션 7개와 칸 52개다.

- 사용자가 학력 구분(고등학교·대학교)과 보훈·장애 "대상"을 미리 고른 뒤 자동기입을 실행한 화면이다. 제품이 처음 화면에서
  학력 구분을 직접 고르는 흐름은 튜닝용(initial)의 준비 단계 결정 호출로만 잰다.
- 정제본은 선택 상태를 지우고, 이미 펼쳐진 학력 행은 제품 준비 단계가 학력 구분 선택 대상으로 보지 않는다. 그래서 최종
  평가용에는 준비 단계 결정 호출이 없고 매핑 요청에 학력 기록 힌트(`recordSectionId`)가 없다.
- 제품이 처음 화면에서 "대학교"를 고르고 페이지가 칸을 펼치는 흐름을 jsdom으로 흉내 내 대학교 화면 요청과 비교했다.
  학력 칸 10개 중 8개(학교명·입학연월·졸업연월·입학구분·졸업구분·주전공·전공추가·복수/부전공)의 요청이 같았다.
  학력 구분 선택 칸에만 단계 표시("대학교")가 더 붙었고, 야간 체크박스의 라벨 차이는 흉내 방식 때문일 수 있어 확정하지
  않았다. 학력 칸의 학력 기록 모호성은 녹화 방식이 아니라 제품 요청의 성질이다.

### 단계별 채점 범위

- 우아한형제들 최종 평가용의 준비 단계는 섹션 분류 호출 1건(병역·학력·첨부자료·지원경로 4개 항목)뿐이다. 준비 정확도는 이 4개
  항목으로 정해지며, 두 화면의 섹션 구성이 같아 사실상 같은 질문을 반복해 잰다.
- 항목 단위 집계에서 최종 평가용 사례 하나의 준비 단계 비중은 약 7%(4 ÷ 55~57 항목)다.
- 판단 보류(ABSTAIN)는 누락으로 센다. 제품은 보류한 섹션의 후보를 전체로 넓히고 확인을 요구하므로, 다른 키를 고른 오답과
  위험이 다르다. 정확도와 함께 보고의 `quality.items`(오답·누락·불필요 제안 수)를 본다.
