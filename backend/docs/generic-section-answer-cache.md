# 범용 칸 분석의 섹션 단위 결과 캐시

범용 칸 분석(`POST /api/v1/generic/fields/analyze`)은 섹션마다 분류 공급자를 부른다. 공급자에 보낼 내용이 같은 섹션은 서버가 한 번만 묻고, 그 뒤 요청에는 저장한 답을 쓴다. 요청에는 양식의 구조만 있고 프로필 값과 현재 입력값이 없어서 사용자가 달라도 같은 답을 쓴다.

결정의 이유와 버린 대안은 ADR `llm-wiki/raw/issues/CF-467/documents/adr/467-generic-section-answer-cache.md`에 있다.

## 동작

1. `ChoiceFieldResolver.resolveSection`이 섹션 하나의 키를 만들어 `SectionAnswerCache`에서 찾는다.
2. 있으면 공급자를 부르지 않고 저장한 답을 쓴다. 응답의 `diagnostics.jevCalls`는 실제 호출만 세므로 전부 적중하면 0이다.
3. 없으면 지금처럼 공급자를 부르고, 모든 질문에 답을 받았을 때만 저장한다.
4. 답을 칸(`candidateId`)에 붙이는 일과 그 뒤 후처리(이름 묶기, 날짜 조각 맞추기, 서비스의 규칙)는 적중 여부와 관계없이 요청마다 한다.

응답 형식은 바뀌지 않는다. 적중은 서버 지표로만 본다.

## 키

모델 이름(`ChoiceModel.model()`), 섹션 상태(`state(work, work.questions(), false)`), 선택 기준(`work.criteria()`)을 Map 키를 정렬한 JSON으로 직렬화한 SHA-256이다. 공급자에 보내려고 코드가 만든 것을 통째로 쓰므로 관찰값에 항목이 늘면 키도 따라 바뀐다.

| 키에 들어가는 것 | 내용 |
|---|---|
| 섹션 상태 | 섹션 제목, 확정 범주, 상위 섹션 제목, 질문별 관찰값(라벨, placeholder, 요소와 입력 종류, 보임 여부, 덧붙은 라벨, input type, autocomplete, 필수 여부, 최대 길이, 선택지), 안내문(`confusionBoundaries`) |
| 선택 기준 | 고를 수 있는 프로필 필드 키와 그 설명 문구 |
| 모델 이름 | 설정의 모델 이름(기본 `jev-latest`) |

키에 넣지 않는 것: `snapshotId`, `candidateId`, 섹션 id, DOM의 id와 name, host, 경로. 공급자가 받지 않는 값이고 요청이나 사이트마다 달라 넣으면 적중만 준다.

질문 지시문(`instructions`)과 질문 묶음 크기(`field-batch-size`)도 키에 없다. 코드와 설정에 고정된 값이라 바뀌는 때가 배포이고, 배포하면 캐시가 비워진다.

질문 번호는 섹션 안에서 0부터 붙는다(`field_0`). 구조가 같은 반복 줄은 질문 한 벌로 합쳐지므로(`fingerprint`), 줄의 묶음 값(`itemGroupId`)이 같으면 줄이 하나인 요청과 셋인 요청의 키가 같다.

## 값과 저장 조건

값은 질문 번호별 선택과 확신도다. 선택지별 확률은 분석이 쓰지 않아 저장하지 않는다. 지원서 값은 들어가지 않는다.

| 경우 | 저장 |
|---|---|
| 모든 질문에 답을 받음(판단 보류 `ABSTAIN` 포함) | 한다 |
| 공급자 실패(`LLM_UNAVAILABLE`) | 안 한다 |
| 서버 전체 동시 호출 허가 대기 초과 | 안 한다 |
| 토큰 한도로 일부 질문의 답이 빠짐 | 안 한다 |

실패를 저장하면 공급자가 잠깐 죽은 동안의 빈 결과가 기한까지 굳는다.

찾기(`getIfPresent`)와 넣기(`put`)를 따로 한다. 같은 섹션이 처음에 동시에 오면 각자 공급자를 부르고 나중 것이 덮어쓴다.

## 붙는 곳

Spring이 만드는 운영 분석기에만 붙는다. `withModel`, `withBatching`으로 만든 평가용 사본과 캐시 없이 만든 분석기는 읽지도 쓰지도 않는다. 평가는 같은 입력을 되풀이해 공급자의 흔들림을 재기 때문이다. 평가의 동작 지문(`BehaviorFingerprint`)도 바뀌지 않는다.

## 설정

`application.yml`의 `career-form.analysis.jev.section-cache`.

| 설정 | 기본값 | 의미 |
|---|---|---|
| `enabled` | `true` | 끄면 호출 횟수와 응답이 캐시가 없을 때와 같다 |
| `max-sections` | `5000` | 저장할 섹션 수의 상한. 넘으면 Caffeine이 덜 쓰이는 것부터 버린다 |
| `ttl` | `7d` | 저장한 뒤 이 시간이 지나면 버린다 |

환경 변수 자리표시(`CAREER_FORM_JEV_SECTION_CACHE_ENABLED`, `..._MAX_SECTIONS`, `..._TTL`)가 있지만 배포 구성은 이 변수를 전달하지 않는다. 서버에서는 기본값으로 돌고, 운영에서 끄려면 기본값을 바꾼 수정 배포가 필요하다.

캐시는 프로세스 메모리에만 있어 배포하거나 재시작하면 비워진다.

## 지표

카운터 `career.form.analysis.section.cache`(Prometheus 이름 `career_form_analysis_section_cache_total`), 태그 `outcome`은 `hit`과 `miss`다. 질문이 있는 섹션 하나를 찾을 때마다 하나씩 오른다. 캐시를 끄면 오르지 않는다.

## 측정

`GenericSectionAnswerCacheDatasetTest`가 평가 데이터셋 `generic-matching` v5의 칸 분석 요청 4개를 순서대로 넣어 센 값이다. 섹션 동시 수 1, 질문 묶음 5, 호출을 세는 가짜 모델을 쓴다.

| | 캐시 없음 | 캐시 있음 |
|---|---|---|
| 질문이 있는 섹션 | 31 | 31 |
| 적중한 섹션 | 0 | 13 |
| 공급자 호출 | 47 | 29 |

요청별 적중은 같은 양식의 화면 셋이 0/8, 7/8, 6/8이고 다른 사이트의 화면이 0/7이다. 두 사이트 사이에 같은 섹션은 없었다.

섹션 5,000개를 채웠을 때의 힙 사용량 어림(JDK 21, 선택 문자열을 섹션마다 따로 둔 경우): 섹션당 질문 5개면 약 6MB, 10개면 약 10MB, 20개면 약 19MB.

## 한계

- 배포할 때마다 처음부터 다시 쌓는다. 사용자가 적고 배포가 잦으면 적중률이 낮다.
- 글자는 그대로인데 칸의 뜻만 바뀌는 변화는 키가 잡지 못한다. 기한이 그 영향이 이어지는 시간을 묶는다.
- 공급자의 답이 흔들린 경우 처음 저장된 답을 같은 섹션을 보내는 모든 사이트가 기한까지 받는다.
- 반복 줄을 줄 묶음(`items`)이 아니라 섹션의 칸으로 보내는 양식은 줄 수가 다르면 키가 달라진다.
