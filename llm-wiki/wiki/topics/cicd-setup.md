## 현재 상태

세 deploy workflow는 같은 이름의 설정을 GitHub Environment(`development`, `staging`, `production`)별 값으로 읽는다. 변수는 `DOCKERHUB_IMAGE`(저장소), `BACKEND_PORT`, `SERVER_FORWARD_HEADERS_STRATEGY`, `CAREER_FORM_LLM_ENABLED`, `CAREER_FORM_QUALITY_ENABLED`, `CAREER_FORM_QUALITY_MANAGEMENT_URL`, `CAREER_FORM_QUALITY_DISCORD_ENABLED`, `CAREER_FORM_QUALITY_DISCORD_ENVIRONMENT`, `CAREER_FORM_QUALITY_SELECTION_DAYS`, `CAREER_FORM_QUALITY_SELECTION_MINIMUM_SAMPLE`, `CAREER_FORM_NOTIFICATION_ENABLED`, `CAREER_FORM_PUSH_DISPATCH_INTERVAL`, `CAREER_FORM_PUSH_CONCURRENCY`, `CAREER_FORM_JEV_DATA_POLICY_REVIEWED`(저장소) 14개, 시크릿은 `DOCKERHUB_USERNAME`, `DOCKERHUB_TOKEN`, `OPENAI_API_KEY`(저장소), `SPRING_MONGODB_URI`, `CAREER_FORM_QUALITY_PASSWORD_HASH`, `CAREER_FORM_QUALITY_QUERY_TOKEN_HASH`, `CAREER_FORM_QUALITY_DISCORD_WEBHOOK`, `CAREER_FORM_PUSH_VAPID_PUBLIC_KEY`, `CAREER_FORM_PUSH_VAPID_PRIVATE_KEY`, `CAREER_FORM_PUSH_VAPID_SUBJECT`, `JUSO_API_KEY`, `TYPESAFE_API_KEY`(환경) 12개다. development는 여기에 #423의 평가 설정 변수 `CAREER_FORM_EVALUATION_ENABLED`, `CAREER_FORM_EVALUATION_AUTO_RUN_ENABLED`, `CAREER_FORM_EVALUATION_OPENAI_ENABLED`와 시크릿 `CAREER_FORM_EVALUATION_PROVIDER_KEYS`를 더 읽는다(compose 기본 false와 빈 값). 미설정 값은 `infra/compose.deploy.yaml` 기본값으로 채워지고 여기 없는 환경변수는 컨테이너에 전달되지 않는다. `deploy.sh` 필수값은 `DEPLOY_ENVIRONMENT`, `BACKEND_IMAGE`(digest 고정), `BACKEND_PORT`, `SPRING_PROFILES_ACTIVE`, `SPRING_MONGODB_URI`, `OPENAI_API_KEY`이고 환경:profile은 development:dev, staging:staging, production:prod만 허용한다. Environment 배포 브랜치 제한은 develop, release/*, main이며 production에 required reviewer를 두지 않는다.

운영에서 LLM 범용 기입은 한 번도 활성화된 적이 없다. 1.0.0 compose의 고정 true는 그 배포가 실패해 운영에 반영되지 않았고, CF-146에서 변수화하며 기본 false로 바꾼 뒤 2026-10-03에 세 환경 모두 false로 만든 변수가 바뀌지 않았다. 1.4.0은 기본 분석 공급자를 openai→jev로 바꿨는데 compose가 `OPENAI_API_KEY`만 전달하고 `TYPESAFE_API_KEY`·`CAREER_FORM_JEV_DATA_POLICY_REVIEWED` 전달 경로가 없어 변수만으로는 켤 수 없었고, CF-410(PR #411)이 2026-11-04 두 값의 전달 경로를 추가했다. 운영 host는 nginx 80 포트로 `/api`와 `/quality`를 HTTP 공개 중이며 HTTPS와 도메인은 미도입이다. runner, registry, host bootstrap, ARM64 빌드 cache는 이전 근거를 따른다.

공고 구독 알림(Web Push)은 `CAREER_FORM_NOTIFICATION_ENABLED`(기본 false)로 켜고, 켤 환경에는 VAPID 시크릿 세 개를 먼저 등록해야 한다. 토글이 true인데 시크릿이 비어 있으면 backend가 기동에 실패해 `deploy.sh`가 이전 digest로 되돌린다. 선택값 `CAREER_FORM_PUSH_DISPATCH_INTERVAL`(60s)·`CAREER_FORM_PUSH_CONCURRENCY`(20)의 기본값은 compose가 backend `application.yml`과 같게 채운다. workflow는 Environment 값이 없으면 빈 문자열을 넘기고 Spring placeholder는 빈 문자열에 기본값을 적용하지 않기 때문이다. Environment 변수·시크릿은 배포 시점에 읽히므로 바꾼 뒤 새 배포가 있어야 반영되고, development는 workflow_dispatch가 없어 paths 필터에 걸리는 develop push가 필요하다. 키 생성·등록·회전 절차는 [Web Push VAPID 키와 알림 기능 배포 설정](../../../infra/WEB_PUSH_VAPID.md)을 따른다([CF-350 근거](../../raw/issues/CF-350/documents/notification-deployment-levers.md)). 공고 직무 필터 전환 변수 `CAREER_FORM_PUSH_ROLE_FILTER_ENFORCED`는 CF-413이 배포 경로에 더했다가([CF-413 근거](../../raw/issues/CF-413/documents/role-filter-toggle-deployment.md)), CF-432에서 backend가 읽지 않게 된 뒤 CF-435에서 workflow·compose·`infra/tests/test_notification_deployment.py`·`infra/WEB_PUSH_VAPID.md`에서도 지웠다. 같은 계약 테스트가 이 이름이 workflow나 compose에 다시 들어오면 실패하고, 2026-11-07 확인 때 세 Environment에는 이 변수가 없었다([CF-435 근거](../../raw/issues/CF-435/documents/role-filter-variable-removal.md)).

## 변경 이유

이전 topic은 `BACKEND_PORT`, `SPRING_MONGODB_URI`, `CAREER_FORM_LLM_ENABLED`만 기록해 품질 관측 설정 7개와 선택 변수가 빠져 있었고, 운영 공개 상태가 CF-41의 비공개 전제와 달라졌다. 1.4.0 릴리스에서 운영 설정 변경 필요 여부와 LLM 활성 여부를 판단하면서 workflow·compose·deploy.sh·GitHub Environment를 대조해 전체 목록과 이력을 기록했다. CF-350에서 `[BE]` #348 발송기의 VAPID 서명에 필요한 알림 토글과 시크릿 전달 경로를 세 환경에 추가하며 변수 13개, 시크릿 10개로 목록을 갱신하고, 빈 문자열과 Spring placeholder 기본값의 관계를 기록했다. CF-413은 #394가 더한 직무 필터 전환 설정이 배포 경로에 없어 운영에서 켤 수 없던 틈을 메우며, CF-409·CF-410이 더했지만 topic에 빠져 있던 이름까지 넣어 변수 15개·시크릿 12개로 목록을 갱신했다. CF-432는 직무를 고르지 않은 구독도 모든 공고를 받는 정책(CF-431)에 맞춰 backend의 전환 설정을 없애, 이 변수가 효과 없이 전달만 되는 상태를 기록했다. Current 정본이 전체 목록을 담아야 해서 #423이 development에 더한 평가 설정 이름도 함께 적었다. CF-435는 효과 없이 남은 이 변수의 전달과 켜는 절차를 배포 경로에서 지우고 재유입을 막는 계약 테스트를 더해 변수 14개·시크릿 12개로 목록을 갱신했다.
