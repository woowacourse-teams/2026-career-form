## 적용 범위

Java 21, Spring Boot, MongoDB 기반 백엔드의 신규 코드, 변경 코드와 관련 테스트에
적용한다. 기존 API와 제품 정책은 품질 개선만으로 바꾸지 않는다. 기존 코드 전체를
현재 기능 Issue에서 고치라는 권한도 아니다.

- 필수: 위반이면 Standards finding으로 보고한다.
- 권고: 구체적인 이해 비용과 변경 위험을 근거로 판단하며 취향만으로 차단하지 않는다.
- 조건부 필수: 명시된 조건이 발생했을 때 적용한다.

객관적인 구조 규칙은 ArchUnit과 backend CI가 신규 위반을 차단한다. 의미, 책임,
가독성은 기능 테스트와 사람, AI 리뷰가 판단한다. 해석 사례는
[백엔드 품질 해석 사례](backend-code-quality-examples.md)를 참고하되 사례의 모양을
새 의무로 만들지 않는다.

## BQ-01. 일관성과 비획일화 - 필수

책임, 의존 방향, 이름의 의미와 외부 계약은 일관되게 지킨다. 모든 기능에 같은 단계,
메서드, 파일 수를 요구하지 않는다.

- 단순 조회는 짧은 Service를 허용하고 외부 연동이나 상태 변경은 필요한 검증을 둔다.
- 예제의 처리 순서, 빈 Input, 형식용 검증, 인터페이스, Mapper를 모양만 맞추려고 만들지 않는다.
- 단계를 줄이기 위해 필요한 안전성 검사나 제품 계약을 제거하지 않는다.

## BQ-02. 패키지와 소유권 - 필수

기능을 먼저 묶고 그 안에서 `api`, `application`, 필요한 `domain`,
`infrastructure/adapter/<기술>`, `config`를 책임에 맞게 구분한다.

- `api/dto`는 HTTP 요청과 응답을 소유한다.
- `application/dto`는 유스케이스 입력과 결과, `application/port`는 외부 기능 계약을 소유한다.
- `domain`은 실제 업무 모델과 규칙이 있을 때 만든다.
- Adapter는 공급자 DTO, DB 구현과 기술별 저장소를 소유한다.
- `config`는 생성과 주입만 담당하고 기능 로직을 두지 않는다.
- `common`이나 `shared`는 실제 두 기능 이상이 쓰는 기능 중립 코드만 둔다.

기존 작은 기능을 파일 이동만을 위해 재배치하지 않는다. 파일 수나 미래 재사용 가능성은
새 패키지와 공통화를 만드는 근거가 아니다.

## BQ-03. 코드 의존 방향 - 필수

- API는 공개 Application Service, DTO와 오류 계약을 사용한다. Domain, Port, 구체
  Adapter, 저장소를 직접 사용하지 않는다.
- Application은 자기 기능의 Domain, Application DTO와 Port를 사용한다. API DTO,
  HTTP 응답, 구체 Adapter, Spring Data API와 공급자 SDK에 의존하지 않는다.
- Port는 내부 소유 타입, Domain과 JDK 타입으로 계약을 표현한다. API나 공급자 SDK
  타입을 노출하지 않는다.
- Domain은 API, Application, Infrastructure, 웹과 DB 클라이언트에 의존하지 않는다.
- Adapter는 Port, 내부 계약과 같은 기술의 타입을 사용한다. Service를 호출해 업무
  흐름을 역으로 시작하지 않는다.
- config는 조립을 위해 구체 타입을 알 수 있다.

`SupportedProfileFields.keys()`의 읽기 전용 조회는 provider schema와 Application
allowlist가 같은 목록을 쓰기 위한 좁은 허용 계약이다. 다른 Application 정책 호출을
허용하지 않는다. 의존은 import뿐 아니라 서명, 상속, 구현, 필드, 어노테이션과 중첩
타입까지 판단한다.

## BQ-04. 기능 사이 관계 - 필수

다른 기능은 그 기능이 공개한 Application Service와 DTO를 사용한다. 다른 기능의
Domain 내부, Adapter와 저장소를 직접 접근하지 않는다. Java `public`만으로 공개 계약이
되지는 않는다. 기능과 계층 사이의 순환 의존을 만들지 않고, 이름만 `common`으로 옮겨
순환을 숨기지 않는다. JVM 내부 기능 호출마다 Port를 추가할 필요는 없다.

## BQ-05. DTO와 경계 변환 - 필수

HTTP Request, Response와 Application Input, Result를 요청과 응답 양방향에서 분리한다.
API DTO와 그 중첩 record, enum을 Service나 Port 계약으로 재사용하지 않는다.

- 여러 값이 함께 이동하면 `<기능>Input`, `<기능>Result`를 기본으로 사용한다.
- 입력 없는 조회에 빈 Input을 만들지 않는다. 의미가 분명한 값 하나는 직접 전달할 수 있다.
- API Response 필드에 Result, Domain, Document, 공급자 DTO를 중첩하지 않는다.
- Request의 `toInput()`, Response의 `from(result)` 같은 작은 팩터리는 허용한다.
- 한 endpoint만 쓰는 작은 타입은 소유 DTO 안에 둘 수 있다.
- 데이터 운반에는 record를 우선하되 컬렉션과 가변 객체의 소유권은 방어적으로 관리한다.

DTO를 분리해도 기존 JSON 필드명, 중첩, null과 생략 의미는 바꾸지 않는다.

## BQ-06. Controller, Service, Port, Adapter - 필수

Controller는 HTTP 계약, Service는 유스케이스 순서, Port는 내부가 요구하는 외부 기능,
Adapter는 외부 기술 연결을 담당한다.

- Service는 생성자 주입을 사용하고 실행 중 구현체를 직접 생성하거나 전역 조회하지 않는다.
- Application에는 필요한 Spring 조립과 트랜잭션 메타데이터를 허용하되 HTTP, DB 조회
  API와 공급자 SDK 의존은 허용하지 않는다.
- Service 인터페이스, 모든 유스케이스의 UseCase 인터페이스와 CRUD별 Port는 필수가 아니다.
- 구현체가 하나여도 외부 기술 경계와 대체 테스트에 필요한 Port는 유지할 수 있다.
- 여러 구현체는 입력, 출력, 실패 의미를 지키고 선택과 fallback 정책은 제품 계약으로 정한다.

## BQ-07. Domain과 저장 모델 - 조건부 필수

통합 모델과 분리 모델 중 하나를 전역 기본값으로 강제하지 않는다. 다음 조건이면 저장
전용 Document를 Infrastructure에 두고 Adapter가 검증과 변환을 소유한다.

- 저장 구조와 업무 모델의 구조나 생명주기가 다르다.
- 업무 규칙에서 사용하기 전에 저장 값을 검증하고 유효한 Domain을 만들어야 한다.
- 여러 저장 표현이 같은 Domain을 공유하거나 독립적으로 변경된다.
- 저장 프레임워크 제약이 Domain 불변 조건을 침범한다.

조건이 없고 통합 모델이 책임을 흐리지 않으면 Domain에 MongoDB 저장 선언용 메타데이터를
둘 수 있다. `@Document`, `@Field`, `@Id`, `@Version`, `@Transient`, `@TypeAlias`,
`@PersistenceCreator`로 범위를 제한하며 Repository, Template과 조회 API는 허용하지 않는다.

현재 회사 정책은 `Mongo Document -> validation -> CompanyFormPolicy ->
router/fingerprint -> adapter route` 흐름을 유지한다. 품질 기준을 이유로 검증 전 Document를
업무 규칙에 넘기거나 제품 흐름을 바꾸지 않는다.

## BQ-08. 상태와 불변성 - 필수

불변 객체를 기본으로 하고 Domain 상태 전이는 검증한 새 객체를 반환한다. Service는
그 결과를 저장 Port에 전달하고 저장 반환값을 사용한다.

- DTO, 값 객체와 공유 목록은 public setter나 변경 가능한 내부 컬렉션을 노출하지 않는다.
- 생성자와 팩터리는 유효한 상태를 만들고 식별자와 버전 계약을 보존한다.
- 지역 변수와 로컬 누적 컬렉션은 허용한다. 불변성을 위해 모든 계산을 Stream으로 바꾸지 않는다.
- record 선언만으로 깊은 불변성을 주장하지 않고 저장 왕복과 컬렉션 변경을 테스트한다.

측정된 비용이나 기술 제약으로 가변 Domain이 필요하면 EX-01 승인을 받는다.

## BQ-09. 검증 소유권 - 필수

- API는 HTTP 필수 여부, 길이와 형식을 검사한다.
- Application은 유스케이스 정합성, 권한과 외부 결과 수용 조건을 검사한다.
- Domain 생성과 행위는 상태 불변 조건을 검사한다.
- Adapter는 공급자 JSON, 저장 결과의 변환 계약을 검사한다.

목적이 다른 경계 검증은 값이 같아도 유지한다. 같은 소유권의 동일 검사는 복제하지 않는다.
현재 분석 기능의 exact-set, canonical key, provider omission 보완, 개인정보와 브라우저
실행 책임은 별도 제품 결정 없이 바꾸지 않는다.

## BQ-10. 명명과 파일 책임 - 권고

이름은 기능, 역할과 부수 효과를 설명한다. Controller, Service, Repository, Resolver,
Policy, Client와 Adapter 같은 익숙한 역할명을 사용한다. `Manager`, `Helper`, `Util`,
`Common`이라는 문자열만으로 위반 판정하지 않고 실제 책임 은폐를 근거로 판단한다.
저장, 삭제와 전송은 이름에서 예측 가능해야 한다. 파일 책임을 한 문장으로 설명하고
서로 다른 이유로 바뀌는 로직이 섞였는지 검토한다.

## BQ-11. 메서드, 클래스 분리와 크기 - 권고

추출로 독립 책임과 규칙에 이름이 생기면 분리한다. 호출 위치만 늘어나면 분리하지 않는다.
함수 50줄 이내는 목표이고 파일 800줄은 기존 상한이다. 50줄 초과는 검토 신호이지
자동 분해 명령이 아니다. 상한을 맞추려고 책임 없는 파일을 만들지 않는다. 변경 이유가
다른 유사 코드는 서둘러 공통화하지 않고, 동일 업무 규칙의 복제는 소유자를 찾아 통합한다.

## BQ-12. Java 표현과 제어 흐름 - 권고

- 순수 변환이 분명한 Stream은 허용한다. 저장, 원격 호출, 공유 상태 변경과 예외를
  람다에 숨기지 않는다.
- 짧고 부수 효과 없는 두 값 선택은 삼항 연산자를 허용한다. 중첩 업무 분기는 풀어 쓴다.
- 가드 절과 조기 반환을 선호하지만 모든 `else`와 중첩을 금지하지 않는다.
- 일반 메서드와 enum이면 충분한 곳에 리플렉션, 동적 등록과 복잡한 제네릭을 추가하지 않는다.
- `var`는 생성식처럼 타입이 분명한 지역 변수에만 사용한다.

문법 사용 여부를 정규식 기반 오류로 만들지 않는다.

## BQ-13. Java 스타일과 문서화 - 필수, 권고

필수 기본값은 UTF-8, LF, 탭 없는 4칸 들여쓰기, 미사용 import 제거, wildcard import
금지, 파일당 공개 최상위 타입 하나와 Java 표준 명명이다. 기존 파일 전체를 기능 Issue에서
재포맷하지 않는다.

생성자 주입과 `private final` 의존 필드를 우선한다. 보일러플레이트만을 이유로 Lombok을
추가하지 않고 `@Data`로 Domain setter, 동등성과 문자열 출력을 한꺼번에 만들지 않는다.

함수마다 Javadoc을 쓰지 않는다. 이름과 타입만으로 드러나지 않는 외부 계약, 실패와
부수 효과, 복잡한 제약, 비자명한 결정 이유만 문서화한다. 코드 반복 주석과 낡은 주석은
제거하고 TODO에는 Issue나 담당과 해소 조건을 둔다. Javadoc이나 주석 개수는 CI에서
검사하지 않는다.

## BQ-14. 오류와 부재 - 필수

정상적인 없음, 잘못된 입력, Domain 거부, 외부 장애와 예상하지 못한 버그를 구분한다.

- HTTP 상태와 오류 JSON 변환은 API 오류 처리기가 맡는다.
- Adapter는 해석 가능한 공급자 오류를 내부 계약으로 바꾸고 모든 예외를 성공이나 빈
  결과로 삼키지 않는다.
- fallback, 우회와 재시도는 제품 계약이 있을 때만 구현한다.
- 원인을 추적 가능하게 보존하되 요청 body와 민감한 예외 문자열을 응답이나 로그에 노출하지 않는다.
- 내부 컬렉션 부재는 빈 컬렉션을 우선하고 단건 Port의 정상 부재에는 Optional을 쓸 수 있다.
- 기존 API의 null, 생략과 오류 코드는 호환 계약을 우선한다.

Issue와 기존 제품 계약이 오류, 부재, 우회, 재시도나 부수 효과를 정하지 않았다면 AI는
구현 전에 하나의 구체적인 질문으로 확인한다. 답을 추측해 코드로 확정하지 않는다.

## BQ-15. DB, 외부 호출과 트랜잭션 - 조건부 필수

DB 접근은 Adapter에 둔다. 트랜잭션은 유스케이스의 원자성에 맞추며 모든 Service에
일괄 적용하지 않는다.

- MongoDB를 JPA dirty checking처럼 취급하지 않고 명시적 저장 계약을 사용한다.
- 문서 갱신, 동시 충돌, 저장 실패, ID와 버전, 저장 반환값을 테스트한다.
- DB 트랜잭션이 원격 HTTP까지 원자적으로 묶는다고 가정하지 않는다.
- 외부 호출은 유한 timeout을 두고 재시도의 중복 부수 효과와 비용을 검토한다.
- 비동기, 캐시와 공유 상태는 요구나 측정 근거가 있을 때 도입하고 종료와 오류 전파를 검증한다.

## BQ-16. 개인정보, 보안과 관측 - 필수

실제 프로필 값, 계정, 세션, 인증정보, 원문 HTML, 상세 URL을 로그, fixture, 문서와
공급자 payload에 넣지 않는다. 테스트는 합성, 비식별 데이터를 사용하며 정책상 금지된
사용자 동작을 자동 실행하지 않는다.

외부 장애를 완화해 보여도 개발자는 안전한 오류 분류, 컴포넌트, 추적 식별자와 건수로
원인을 구분할 수 있어야 한다. 무차별 payload 로깅과 민감한 예외 노출은 금지한다.
이 규칙은 새 관측 도구, 인증 숫자, 요청 제한이나 LLM fallback 정책을 확정하지 않는다.

## BQ-17. 테스트와 검증 가능한 설계 - 필수

동작 변경은 실패하는 테스트에서 시작하고 정상, 실패와 경계를 검증한다.

- Domain과 Service 정책은 단위 테스트로 확인한다.
- HTTP validation, 직렬화와 오류 매핑은 API 경계에서 확인한다.
- DB 매핑, 쿼리, 버전, 트랜잭션과 공급자 변환은 통합 또는 계약 테스트로 확인한다.
- Fake와 Stub은 실제 Service 결과와 부수 효과를 검증하는 데 사용한다.
- 테스트를 위해 불필요한 인터페이스, public 메서드와 운영 분기를 추가하지 않는다.
- 실제 네트워크, LLM과 개인정보에 의존하는 테스트를 기본 검증에 섞지 않는다.

현재 JaCoCo LINE 80% 이상 기준과 기존 제외 범위를 유지한다. 커버리지를 맞추려고 의미
있는 production 클래스를 제외하거나 호출만 하는 테스트를 늘리지 않는다.

## BQ-18. 리뷰와 증거 - 필수

Standards와 Spec을 별도로 보고한다. 백엔드 Standards finding은
`규칙 ID / 파일·심벌 / 영향 / 최소 수정안 / 필수·권고 / 불확실성` 순서로 작성한다.
기능 통과로 규칙 위반을 숨기거나 스타일 준수로 기능 누락을 숨기지 않는다.

가독성은 이름, 흐름, 책임과 탐색 비용의 구체적 근거로 설명한다. 개인 취향, 예제와의
모양 차이와 미래 가능성만으로 변경을 강제하지 않는다. 자동 검사 결과는 인용하고,
미실행과 오류는 통과로 표시하지 않는다. 필요한 호출자와 타입 경계까지 확인한다.

## EX-01. 예외와 변경 - 필수

이미 명시한 허용 사례 외에 필수 구조 규칙을 벗어나야 하면 별도 예외 registry에 다음을
정확히 기록한다.

`예외 ID / 규칙 ID / 정확한 위반과 대상 / 이유 / 검토한 대안 / 보완 테스트 / 연결 Issue / 해소 조건 / 작성자 / 다른 백엔드 검토자`

고정 30일 만료는 두지 않는다. 대상 코드, 규칙, 테스트, 해소 조건이 바뀌거나 실제 관계와
일치하지 않으면 재검토한다. wildcard와 패키지 전체 제외는 허용하지 않는다. 개인정보,
보안과 제품 동작을 바꾸는 권한으로 사용할 수 없다. 영구적으로 필요한 허용은 새 정책
결정과 검사 사례로 정본을 갱신한다.

## 강제와 범위

A1부터 A6까지의 구조 규칙만 ArchUnit 1.5.0으로 차단한다. 기존 22개 관계는 시작 commit과
함께 baseline에 두고 같은 규칙의 신규 관계만 실패시킨다. 해결된 baseline과 더 이상 맞지
않는 예외는 stale 실패로 제거한다. 검사 대상 0건, import와 설정 오류, 미실행은 PASS가 아니다.

운영 절차와 파일 소유권은 `harness/policies/backend-quality-enforcement.md`가 담당한다.
production 리팩터링, formatter와 Checkstyle, AI 행동 eval, 수동 AI smoke, 모델 비교와
LLM 점수 차단은 이 정본의 도입 범위가 아니다.
