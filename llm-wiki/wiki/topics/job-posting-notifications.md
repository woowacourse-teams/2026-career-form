## 현재 상태

팀이 관리 화면에서 등록한 채용 공고를 접수 가능 시점(등록 시각과 접수 시작 중 늦은 쪽)에
그 공고의 직무를 받기로 한 구독자에게 Web Push(FCM)로 한 번 알린다. 마감 리마인더는 기존
CF-161 로컬 알림이 맡는다. 서버 책임은 FCM 수락 응답을 받을 때까지 재시도하는 것이고 기기
도착과 열람은 책임지지 않는다. 그 빈틈은 확장의 공지함(진행 중 공고 목록 조회)이 메우며
확장은 수신 확인을 보내지 않는다.

직무 분류 정본은 `backend/src/main/resources/notification/job-categories-v1.json`(버전,
대분류·소분류 코드와 한글 라벨, 코드는 `IT.BACKEND`처럼 점으로 이은 안정 문자열)이며 기동 시
검증해 틀리면 기동을 막고, 코드는 추가만 한다. 확장은 `GET /api/v1/notifications/job-categories`로
분류를 받는다. 공고는 소분류 코드 `roles` 1~10개가 필수이고 구 확장용 `role` 라벨은 서버가
라벨을 가운뎃점으로 이어 120자 안에서 파생한다. 구독 문서의 `roles`는 받을 소분류 코드
배열(없으면 미선택)이며 구독 등록 요청에 실어 보낸다(값은 덮어쓰기, 빈 배열은 미선택, 필드
없음은 유지). 등록 시 `roles`가 겹치는 구독에만 대기 발송을 만들고, 발송기는 선점 뒤 구독의
현재 `roles`를 다시 봐 겹치지 않으면 FCM 호출 없이 `FILTER_MISMATCH`로 포기한다. `roles`
없는 레거시 공고는 재분류하지 않고 전원에게 간다. 전환 설정
`career-form.notification.role-filter.enforced`(기본 꺼짐)가 꺼진 동안은 미선택 구독도 받으므로
백엔드를 먼저 배포하고, 확장 게시와 보급 확인(요약의 직무 선택 구독 수) 뒤 사람이 켠다.

작업 저장은 MongoDB 발송 문서(공고 × 구독 쌍, 상태 대기·발송 중·수락됨·포기)와 `@Scheduled`
fixedDelay 1분 주기 발송기다. 발송기는 FCM 호출 전 `findOneAndUpdate` 조건부 갱신으로
발송 중과 리스 만료 시각을 찍어 선점하므로 발송기가 둘이어도 중복이 번지지 않고, 서버가
재시작해도 리스가 만료된 건을 다음 주기가 이어 보낸다. 재시도 표는 2xx 수락됨, 404·410 포기와
구독 삭제, 429와 Retry-After 있는 503은 응답이 준 시각 뒤, 그 밖의 오류와 시간 초과는
1·2·4·8·16·32·64분 지수 백오프, 400·403·413 포기이며 포기 기준은 시도 8회 또는 공고 마감
경과 중 먼저 오는 것이다. 동시성은 20(가상 스레드)이고 장애당 중복 알림 최대 1건을 허용한다.

규모 가정은 구독자 1,000명(실측 피크 500명의 2배), 하루 등록 5건 이하, 공고당 푸시 1,000건이며
최악 5,000건이 동시성 20에서 25초라 큐가 풀 병목이 없다는 것이 메시지 큐를 두지 않은 근거다.
직무 필터는 대상 수를 줄일 뿐 이 가정을 바꾸지 않는다. SQS·별도 워커·2중화·관심 기업 필터·
필터 변경 뒤 기존 공고의 발송 보충·공고 수정·수신 확인·계정은 범위 밖이고, 공고당 푸시 1만 건
초과나 한 주기 이용률 70% 초과(약 8,400건)에서 큐와 워커 분리를, 서버 발송 채널 확장이 없으면
확장 폴링으로의 축소를, 가용성 목표 상향에서 2중화를 재검토한다. 1차 실측 뒤 2차에서 장애 격리와
채널 확장을 이유로 SQS 도입을 같은 숫자로 비교한다. 설정 키, API 경로, 상태 전이 표와 관측
지표는 `backend/docs/job-posting-notifications.md`를 따르고 VAPID 시크릿과 배포 설정은
#350, 확장의 구독·수신·공지함과 받을 직무 선택기는 #349·#395가 맡는다.

## 변경 이유

확장의 알림이 CF-161의 로컬 마감 알림뿐이어서 팀이 고른 대기업 공채 공고를 사용자에게 알릴
수단이 없었다. 2026-10-25 설계 세션에서 전달 경로와 발송 보장 수준을 정하고 ADR로 기록했다.

1차는 전원 발송이었으나 2026-11-02 검토에서 알림을 사용자가 고른 직무로 좁히기로 했다. 공고의
직무가 자유 글자 선택 입력이라 거를 기준이 없었고 구독 문서에 사용자의 선호가 없었다. #386을
서버 #394와 확장 #395로 나눴고, 서버 쪽(CF-394)이 분류 정본, 공고 직무 필수, 구독별 받을 직무,
대상 산정과 발송기 재검사, 전환 설정을 더했다.
