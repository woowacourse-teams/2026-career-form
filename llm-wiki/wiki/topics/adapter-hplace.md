## 현재 상태

MRS2 등록의 이름·휴대전화·이메일과 기존 기본정보 계약을 유지하고 새 범주를 v4 실행 정책과 공통 native 실행기로 연결한다. 학력·중첩 전공·숫자 GPA·경력·프로젝트·비인증 어학·자격증·현주소는 검증된 소유 구조와 활성 정책에서만 실행한다. v1 지원자 앱은 1단계 기본정보, 2단계 학력·경력, 3단계 자격증·외국어활용능력을 별도 정책으로 지원한다(아래 v1 절). v1 1단계의 현주소와 사진은 사이트 창을 거쳐 기입한다. v1 테넌트마다 구역 구성이 달라 단계마다 알려진 구역 제목 하나 이상으로 판별하고 블록과 종류를 각각 따로 다룬다(CF-510). v1 3단계의 나머지 블록, 4단계 이후와 JOBDA의 입력 구조는 지원하지 않는다.

13범주 127키 중 활성 구현 또는 간접 소비는 95키다. 나머지는 의미 불일치13·구조 미확인16·지정 화면 부재1·파일 사용자 처리2로 구분한다. 사이트 전용27행은 별도 집계하며 required라는 이유로 대응 값을 추정하지 않는다. 전체 표는 [필드 현황](adapter-field-inventory.md)과 raw를 따른다.

기존 엔티티 전체 보호, 동일 위젯의 검색 tuple 확정, 현주소3값의 승인·로컬 모달 확정·최종 receipt, 부모와 역할을 함께 확인하는 중첩 전공 계약을 적용한다. 구조·옵션·정체성이 불명확하면 수동 처리하며 범용 실행기로 우회하지 않는다. 지원서 저장·제출·탭 이동·인증·파일은 자동 실행하지 않는다.

## step 2·3 실화면 수정 (2026-10-20)

- **검색 확정:** legacy Enter의 keyCode/charCode/which는 `KeyboardEventInit`로 넘긴다. content script에서 이벤트 속성을 덮으면 격리 world 래퍼에만 남아 사이트 핸들러가 0을 읽는다. 브라우저가 init 값을 무시하면 즉시 실패로 끝낸다. 같은 world의 jsdom 테스트는 이 결함을 잡지 못하므로 page world getter로 Enter를 확인하는 수신기로 단언한다.
- **검색 의존 driver:** 학위구분·고교 졸업구분 driver의 검색 필드 의존은 hidden 학교명 입력의 visible이 아니라 같은 위젯 query로 판정한다. 위젯을 인식하지 못하면 이름 기반 판정으로 돌아가 보류하고 driver 실패 시 학교 검색도 보류한다.
- **확정 뒤 종속 대기:** tuple readback·자격증 등록번호 숨김·시험 detail로 확정을 엄격히 판정한 뒤 즉시 행 기입과 검색 receipt를 기록한다. 종속 control은 클릭 전에 있던 것을 기준으로 라디오는 그룹 전체, 그 밖은 정확히 1개가 활성화될 때까지 soft로 기다린다. 시간 초과·소실·중복에도 기입을 유지하고 `disabled-timeout` 진단만 남긴다. linkedForm 세부 활성화는 focus 200ms poll·blur 평가로 비동기이며 native `blur()`에 의존하지 않는다.
- **driver 실행:** native driver는 stage 단위 한 pass로 모두 실행하고 실패 driver와 대상 요소가 겹치는 뒤 driver만 제외한다. 마지막 허용 요청에서 남은 driver는 `DRIVER_LIMIT_REACHED`로 보고한다. 자기 값이 검증된 비검색 driver는 종속 정착 실패와 무관하게 입력 완료이며, 보류 종속은 비검색 driver면 `ROW_DRIVER_UNCONFIRMED`, 검색 driver면 `ROW_SEARCH_UNCONFIRMED`다.
- **리뷰 비교:** native 라디오 현재값은 체크된 사이트 코드가 정책 options에서 정확히 대응될 때만 라벨로 바꾼다. 사이트가 정규화한 숫자 자기 기입(합성 `3.650` → `3.65`)은 둘 다 십진수이고 수치가 같을 때만 같은 값이다. 사용 불가 native 항목도 자기 행 itemIndex를 유지한다.
- **선택지와 정규화:** 같은 MRS2 template이라도 선택지 카탈로그는 테넌트마다 다르다. native select/radio의 활성 옵션에 프로필 라벨이 없으면 `OPTION_UNMATCHED`로 입력 불가 처리하고, 제공되지 않는 고용형태의 경력 행은 추가하지 않는다. 대입 검정고시 프로필은 고교 섹션 전체를 입력 불가로 둔다. 시험 등급은 닫힌 ACTFL 약어 표로만 확장하고, 주야간 표준값은 정책 `normalizations`로 `주간`/`야간`에 대응한다. 날짜 정밀도는 섹션 `data-dates` 토큰이 정한다.

## C12·C13와 미검증 테넌트 시연 수정 (2026-10-20)

- **프로젝트154 활성화:** 실구조에서 projectName이 행 구동자(maxlength 128)이고 시작·종료일은 YMD, 역할은 maxlength 128이다. 사용자 승인으로 활성화했고 gsenc·abl step 2에서 이름·기간·역할이 일치했다. 사이트 필수인 발주처·근무지는 프로필 키가 없어 비워 두며 확인 필요에도 표시되지 않으므로 사용자가 직접 입력한다. abl의 기여도도 비워 둔다.
- **자격증 등록번호:** maxlength 64이며 검색 결과 선택이 hidden code 입력을 focus해 linkedForm이 발급기관·등록번호·취득일을 연다.
- **C14 종료:** 실화면 step 3에서 metadata 이탈 진단이 0건이라 null/undefined 허용 보강은 하지 않았다.
- **지원 방식 판별:** 공고 상세·position API·공개 리소스로는 구분되지 않고 "지원하기" 뒤 도착 경로가 기준이다. `/app/applicant/registResume`는 MRS2, `/v1/applicant/write-resume/login`은 v1, `www.jobda.im/jobflex/login`은 JOBDA다(표본: ligdna v1, dorco JOBDA, huonsgroup·com2us·kdi MRS2).
- **현주소·생년월일 없는 기본정보:** com2us처럼 섹션 13에 주소 제어가 전혀 없거나 kdi처럼 생년월일·성별 칸이 없어도 상세 기본정보를 처리한다. 상세 섹션에 필수 앵커는 없고(후속 보완에서 정정) 칸이 있는데 형식이 다른 칸만 차단한다. 아래 후속 보완 묶음 절을 따른다.
- **병역 날짜 정밀도:** 시작일 토큰이 `:YM`이면 월, `:YMD`(huonsgroup)면 일까지 기입·비교한다. 시작일을 인식하지 못하면 병역 하위 칸 전체가 비는 연쇄가 있었다.
- **영문 이름 순서:** 회사 안내가 순서를 명시하면 그 순서, 순서 문구 없이 홍길동 표준 예시가 한 순서로만 있으면 예시 순서(kdi `Hong, Gildong`→성 이름, 같은 순서 반복 허용, 쉼표 없이 띄어쓰기), 안내가 전혀 없으면 성 이름(사용자 결정)이다. 안내가 다른 영역에만 있거나 중복·섞인 순서·홍길동 아닌 예시는 미기입이고, 순서 접미사 없는 후보는 BE 응답과 무관하게 FE 쓰기에서 거부한다. 안내 없는 회사가 이름 성 순서를 기대할 수 있다는 한계가 있다.
- **구조 미확인 칸 표시:** 1단계에서 칸이 화면에 있고 열려 있으며 프로필 값이 있는데 상세·기본 계약을 통과하지 못하면 결과 "확인 필요"에 `입력 불가(화면 구조 확인 불가)`(`STRUCTURE_UNVERIFIED`)로 표시한다. 화면에 없는 칸·닫힌 조건부 칸·값 없는 칸·범용 실행은 제외하며, location이 없는 분리 문서에서는 판정 전에 빠져나온다.
- **진단 로그:** 기본으로 꺼져 있고 `VITE_AUTOFILL_DEBUG=true` 빌드에서만 켜진다(하네스는 명시해 빌드). 시연 중 콘솔 오류(CSP `script-src:` 오타, fonts.gstatic.com CORS)는 사이트 쪽이다.

## 후속 보완 묶음 (2026-10-20)

- **칸 단위 인식:** 1단계 상세 기본정보의 인식 조건은 플랫폼 지문(MRS2 writeResume 자산, 유일한 `form#frm`, 섹션 11·13 각 1개)뿐이다. 영문 이름·생년월일·현주소·비상연락처는 각각 검증해 없는 칸은 생략하고 형식이 다른 칸만 제외하며(진단 키 `hplace.detail.<칸>`), 제외된 칸은 구조 미확인 표시로 드러난다. 성별 수집은 영문 이름에 의존하지 않고 BE `DETAIL_REQUIRED`는 빈 집합이다. 이전의 묶음 인식은 com2us·kdi처럼 칸 하나가 없을 때마다 모듈 전체가 빠지는 원인이었다.
- **효율:** `nativeForm()` 검증과 형식 지문은 정책 객체별 한 번만 계산하고 소유 섹션 하나만 다시 스캔한다. 검색 확정·주소 대기 루프는 매 틱 JSON 직렬화 대신 참조·필드 비교를 쓰고 저장 프로필 재로드는 대기 시작 전과 결과 반환 직전에만 한다(쓰기 직전 재확인 유지). 정책을 객체째 교체하면 재검증·중단되며, 테스트는 정책을 제자리에서 바꾸지 말고 교체해야 한다.
- **안내 구분:** 정책 비호환(`POLICY_INCOMPATIBLE`)은 확장 업데이트 안내, 정책 미등록(`ADAPTER_POLICY_UNAVAILABLE`)은 정책 없음 안내, v1 지원자 앱·채용 빌더 페이지는 미지원 사유를 보인다(`hplaceDocumentKind()`). `npm run zip`은 `VITE_AUTOFILL_DEBUG=true`면 실패한다.
- **금지 동작과 재실행:** 공용 workflow 테스트 하네스가 단계 탭·이전·임시저장·다음·제출·동의·인증 클릭과 모든 submit을 금지로 집계하고(허용은 staged address 모달의 자체 저장뿐), 같은 프로필로 2단계를 두 번 실행하거나 사이트가 날짜·학교명을 정규화한 뒤에도 행·검색·입력이 늘지 않는다. 신원 필드 둘 이상인 섹션에서 기존 행이 한 필드만 다르면 중복 행을 추가하지 않고 섹션을 사용자 처리로 넘긴다.
- **저장 후 다시 연 페이지:** 신원이 맞는 기존 행은 짝인 프로필 항목(`itemIndex`)을 유지하고, 결과는 승인·선택 없이 사이트 형식(점 날짜·옵션 라벨·검색명·숫자 평점)으로 비교해 같으면 "기존 값 유지", 다르면 "기존 값과 다름"으로 보고한다. 기존 행 충돌 검사와 검토 계획의 충돌 판정도 같은 형식으로 비교하며 주/야간 같은 표준 토큰은 라벨로 바꾼다. 사용자가 직접 고친 값이 있는 행의 섹션은 그대로 사용자 처리로 남는다(안내 문구는 아직 "자동으로 입력하지 못했어요"라 후속 과제). gsenc·abl 2단계 실화면에서 76·71건 "입력 못함"이 직접 고친 직장경력 17건으로 줄었다.

## 요청 구조 (2026-10-21)

- 저장은 `/mrs2/applicant/resume/saveStep<단계>`로 간다. 하단 임시저장 버튼(`data-type="tempSave"`)만 같은 경로에 `validateYn=false`를 붙여 저장하고 이동하지 않는다. 작성 모드 1–4단계의 단계 탭과 다음 버튼은 `type="submit"`이라 검증을 거쳐 `validateYn=true`로 저장한 뒤 이동한다. 5단계의 `saveStep5`는 임시저장이 아니라 최종제출이다.
- `/mrs2/applicant/resume/step<단계>.json`은 화면이 단계 데이터를 불러오는 POST이며 저장하지 않는다.
- 학교·전공·자격증·어학 조회는 `/com/code/retrieve*List` POST다(2026-10-21 다섯 테넌트에서 관측).
- 무저장 단계 이동은 사이트 `locationSubmit`과 같이 `resumeSn`, `recruitNoticeSn`, `step`만 담아 `writeResume`에 보내는 POST다. 사이트도 미리보기 모드와 5단계 화면에서는 저장 없이 이 요청만 보낸다.
- 실사이트 QA 하네스(`frontend/scripts/live-qa`, CF-177 live-eval 도구에서 일부를 옮김)의 요청 허용 목록과 원복이 이 구조를 쓴다. 근거는 [CF-310 요청 구조](../../raw/issues/CF-310/documents/hplace-mrs2-requests.md)를 따른다.

## 4단계 분석 예외와 결과 패널 집계 (2026-10-22)

- 4단계(자기소개서)는 컨트롤이 자기소개서 textarea뿐이라 에이치닷 섹션 수집기가 모두 건너뛰고 필드 수집 16개가 전부 거절된다(accepted=0). 확장은 그래도 `AUTOFILL_ANALYZE_FIELDS`를 호출하고 백엔드가 `BAD_REQUEST`를 돌려줘 패널이 "현재 지원서 구조를 분석할 수 없습니다" 예외로 끝난다. 2026-10-22 다섯 테넌트(abl·careerhyundai·gsenc·gsretail·hankooktire) 모두 재현됐다. 기대 동작은 수락 필드 0건이면 분석을 부르지 않고 안내를 보여 주는 것이다.
- 패널 "입력 완료"는 실행 뒤 DOM에서 값이 있는 칸 수와 같다. 저장 값을 지우지 않은 지원서에서는 저장 행을 같은 값으로 다시 채운 칸도 포함되므로 확장이 새로 쓴 칸 수가 아니다. "확인 필요"는 1–3단계 15페이지에서 모두 0건이었지만 빈 칸이 47개(의도적 미지원 46 + 논문 발표 여부 1) 있었다. 패널 수치는 항목 단위 참고값이고 입력률은 DOM 칸 단위로 센다.
- 근거는 [CF-310 4단계 분석·패널 근거](../../raw/issues/CF-310/documents/hplace-step4-analyze-and-panel.md)를 따른다.

## 수락 필드 0건인 단계의 분석 생략 (2026-10-22)

확장 워크플로는 수집 요청의 필드 수가 0이면 `AUTOFILL_ANALYZE_FIELDS`를 부르지 않고 `ADAPTER/COMPLETE`, 필드 없음, 설치된 `executionPolicy`를 그대로 넣은 분석으로 진행해 결과 화면으로 끝난다. 정책을 넣지 않으면 네이티브 정책 digest 대조에서 "페이지 실행 정책이 변경되었습니다" 예외가 난다. 수정 빌드로 GS건설 4단계를 재측정하면 예외 없이 입력 완료 0·확인 필요 0이다. 근거는 [CF-310 빈 단계 분석 생략 근거](../../raw/issues/CF-310/documents/hplace-empty-step-analysis-skip.md)를 따른다.

## v1 지원자 앱 1단계 (2026-11-21)

- **범위:** 경로 `/v1/applicant/resume-form/<숫자>`, 쿼리 `step=1`, v1 플랫폼 지문, 검증된 칸 1개 이상일 때만 지원 화면이다. 대상은 영문이름·생년월일·성별·비상연락처, 병역 상태와 하위 6칸, 장애 여부와 하위 3칸, 보훈 여부와 하위 2칸, 국적의 19칸이다. v1 로그인·마이페이지·4단계 이후는 미지원 안내를 유지한다. 2단계와 3단계는 아래 각 절을 따른다(CF-509, CF-510).
- **식별:** 빌드 해시 클래스는 쓰지 않는다. 고정 `name`, 행 제목(행의 첫 자식 `span[aria-hidden="true"]`), placeholder, 선택지 글자와 구조로 찾는다. 상태 행 제목은 `병역`, `장애여부`, `보훈여부`다. 칸 단위로 검증해 다르면 그 칸만 제외한다.
- **위젯:** 성별 라디오는 감싼 `label`을 눌러야 선택된다. 상태 선택은 `li > button` 묶음이고 선택 표시는 클래스 두 개뿐이다. 드롭다운은 버튼과, 열렸을 때만 있는 `#dropdown-body`의 `ul > li > button[value]`이며 Escape로 닫히지 않는다. 입대일은 포커스를 잃으면 월 정밀도로 바뀐다.
- **전송 계약:** 섹션 `hplace-v1-basic`, 칸 이름 `hplace.v1.<key>`. 버튼형 위젯은 `input`/`radio`와 `select`/`select`로 보내고 실제 조작은 프론트 v1 writer가 한다.
- **정책 분리:** 백엔드 v1 규칙은 저장하지 않는 v1 전용 정책 객체에 있다. MRS2 저장 문서(v3, v4), `hplace-mrs2-v4.json`, 활성 정책 버전 기본값은 바꾸지 않는다. 백엔드는 단계를 알 수 없어 섹션 ID와 칸 이름 허용 목록으로만 판정하고 `step=1`은 프론트가 확인한다.
- **실행 순서:** 병역·장애·보훈 상태는 stage 1 driver다. 하위 칸은 잠금이 풀린 뒤 다음 분석에서 기입하며 분석 한도 3회 안에서 끝난다. 선택지 불일치는 기입 단계에서 `OPTION_UNMATCHED`로 보고한다. 기존 값은 덮어쓰지 않고, 기본값 비대상만 같은 행 하위 칸이 비어 있을 때 프로필 값으로 바꾼다.
- **실측:** v1 테넌트 1곳에서 분석 ADAPTER·COMPLETE 2회, 18칸 기입, 사이트로 가는 GET 이외 요청 0건이었다. 같은 화면의 범용 실험은 2칸 기입이었다. 미필·면제·복무중이 여는 칸은 측정하지 않았다.
- **정책 조회:** 확장 백그라운드의 정책 조회는 호스트 일치와 경로 형식만 검사한다. 이전의 경로 일치 검사는 같은 문서 안에서 경로가 바뀌는 화면(v1의 로그인 → 지원서)에서 조회를 거절해 자동 기입이 시작되지 않았다.
- **현주소 창:** 현주소 3칸(`hplace.v1.postalCode`, `addressLine1`, `addressLine2`)은 잠겨 있고 사이트 자체 검색 창(제목 `주소입력`, iframe 없음)으로만 채워진다. 잠긴 칸이지만 창을 거쳐 쓰는 대상이라 보이는 후보로 수집한다. 백엔드 v1 정책에 세 칸의 규칙과 허용 목록이 있다.
- **결과 선택:** 프로필 기본주소로 한 번 검색하고, 도로명이 일치하는 결과가 정확히 한 줄일 때만 고른다. 상세주소를 넣고 창의 `확인`을 누른다. 일치가 없거나 여럿이면 `취소`로 닫고 확인 필요로 남긴다. 결과 줄에는 우편번호가 없다. 결과 목록을 감싼 스크롤 상자는 항상 그려지지 않으므로 결과 줄은 `도로명` 라벨이 있는 목록 줄로 찾는다.
- **확정 뒤 모양:** 확인 뒤 사이트가 현주소 행을 다시 그린다. 우편번호와 주소 칸은 읽기 전용(잠김 아님), 상세주소 칸은 편집 가능이 된다. 행 검증은 빈 모양(세 칸 잠김)과 확정 모양을 모두 인정한다. 주소 칸에는 도로명 뒤에 괄호 부분(법정동, 건물명)이 붙으므로 재확인과 기존값 비교는 끝의 괄호 부분을 뗀 도로명으로 한다. 우편번호와 상세주소는 정확히 일치해야 한다.
- **기존 주소:** 본문에 값이 이미 있으면 창을 열지 않는다. 같은 주소면 유지로, 다른 도로명이면 충돌로 보고한다.
- **사진 등록 창:** 공용 첨부 기능이 사진 파일을 넣으면 제목 `사진 등록` 창이 뜬다. 자르기 그림이 준비되기 전에 `저장`을 누르면 창만 닫히고 사진은 남지 않는다. 확장은 그림 준비를 기다려 `저장`을 한 번 누른다. 사이트가 사진 파일을 서버로 올리며 지원서 임시저장은 아니다. 사진 카드의 파일 칸이 사라지면 성공, 그대로면 실패로 보고한다. 확장이 넣기 전에 떠 있던 창과 제목이 다른 창은 누르지 않는다.
- **공용 첨부 경계:** 공용 첨부 구역에는 사이트 지식 없는 선택적 후속 단계(`attachFollowUp`) 하나만 있다. v1 동작은 어댑터 쪽에 있고, 다른 화면과 다른 사이트의 첨부 동작은 바뀌지 않는다.
- **사용자 결정:** `주소입력` 창의 `확인`과 `사진 등록` 창의 `저장`을 확장이 누르는 것은 2026-11-21 사용자 결정이다. `직접입력`(해외 주소)과 사진 자르기 영역 조정은 다루지 않는다.
- 필드별 현황은 [필드 현황](adapter-field-inventory.md), 근거는 [CF-505 v1 지원자 앱 1단계 근거](../../raw/issues/CF-505/documents/hplace-v1-step1.md)와 [CF-507 v1 현주소·사진 등록 근거](../../raw/issues/CF-507/documents/hplace-v1-address-photo.md)를 따른다.

## v1 지원자 앱 2단계 (2026-11-22)

- **범위:** 경로 `/v1/applicant/resume-form/<숫자>`, 쿼리 `step=2`, v1 플랫폼 지문, `학력사항`·`경력사항` 구역과 종류별 추가 컨트롤로 판별한다. 카드가 0장이어도 지원 화면이다. 대상은 고등학교 6칸, 대학교·대학원 각 10칸(전공명 1개, 본교/분교 포함), 직장경력 8칸이다. 첨부·파일, 계열·학과계열, 기간 버튼, 이수학점, 전공 평점·석차·전체인원, 두 번째 이후 전공, 대학교·대학원 소재지 쓰기, 카드 이동·삭제, v1 3단계 이후는 다루지 않는다.
- **구역과 카드:** 종류별 구역은 id가 숫자인 `div`이고 형제로 놓인다. 카드는 구역의 직접 자식이며 [머리, 본문] 두 자식을 갖는다. 중간 목록 상자는 없다. 추가 컨트롤도 구역의 직접 자식이다. 카드가 0장이면 `button`, 1장 이상이면 `tabindex="0"`인 `div`이고, 둘 다 유일한 `p`의 글자가 종류 이름이다.
- **짝짓기:** 카드의 종류는 카드가 든 구역의 추가 컨트롤 이름으로 판별한다(CF-510에서 바뀜, 아래 두 번째 테넌트 절). 추가 컨트롤이 없는 구역만 카드 자신의 행 구성으로 판별한다. 새 카드는 아래에 붙고 이름이 있는 입력 칸의 색인은 같은 종류 안의 카드 순서(0부터)와 같다. 종류를 판별하지 못하거나 카드 수와 프로필 항목 수가 다르면 그 구역은 입력하지 않는다.
- **기본 선택과 날짜:** 새 카드에는 사이트 기본 선택(졸업, 주간, 학사, 본교, 입학, 석사, 재직중)이 있다. 확장은 이 기본값만 프로필 값으로 바꿀 수 있는 값으로 보고 다른 선택은 덮어쓰지 않는다. 날짜 칸은 첫 번째 테넌트에서 연.월.일 전체만 받는다(월 단위만 남기는 테넌트는 아래 두 번째 테넌트 절). 미래 졸업일은 졸업구분과 관계없이 6년 이내면 넣는다(CF-510). 본교/분교는 프로필 학교명과 같은 이름의 카탈로그 학교가 본교나 분교 하나로 정해질 때만 고르고, 정해지지 않으면 그 칸을 실행에서 뺀다(CF-510).
- **추천 목록:** 학교명·전공명·회사명 입력은 자기 칸 안에 추천 목록을 띄우고 줄은 `li > button > span` 이름이다. 목록은 Escape나 포커스 이동으로 닫히지 않고 행 제목을 누르면 닫힌다. 학교를 고르면 입력 칸이 선택 표시로 바뀐다. 검색은 프로필 값으로 한 번 하고 정확히 일치하는 줄이 하나일 때만 고른다. 없거나 여럿이면 입력 칸을 비우고 확인 필요로 남긴다. 회사명 추천은 고르지 않고 닫는다.
- **전송 계약:** 섹션 `hplace-v1-history`, 칸 이름 `hplace.v1.<group>.<i>.<field>`(`highschool` i=0, `college`·`graduateSchool`·`career` i=0~9)다. 반복 항목은 `items`가 아니라 평평한 정확한 이름으로 보낸다. 백엔드는 생성한 정확한 이름 목록만 허용하고 `hplace-v1-basic`과 섞인 요청을 거절한다. 잠긴 칸을 보내면 요청 전체가 거절되므로 보내지 않는다.
- **카드와 전공 줄 추가:** `hplace.v1.<group>.add`와 `hplace.v1.{college,graduateSchool}.<i>.major.add`는 준비 요청의 `ADD_REPEATABLE_GROUP`이다. 응답에는 추가 횟수가 없다. 프론트가 프로필 항목 수에서 이미 있는 카드 수를 뺀 만큼 누르고, 클릭마다 1장 증가와 앞 카드 불변을 확인한다. 전공 줄은 전공명이 있는 항목에만 1줄 추가한다. 준비 요청은 필드 분석 3회 한도에 들어가지 않는다.
- **실행 순서:** 재직중/퇴사와 학교명·전공명 검색 칸은 먼저 실행하는 드라이버다. 퇴사일처럼 그 뒤에 열리는 칸은 다음 분석에서 쓴다. 평점과 만점기준은 둘 다 써질 때만 남긴다.
- **자동 기입 정책:** `autofillPolicy`는 v1 규칙이 아니라 프로필 칸마다 정해진다. 학교명, 졸업구분, 소재지, 주간/야간, 학위구분, 입학구분, 만점기준, 전공명, 회사명은 CONDITIONAL이고 나머지는 ALLOWED다. CONDITIONAL 항목은 `needs-review`로 자동 실행에 선택되므로 어댑터의 쓰기 승인 조건은 두 정책을 모두 받는다. 테스트용 백엔드 응답은 실제 응답 표본에서 만든다([회사 어댑터 개발](adapter-development.md)).
- **등록하기와 전공 확인:** 정확히 일치하는 줄이 없고 목록에 친 이름의 등록하기 줄 하나만 있을 때만 그 줄을 한 번 누른다(사용자 결정 2026-11-22). 그 줄의 맨 안쪽 `span`에는 따옴표로 감싼 이름만 있고 `등록하기`는 `span` 밖의 별도 글자다. 전공 등록 뒤 하위 줄이 다시 그려지면 검색 입력이 사라지고, 선택 표시는 input·li·button이 없는 `span[data-review-key] > div > div > p` 하나로 읽는다. 전공 구분 토글과 성적 위젯은 선택 표시나 하위 줄로 세지 않고 누르지 않는다.
- **목록 안정과 실패 처리:** 검색 목록은 300ms 동안, 그리고 연속 12회 읽기에서 바뀌지 않아야 안정이다. 등록하기 줄 하나뿐인 목록은 입력 뒤 1000ms도 지나야 한다. 입력이 사라진 뒤 검색이 실패하면 그 카드의 검색 행만 따로 두고(`stateDriverFailureTargets`) 실행을 계속한다.
- **경력기술서·포트폴리오:** `추가하기`는 창이나 요청 없이 파일 입력과 URL 입력이 있는 항목 1개를 붙인다. 프로필에 `resume`(경력기술서) 또는 `portfolio` 종류의 파일이나 링크가 있고 행에 항목이 없을 때만 한 번 누른다(`hplace.v1.careerDescription.add`, `hplace.v1.portfolio.add`). 붙은 항목은 공용 첨부 구역이 어댑터 힌트(`attachmentFieldHint`)로 처리한다. 졸업증명서 첨부는 범위 밖이다.
- **실측:** v1 테넌트 1곳에서 구조, 기본 선택, 날짜 형식, 추천 목록 모양과 닫기 동작을 측정했다. 빌드 aaa814f의 실행에서 고등학교·대학교(전공 포함)·직장경력의 대상 칸이 모두 채워졌고, 분석 2회, 패널 확인 필요 0건, 사이트로 보낸 GET 외 요청은 검색 POST뿐이었으며 임시저장·다음 단계·제출은 누르지 않았다. 대학원 카드, 종류별 카드 상한, 새 첨부 항목이 파일을 받는지는 실측하지 않았다.
- 필드별 현황은 [필드 현황](adapter-field-inventory.md), 근거는 [CF-509 v1 지원자 앱 2단계 근거](../../raw/issues/CF-509/documents/hplace-v1-step2.md)를 따른다.

## v1 지원자 앱 3단계 (2026-11-22)

- **범위:** 경로 `/v1/applicant/resume-form/<숫자>`, 쿼리 `step=3`, v1 플랫폼 지문, 알려진 구역 제목(`h5`: `어학`, `자격/지식/기술`, `경험`) 중 하나 이상이 중복 없이 있고 대상 블록이 하나 이상일 때 지원 화면이다. 대상 블록은 있는 것만 따로 다룬다. 대상은 `자격증` 하위 줄 4칸(자격증명, 발급기관, 취득일, 등록번호)과 `외국어활용능력` 하위 줄의 언어 1칸이다.
- **블록과 하위 줄:** 첫 번째 v1 테넌트에는 `어학` 아래 `공인외국어시험`·`외국어활용능력`, `자격/지식/기술` 아래 `자격증`·`컴퓨터활용능력` 블록이 있다. 블록마다 자기 `추가하기`가 블록 안에 하위 줄을 붙인다. 블록 모양은 본문 > 감싸개 > [목록, `추가하기`], 하위 줄은 [내용 `div`, 아이콘 버튼]이다. `경험` 구역(수상경력 등 5개)은 구역 이름의 버튼으로 카드를 붙인다. 처음에는 입력 칸이 없다.
- **공인외국어시험 제외:** 시험을 고르면 새 탭으로 외부 성적 확인 페이지가 열리고 성적 칸은 잠긴 채로 남는다. 어댑터는 이 블록에서 아무것도 찾거나 수집하거나 누르지 않는다.
- **자격증:** 이름 없는 검색 입력에서 `POST …/search-filter/license`로 검색하고 정확히 일치하는 줄만 고른다. 고르면 창 없이 선택 표시(`span[data-review-key] > div > div > p`, review-key가 없으면 이름 묶음의 유일한 글자 잎), 발급기관, 이름 없는 취득일 칸(과거 날짜만, 페이지가 `YYYY.MM`만 남기면 같은 연월이면 유지), 등록번호 칸이 나타난다. 검색 확정·등록하기·목록 안정 규칙은 2단계와 같고 공용 모듈 `v1-search.ts`를 함께 쓴다.
- **외국어활용능력:** 언어 드롭다운에서 정확히 같은 선택지만 고른다. 기존 값과 다른 이름의 선택 표시는 덮어쓰지 않는다.
- **전송 계약:** 섹션 `hplace-v1-extra`, 칸 이름 `hplace.v1.certificate.<i>.{licenseName,organization,acquireDate,registNumber}`와 `hplace.v1.languageSkill.<i>.language`(i=0~9, 정확한 이름 50개)다. 추가 동작 `hplace.v1.certificate.add`, `hplace.v1.languageSkill.add`는 준비 요청의 `ADD_REPEATABLE_GROUP`이고 프론트가 프로필 항목 수에서 이미 있는 하위 줄 수를 뺀 만큼 누른다. 자격증명·발급기관·언어는 CONDITIONAL, 취득일·등록번호는 ALLOWED다.
- **범위 밖:** `경험` 구역, `컴퓨터활용능력`(프로필 범주 없음), 회화수준, 자격증 등급, 파일 칸. 백엔드는 이 이름을 거절한다.
- **실측:** 구조와 칸 모양은 첫 번째 v1 테넌트에서 측정했고 그 공고가 2026-11-22에 마감돼 그곳에서는 3단계를 실행하지 않았다. 두 번째 v1 테넌트에서 빌드 fc0d9bc가 자격증 4칸을 채웠으나 자격증명에 확인 필요 1건이 남았다(아래 두 번째 테넌트 절). 외국어활용능력 실화면 기입과 처음 30개 이후의 언어 선택지는 실측하지 않았고 안전 쪽으로 실패한다.
- 필드별 현황은 [필드 현황](adapter-field-inventory.md), 근거는 [CF-510 v1 지원자 앱 3단계 근거](../../raw/issues/CF-510/documents/hplace-v1-step3.md)를 따른다.

## v1 두 번째 테넌트 실측 (2026-11-23)

- **구역 구성:** v1 테넌트마다 구역 구성이 다르다. 두 번째 v1 테넌트의 2단계 구역 제목은 `학력사항`·`경력사항`뿐일 수 있고 3단계에는 `어학` 없이 `자격/지식/기술`(자격증 블록)과 `경험`만 있다. 단계 이동 글자(예: `학력 및 경력`, `자격/기타`)는 판별에 쓰지 않는다. 판별은 경로, step, v1 지문, 알려진 구역 제목 하나 이상(중복 없음)이고 범위 안의 블록과 종류는 각각 따로 다룬다.
- **추가 컨트롤과 카드 종류:** 추가 컨트롤 글자에 필수 표시가 붙을 수 있다(`고등학교 *`, 이름 뒤 `*`만 허용). 첫 카드 뒤에는 필수 표시 없는 `div[tabindex=0]`이 된다. 대학교와 대학원 카드는 행이 같을 수 있어 카드 종류는 구역의 추가 컨트롤 이름으로 정한다. 다른 종류의 측정 행이 있으면 그 종류는 입력하지 않고, 어느 종류도 측정하지 않은 행(예: `퇴직사유`)은 건너뛰고 입력 불가로 보고한다.
- **저장되는 카드:** 사이트가 추가한 카드를 저장해 다시 불러와도 남기는 테넌트가 있다. 이미 있는 빈 카드도 프로필 항목 수에 세어 중복 추가하지 않고 채운다. 이름 있는 입력이 없는 전공 하위 줄은 검색 입력 수로 센다. 준비 단계가 멈추면 값 없는 `stop stage=preparation` 줄을 남긴다.
- **review-key 없는 화면:** `data-review-key` span이 없는 테넌트에서는 검색 목록(`#dropdown-body`)이 입력의 행 밖, 같은 숫자 id 구역 안에 붙는다. 엔진은 입력 뒤 새로 나타난 목록 하나만 읽는다. 고른 값은 이름 묶음의 유일한 글자 잎으로 읽고 없거나 여럿이면 읽지 않는다.
- **월 단위 날짜:** 입학일·졸업일·취득일은 페이지가 `YYYY.MM`만 남길 수 있고 같은 연월이면 유지로 본다. 월까지만 있는 프로필 날짜는 `YYYY.MM`으로 쓴다.
- **첨부:** 경력기술서 항목은 파일+URL 입력, 포트폴리오 항목은 파일만일 수 있다. 공용 첨부 구역은 결과 화면에서 저장된 프로필 파일을 붙인 항목에 자동으로 올린다(업로드 POST 1회). 그 테넌트에서는 업로드 뒤 다시 그려지며 포트폴리오 항목이 사라질 수 있다(페이지 동작, 바꾸지 않음).
- **실화면:** 2단계는 빌드 fc0d9bc에서 패널 안내 0건으로 끝났다(모든 카드 채움, 분석 2회, GET 외 요청은 검색 POST와 첨부 업로드 1회, 임시저장·다음 단계·제출 클릭 없음). 3단계는 자격증명·발급기관·취득일·등록번호를 채웠고 자격증명에 `입력 결과를 확인하지 못했어요` 1건이 남았다. 진단 빌드 0eb8030은 2026-11-23 사이트 세션 만료(로그인 화면)로 실행하지 못했다.
- 근거는 [CF-510 v1 두 번째 테넌트 실측](../../raw/issues/CF-510/documents/hplace-v1-second-tenant.md)를 따른다.

## 검증과 배포 경계

10월18/19 두 테넌트의 구조 관측과 P4 자동 검증은 로컬 구현의 근거다. 10월12/13 설치 관측은 과거 revision의 제한된 증거이며 소실된 임시 원본을 복구·재검증한 것으로 취급하지 않는다.

2026-10-20 live-eval 하네스로 `1759db5`와 `f586619`(C9·C7·C11 포함) CLEAN 빌드에서 abl·careerhyundai·gsenc의 step 1–3 실화면 평가를 통과했고 두 실행의 수치는 같았다. 이로써 이전의 검색·주소·linkedForm 미확인 상태를 정정한다. 이후 `4962c96`(C13)과 `6a7a141`(시연 수정)에서도 3사 step 1–3이 모두 통과했다. 후속 보완 묶음 `b809920`에서는 빈 페이지(careerhyundai)와 임시저장 값이 남은 페이지(gsenc·abl)를 함께 돌려, 사용자가 직접 고친 행의 섹션만 확인 필요로 남았다. 포커스 없는 창·사이드 패널 동작(H7), 공식 WSL/Linux 검증과 운영 배포는 별도다. 하네스는 상주 Chromium에 CDP로 붙고 무저장 단계 이동만 하며, 서빙 정책 지문이 대상 HEAD 정책과 match일 때만 평가한다. 정책을 고친 뒤에는 사람이 승인한 로컬 DB 재설정으로 재시드해야 한다.

새 확장 배포 → 대상 설치/보급 확인 → BE 배포 순서를 따른다. resource enabled를 운영 활성화로 해석하지 않으며 이 수집에서 migration·배포를 실행하지 않는다.

## 활성 정책 버전은 설정값 (2026-10-23)

활성 정책 버전은 DB 포인터가 아니라 Spring 속성 `careerform.hplace.active-policy-version`이며 기본값이 4다. `HplaceFormPolicySeeder`는 v3·v4 문서를 없을 때만 insert하고 `MongoHplacePolicyProvider`는 설정값으로 문서를 고른다(4가 없으면 3). `application-prod.yml`, `infra/compose.deploy.yaml`, deploy workflow 어디서도 이 값을 전달하지 않아 백엔드 배포 즉시 v4가 활성화되고 운영에서 끌 레버가 없다. 끄거나 v3로 되돌리려면 설정 전달 경로를 추가하는 infra 변경이 필요하다. 이전 raw의 "DB 활성 포인터를 사람이 올린다"는 서술은 이 내용으로 정정하며, 그 결과 [확장·백엔드 호환 배포](release-compatibility.md)의 순서가 v4 활성화를 제어하는 유일한 수단이다. 근거는 [CF-327 활성 정책 버전 설정값 근거](../../raw/issues/CF-327/documents/hplace-active-policy-version.md)를 따른다.

## 변경 이유

2026-11-21에는 v1 지원자 앱을 범용 경로로 보낸 실험이 2칸 기입에 그쳐, 사용자 결정으로 v1 1단계를 정적 어댑터로 추가했다(CF-505). 같은 날 v1 1단계의 현주소 창 기입과 사진 등록 창 저장을 더했다(CF-507). 2026-11-22에는 사용자 결정(2026-11-21)에 따라 v1 2단계의 학력·경력 카드 추가와 기입을 더했고, 같은 날 사용자 결정으로 검색 등록하기 줄 누르기와 경력기술서·포트폴리오 항목 추가를 더했다(CF-509). 같은 날 v1 3단계의 자격증·외국어활용능력 하위 줄 추가와 기입을 더하고 외부 성적 확인 탭을 여는 공인외국어시험은 뺐다(CF-510). 2026-11-23에는 두 번째 v1 테넌트의 다른 구역 구성, 행이 같은 카드, review-key 없는 화면, 월 단위 날짜, 저장되는 카드에 맞춰 v1 2·3단계 판별과 판독을 고쳤다(CF-510).

2026-10-20 후반에는 실화면 정제 fixture로 합성 builder를 대조하고(C12), 프로젝트154를 활성화했으며(C13), 처음 보는 테넌트 시연에서 드러난 현주소 앵커·병역 날짜 정밀도·영문 이름 순서 문제를 고쳤다. v3의 등록·기본정보 범위에 후속 단계 구조와 정책 계약을 추가했다. 2026-10-20에는 실화면에서 드러난 분석 루프 정체와 학교·전공·자격·시험 검색 미실행의 원인(격리 world의 Enter 속성, 첫 실패 driver 정지와 예산 소진, hidden 검색 의존, 라디오 코드/라벨 비교 등)을 수정하고 3사 실화면으로 확인했다. 과거 주소 모달 저장 제외 판단은 원래 주소로 복사하는 로컬 확정 근거로 정정했다. 상세한 현재 계약·역사·검증 제한은 연결된 raw를 따른다.
