# 백엔드 품질 정본과 계층형 강제

## 상태

승인됨

## 날짜

2026-09-17

## 관련 Issue

- #91

## 배경

AI가 작성하고 리뷰하는 백엔드 코드에 공통 품질 기준이 없었다. 규칙을 각 지침에
복사하면 내용이 갈라지고, 모든 판단을 자동 검사로 바꾸면 의미와 가독성을 잘못
차단할 수 있다. 기존 production 코드에는 새 구조 기준의 위반이 있으나 이번 Issue는
그 코드를 리팩터링하지 않는다.

## 결정

`llm-wiki/wiki/topics/backend-code-quality.md`를 Java, Spring 백엔드 품질 규칙의
단일 정본으로 사용한다. AGENTS와 구현, 리뷰 Skill은 규칙 전문을 복사하지 않고 이
topic을 읽는다. 해석 사례는 별도 examples topic에 두며 정본을 덮어쓰지 않는다.

객관적인 타입 관계로 판정 가능한 A1부터 A6까지만 ArchUnit 1.5.0으로 검사한다.
검사 범위는 API와 Application DTO 경계, Controller와 Service의 금지 의존,
Domain의 외부 의존, Port의 공급자 타입 누출, Adapter의 Service 역호출, 계층과
기능 순환, API 응답의 내부 타입 누출이다. 의미, 가독성, 오류와 트랜잭션의 적절성,
주석 필요성은 기능 테스트와 Standards 리뷰에 남긴다.

시작 commit `8790c7306af7b9b1be46f5457715aba563a27a42`의 production 전체를 검사해
A1 21건과 A5 1건, 총 22개의 정확한 관계를 기존 위반 기준선으로 기록한다. 기준선은
신규 위반을 허용하는 예외가 아니며 실제 관계가 해결되면 stale 실패로 제거를 요구한다.
일반 기능 변경으로 기준선을 늘릴 수 없고, guarded Gradle task와 `harness-change`
절차로만 갱신한다.

팀이 의도적으로 허용하는 관계는 기준선과 별도 JSON에 둔다. 규칙, 정확한 관계와
대상, 이유, 대안, 보완 테스트, 연결 Issue, 해소 조건, 작성자와 다른 백엔드 검토자를
기록한다. 고정 30일 만료는 두지 않는다. 대상 코드, 규칙, 보완 테스트, 해소 조건이
바뀌거나 실제 관계와 일치하지 않으면 재검토한다.

API DTO와 Application DTO는 요청과 응답 양방향에서 분리한다. 저장 모델은 통합이나
분리 중 하나를 전역 기본값으로 정하지 않는다. 저장 구조가 다르거나 업무 사용 전에
검증해야 하면 Domain과 Document를 분리하고 Adapter에서 변환한다. 현재 회사 정책의
`Mongo Document -> validation -> CompanyFormPolicy -> router/fingerprint -> adapter route`
흐름은 유지한다.

함수마다 Javadoc을 요구하지 않는다. 이름과 타입으로 드러나지 않는 외부 계약,
실패와 부수 효과, 비자명한 결정 이유만 문서화한다. Javadoc이나 주석 개수는 CI에서
검사하지 않는다.

Issue와 제품 계약에 오류, 부재, 우회, 재시도, 부수 효과가 정해져 있지 않으면 AI는
구현 전에 구체적인 질문을 한 번에 하나씩 한다. 리뷰는 Standards와 Spec을 분리하고
`규칙 ID / 파일·심벌 / 영향 / 최소 수정안 / 필수·권고 / 불확실성`을 보고한다.

## 검토한 대안

- 산문 지침만 사용: 신규 구조 위반을 결정론적으로 차단할 수 없어 채택하지 않았다.
- AGENTS, Skill, CI에 규칙 전문 복사: 변경 시 정본이 갈라져 채택하지 않았다.
- 모든 품질 규칙 자동 차단: 의미와 가독성의 오탐을 피할 수 없어 채택하지 않았다.
- 기존 코드를 먼저 전부 리팩터링: 범위와 제품 위험이 커 후속 작업으로 남겼다.
- AI 행동 eval과 모델별 비교: 이번 Issue의 코드 품질 계약을 검증하지 않으므로 제외했다.

## 결과

AI 작성과 리뷰는 같은 BQ 규칙을 사용하고 객관적인 신규 구조 위반은 backend CI에서
차단된다. 기존 기술 부채는 숨지 않고 개별 관계로 남는다. 검사 대상이 없거나 import,
설정, registry가 실패하면 PASS가 아니라 NOT_APPLICABLE 또는 ERROR로 구분된다.

ArchUnit 규칙, 기준선과 예외의 유지 비용이 생긴다. 자동화하지 않은 의미 판단은 계속
테스트와 사람 리뷰가 필요하다. production 리팩터링, 제품 동작 변경, formatter와
Checkstyle 도입, AI 자동 평가는 별도 결정으로 남는다.
