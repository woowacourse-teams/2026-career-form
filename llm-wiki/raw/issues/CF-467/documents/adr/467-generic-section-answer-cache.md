# 범용 칸 분석의 섹션 단위 결과 캐시

## 상태

승인됨

## 날짜

2026-11-17

## 관련 Issue

- #467 범용 칸 분석의 섹션 단위 결과 캐시
- #244 범용 매칭 흐름 통합(확장의 섹션 분석 캐시)
- #448 공고 알림 발송 중 공고 조회 잠금으로 발송이 멈추는 문제 수정(가상 스레드 고정)

## 배경

범용 칸 분석은 요청마다 섹션별로 분류 공급자를 부른다. 요청에는 양식의 구조만 있고 프로필 값이 없어서, 같은 양식을 여는 사용자들은 같은 내용을 보내고 같은 답을 받는다. CF-222 ADR의 측정에서 JEV는 같은 입력을 반복했을 때 69개 중 68개에서 같은 결과를 냈다. 답을 다시 쓸 수 있는 조건이 갖춰져 있는데 서버에는 캐시가 없었다.

확장에는 섹션 분석 캐시가 있지만(#244) 한 실행과 한 URL 안에서만 산다. 사용자 사이에서 나눠 쓰려면 서버에 있어야 한다.

## 검토한 대안

### 1. 저장 단위

- A. 화면 전체: 요청 하나를 통째로 저장한다. 단순하다. 그러나 사용자마다 반복 줄 수와 고른 유형이 달라 화면 전체가 같은 경우가 드물다. 평가 데이터셋 `generic-matching` v5의 칸 분석 요청 4개 가운데 모든 섹션이 적중한 요청은 없었다.
- B. 섹션 (선택): 분석이 이미 섹션 단위로 돌아 끼울 자리가 있다. 같은 데이터에서 질문이 있는 섹션 31개 가운데 13개가 적중했다. 한 섹션만 실패해도 나머지 섹션은 저장된다.

### 2. 키에 넣을 값

- A. 요청의 식별자를 포함: `snapshotId`는 요청마다 새로 만들어져 캐시가 한 번도 맞지 않는다. `candidateId`는 화면 전체의 순번이라 앞 섹션의 줄 수가 다르면 밀린다. DOM의 id와 name은 사이트가 그때그때 만들 수 있다.
- B. host를 포함: 틀린 답이 저장돼도 한 사이트 안에 머문다. 그러나 공급자는 host를 받지 않으므로 입력이 같으면 답이 같고, 캐시가 없어도 그 사이트는 같은 답을 받는다. host는 확장이 보내는 값이라 경계가 되지 못한다. 같은 채용 플랫폼을 쓰는 회사들은 양식이 같고 host만 달라 서로 나눠 쓰지 못하게 된다. 데이터셋 v5의 두 사이트 사이에는 같은 섹션이 없어서, 따로 만든 사이트끼리는 넣든 빼든 적중이 같다.
- C. 공급자에 보내는 내용 그대로 (선택): 분석이 읽는 값을 키에서 빠뜨릴 수 없다. 관찰값에 항목이 늘어도 키가 따라 바뀐다. 프롬프트의 안내문과 선택 기준이 들어 있어 프롬프트를 고치면 키도 바뀐다.

### 3. 양식이나 분석 기준이 바뀔 때

- A. 변화를 감지해 지우는 장치: 사용자가 오지 않아도 양식을 주기적으로 확인해야 하고, 놓치면 틀린 답이 나간다.
- B. 키와 기한 (선택): 양식이 바뀌면 키가 달라져 새로 분석한다. 옛 항목은 다시 읽히지 않고 기한이 지나면 지워진다. 코드, 프롬프트, 설정이 바뀌는 때는 배포이고 배포하면 프로세스 안 캐시가 비워진다. 공급자가 같은 모델 이름 뒤에서 모델을 바꾸는 경우는 기한이 맡는다.

### 4. 저장 위치

- A. Redis: 배포해도 남고 서버가 여러 대여도 함께 쓴다. 그러나 운영 서버가 한 대라서 함께 쓸 상대가 없다. 서버 밖 캐시의 가장 큰 이점이 여기서는 쓰이지 않는다. 치르는 것은 새 컨테이너와 접속 설정, Redis가 죽거나 느릴 때의 처리(제한 시간을 두고 실패하면 캐시가 없는 것처럼 돌게 해야 하고, 빼먹으면 캐시가 없을 때보다 나빠진다), 키 버전 관리, 배포 구성 변경이다. 같은 서버에 컨테이너로 띄우면 돈은 들지 않지만 일과 고장 지점이 는다. 조회 속도는 프로세스 안이 더 빠르다.
- B. MongoDB: 이미 떠 있어 새 구성 요소가 없고 배포해도 남는다. 직렬화와 조회 왕복, 키 버전 관리가 든다.
- C. 프로세스 안의 캐시, Caffeine (선택): 서버가 한 대이고, 캐시가 사라져도 다시 분석하면 되어 정확성 문제가 없다. 배포로 비워지는 것이 옛 코드와 옛 프롬프트로 만든 답을 지우는 구실을 해서 키에 버전을 넣어 관리할 필요가 없다. 크기 상한과 기한이 라이브러리에 들어 있다. Spring Boot가 버전을 관리한다(4.1.0 기준 3.2.4).

### 5. 같은 섹션이 동시에 올 때

- A. 한 번의 호출로 합치기: 값을 만드는 함수를 캐시에 넘기면(`Cache.get(key, 함수)`) 호출이 한 번이다. 그러나 Caffeine 3.2.4의 Javadoc은 이 호출 전체가 원자적으로 돌고, 계산이 도는 동안 이 캐시의 다른 쓰기 일부가 막힐 수 있으니 계산을 짧고 단순하게 두라고 적는다. 그 함수 안에서 공급자를 부르면 섹션들이 도는 가상 스레드가 묶일 수 있다. #448에서 `computeIfAbsent` 안의 DB 조회로 같은 일을 겪었다.
- B. 찾아보고, 없으면 부른 뒤 넣기 (선택): `getIfPresent`와 `put`을 따로 쓴다. 잠금을 쥔 채 외부 호출을 하지 않는다. 처음에 동시에 온 요청은 각자 공급자를 부른다. 답이 같아서 나중 것이 덮어써도 된다.

### 6. 켜고 끄기

- A. 환경 변수로 환경마다: 환경별로 따로 켜고 끌 수 있다. 그러나 배포 workflow와 `infra/compose.deploy.yaml`을 고치는 [Infra] Issue가 따로 필요하다.
- B. `application.yml`의 기본값으로 켬 (선택): Issue 하나로 끝난다. 끄려면 기본값을 바꾼 수정 배포가 필요하다. 동시 호출 수 같은 기존 `jev` 설정과 같은 방식이다. 다른 `jev` 설정처럼 환경 변수 자리표시는 두지만 배포 구성이 전달하지 않는다.

## 결정

- 섹션 단위로 저장한다.
- 키는 모델 이름, 섹션 상태, 선택 기준을 Map 키를 정렬한 JSON으로 직렬화한 SHA-256이다. host, 경로, `snapshotId`, `candidateId`, 섹션 id, DOM의 id와 name은 넣지 않는다. 모델 이름은 `ChoiceModel.model()`로 읽는다.
- 값은 질문 번호별 선택과 확신도다. 선택지별 확률은 분석이 쓰지 않아 버린다. 답을 칸에 붙이는 일과 후처리는 요청마다 한다.
- 모든 질문에 답을 받은 섹션만 저장한다. 공급자 실패, 허가 대기 초과, 토큰 한도로 답이 빠진 섹션은 저장하지 않는다. 판단 보류는 답으로 보고 저장한다.
- 무효화는 키와 기한으로 한다. 기한의 기본값은 7일, 크기 상한의 기본값은 섹션 5,000개다.
- 저장 위치는 백엔드 프로세스 안의 Caffeine 캐시다. Redis와 MongoDB는 쓰지 않는다.
- 조회와 저장은 따로 한다. 값을 만드는 함수를 캐시에 넘기지 않는다.
- 캐시는 Spring이 만드는 운영 분석기에만 붙인다. `withModel`, `withBatching` 사본과 캐시 없이 만드는 생성자(평가 조립이 운영 분석기가 없을 때 쓴다)에는 붙이지 않는다.
- 설정은 `application.yml`의 기본값으로 켠다. 응답 형식은 바꾸지 않고 적중은 서버 지표(`career.form.analysis.section.cache`, `outcome`은 `hit`과 `miss`)로 본다.

## 결과

- 효과: 같은 섹션을 다시 분석할 때 공급자 호출과 대기 시간이 없어진다. 데이터셋 v5의 칸 분석 요청 4개를 순서대로 넣은 테스트(`GenericSectionAnswerCacheDatasetTest`, 섹션 동시 수 1, 질문 묶음 5)에서 공급자 호출이 47회에서 29회로 줄었다. 요청별 적중은 같은 양식의 화면 셋이 0/8, 7/8, 6/8이고 다른 사이트의 화면이 0/7이다.
- 비용: Caffeine 의존성(실행 jar 약 1.03MB 증가), 백엔드 힙 사용(섹션 5,000개에 섹션당 질문 5개면 약 6MB, 10개면 약 10MB, 20개면 약 19MB), 처음 동시에 온 요청의 중복 호출.
- 남은 한계: 배포하거나 재시작하면 캐시가 비워진다. 사용자가 적고 배포가 잦으면 적중률이 낮다. 글자는 그대로인데 칸의 뜻만 바뀌는 변화는 키가 잡지 못하고, 기한이 그 영향이 이어지는 시간을 묶는다. 공급자의 답이 흔들린 경우 처음 저장된 답을 같은 섹션을 보내는 모든 사이트가 기한까지 받는다. 질문 지시문과 질문 묶음 크기는 키에 없고, 바뀌는 때가 배포라서 배포로 비워지는 것에 기댄다. 서버 밖 저장으로 옮기면 이 둘을 키에 넣거나 키 버전으로 관리해야 한다.
- 재검토 조건: 서버가 두 대 이상이 되거나 배포 뒤 적중률이 떨어지는 것이 지표로 확인되면 서버 밖 저장(MongoDB, Redis)을 검토한다. 운영에서 환경별로 켜고 꺼야 하면 [Infra] Issue로 설정 전달을 더한다.
