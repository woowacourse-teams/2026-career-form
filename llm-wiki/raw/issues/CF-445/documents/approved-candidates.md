# CF-445 승인 후보 스냅샷

> Issue: [CF-445](https://github.com/woowacourse-teams/2026-career-form/issues/445)
> Collected: 2026-11-10
> Approval-Digest: ea356ce89986bea6f83cd3530e98d1cf7daa81dd5362d312f9f617af633bc226

worktree 체크포인트에 기록한 후보 일곱 개의 원문이다. 사람이 2026-11-10 "승인"으로 확정했다.

1. [결정] 공고 알림 발송의 SQS 릴레이·워커 구조(2026-11-10, CF-445, ADR): 팀원 제안(Outbox 트랜잭션 + FIFO + 가시성 타임아웃 재시도) 대신 발송 문서(push_deliveries)를 상태 정본으로 유지하고 표준 큐 + DLQ를 그 사이에 둔다. 큐 메시지 본문은 발송 문서 id만 담고, 중복 발송은 워커의 조건부 갱신 선점으로 막으며, 재시도 대기는 지금처럼 nextAttemptAt에 적는다. 발송 방식은 설정 push.transport(direct 기본, sqs)로 고른다. Outbox 트랜잭션과 MongoDB replica set은 넣지 않고 등록 빈틈은 CF-439의 재등록 보충으로 메운다(팀 측정 계획의 S8 기준은 이 전환에서 뺀다). 서버는 인스턴스 역할 자격 증명으로 SQS를 부르고 액세스 키를 만들지 않는다. 개발·운영 적용과 릴레이·워커 배치는 전후 측정 결과를 보고 후속 Infra Issue에서 정한다. ADR 전문은 Issue #445 본문의 것을 raw documents/adr/445-push-sqs-relay-worker.md로 기록한다.
2. [사실] SQS 방식의 동작 규칙(CF-445 구현): 상태는 PENDING → QUEUED → SENDING → ACCEPTED·ABANDONED·PENDING(재시도)다. 릴레이는 발송기와 같은 주기와 한 주기 상한으로 때가 된 PENDING, 큐 리스(기본 15분)가 지난 QUEUED, lease가 지난 SENDING을 찾아 큐에 먼저 넣고, 넣은 건만 QUEUED로 표시한다. 그래서 표시 전에 릴레이가 멈춰도 메시지는 남고, 다시 넣은 중복은 워커 선점이 거른다. 워커는 남은 동시 발송 수만큼(최대 10건) long polling으로 받고 QUEUED, 때가 된 PENDING, lease가 지난 SENDING만 선점해 보낸다. 선점하지 못한 메시지는 지우고, 발송 id 형식(32자 hex)이 아닌 메시지는 지우지 않아 DLQ로 가게 둔다. 워커가 죽은 건은 lease 120초 뒤 릴레이가 다시 넣고, 큐에서 사라진 건은 큐 리스 뒤 다시 넣는다. sqs에서 direct로 되돌리면 발송기가 큐 리스가 지난 QUEUED까지 집어 보낸다. 관리 화면의 발송 진행과 요약 API는 QUEUED를 대기에 합쳐 세고, 공고 삭제는 PENDING과 QUEUED를 함께 취소한다.
3. [사실] 가상 스레드와 맵 잠금(2026-11-10 로컬 리허설에서 확인): ConcurrentHashMap.computeIfAbsent 안에서 저장소(MongoDB)를 부르면 맵 잠금을 쥔 채 I/O를 하게 되고, JDK 21의 가상 스레드는 그 잠금을 쥐거나 기다리는 동안 운반 스레드를 놓지 못한다. CPU 2개로 제한한 컨테이너(운반 스레드 2개)에서 워커가 같은 공고의 발송 10건을 한꺼번에 받자 1,000건 중 971건에서 발송 전체가 멈췄다(-Djdk.tracePinnedThreads=full로 위치 확인). 조회를 잠금 밖(get 뒤 putIfAbsent)으로 옮겨 고쳤다. 이 코드는 지금 방식(direct) 발송기에도 원래 있었고, 발송기는 한 건씩 선점하며 넘겨서 드러날 확률이 낮았을 뿐이다. 가상 스레드에서 도는 코드는 synchronized나 computeIfAbsent 안에서 I/O를 하지 않는다.

[사실] 알림 조립과 테스트 규칙(CF-445): NotificationConfiguration 안쪽의 방식별 조립 클래스에 @Configuration을 붙이면 컴포넌트 스캔이 바깥 조건(알림 켜짐)과 무관하게 따로 읽어 알림이 꺼진 컨텍스트가 깨진다. 안쪽 클래스에는 조건과 @Bean 메서드만 둔다. push.transport가 direct·sqs가 아니거나 비어 있으면 조건이 둘 다 맞지 않아 발송이 조용히 꺼질 수 있으므로 PushTransport가 기동을 멈춘다. ApplicationContextRunner로 조립을 시험할 때는 ApplicationConversionService를 넣어야 60s·15m 같은 기간 값을 읽는다. SQS 어댑터는 실제 AWS SDK 클라이언트를 로컬 HTTP 서버(AWS JSON 응답 흉내, 본문 MD5 포함)에 붙여 검증한다.
5. [사실] 발송 시험 스택의 SQS 방식(CF-445): compose의 worker 서비스(profile sqs)는 백엔드와 같은 이미지에서 워커만 켜고, 백엔드는 릴레이만 돌려 동시 발송 수 합계 20을 유지한다. compose는 꺼진 profile의 서비스도 변수를 풀기 때문에 그 서비스에 필수 변수(${VAR:?})를 쓰면 지금 방식 실행까지 실패한다. AWS 자격 증명은 compose 파일에 값을 적지 않고 값 없는 항목(셸에 있을 때만 넘겨주기)으로 두어, EC2에서는 인스턴스 역할을 쓰고 노트북 리허설에서만 SQS 대체물(ElasticMQ, profile local-sqs)용 가짜 값을 셸에 준다. 백엔드와 워커가 다른 프로세스라 자원 기록은 프로세스별로 지표를 읽고(--metrics-url backend=…,worker=…), 카운터 증가도 프로세스별로 센 뒤 더한다. 합쳐서 세면 한 프로세스가 다시 뜰 때 다른 프로세스의 값을 다시 센다.
6. [사실] 공용 AWS 계정에서 확인한 SQS 사정(2026-11-10 콘솔 읽기): 팀 계정은 공용 역할 ec2-project의 정책을 볼 수 없다(iam:GetRole 거부). 그래서 역할에 SQS 권한이 있는지는 큐를 만든 뒤 역할이 붙은 EC2에서 불러 봐야 안다. SQS 큐 목록은 보이고 다른 팀 큐 25개가 모두 표준 큐였다. 2026-Chalkak은 환경별 표준 큐 + DLQ를 두고 SDK 기본 자격 증명과 ec2-project로 부르며, 팀 큐 범위 권한은 담당자에게 요청하는 것으로 문서에 적었다. 운영 앱 서버와 개발·스테이징 서버에는 역할이 연결돼 있지 않았고 DB 서버만 ec2-project였다.
7. [사실] SQS 방식 로컬 리허설 결과(2026-11-10, 노트북, MongoDB 8.0.4, SQS 대체물 ElasticMQ, 커밋 1abf5c5c): 구독 1,000 × 공고 1건(모의 서버 지연 100ms)은 수락 1,000, 유실 0, 중복 0, 최대 동시 요청 20, 첫 요청부터 마지막 수락까지 5.6초, 큐 대기 평균 2.5초였다. 발송 중 워커를 강제 종료한 2,000건(지연 500ms, 초당 40건)은 유실 0, 중복 20(종료 순간 보내던 건수와 같음), 수락 공백은 종료 뒤 새 워커까지 8.9초와 lease 대기 120.6초였다. lease는 워커가 선점한 시각부터 120초이고 그 뒤 릴레이 주기(60초)를 기다리므로, 강제 종료 때 보내던 건의 복구는 종료 뒤 최대 약 3분이 걸린다. 전 구조(CF-441 리허설: 중복 20, 공백 12.7초와 60.5초)보다 lease 대기 구간이 길다. 가시성 타임아웃(60초) 뒤 다시 온 메시지 20건은 선점하지 못해 보내지 않고 지웠다. 실제 SQS 왕복은 빠진 값이라 전후 비교에는 쓰지 않는다.
