이 문서는 2026-11-10에 승인된 CF-445 후보 가운데 발송 시험에 관한 두 개(5, 7)를 정리한 기록이다. 후보 원문은 [승인 후보 스냅샷](approved-candidates.md)에 있다. 전후 비교 측정 방식과 전 구조의 재시작 동작은 CF-441 기록(`llm-wiki/raw/issues/CF-441/documents/push-dispatch-load-test.md`)이 그대로 유효하다. 실행 절차는 Source-Revision의 `loadtest/push-dispatch/README.md`를 따른다. 호스트 주소, 큐 주소, 키 값, 비밀번호, 구독 endpoint, 대화 전문은 포함하지 않는다.

## 시험 스택의 SQS 방식 (사실)

- compose의 `worker` 서비스(profile `sqs`)는 백엔드와 같은 이미지에서 워커만 켠다. 백엔드는 릴레이만 돌려 동시 발송 수 합계 20을 유지한다.
- compose는 꺼진 profile의 서비스도 변수를 푼다. 그 서비스에 필수 변수(`${VAR:?}`)를 쓰면 지금 방식 실행까지 실패한다.
- AWS 자격 증명은 compose 파일에 값을 적지 않고 값 없는 항목(셸에 있을 때만 넘겨주기)으로 둔다. EC2에서는 인스턴스 역할을 쓰고, 노트북 리허설에서만 SQS 대체물(ElasticMQ, profile `local-sqs`)용 가짜 값을 셸에 준다.
- 백엔드와 워커가 다른 프로세스라 자원 기록은 프로세스별로 지표를 읽는다(`--metrics-url backend=…,worker=…`). 카운터 증가도 프로세스별로 센 뒤 더한다. 합쳐서 세면 한 프로세스가 다시 뜰 때 다른 프로세스의 값을 다시 센다.

## SQS 방식 로컬 리허설 결과 (사실)

2026-11-10, 노트북, MongoDB 8.0.4, SQS 대체물 ElasticMQ, 커밋 `1abf5c5c`. 실제 SQS 왕복이 빠진 값이라 전후 비교에는 쓰지 않는다.

| 실행 | 조건 | 결과 |
|---|---|---|
| 1,000건 | 구독 1,000 × 공고 1건, 모의 서버 지연 100ms | 수락 1,000, 유실 0, 중복 0, 최대 동시 요청 20, 첫 요청부터 마지막 수락까지 5.6초, 큐 대기 평균 2.5초 |
| 워커 강제 종료 | 2,000건, 지연 500ms(초당 40건), 발송 중 워커 SIGKILL | 유실 0, 중복 20(종료 순간 보내던 건수와 같음), 수락 공백은 종료 뒤 새 워커까지 8.9초와 lease 대기 120.6초 |

- lease는 워커가 선점한 시각부터 120초이고 그 뒤 릴레이 주기(60초)를 기다린다. 강제 종료 때 보내던 건의 복구는 종료 뒤 최대 약 3분이 걸린다.
- 전 구조(CF-441 리허설: 중복 20, 공백 12.7초와 60.5초)보다 lease 대기 구간이 길다.
- 가시성 타임아웃(60초) 뒤 다시 온 메시지 20건은 선점하지 못해 보내지 않고 지웠다.
