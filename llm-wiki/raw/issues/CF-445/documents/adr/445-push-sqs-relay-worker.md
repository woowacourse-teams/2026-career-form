# 공고 알림 발송의 SQS 릴레이·워커 구조

## 상태

승인됨

## 날짜

2026-11-10

## 관련 Issue

- #445 공고 알림 발송의 SQS 릴레이·워커 방식 추가
- #348 공고 구독 알림 서버(전달 경로와 발송 보장 ADR)
- #439 등록 빈틈 재등록 보충
- #441 SQS 전환 전후 비교용 발송 시험 도구

## 배경

CF-348 ADR은 MongoDB 발송 문서와 스케줄러 선점(대안 B)을 택하고, 2차에서 큐와 별도 워커(대안 C)를 장애 격리와 채널 확장을 이유로 검토하라고 했다. 팀은 대안 C로 가기로 했고, 팀원 제안은 Outbox 트랜잭션, SQS FIFO, 별도 워커, 가시성 타임아웃 재시도였다. 운영 MongoDB는 단일 노드(replica set 아님)이고 dev·staging·prod가 한 호스트(t4g.micro)를 함께 쓴다. 공용 AWS 계정에서는 IAM을 직접 다룰 수 없고 EC2 공용 역할 `ec2-project`를 쓴다.

## 검토한 대안

### A. 팀원 제안 그대로: Outbox 트랜잭션 + FIFO + 가시성 타임아웃 재시도

- 장점: 공고와 발송 문서가 함께 저장되거나 함께 실패한다. 릴레이의 중복 넣기를 FIFO가 5분 동안 걸러 준다. 릴레이는 한 번만 넣으면 된다.
- 단점: 트랜잭션에 replica set이 필요해 공용 운영 DB를 재시작하고 구성을 바꿔야 한다. FIFO는 순서가 필요 없는 발송에서 동시 처리를 하려면 메시지 그룹을 잘게 나눠야 한다. 재시도 상태가 SQS 수신 횟수와 DB 양쪽에 생겨 시도 횟수와 사유를 맞추기 어렵고, 관리 화면과 시험 도구가 보는 값이 달라진다.

### B. 발송 문서를 상태 기록으로 유지 + 표준 큐 + DB 재시도 (선택)

릴레이가 보낼 때가 된 발송 문서의 id를 표준 큐에 넣고 `QUEUED`로 표시한다. 워커가 꺼내 조건부 갱신으로 선점한 건만 보내고, 결과와 다음 시도 시각을 발송 문서에 적는다.

- 장점: DB 구성을 바꾸지 않는다. 중복 메시지는 선점이 시간 제한 없이 걸러 낸다. `RetryPolicy`, 시도 횟수, 사유, 관리 화면, 시험 도구가 그대로다. `direct`로 되돌릴 수 있다.
- 단점: 등록 빈틈은 트랜잭션이 아니라 #439의 재등록 보충으로 메운다(사람이 다시 등록해야 채워진다). 재시도 건은 릴레이가 살아 있어야 다시 큐에 들어간다. DLQ에는 해석할 수 없는 메시지만 간다.

### C. 큐 없이 발송기만 별도 컨테이너로 분리

- 장점: 새 AWS 자원 없이 배포 중 발송 중단을 없앤다.
- 단점: 채널 확장(소비자 추가)과 워커 수평 확장의 기반이 생기지 않는다. 팀이 정한 방향(큐 도입)과 다르다.

## 결정

대안 B를 택한다.

- 큐는 표준 큐 + DLQ이고 메시지 본문은 발송 문서 id만 담는다.
- 발송 상태의 정본은 `push_deliveries`다. 상태는 `PENDING` → `QUEUED` → `SENDING` → `ACCEPTED`·`ABANDONED`·`PENDING`(재시도)이다.
- 중복 발송은 워커의 조건부 갱신 선점으로 막는다. 재시도 대기는 `nextAttemptAt`에 적는다.
- 발송 방식은 설정(`direct`, `sqs`)으로 바꾸고 기본값은 `direct`다. 개발·운영 적용과 릴레이·워커 배치는 후속 [Infra] Issue에서 전후 측정 결과를 보고 정한다.
- 서버는 인스턴스 역할 자격 증명으로 SQS를 부른다. 액세스 키를 만들지 않는다.

## 결과

- 효과: 워커를 별도 프로세스로 띄우면 API 서버 배포와 장애가 큐에 들어간 발송을 멈추지 않는다. 소비자를 더할 수 있는 큐가 생긴다.
- 비용: AWS SDK 의존성, 큐와 DLQ, `ec2-project`의 SQS 권한 확인(없으면 운영진 요청), 로컬 리허설용 큐 대체물, 워커 프로세스의 메모리.
- 남은 한계: 등록 빈틈은 재등록으로 채운다. 릴레이가 멈추면 새 발송과 재시도 발송이 큐에 들어가지 않는다. 워커가 죽은 건의 복구는 지금처럼 lease 120초 뒤다.
- 재검토 조건: 등록 빈틈이 운영에서 반복되면 Outbox 트랜잭션과 replica set을 별도 Infra Issue로 검토한다. 전후 측정에서 30,000건 완료 시간이 5분을 넘거나 유실·중복 기준을 못 넘으면 운영 적용을 멈추고 `direct`를 유지한다.
