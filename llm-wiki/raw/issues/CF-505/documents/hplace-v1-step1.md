# 에이치닷 v1 지원자 앱 1단계 정적 자동 기입

> Issue: [CF-505](https://github.com/woowacourse-teams/2026-career-form/issues/505)
> Collected: 2026-11-21
> Approval-Digest: 7036bd66de1e2c36d356b4a4084f8db93503281327322fad00b94f87deb3661b
> Source-Revision: 75cd91b

[승인 후보 스냅샷](approved-candidates.md)의 후보 1~5를 적는다. MRS2 실행 정책, 요청 구조, 활성 정책 버전은 Supersedes가 가리키는 CF-327 근거와 그 이전 근거를 그대로 따른다. 실제 지원값, 계정, 세션, 회사 화면 원문, 공고 제목은 적지 않는다.

## 범위 (후보 1)

- 대상은 에이치닷 v1 지원자 앱의 지원서 작성 1단계다. 호스트는 에이치닷 공급자 호스트이고 경로는 `/v1/applicant/resume-form/<숫자>`, 쿼리는 `step=1`이다.
- 프론트는 v1 플랫폼 지문(`hplaceDocumentKind() === "v1"`), 경로, `step=1`, 검증된 칸 1개 이상을 모두 확인했을 때만 지원 화면으로 본다. v1 로그인·마이페이지·2단계 이후는 계속 미지원 안내를 보인다.
- 대상 칸은 19개다: 영문이름, 생년월일, 성별, 비상연락처, 병역 상태, 입대일, 제대일, 병과, 계급, 제대구분, 군별, 장애 여부, 장애등록번호, 장애 정도, 장애 유형, 보훈 여부, 보훈번호, 보훈 관계, 국적.
- 다루지 않는 칸: 사이트가 채운 읽기 전용 칸(이름, 휴대전화, 이메일), 사진 파일, 지원 분야 묶음, 지원경로, 비상연락처 관계, 복무 기간 버튼, 편의 제공 여부, 보훈비율, 현주소(검색 모달), 취미.
- 후속 후보: v1 현주소 검색, v1 2단계(학력·경력), v1 3단계(어학·자격·경험). JOBDA와 채용 빌더는 확인한 지원서 화면이 없다.

## 화면 구조와 식별 기준 (후보 2)

- 클래스 이름 가운데 빌드 해시(`css-…`, `e1…`)는 선택자로 쓰지 않는다. 고정 `name`, 행 제목, placeholder, 선택지 글자, 요소 구조, 디자인 시스템 유틸리티 클래스(`ats-…`)만 쓴다.
- 칸 행은 첫 자식이 `span[aria-hidden="true"]`인 요소이고 그 글자가 행 제목이다. 상태 행의 제목은 `병역`, `장애여부`, `보훈여부`다.
- 텍스트 칸은 고정 `name`을 가진다. 날짜 칸은 `name`이 없어 행 제목과 placeholder로 찾는다.
- 성별은 native 라디오지만 입력 요소 클릭으로는 선택되지 않는다. 감싼 `label`을 클릭하고 `checked`로 확인한다.
- 상태 선택은 `li > button` 묶음이다. ARIA 상태가 없고 선택 표시는 클래스 두 개(`ats-bg-white`, `ats-text-gray-800`)뿐이다. 기본 선택은 비대상이다.
- 드롭다운은 `button`과, 열렸을 때만 있는 형제 `#dropdown-body` 안의 `ul > li > button[value=<코드>]`다. 선택지 목록은 열려 있을 때만 DOM에 있다. 선택하면 버튼 글자가 선택지 글자로 바뀌고 닫힌다. Escape로는 닫히지 않고 버튼을 다시 눌러 닫는다.
- 드롭다운은 선택 뒤 placeholder가 사라지므로 행 제목과 행 안 순서로 찾고, 버튼 글자가 placeholder이거나 알려진 선택지일 때만 인정한다.
- 상태를 고르면 같은 행의 하위 칸 `disabled`가 풀린다. 측정한 조합은 병역 군필, 장애 대상, 보훈 대상이다. 미필·면제·복무중이 여는 칸은 측정하지 않았고, 코드는 가정하지 않고 다음 분석에서 열린 칸만 수집한다.
- 입대일은 `YYYY.MM.DD`로 입력해도 포커스를 잃으면 `YYYY.MM`으로 바뀐다. 기입 확인은 화면이 남긴 정밀도로 비교한다.
- 계급, 제대구분, 장애 정도, 장애 유형의 코드와 글자는 MRS2 기본정보의 표와 같다(장애 유형은 v1 목록에 췌장장애가 없다).
- 조작 중 사이트로 가는 저장 요청은 없었다(자동 저장 없음).

## 정책과 전송 계약 (후보 3)

- v1은 MRS2의 단일 섹션 방식으로 붙였다. 섹션 ID는 `hplace-v1-basic`, 칸 이름은 `hplace.v1.<key>`이고 domName과 domId가 같다.
- 버튼형 위젯은 전송에서 기존 값으로 표현한다. 상태 묶음은 `input`/`radio`, 드롭다운은 `select`/`select`, 텍스트·날짜는 `input`/`text`다. `custom`으로 보내면 백엔드가 쓰기 명령을 주지 않는다. 실제 조작은 프론트 v1 writer가 한다.
- 백엔드 v1 규칙은 저장하지 않는 v1 전용 정책 객체(`HplaceV1CompanyFormPolicyFactory`)에 둔다. MRS2 저장 문서(v3, v4), `hplace-mrs2-v4.json`, `careerform.hplace.active-policy-version` 기본값은 바꾸지 않았다. `rules()`에 넣으면 새 DB의 v3·v4 내용만 달라져 환경 사이가 어긋나기 때문이다.
- MRS2와 뜻이 같은 칸의 binding은 MRS2 detail 규칙에서 가져와 목록이 어긋나지 않게 했다. 영문이름은 안내 문구가 없어 기존 사용자 결정대로 성 이름 순서 한 가지만 보낸다.
- 군별은 프로필 표준 라벨과 화면 글자가 달라 대응표를 둔다: 해병대→해병, 전투경찰→전경, 해양경찰→해경, 의무경찰→의경. 나머지는 같은 글자다.
- 백엔드는 단계를 알 수 없다. 쿼리는 전송하지 않고 경로는 `/v1/applicant/resume-form/*`로 접힌다. 백엔드는 섹션 ID와 칸 이름 허용 목록으로만 판정하고, `step=1` 확인은 프론트가 한다.
- 병역·장애·보훈 상태는 stage 1 driver다. 1차 분석에서 상태를 고르고, 잠금이 풀린 하위 칸은 2차 분석에서 기입한다. 에이치닷 분석 한도 3회 안에서 끝난다.
- 선택지에 정확히 대응하는 항목이 없으면 드롭다운을 닫고 그 칸만 `OPTION_UNMATCHED`로 보고한다. 선택지 목록이 열려 있을 때만 있어서 이 판정은 검토 단계가 아니라 기입 단계에서 나온다.
- 화면에 다른 값이 이미 있으면 덮어쓰지 않는다. 상태 묶음의 기본값 비대상은 같은 행의 하위 칸이 모두 비어 있을 때만 프로필 값으로 바꾼다.
- 저장, 임시저장, 이전·다음, 단계 버튼, 이력서 불러오기, 주소입력, 파일 입력은 누르지 않는다.

## 실측과 한계 (후보 4)

- 2026-11-21 v1 테넌트 1곳의 1단계에서 로컬 백엔드와 로컬 빌드 확장으로 실측했다. 분석은 ADAPTER·COMPLETE로 2회(8칸, 19칸 모두 일치)였고 18칸이 채워졌다. 남은 1칸(비상연락처)은 프로필 값이 없는 것으로 판단했다(패널의 내 정보에 항목 없음, 추정).
- 같은 화면을 범용 경로로 보낸 실험에서는 16칸 수집, 14칸 연결, 2칸 기입이었다. 범용 실행기는 버튼형 상태 선택과 잠긴 하위 칸을 다루지 못했다.
- 실측 중 사이트로 가는 GET 이외 요청은 0건이었다. 읽기 전용 칸과 범위 밖 칸은 바뀌지 않았고 2단계는 미지원 안내를 유지했다.
- 확인한 테넌트는 1곳이다. 다른 테넌트는 칸 구성과 선택지가 다를 수 있다. 칸 단위로 검증해 다르면 그 칸만 제외하고, 화면에 있고 열려 있는데 구조가 다른 칸은 `입력 불가(화면 구조 확인 불가)`로 보인다.
- 국적은 대한민국만 대응한다. 다른 국적이 이미 선택돼 있으면 그 칸은 구조 미확인으로 보인다.
- 배포 순서는 확장 먼저, 백엔드 다음이다. 구 확장은 v1에서 미지원 화면으로 먼저 끝나므로 백엔드 변경의 영향을 받지 않는다.

## 실행 정책 조회의 경로 검사 (후보 5)

- 확장 백그라운드(`policy/background.ts`)는 정책 조회 요청의 경로가 `sender.url`의 경로와 같을 때만 받아들였다. `sender.url`은 문서를 처음 연 주소이고 같은 문서 안 주소 변경(SPA 라우팅)을 따라가지 않는다.
- 그래서 새 로드 없이 경로가 바뀐 화면에서는 조회가 `BAD_REQUEST`로 끝나고 패널이 "자동 기입을 시작하지 못했어요"를 보였다. v1 지원자 앱은 로그인 화면과 지원서 화면이 같은 문서 안에서 바뀐다.
- 호스트 일치 검사는 유지하고 경로는 형식(`/`로 시작, `?`와 `#` 없음)만 검사하도록 바꿨다. 조회에는 요청이 담은 현재 경로를 쓴다. 확장에 `tabs` 권한이 없어 탭의 현재 주소와 대조하는 방법은 쓰지 않았다.
- 이 변경은 모든 사이트의 정책 조회에 적용된다. 정책 내용은 호스트와 경로로 정해지는 공개 실행 규칙이고, 페이지는 자기 경로를 history API로 바꿀 수 있으므로 경로 일치 검사가 막던 것은 없다고 판단했다.
- v1 로그인 화면을 새로 로드한 뒤 주소만 바꿔 확인했다. 수정 전에는 시작 실패, 수정 후에는 정상(미지원 안내)이었다. 로그인 뒤 지원서로 넘어가는 실제 경로는 계정이 필요해 확인하지 못했다.
