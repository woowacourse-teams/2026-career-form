# CF-515 승인 후보 스냅샷

> Issue: [CF-515](https://github.com/woowacourse-teams/2026-career-form/issues/515)
> Collected: 2026-11-25
> Approval-Digest: 918029b3d2478708af28839edf84bd711b3bd301b23152860c9526732dccab75

worktree 체크포인트에 기록한 후보 네 개의 원문이다. 사람이 2026-11-25 Wiki 반영을 요청해 확정했다.

1. 등록 완료 표시 규칙: 공고 문서에 deliveriesReady를 둔다. 새 공고는 false로 저장하고 대상 구독의 발송 문서를 모두 저장한 뒤에만 true로 바꾼다. 공고 문서 하나만 고치므로 단일 노드 MongoDB에서도 원자적이다. 저장 순서는 공고 저장(미완료), 발송 문서 저장, 완료 표시로 고정해 어느 지점에서 끊겨도 공고가 미완료로 남고, 완료인데 발송 문서가 빠진 상태는 생기지 않는다. 필드가 없는 기존 공고는 완료로 보아 데이터 마이그레이션이 없다. 조회는 deliveriesReady가 false와 같은지로 걸러 기존 공고가 걸리지 않게 하고 인덱스는 (deliveriesReady, closesAt)이다.
2. 발송기 주기 보충: 발송기는 주기 시작에 완료 표시가 false이고 마감 전인 공고를 등록 시각 순으로 batch-size만큼 읽어 빠진 대기 발송을 채운 뒤 완료로 바꾼다. 대상과 예정 시각은 CF-439 같은 링크 재등록 보충과 같다(공고 직무의 대상 구독 가운데 공고 등록 시각까지 가입한 구독, 공고 예정 시각). 이미 있는 공고 × 구독 쌍은 push_deliveries 유일 인덱스가 건너뛰어 반복 실행이나 진행 중인 등록과 겹쳐도 쌍마다 발송 문서는 하나다. 보충 실패는 로그만 남기고 그 주기의 발송을 막지 않으며 다음 주기에 다시 시도한다. 마감이 지난 미완료 공고는 채우지 않는다. 같은 링크 재등록 보충도 채운 뒤 완료로 바꾼다. 이로써 CF-439가 SQS 전환 설계로 미뤘던 빠진 발송의 자동 감지·복구를 큐 없이 해결했다.
3. 선택 이유와 한계: Replica Set 전환과 트랜잭션은 운영 DB 재시작과 인증 설정 변경이 필요해 고르지 않았고, 발송 문서를 공고 문서에 넣는 방식은 발송마다 구독자 전원의 상태가 담긴 문서 하나를 고쳐야 해 동시 발송과 맞지 않아 고르지 않았다. 두 저장을 묶지 않고 '완료된 공고는 대상 구독의 발송 문서를 모두 갖는다'는 조건만 지킨다. 복구 시점은 발송기의 다음 주기다. 서버가 살아 있으면 주기(기본 60초) 안이고, 서버 재시작이나 배포로 끊겼으면 다시 뜬 뒤 첫 주기(기동 10초 뒤)다. 끊긴 공고의 알림은 그때까지 늦어진다. 등록 누락이 운영에서 실제로 발생한 기록은 없다.
4. 검증과 관측: 공고 저장 직후, 발송 문서 저장 도중, 완료 표시 직전에 저장소 호출 장애를 주입하는 테스트(RegistrationRecoveryTest, 메모리 저장소와 StoreFaults 프록시)로 다음 주기에 빠진 쌍만 채워지고 반복 보충에도 중복이 없음을 확인했다. 실제 MongoDB로는 저장소 계약 테스트(미완료 공고 조회, 완료 표시)만 돌렸고, 실제 프로세스 강제 종료 리허설은 하지 않았다. 로그 POSTING_REGISTRATION_RECOVERED postingId targets의 targets는 다시 확인한 대상 구독 수이지 새로 만든 발송 수가 아니다. POSTING_REGISTRATION_RECOVERY_FAILED는 미완료 공고 조회 또는 한 공고의 보충 실패다. 진행 중인 정상 등록과 주기가 겹치면 RECOVERED 로그가 남을 수 있다.
