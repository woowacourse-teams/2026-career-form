# Greeting 검색의 직접 입력 선택지 구조와 v19 허용 범위, 검색 실패 사유 코드

> Issue: CF-346
> Collected: 2026-10-25
> Approval-Digest: fe9263182f4be99fa243d40d23b9a65061d4226063cc78707b5149c59599feb3
> Source-Revision: d5a5005cc47d628b9044e460e0956021df523c90

이 문서는 2026-10-25 CF-346([FE] Greeting 검색 칸에 정확한 목록 항목이 없을 때 직접 입력 선택지 미사용 문제 수정)에서 승인된 후보 1·2·4·5를 Greeting 어댑터 관점에서 수집한 기록이다. Approval-Digest는 [승인 후보 스냅샷](approved-candidates.md) 전체 UTF-8 바이트의 SHA-256이다. 바꾸지 않은 내용(열린 Ark UI 팝오버의 숨김 수집과 닫기, 검색 서버 액션 요청 구조, v18 장애 정도 별칭, 필드 확장과 검증 범위)은 Supersedes가 가리키는 CF-334 근거와 그 앞의 근거를 따른다. 실제 지원값·계정·세션은 포함하지 않으며, 전수 조사 값은 합성값이고 컬리·카카오게임즈 지원서는 공개 공고의 빈 양식이다.

## 승인 후보

- (후보 1) Greeting 검색 목록은 정확한 항목이 없으면 유사 이름 20개 뒤에 `직접 입력하기:“값”`(코드 `[[new]]`)을 붙인다. 고교·대학·대학원 학교명, 전공명, 회사명, 자격증명이 같은 구조고, 시험명·국적에는 직접 입력 선택지가 없다. 허용은 정책 `componentPolicy.patterns.directSearch`가 정하고 v19부터 대학·대학원 학교명과 전공명이 들어간다.
- (후보 2) 검색 함수가 사유 없이 실패하면 기본 코드 `SEARCH_UNCONFIRMED`가 붙는다. CF-346부터 `SEARCH_NO_EXACT_MATCH`·`SEARCH_AMBIGUOUS`·`SEARCH_NO_RESULTS`·`SEARCH_TIMEOUT`을 구분해 보고한다.
- (후보 4) 마지막 기입 뒤 재분석의 리뷰 계획이 이미 같은 값인 칸을 다시 승인해 같은 값을 다시 쓴다. 범용 흐름의 별도 후보다.
- (후보 5) 카카오게임즈 양식의 기존 미해결 항목 8칸은 검색 정확 일치와 무관하다.

## 근거

### 직접 입력 선택지의 구조

- Greeting(Component forms) 검색 콤보박스는 입력값으로 서버 액션 검색을 보내고 결과 목록을 Ark UI 팝오버에 그린다. 정확히 같은 정식 항목이 없으면 유사 이름 20개(`…학과`, `…전공`, `응용…` 등) 뒤에 21번째 항목으로 `직접 입력하기:“<입력값>”`을 붙인다. 이 항목의 `data-value`는 `[[new]]`이고, 고르면 `[[new]]-<값>`으로 바뀌며 입력에는 값이 그대로 남는다. 사이트에는 코드 없는 자유 입력으로 저장된다.
- 2026-10-25 전수 조사(정확 일치가 없는 합성값 프로필, 읽기 전용 관찰)에서 종류별 구조는 다음과 같았다.

| 종류 | 칸 | 정확 항목 없음일 때 사이트 | 수정 전(v18) 확장 | v19 |
| --- | --- | --- | --- | --- |
| 대학 학교명 | `educationalBackground.universities.<n>.schoolName` | 유사 목록 20 + 직접 입력 선택지 | 선택 없이 종료, 기본 코드 | 직접 입력 허용 |
| 대학원 학교명 | `educationalBackground.graduateSchools.<n>.schoolName` | 동일 | 동일 | 직접 입력 허용 |
| 전공명 | `….majors.<n>` | 동일 | 동일 | 직접 입력 허용 |
| 고교 학교명 | `educationalBackground.highSchool.schoolName` | 유사 목록 20(이름+지역) + 직접 입력 선택지 | 직접 입력 선택 성공(기존 허용 종류) | 변경 없음 |
| 회사명 | `workHistory.workExperiences.<n>.companyName` | 직접 입력 선택지 제공 | 직접 입력 선택 성공(기존 허용 종류) | 변경 없음 |
| 자격증명 | `languagesCertificationsAndOtherActivity.certificatesLicenses.<n>.credentials` | 유사 목록 20 + 직접 입력 선택지 | 직접 입력 선택 성공(기존 허용 종류) | 변경 없음 |
| 시험명 | `….certifiedLanguageTests.<n>.testName` | 닫힌 목록 20, 직접 입력 선택지 없음 | 기본 코드 | 허용 안 함, `SEARCH_NO_EXACT_MATCH` 보고 |
| 국적 | `basicInformation.nationalityCode` | 전체 250개를 먼저 그린 뒤 클라이언트 필터로 0개, 직접 입력 선택지 없음 | 기본 코드 | 허용 안 함, `SEARCH_NO_RESULTS` 보고 |

- 컬리 양식(대학·대학원·전공명·회사명)은 1차, 카카오게임즈 양식(고교·자격증명·시험명·국적)은 2차에서 관측했다. 컬리 기본 합성 프로필에서는 전공명 세 칸(대학 부전공, 전문대학 주전공, 대학원 부전공)만 정확한 항목이 없어 수정 전 50회 모두 비었고, 같은 양식의 다른 전공명 네 칸은 목록 첫 항목이 정확히 같아 매번 채워졌다. 백엔드 분석은 일곱 칸 모두 `MATCH`·`SEARCH_SELECTION`으로 정상이었다.

### v19 허용 범위

- 직접 입력 허용은 `workflow-search.ts`의 `canCreateSearch`가 `componentPolicy.patterns.directSearch` 정규식으로 정한다. v18까지는 고교 학교명·회사명·자격증명만 있었고, v19는 대학·대학원 학교명과 전공명을 더한다. fieldRule·actionRule은 v18과 같다. 시드(`startup-policy-seed-v1.json`), 브라우저 정책 자원(`greeting-browser-v1.json`, 로컬 factory v9), 프론트 fixture가 같은 패턴을 쓴다. 자원과 시드의 `freshDefaults`·`searchKinds`는 그 전부터 달랐고 CF-346에서 맞추지 않았다.
- 직접 입력 경로의 검증은 기존 고교·회사·자격 경로와 같다. `matchesSearchOption`은 `[[new]]` 선택지를 라벨이 `직접 입력하기:“<프로필 값>”`과 정확히 일치하고 유일할 때만 받고, 선택 뒤 입력값과 체크 상태를 확인한다. 정확한 정식 항목이 하나 있으면 그 항목을 고르고, 유사 이름은 고르지 않는다(퍼지 매칭 없음). 정식 항목이 여러 개 정확히 일치하면 직접 입력으로 우회하지 않는다.
- 프로필에 카탈로그 신원(KESS 학교 코드)이 확정된 학교는 `matchesOption`이 `[[new]]`를 거부하므로 v19 뒤에도 직접 입력으로 바뀌지 않는다. 합성 프로필의 학교는 신원이 없어 이름만 비교한다.
- 시험명은 사이트 목록이 닫혀 있고 국적은 전체 목록을 클라이언트 필터로 비우는 구조라 둘 다 직접 입력 선택지가 없다. v19는 두 종류를 허용하지 않고 사유 코드만 정확히 보고한다.

### 검색 실패 사유 코드

- 검색 함수 `search()`는 `report` 콜백으로 실패 사유를 보고하고, 아무 사유도 보고하지 않으면 `workflow.ts`의 래퍼가 기본 코드 `SEARCH_UNCONFIRMED`("목록 선택을 확인하지 못했어요")를 붙인다. 수정 전에는 정확 항목 없음·중복·빈 목록이 모두 이 기본 코드로 뭉개졌다.
- CF-346부터 옵션 대기 중 렌더된 코드 있는 항목 수를 세고, 대기가 끝난 뒤 `current()`와 입력값이 그대로일 때만 보고한다. 결과가 `null`(정확 항목 여러 개)이면 `SEARCH_AMBIGUOUS`, 마지막 스냅샷에 항목이 있었으면 `SEARCH_NO_EXACT_MATCH`("등록한 값과 정확히 일치하는 검색 결과가 없어요"), 한때 항목이 있었다가 비었으면 `SEARCH_NO_RESULTS`, 팝업은 열렸는데 항목이 끝내 없으면 `SEARCH_TIMEOUT`이다. 기본 코드는 팝업이 열리지 않은 경우에만 남는다.
- 결과 패널 집계는 같고 문구만 바뀐다. 카카오게임즈의 동명 고교(세 지역, 합성 프로필 한계)는 "여러 개"로, 시험명 불일치는 "정확히 일치하는 결과가 없어요"로 보인다.
- 회귀 테스트 `workflow-search-no-exact-match.test.ts` 11개: 전공명·대학·대학원 학교명 직접 입력 선택, 정확 항목 우선, 직접 입력 없음 → `SEARCH_NO_EXACT_MATCH`, 정확 항목 2개 → `SEARCH_AMBIGUOUS`, 렌더 뒤 빈 목록 → `SEARCH_NO_RESULTS`, 항목 없는 열린 목록 → `SEARCH_TIMEOUT`, 비허용 종류(시험명)와 v18 패턴에서는 직접 입력을 고르지 않음. 백엔드 `StartupPolicySeedGreetingV19Test`는 v19가 v18에서 패턴 하나만 다르고 활성 버전이 19임을 확인한다.

### 마지막 기입 뒤 같은 값 재기입 (별도 후보)

- 컬리 10회 중 5회에서 마지막 기입(SET_TEXT 12건) 뒤 재분석이 같은 12건을 다시 승인해 한 번 더 기입했다. 진단 로그(`VITE_LOCAL_WORKFLOW_DIAGNOSTICS=1`)로 본 원인은 페이지가 기입 뒤 입력 노드를 다시 그려 재수집이 변경으로 판정되고, 재분석의 리뷰 계획이 현재값이 이미 프로필 값과 같은 칸도 `available`·선택 상태로 다시 승인하는 데 있다. 구조 서명이 반복되면 멈추므로 회차당 3~5회로 끝난다. 상태 드라이버(검색·날짜·버튼)는 완료 키가 있어 다시 돌지 않는다.
- Greeting 검색 문제가 아니라 범용 재분석·리뷰 계획 흐름이라 CF-346에서 고치지 않고 별도 후보로 남긴다. 수정 전 10회 중 1회에서 숨김 복귀 뒤 대학원 주전공명이 비어 끝난 것은 완료 키가 어긋나 검색 드라이버가 다시 돌았을 가능성이 있으나 로그가 없어 확정하지 못했다.

### 카카오게임즈 기존 미해결 항목

- v19 빌드(d5a5005, 로컬 스택 활성 19)의 기본 합성 프로필 1회에서 확인 필요 12 → 9. 전공명 세 칸이 해소됐고, 남은 9개 중 동명 고교 1개는 "여러 개"로 정확히 표시된다. 나머지 8개(어학 2·자격 3 취득일 "선택값이 유지되지 않았어요", 어학 등급/점수 선택지 불일치 1, 회화수준 2)는 2026-10-24 기본 프로필 실행에도 똑같이 있던 기존 항목으로 검색 정확 일치와 무관하다.

## 한계

- 전수 조사는 컬리·카카오게임즈 두 양식의 1회 관측이다. 다른 Greeting 기업 양식에서 직접 입력 선택지의 유무가 같다고 입증하지는 않았다.
- v19 실사이트 검증은 로컬 스택(seed·DB 활성 19)과 로컬 API 빌드로 했다(컬리 4회 + 최종 1회 완료 74·확인 필요 0, 카카오게임즈 1회). 머지 뒤 dev 배포 빌드의 재확인은 남아 있다.
- 직접 입력으로 저장된 전공명이 지원서 미리보기에서 어떻게 보이는지는 사람이 확인한다.
