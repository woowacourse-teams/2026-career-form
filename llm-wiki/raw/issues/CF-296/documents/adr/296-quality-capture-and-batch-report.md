# 품질 가공의 비동기 경계

## 결정과 이유

CF-288은 저장과 집계를 요청 대기에서 분리했다. CF-296은 응답 전에 남아 있던 구조 투영, 해시, 사유와 카운트 계산, 품질 크기 확인용 JSON 직렬화도 작업자로 옮긴다. 요청 경로에는 비식별 불변 캡처와 큐 접수, 개인정보 정제, 실제 HTTP 응답 직렬화가 남는다. 원본 요청, 응답 객체를 작업자가 나중에 읽지 않는다. 기존 저장 형식과 구조 fingerprint v1은 유지한다.

## 보관과 작업 정책

큐 64개, 보관 4MiB, 이벤트 128KiB, 만료 30초, 작업자 1개, 집계 60초를 유지한다. 기본 설정에서 캡처 중 최대 2MiB를 먼저 예약하고 캡처 후 보수적 객체 예산으로 줄인다. 직렬화 바이트와 객체 메모리를 구분하며 이 예산은 전체 JVM heap 상한이 아니다. 공간이 없으면 품질 기록을 버리고 분석 응답을 계속한다.

배치는 항목 사이 기존 100ms 지연 재접수로 작업자를 양보하고 준비된 스냅샷부터 처리한다. 포화, 실패, 만료로 일부 기록이 유실될 수 있다. 실행 번호와 토큰의 별도 등록, 지연 집계와 부분 유실 허용 정책은 유지한다.

## 적용과 측정

단건 호환 백엔드를 먼저 배포한 뒤 새 확장을 적용한다. 202는 접수이며 저장 완료가 아니다. HTTP 서버 span과 버튼 시작, 완료 표식으로 비교한다. 응답 이후 비동기 span을 포함하는 trace 전체 Duration은 응답 시간이 아니다. 보고 횟수, 드랍, 실패, 대기, 보관량을 함께 확인한다. 배포 후 개선량과 부하 안전성은 아직 측정하지 않았다.

## 검토한 대안

요청 경로에서 품질 가공을 마친 뒤 접수하는 기존 방식 대신 비식별 최소 캡처 직후로 비동기 경계를 옮긴다. 보고는 스냅샷별 고정 분할 대신 실행 단위 크기 제한 배치를 사용한다. 같은 백엔드와 제한 큐를 유지하며 큐 상한 증설, 무제한 배치, 전량 영속 보장은 도입하지 않는다.
