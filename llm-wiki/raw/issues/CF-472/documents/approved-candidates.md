## 후보 1

[기술] 범용 수집은 페이지 이름과 같은 글자를 섹션 제목과 섹션 머리 라벨로 쓰지 않는다(2026-11-17, CF-472). 새 topic `generic-page-title-exclusion`에 기록한다.

- 문제: 공고 제목이 범용 요청의 섹션 제목(칸 분석의 `displayName`, 섹션 분류의 `title`)이나 칸의 `section-heading` 라벨로 들어가, 같은 양식인데도 서버의 섹션 결과 캐시(CF-467) 키가 공고마다 달라졌다. 나인하이어 양식은 인적 사항 칸 바로 위의 굵은 글씨가 공고 제목이라 구간 제목이 됐고(문서 제목은 `<공고 제목> | <회사>`), 우아한형제들 비회원 양식은 양식 위 `h2`가 공고 제목이라 섹션 밖 마지막 확인 문항 한 칸의 섹션 머리 라벨이 됐다(문서 제목은 사이트 이름).
- 규칙: 글자가 페이지 이름 전체와 같거나, 공백으로 둘러싸인 구분자(`|`, `-`, `–`, `—`, `:`, `·`)에서 잘린 앞부분·뒷부분과 같으면 섹션 제목 후보에서 뺀다. 페이지 이름은 (1) `document.title`, (2) 페이지 맨 위 제목이다. 맨 위 제목은 문서의 첫 비어 있지 않은 제목 요소(`h1`~`h6`, `[role=heading]`)이고, 그 요소와 첫 입력 칸 사이에 다른 제목 요소가 있을 때만 인정한다. 첫 입력 칸 바로 위 제목은 그 칸 묶음의 이름이라 대상이 아니다.
- 보호: 양식 용어 사전(프로필 범주·섹션·필드 이름 포함)과 정확히 같은 글자는 페이지 이름과 같아도 남긴다(문서 제목이 `학력 | 회사`인 단계별 양식).
- 적용 위치: `frontend/src/autofill/dom/page-title.ts`의 `pageTitleMatcher`, `semantic-context.ts`의 `pageTitleHeadingMatcher`(사전 보호 포함)와 `genericContextLabels`, `generic/section-segments.ts`의 `headingsBetweenFields`. 정적 정책 경로(`contextLabels`, `sectionName`), 요청 형식, 서버 캐시 키는 그대로다.
- 버린 대안: 문서 제목 일치만(우아한형제들은 문서 제목에 공고 제목이 없어 못 잡음), 구조만으로 양식 전체를 덮는 제목 제거(나인하이어는 칸 바로 위 제목이라 못 잡고, 단일 섹션 양식의 제목을 지움), 양식 용어 사전에 없는 제목 제거(자유 문구 제목 대부분을 지우고, 공고 제목에 `경력`·`test` 같은 용어가 들어 있어 가르지 못함).
- 확인: 공개 지원서 화면 12개(카카오스타일 5, 잉카인터넷 1, 퍼즐원스튜디오 1, 우아한형제들 비회원 5)를 수정 전후 수집 코드로 읽어 비교했다(읽기 전용, 클릭·입력·서버 호출 없음). 공고 제목이 수집되던 11개는 화면마다 달라진 곳이 하나였다. 나인하이어 6개는 첫 구간 제목이 공고 제목에서 `지원서 작성`으로, 우아한형제들 5개는 마지막 확인 문항의 섹션 머리 라벨이 공고 제목에서 없음으로 바뀌었다. 공고 제목이 섹션 제목이 아니던 퍼즐원스튜디오(칸 1개 양식)는 달라진 곳이 없다. 평가 데이터셋 `generic-matching` v5의 사례 5개는 요청 지문이 그대로여서 새 버전을 만들지 않았다. 서버 응답(분류와 매핑)은 이 확인에 없고 머지 뒤 실사이트 측정에서 본다.
- 한계: 문서 제목에 없고 첫 칸 바로 위에 있는 공고 제목은 잡지 못한다. 머리말의 검색창처럼 입력 칸이 제목보다 앞에 있으면 맨 위 제목 규칙이 걸리지 않는다. 제목이 두 단계인 페이지에서 맨 위 제목이 보호자처럼 다른 사람을 가리키면 섹션 밖 칸의 라벨에서 그 문맥이 빠진다. 굵은 안내 문구(회사 이메일, 보유 기간 문장)가 구간 제목이 되는 것은 그대로라 같은 플랫폼 다른 회사의 동의 구간은 계속 다르다. 확인한 플랫폼은 둘이다.

## 후보 2

[기술] CF-472에서 코드로 확인한 사실(2026-11-17). topic `generic-page-title-exclusion`의 payload에 함께 기록한다.

- 범용 칸 분석 요청의 `sections[].displayName`, 섹션 분류 요청의 `title`, 준비 결정 요청의 `sectionTitle`은 모두 `segmentGenericSections`의 구간 제목에서 온다(`structure-loop.ts`의 묶음 제목도 구간 제목이다). 구간 제목은 칸 앞의 마지막 제목 요소(태그 제목, 또는 굵기 600 이상이거나 다음 칸의 라벨보다 글자가 큰 30자 이하 글자)다. 그래서 구간 제목에서 빼면 세 요청에서 함께 빠진다. `metadata.ts`의 `sectionName`과 `semantic-context.ts`의 `nearestStructuralHeading`은 정적 정책 경로용이라 범용 요청에 쓰이지 않는다(Issue #472 배경의 수집 위치 표기와 다르다).
- 범용 칸의 `section-heading` 라벨은 `genericContextLabels`가 칸에서 위로 8단계까지 올라가며, 직속 제목과 한 단계 감싼 제목의 글자가 하나뿐인 첫 조상에서 가져온다.
- 평가 데이터셋 v5의 우아한형제들 fixture는 양식 영역만 담아 공고 제목 요소가 없다. 그래서 기존 fixture로는 이 문제가 재현되지 않고, 수정해도 데이터셋 요청이 바뀌지 않는다. `woowahan-dataset.test.ts`, `nhn-dataset.test.ts`가 요청 지문을 고정하므로 수집 변경이 데이터셋에 닿으면 이 테스트가 실패한다.
- 요청 수준 테스트는 `evaluation/capture/record-calls.ts`의 `recordGenericCalls`로 제품 범용 흐름을 jsdom에서 그대로 돌려 `snapshotId`를 뺀 요청 지문을 비교한다. 굵은 글씨 제목은 jsdom에서 인라인 `style`로 재현된다.
- 수집 코드만 묶어 실제 화면에서 읽는 진단: Vite 라이브러리 빌드(IIFE)로 `collectFieldsSnapshot`과 `segmentGenericSections`를 묶고 Playwright로 공개 화면에 넣어 실행하면 클릭·입력·서버 호출 없이 구간 제목과 라벨을 읽을 수 있다. 저장소에는 넣지 않았다.

## 후보 3

[기술] 서버 섹션 결과 캐시의 2026-11-17 실측 보고와 CF-467 ADR 기대의 정정(CF-472). topic `generic-section-analysis-cache`의 새 Current raw에 기존 현재 상태와 함께 기록한다. 머지된 CF-467 raw는 고치지 않는다.

- 조건: 개발 서버(develop 104b4795, PR #468), 실제 공급자, 확장의 개발 서버용 빌드, 측정용 합성 프로필, 분석 단계만 실행(칸 분석 응답을 확장에 전달하지 않아 글자 칸 기입 0건). 캐시 없음 호출 수는 저장소의 분석기와 캐시 코드에 호출만 세는 가짜 공급자를 끼운 모형이 센 값이고, 관측은 서버 응답의 `jevCalls`다.
- 합격 기준 7개(측정 전 고정)를 모두 통과했다. 동일성(재전송한 칸 3,228개 중 다른 칸 0), 예측 일치(배포 뒤 요청 104건 모두 모형 예측 = 서버 호출 수), 재분석(같은 요청 재전송 71건 모두 호출 0회), 음성 대조(첫 섹션 제목만 바꾸면 그 섹션만 실패), 속도(전부 적중한 요청의 서버 분석 80회 중앙값 8ms), 무간섭(카운터가 매 시점 모형과 같음), 안전(22회 실행 모두 글자 칸 기입 0, 금지 클릭 0, 폼 제출 0).
- 칸 분석의 공급자 호출 수:

| 시나리오 | 캐시 없음 | 관측 | 섹션 적중 |
|---|---|---|---|
| 처음 보는 양식(우아한형제들 공고 1) | 21 | 21 | 0/16 |
| 같은 회사의 다른 공고(우아한형제들 공고 2~5) | 80 | 9 | 55/62 |
| 같은 공고의 다른 사용자(우아한형제들 공고 1~5) | 101 | 0 | 78/78 |
| 같은 공고 재실행(우아한형제들 공고 1~5) | 101 | 0 | 78/78 |
| 같은 회사의 다른 공고(카카오스타일 공고 2~5) | 14 | 6 | 8/14 |
| 같은 플랫폼의 다른 회사(퍼즐원스튜디오, 잉카인터넷) | 4 | 4 | 0/4 |

- 확장 실행 한 번(첫 서버 호출부터 칸 분석 응답까지)은 처음 3,795ms, 전부 적중한 실행 10회 중앙값 1,346ms다. 남는 시간은 캐시 대상이 아닌 섹션 분류 3건과 준비 결정 2건이다.
- 정정: CF-467 ADR은 키에서 host를 뺀 이유로 "같은 채용 플랫폼을 쓰는 회사들이 답을 나눠 쓴다"를 들었지만 이 표본에서는 확인되지 않았다(같은 플랫폼의 다른 회사 적중 0/4). 원인은 확장이 공고 제목을 섹션 제목이나 섹션 머리 라벨로 보내 키가 공고마다 달라진 것이다. 같은 이유로 같은 회사의 다른 공고도 공고마다 섹션 하나가 실패했다. host를 뺀 것 자체는 손해가 없다. 서버의 글자 정제(`RawLabelMask.mask`, `GenericProfileSemantics.project`)는 공고 제목을 거르지 못한다.
- 모형 계산(서버 호출 없음): 나인하이어 요청 7건에서 첫 섹션 제목이 공고와 무관하면 호출이 21회에서 8회가 된다(실제 13회).
- CF-472가 확장의 범용 수집에서 공고 제목을 뺐다(topic `generic-page-title-exclusion`). 수정 뒤 실측은 머지 뒤에 재므로 이 기록에는 없다.
- 한계: 회사 네 곳, 개발 서버, 하루 측정이다. 처음 분석은 요청마다 한 번만 쟀다. 운영 적중률은 재지 않았다. 요청과 응답 본문은 보존하지 않았다.
