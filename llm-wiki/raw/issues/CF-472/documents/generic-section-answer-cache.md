# 범용 섹션 분석 캐시: 실측과 공고 제목 문제

> Issue: [CF-472](https://github.com/woowacourse-teams/2026-career-form/issues/472)
> Collected: 2026-11-17
> Approval-Digest: e9f2d655d212b195599e50e1d814da78a9c8eb9e98efeb602478f48816ec6f67
> Source-Revision: a8a59f31

범용 섹션 분석 캐시의 현재 상태에 2026-11-17 실측과 CF-467 ADR 기대의 정정을 더한다. [승인 후보 스냅샷](approved-candidates.md)의 후보 3을 적는다. 두 캐시의 구성은 CF-467 payload(범용 섹션 분석 캐시: 확장 쪽과 서버 쪽)에서 달라지지 않았고, 그 payload의 구현 중 확인한 사실과 테스트 주의, CF-467 ADR의 결정은 그대로 유효하다. 달라진 것은 ADR이 기대한 효과 하나에 대한 실측과, 그 원인을 없앤 확장 쪽 수정이다.

## 두 캐시의 현재 상태 (CF-467에서 그대로)

확장 쪽 캐시(#244)는 그대로다. 섹션 지문, 제목, 상위 제목, 반복 행 여부, 칸별 visibility/disabled/readonly/inert를 키로 쓰고, 워크플로우 실행 객체별 WeakMap과 URL로 수명을 정한다. 실패와 reason이 있는 칸 응답은 저장하지 않는다.

서버 쪽 캐시(#467)를 더했다. `SectionAnswerCache`가 공급자에 보내는 내용(모델 이름, 섹션 상태, 선택 기준)을 Map 키 정렬 JSON으로 직렬화한 SHA-256을 키로, 질문 번호별 선택과 확신도를 값으로 둔다. `ChoiceFieldResolver.resolveSection`이 공급자를 부르기 전에 찾고, 모든 질문에 답을 받았을 때만 넣는다(판단 보류는 넣고, 공급자 실패, 허가 대기 초과, 토큰 한도로 답이 빠진 섹션은 넣지 않는다). 답을 `candidateId`에 붙이는 일과 후처리는 요청마다 한다. Spring이 만드는 운영 분석기에만 붙고 평가용 사본(`withModel`, `withBatching`)에는 붙지 않는다.

둘의 차이:

| | 확장 쪽(#244) | 서버 쪽(#467) |
|---|---|---|
| 사는 범위 | 한 실행, 한 URL | 백엔드 프로세스(배포나 재시작까지), 기한 7일, 섹션 5,000개 |
| 키 | 섹션 지문, 제목, 상위 제목, 반복 여부, 칸 상태 | 공급자에 보내는 내용의 해시(모델 이름, 섹션 상태, 선택 기준) |
| 나눠 쓰는 대상 | 같은 사용자의 같은 실행 | 모든 사용자, 모든 사이트 |
| 줄이는 것 | 서버 요청 | 공급자 호출 |
| 저장하는 것 | 서버 응답(분류와 매칭 결과) | 공급자의 답(선택과 확신도) |

저장 위치는 프로세스 안의 Caffeine이다. Redis를 쓰지 않은 까닭은 운영 서버가 한 대라서 서버 사이에 나눌 것이 없기 때문이다. Redis는 새 컨테이너, 접속 설정, 장애와 지연 처리, 키 버전 관리, 배포 구성 변경을 치른다. 캐시가 사라져도 다시 분석하면 되고, 배포로 비워지는 것이 옛 코드와 옛 프롬프트의 답을 지운다. MongoDB도 직렬화와 조회 왕복, 키 버전 관리가 들어 버렸다.

설정은 `career-form.analysis.jev.section-cache`의 `enabled`(true), `max-sections`(5000), `ttl`(7d)이고 배포 구성은 환경 변수를 전달하지 않는다. 지표는 카운터 `career.form.analysis.section.cache`의 `outcome`=`hit`|`miss`다. 응답 형식은 그대로이고 전부 적중한 응답은 `COMPLETE`에 `jevCalls` 0이다.

측정(`GenericSectionAnswerCacheDatasetTest`, 데이터셋 `generic-matching` v5의 칸 분석 요청 4개, 섹션 동시 수 1, 질문 묶음 5): 질문이 있는 섹션 31개 가운데 13개 적중, 공급자 호출 47회에서 29회. 요청별 적중은 같은 양식의 화면 셋이 0/8, 7/8, 6/8, 다른 사이트의 화면이 0/7이다.

한계: 배포할 때마다 처음부터 쌓는다. 글자는 그대로인데 칸의 뜻만 바뀌는 변화는 키가 잡지 못한다. 공급자의 답이 흔들린 경우 처음 저장된 답이 기한까지 모든 사이트에 쓰인다. 반복 줄을 줄 묶음(`items`)이 아니라 섹션의 칸으로 보내는 양식은 줄 수가 다르면 키가 달라진다. 재검토 조건: 서버가 두 대 이상이 되거나 배포 뒤 적중률이 떨어지는 것이 지표로 확인되면 서버 밖 저장(MongoDB, Redis)을 검토한다. 운영 문서는 `backend/docs/generic-section-answer-cache.md`다.

## 2026-11-17 실측과 정정 (후보 3)

- 조건: 개발 서버(develop 104b4795, PR #468), 실제 공급자, 확장의 개발 서버용 빌드, 측정용 합성 프로필, 분석 단계만 실행(칸 분석 응답을 확장에 전달하지 않아 글자 칸 기입 0건). 캐시 없음 호출 수는 저장소의 분석기와 캐시 코드에 호출만 세는 가짜 공급자를 끼운 모형이 센 값이고, 관측은 서버 응답의 `jevCalls`다.
- 합격 기준 7개(측정 전 고정)를 모두 통과했다. 동일성(재전송한 칸 3,228개 중 다른 칸 0), 예측 일치(배포 뒤 요청 104건 모두 모형 예측 = 서버 호출 수), 재분석(같은 요청 재전송 71건 모두 호출 0회), 음성 대조(첫 섹션 제목만 바꾸면 그 섹션만 실패), 속도(전부 적중한 요청의 서버 분석 80회 중앙값 8ms), 무간섭(카운터가 매 시점 모형과 같음), 안전(22회 실행 모두 글자 칸 기입 0, 금지 클릭 0, 폼 제출 0).
- 칸 분석의 공급자 호출 수:

| 시나리오 | 캐시 없음 | 관측 | 섹션 적중 |
|---|---|---|---|
| 처음 보는 양식(우아한형제들 공고 1) | 21 | 21 | 0/16 |
| 같은 회사의 다른 공고(우아한형제들 공고 2~5) | 80 | 9 | 55/62 |
| 같은 공고의 다른 사용자(우아한형제들 공고 1~5) | 101 | 0 | 78/78 |
| 같은 공고 재실행(우아한형제들 공고 1~5) | 101 | 0 | 78/78 |
| 같은 회사의 다른 공고(카카오스타일 공고 2~5) | 14 | 6 | 8/14 |
| 같은 플랫폼의 다른 회사(퍼즐원스튜디오, 잉카인터넷) | 4 | 4 | 0/4 |

- 확장 실행 한 번(첫 서버 호출부터 칸 분석 응답까지)은 처음 3,795ms, 전부 적중한 실행 10회 중앙값 1,346ms다. 남는 시간은 캐시 대상이 아닌 섹션 분류 3건과 준비 결정 2건이다.
- 정정: CF-467 ADR은 키에서 host를 뺀 이유로 "같은 채용 플랫폼을 쓰는 회사들이 답을 나눠 쓴다"를 들었지만 이 표본에서는 확인되지 않았다(같은 플랫폼의 다른 회사 적중 0/4). 원인은 확장이 공고 제목을 섹션 제목이나 섹션 머리 라벨로 보내 키가 공고마다 달라진 것이다. 같은 이유로 같은 회사의 다른 공고도 공고마다 섹션 하나가 실패했다. host를 뺀 것 자체는 손해가 없다. 서버의 글자 정제(`RawLabelMask.mask`, `GenericProfileSemantics.project`)는 공고 제목을 거르지 못한다.
- 모형 계산(서버 호출 없음): 나인하이어 요청 7건에서 첫 섹션 제목이 공고와 무관하면 호출이 21회에서 8회가 된다(실제 13회).
- CF-472가 확장의 범용 수집에서 공고 제목을 뺐다(topic `generic-page-title-exclusion`). 수정 뒤 실측은 머지 뒤에 재므로 이 기록에는 없다.
- 한계: 회사 네 곳, 개발 서버, 하루 측정이다. 처음 분석은 요청마다 한 번만 쟀다. 운영 적중률은 재지 않았다. 요청과 응답 본문은 보존하지 않았다.
