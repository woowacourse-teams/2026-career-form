# CF-431 승인 후보 스냅샷

worktree 체크포인트에 기록한 후보 세 개의 원문이다. 사람이 2026-11-06 "승인"으로 확정했다.

1. 공고 알림 직무 미선택 정책(CF-431): 받을 직무를 하나도 고르지 않은 구독은 모든 공고를 받는다. 확장의 matchesSelectedRoles가 빈 선택이면 직무가 붙은 공고도 통과시켜 푸시 표시, 배지, 새 공고 탭에 함께 적용된다. #394·#395의 '미선택이면 받지 않는다'를 뒤집은 것이며 알림 설정에는 '선택 없음 · 모든 공고 받는 중'과 '하나도 고르지 않으면 모든 공고를 받아요'를 보이고 새 공고 탭과 사이드 패널의 직무 유도 안내는 없앴다. 서버 전환 설정 CAREER_FORM_PUSH_ROLE_FILTER_ENFORCED를 켜면 이 동작이 다시 막히므로 #432가 설정을 없애기 전에는 켜지 않는다. 이미 배포된 1.5.0은 자동 업데이트 전까지 미선택이면 계속 거른다.
2. 확장 첫 설치 온보딩 여섯 단계(CF-431): onboarding.html 기본 경로는 선택 화면 없이 이름, 이메일, 직무 선택, 알림 안내, Greeting, 사용법 순서의 한 줄 흐름(entrypoints/onboarding/flow)이고 ?page= 경로의 소개·체험·정책 페이지와 웹 /onboarding 4단계 사용 안내는 그대로다. 현재 단계 이름만 careerForm.onboarding.step에 저장해 다시 열면 이어지고 끝내지 않았으면 관리 페이지 머리글에 '시작 안내 이어하기'가 보인다. 온보딩 페이지의 구독 메시지 허용은 status, enable, disable, test, record, categories, roles이고 inbox, later는 차단한다. 직무 선택 단계는 대분류마다 맨 앞의 '전체'로 그 분류를 한 번에 고르거나 해제한다(일부만 고르면 aria-pressed=mixed). Greeting 단계는 사용자 결정(2026-11-06)으로 선택 안내다. '혹시 모든 인적사항을 입력하기 번거로우신가요?'로 묻고 가져오기 방법을 보여 줄 뿐, 가져오기를 실행하거나 감지하거나 기다리지 않고 '다음'으로 넘어간다. 예시 회사 16곳은 표시용 상수이며 지원 보장이 아니다. 사용법 단계도 사용자 결정(2026-11-06)으로 '전체 프로필 입력하기'(관리 페이지 전체 프로필, 채워진 주 버튼)와 '지금 채용 중인 회사 보기'(새 공고 탭, 테두리 버튼)만 두고, 일시정지는 설명 옆의 작은 글자 버튼이다. 이전·다음과 사용법 단계의 버튼은 사용자 요청(2026-11-06)으로 창 아래 고정 막대(StepBar)에 두어 카드 크기와 관계없이 모든 단계에서 같은 자리에 있다(이전은 내용 열 왼쪽 끝, 주 버튼은 오른쪽 끝). 온보딩에서 쓰지 않게 된 단계형 등록(QuickStart, CF-193)과 quick_profile_viewed 이벤트는 지웠다. Greeting과 사용법 단계의 장면은 Greeting 형식의 가상 지원서와 Career Form 패널을 880×560 무대에 그려 폭에 맞춰 줄이고, 페이지의 Career Form 버튼에서 시작해 패널 조작까지 단계 시간표 훅(useLoopTimeline)으로 반복한다. 패널을 쓰는 동안 패널 쪽으로 확대하고, 왼쪽 단계 목록이 장면과 함께 강조되며, 일시정지할 수 있고 동작 줄이기에서는 결과 화면에 멈춘다. 흐름은 랜딩의 하늘색 값을 Flow.module.css 범위에 literal로 두고 theme.css와 extension-theme.css는 바꾸지 않는다. 계측은 onboarding_step_viewed(step)와 onboarding_completed를 더하고 onboarding_autofill_selected, onboarding_postings_selected, quick_profile_skipped, quick_profile_viewed를 뺐다.
3. 온보딩 화면 검증 방법과 함정(CF-431): 빌드한 확장을 Playwright Chromium에 --load-extension으로 새로 설치하면 onInstalled가 onboarding.html을 스스로 열어 여섯 단계를 실제로 조작할 수 있고, 직무 분류와 알림은 VITE_API_BASE_URL을 로컬 백엔드로 두고 빌드해 확인한다. 로컬 백엔드는 local 프로필이어야 회사 정책이 시드돼 Greeting 가져오기가 나온다. 헤드리스에서는 OS 알림 표시를 확인할 수 없어 사람이 실제 Chrome에서 확인한다. 반복 장면은 시간대별 스크린샷으로 단계마다 확인한다. 이 방식과 설계를 모르는 독립 검토자의 처음 설치한 사용자 역할 점검으로 결함을 찾았다. CSS 모듈에서 상태 문구의 수식 클래스가 장면 클래스 이름과 같으면 장면 애니메이션이 문구까지 숨기고, 범위 루트의 '.flow p' 같은 reset은 컴포넌트 클래스보다 특이도가 높아 여백을 지우므로 :where()로 특이도를 0으로 둔다. 같은 특이도의 좁은 화면 덮어쓰기는 기본 규칙보다 뒤에 있어야 이긴다. 사용자가 헷갈린 것은 설명 없는 Greeting, 패널과 톱니라는 낱말, '새 탭'과 '새 공고 탭'의 혼용, 명령형 제목이었다. 회사가 Greeting으로 지원서를 받는지는 <회사>.career.greetinghr.com 루트가 200이고 og:title에 회사 이름이 나오는지, 자체 도메인이면 CNAME이 *.career.greetinghr.com인지로 확인한다(없는 주소는 404). 이동 막대는 단계 컴포넌트 안의 position: fixed라서 단계 루트나 카드에 transform·filter를 주면 그 요소를 기준으로 놓여 함께 움직인다. 버튼 자리가 같은지는 조작 스크립트에서 단계마다 버튼 boundingBox를 재서 비교한다.
