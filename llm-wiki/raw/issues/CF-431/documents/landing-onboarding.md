# 확장 첫 설치 온보딩 여섯 단계

> Issue: [CF-431](https://github.com/woowacourse-teams/2026-career-form/issues/431)
> Collected: 2026-11-06
> Approval-Digest: 2b1c944c4eeec4e7481efa999e40d57f4709500cea784143009e2fdab1bbaae3
> Source-Revision: cc7f723b

확장을 처음 설치했을 때 열리는 `onboarding.html`의 구성과 검증 방법이다. [승인 후보 스냅샷](approved-candidates.md)의 후보 2와 3을 적는다. 웹 랜딩, 체험, 기술 소개, 정책 페이지와 웹 `/onboarding/`의 4단계 사용 안내는 CF-427 payload의 내용이 그대로 유효하며 여기서는 확장 온보딩에서 바뀐 부분만 더한다. 실제 지원값, 계정, 세션, 대화 전문은 기록하지 않는다.

## 흐름 (후보 2)

`onboarding.html`의 기본 경로는 "설치 완료" 선택 화면 없이 이름, 이메일, 직무 선택, 알림 안내, Greeting, 사용법 순서의 한 줄 흐름이다(`frontend/entrypoints/onboarding/flow`). 입력 영역 위 진행 바가 여섯 단계와 현재 위치를 보이고 720px 이하에서는 `n / 6 단계 이름`으로 보인다. `?page=`로 여는 소개, 체험, 기술 소개, 정책 페이지는 계속 `SiteApp`이 그린다.

- 이름과 이메일은 기존 `useProfileEditor` 저장 경로로 자동 저장한다. 넘어가는 버튼은 하나이고 칸이 비면 "건너뛰기", 값이 있으면 "다음"이다.
- 이전·다음과 사용법 단계의 버튼은 사용자 요청(2026-11-06)으로 창 아래 고정 막대(`StepBar`)에 둔다. 카드 크기가 단계마다 달라도 이전은 내용 열의 왼쪽 끝, 주 버튼은 오른쪽 끝에 있어 모든 단계에서 같은 자리다. 이름·이메일 단계의 막대는 양식 안에 있어 Enter로도 넘어간다.
- 현재 단계 이름만 `careerForm.onboarding.step`에 저장한다. 다시 열면 그 단계에서 시작하고, 사용법 단계에 닿지 않았으면 관리 페이지 머리글에 "시작 안내 이어하기" 링크가 보인다. 프로필 저장 키와 형식은 바꾸지 않는다.
- 직무 선택 단계는 "모든 직무의 공고 받기"(기본)와 "직무를 골라 받기" 두 가지다. 고르기에서는 대분류마다 맨 앞의 "전체"로 그 분류를 한 번에 고르거나 해제하고, 일부만 고른 분류의 "전체"는 `aria-pressed="mixed"`다. 카드 아래에 알림 상태, 테스트 알림, 끄기와 켜기를 둔다. 알림은 설치 때 이미 켜져 있으므로 이 단계는 켜는 화면이 아니다.
- 알림 안내 단계는 세 안내 사이를 옆의 번호나 글로 옮긴다.
- Greeting 단계는 사용자 결정(2026-11-06)으로 선택 안내다. "혹시 모든 인적사항을 입력하기 번거로우신가요?"로 묻고 예전에 Greeting 지원서에 입력한 정보를 지원서 탭의 패널에서 가져오는 방법을 보여 줄 뿐, 가져오기를 실행하거나 감지하거나 기다리지 않고 "다음"으로 넘어간다. 예시 회사 16곳(`greeting-companies.ts`)은 표시용 상수이며 지원 보장이 아니다.
- 사용법 단계도 사용자 결정(2026-11-06)으로 "전체 프로필 입력하기"(관리 페이지 전체 프로필, 채워진 주 버튼)와 "지금 채용 중인 회사 보기"(새 공고 탭, 테두리 버튼)만 둔다.
- Greeting과 사용법의 장면은 Greeting 형식의 가상 지원서와 Career Form 패널을 880×560 무대에 화면 컴포넌트로 그려 폭에 맞춰 줄인다(`flow/scenes`). 페이지의 Career Form 버튼에서 시작해 패널 조작까지 단계 시간표 훅(`useLoopTimeline`)으로 반복하고, 패널을 쓰는 동안 패널 쪽으로 확대하며, 왼쪽 단계 목록이 장면과 함께 강조된다. 영상 파일은 쓰지 않는다. 일시정지는 설명 옆의 작은 글자 버튼이고, 동작 줄이기 설정에서는 결과 화면에 멈춘다.
- 온보딩에서 쓰지 않게 된 단계형 등록(`QuickStart`, CF-193)은 지웠다.
- 온보딩 페이지가 백그라운드에 보낼 수 있는 구독 메시지는 `status`, `enable`, `disable`, `test`, `record`, `categories`, `roles`이고 `inbox`, `later`는 차단한다.
- 여섯 단계는 랜딩의 하늘색 값을 `Flow.module.css` 범위에 literal로 둔다. `theme.css`와 `extension-theme.css`는 바꾸지 않는다.
- "설치 완료" 선택 화면, 알림 타일, 공고 저장 3단계 안내와 `SiteApp`의 확장 전용 속성은 없앴다.

## 검증 방법과 함정 (후보 3)

빌드한 확장을 Playwright Chromium에 `--load-extension`으로 새로 설치하면 `onInstalled`가 `onboarding.html`을 스스로 열어 여섯 단계를 실제로 조작할 수 있다. 직무 분류와 알림은 `VITE_API_BASE_URL`을 로컬 백엔드로 두고 빌드해 확인한다. 로컬 백엔드는 `local` 프로필이어야 회사 정책이 시드되어 Greeting 가져오기가 나온다. 헤드리스에서는 OS 알림 표시를 확인할 수 없어 사람이 실제 Chrome에서 확인한다. 반복 장면은 시간대별 스크린샷으로 단계마다 확인하고, 버튼 자리가 같은지는 조작 스크립트에서 단계마다 버튼 `boundingBox`를 재서 비교한다.

조작 확인과, 설계를 모르는 독립 검토자가 처음 설치한 사용자 역할로 화면을 순서대로 보는 점검에서 다음을 찾았다.

- CSS 모듈에서 상태 문구의 수식 클래스가 장면 클래스 이름과 같으면 장면 애니메이션이 문구까지 숨긴다. 글자가 있는지만 보는 테스트는 이를 잡지 못한다.
- 범위 루트의 `.flow p` 같은 reset은 컴포넌트 클래스보다 특이도가 높아 여백을 지운다. reset은 `:where()`로 특이도를 0으로 둔다.
- 같은 특이도의 좁은 화면 덮어쓰기는 기본 규칙보다 뒤에 있어야 이긴다.
- 이동 막대는 단계 컴포넌트 안의 `position: fixed`라서 단계 루트나 카드에 `transform`·`filter`를 주면 그 요소를 기준으로 놓여 함께 움직인다.
- 사용자가 헷갈린 것은 설명 없는 Greeting, 패널과 톱니라는 낱말, "새 탭"과 "새 공고 탭"의 혼용, 명령형 제목이었다.

회사가 Greeting으로 지원서를 받는지는 `<회사>.career.greetinghr.com` 루트가 200이고 `og:title`에 회사 이름이 나오는지, 자체 도메인이면 CNAME이 `*.career.greetinghr.com`인지로 확인한다. 없는 주소는 404다.
