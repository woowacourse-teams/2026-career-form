# 범용 매칭 모델 평가

CF-356에서 승인한 지식 후보 16개를 정리한 문서다(2026-10-30 7개, 2026-11-05 9개 추가). 결정 배경과 대안은 [ADR](adr/356-versioned-model-evaluation.md)에 있다. 코드 위치는 `backend/src/main/java/com/careerform/evaluation/`, 데이터셋은 `backend/src/main/resources/evaluation/datasets/generic-matching/v1/`, 운영 설명은 `backend/docs/model-evaluation.md`다.

## 2026-11-05 기준 현재 상태

이 절이 아래 절보다 우선한다. 아래 절의 호출 단위 채점과 수집 경계는 2026-10-30 시점 기록이다.

- 대표 점수: 모델 비교와 개선 판단은 정밀도를 채움률보다 2배 중시한 F0.5로 한다. 잘못 답하면 사용자가 찾아 고쳐야 하지만 놓친 것은 직접 입력하면 되기 때문이다. 전체(자동기입 점수), 준비, 매핑을 같은 식으로 내고, 칸 매핑은 제품과 같은 확신도 0.8 이상만 답으로 본다. 항목 단위 정확도(`item-weighted-exact-v2`)는 깎인 이유를 보는 진단 지표다.
- 자동기입 1번: 같은 반복·같은 사이트에서 준비만 있는 처음 화면의 호출과 칸 매핑이 있는 화면 하나의 호출을 합친다. 시간에 클릭, 칸 입력, 네트워크 왕복은 들어가지 않는다. AI 응답 시간은 모델 시도 1번, 요청 처리 시간은 서버 요청 1개다. 제품 요청 하나가 배치마다 모델을 여러 번 부르므로 두 번째 이후 시도를 재시도로 세면 안 되고, 실패 시도는 성공하지 못한 시도만 센다.
- 흔들림: 프롬프트·모델·설정이 같은 두 실행에서도 OpenAI 자동기입 점수가 4.7%p 움직였다(이전 반복 1회, 2026-11-03). 전후 비교는 둘 다 반복 3회 이상으로 하고, 어느 한쪽이 반복 1회이거나 반복별 점수 범위가 겹치면 좋음·나쁨 대신 구분 불가로 표시한다. 평가 실행 반복 수 기본값은 3이다.
- 데이터셋 v4: v3의 우아한형제들 4개 화면을 바이트 그대로 두고 NHN Careers 지원서 1단계 최초 화면을 최종 평가용으로 더했다(반복 1회에 호출 15개, 칸 170개). NHN은 직접 만든 드롭다운이라 선택지가 DOM에 없고, 제품이 섹션 제목을 거의 못 읽어 여러 항목이 한 섹션으로 묶인다. 정답 결정: 구분을 고르지 않은 첫 학력 행은 대학교 기준, 장애 선택칸은 placeholder가 정제로 가려졌지만 `disabilityStatus`, 부서명/직책은 `department`, 학력 행 추가 결정은 + 버튼이다. 자동 임시 저장이 있는 지원서라 선택을 바꾼 상태는 수집하지 않았다.
- 목록 파일: `evaluation/datasets/<id>/catalog.json`이 현재 버전과 공고·화면의 이름·설명을 가진다. 평가 화면과 자동 평가가 이 파일을 읽으므로 공고나 화면을 더할 때 이 파일과 새 버전 폴더만 고치면 된다. 칸·화면·요청 수는 데이터셋에서 계산한다. 이름 누락과 `currentVersion` 미갱신은 `DatasetLoaderTest`가 잡는다. 확정한 버전 폴더는 지문이 걸려 있어 고치지 않으므로 목록 파일은 그 밖에 둔다. 화면의 실행 조건과 개수는 고른 실행의 데이터셋 버전 기준으로 보인다.
- 자동 평가: 개발서버는 평가 입력이 바뀐 배포에서만 돌린다(`CAREER_FORM_EVALUATION_AUTO_RUN_ENABLED`). 입력은 동작 지문, 프롬프트, 설정, 공급자 연결 코드(adapter Git 트리), 데이터셋이다. 동작 지문은 데이터셋 요청을 제품 코드에 넣고 `ChoiceModel` 자리의 가짜 모델로 돌려 AI에 간 질문과 최종 응답을 해시한다. AI 호출과 비용이 없고 변수명 변경에는 그대로이며 프롬프트 변경에는 달라진다. 실행 이름은 바뀐 입력과 커밋이다(`prompt-391fbd8`, `call-…`, `settings-…`, `provider-…`, `dataset-…`, `multi-…`, `first-…`). 알 수 없는 변경은 공급자가 같은 이름으로 바꾼 모델, 속도만 바뀐 변경, 가짜 답이 지나가지 않는 후처리 분기다. 실패·취소된 자동 평가는 같은 입력으로 다시 돌지 않는다.
- 환경 운영: 로컬은 `scripts/evaluation_local.py`로 체크아웃 코드를 띄워 고칠 때마다 재고, 커밋 전 변경은 코드 버전에 `-dirty-`를 붙여 구분한다. 개발서버는 development Environment 값으로 켜고 staging·production 워크플로는 평가 값을 넘기지 않는다. 코드 버전은 이미지에 담긴 커밋이라 롤백해도 맞다. 기록 삭제는 `CAREER_FORM_EVALUATION_RECORD_DELETE_ENABLED`(기본 꺼짐)로 로컬에서만 켜서, 개발서버 기록은 팀의 변경 이력으로 남는다. 배포 워크플로 변경이 있어 PR과 Issue에 `harness-change` 라벨이 필요하다.
- 수집 예외: NHN 화면은 사용자가 승인해 에이전트가 사용자 Chrome에서 수집 지침 정제 스크립트를 실행했다. 입력칸 변경, 저장, 제출, 미리보기, 페이지 이동은 하지 않았다. 정제본 전달은 임시 복사 버튼 클릭으로 했고 브라우저 쪽 sha256과 대조한 뒤 임시 요소를 지웠다. 로컬 서버 전송과 인코딩 출력은 도구 보호 장치에 막혔고 우회하지 않았다.

## 채점

- 채점 단위는 제품 API 호출 1건이다. 서버 내부의 모델 호출 수는 비중에 쓰지 않는다. 배치 크기가 바뀌어도 분모가 그대로이기 때문이다.
- 호출 점수 = 맞힌 항목 ÷ 정답 항목이다. 정답 항목에는 매핑 불가와 기권이 포함된다. 부분 점수는 없다.
- 누락, 다른 키, 불필요한 제안은 모두 그 항목의 오답이다.
- 공급자가 쓸 수 없다고 한 항목은 분모에서 뺀다. 모델 시도가 모두 실패한 호출은 실패율에 넣는다.
- 단계는 호출 종류가 아니라 호출이 일어난 단계로 센다. 준비 루프 안의 섹션 분류는 준비 단계다.

## 범용 자동기입의 준비 단계 구조

- 범용 경로는 `/api/v1/preparation/analyze`를 쓰지 않는다. 준비 루프는 반복·학력 후보 섹션만 섹션 분류하고, interaction-decisions(REPEAT_ADD, SECTION_REVEAL, ROW_KIND_OPTION)로 누를 버튼과 고를 선택지만 묻는다.
- 행 추가 횟수와 순서는 프로필 항목 수로 프론트엔드가 로컬에서 정한다. 모델 평가 대상이 아니다.
- 학력 행 종류 질문의 정답은 프로필과 무관한 "학력 단계별 선택지" 대응표다. 사용자 학력은 모델에 보내지 않고, 실제 값 선택은 프론트엔드가 한다.
- 준비 루프가 동작에 쓰는 범주는 반복 범주 6개(EDUCATION, CAREER, CERTIFICATE, LANGUAGE, PROJECT, PUBLICATION)뿐이다. 그래도 준비 단계 섹션 분류는 범주 이름을 정확히 채점한다. 병역 섹션의 정답은 SENSITIVE다.
- 매핑은 섹션 분류 1회와 필드 매핑 1회다.

## 평가 데이터 수집 경계

- 로그인과 화면 준비는 사람이 한다. AI는 페이지를 조작하지 않는다.
- 순서: 개수만 내는 구조 통계 → 대상별 정제 스크립트(사람 승인) → 사람이 Console에서 실행하고 남는 글자 목록을 확인 → 그 뒤에만 정제본을 넘긴다. 수집 지침은 `backend/src/main/resources/static/evaluations/collection-skill.md`다.
- 정답은 칸이 뜻하는 지원 프로필 필드다. 프로필 값 유무와 무관하다. 지원 필드에 없는 의미는 매핑 불가다.
- 병역·보훈·장애도 지원 필드라 정답에 넣는다. 현재 자동기입은 민감 값에 별도 확인을 요구하지 않는다.
- 요청은 제품 코드가 fixture에서 만든다. 손으로 쓰지 않는다. 후속 요청은 정답 오라클로 만든다.

## 측정 범위

- 제품 호출 시간: 작업자가 서비스를 부르고 반환받을 때까지다. 내부 배치와 동시 호출 상한 대기를 포함하고 HTTP는 제외한다.
- 모델 시도 시간: HTTP 전송 직전부터 전체 응답 수신까지를 시도마다 잰다.
- 흐름 시간: 반복 하나에서 사례 하나의 호출 시간 합이다.
- 처리량: 완료 호출 ÷ 실행 경과 초다.
- 토큰은 공급자가 알려 준 값만 쓴다. 알려 주지 않은 호출은 null로 두고 평균에서 빼며 개수를 따로 센다.
- 비용은 평가 화면에 사용자가 입력한 단가로만 계산한다.

## 프롬프트 버전

- `formanalysis`의 `PromptSource`가 모델 요청의 고정 문구를 조각으로 내놓고, `PromptCatalog`가 sha256 해시를 만든다.
- 실제 모델 요청 문구가 모두 조각에 들어 있는지 확인하는 테스트가 있어, 프롬프트를 바꾸고 조각 갱신을 빠뜨리는 일을 막는다.
- 입력 데이터 형태(state 구조) 변경은 해시로 구분되지 않는다. 코드 버전으로 구분한다.

## 실행 운영

- `career-form.evaluation.enabled`는 development 서버에서만 켠다. 평가 호출이 사용자 요청과 JEV 동시 호출 상한을 함께 쓰기 때문이다.
- 평가 API와 화면(`/evaluations/`)은 품질 확인 공용 비밀번호로 보호한다.
- 진행 중인 실행은 저장소 전체에서 1건이다(Mongo 부분 고유 색인).
- 작업자는 임대로 실행을 가져가고, 결과가 이미 있는 호출은 건너뛰며 이어받는다.
- 결과와 재채점은 추가만 한다.

## 첫 데이터셋

generic-matching v1은 우아한형제들 공고 1개의 화면 상태 3개(initial은 tuning, high-school과 university는 final)와 합성 프로필로 만들었다. 매핑 정답과 준비 단계 정답 모두 2026-10-30에 사람이 검토했다. 이 Issue에서 실제 모델 평가 수치는 아직 측정하지 않았다.
