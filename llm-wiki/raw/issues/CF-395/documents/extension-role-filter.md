# 확장 받을 직무 선택과 직무별 거르기, 사이드 패널 안내

> Issue: [CF-395](https://github.com/woowacourse-teams/2026-career-form/issues/395)
> Collected: 2026-11-04
> Approval-Digest: 06bed9b73b031ba11fd558442feb39e15b45b702740a2cf873c46a68bc574dbd
> Source-Revision: 4e6283fa

공고 알림을 사용자가 고른 직무로 좁히는 확장 쪽 결정이다. 2026-11-02 검토에서 #386을 서버 #394와 확장 #395로 나눴고, 서버 계약(분류 API, 공고 `roles`, 구독 `roles`)은 CF-394 payload(공고 구독 알림 topic의 Current)가 정본이다. 이 문서는 #395 구현(브랜치 CF-395, develop 10ed407b 병합 뒤)에서 확정한 확장 쪽 규칙을 [승인 후보 스냅샷](approved-candidates.md)의 7개 후보 순서로 적는다. 후보 4(계측)는 선택적 이용 계측 topic용 payload에도 같은 내용으로 적는다. 구독 수명주기, 푸시 검증, 공지함, 자가 진단, 배지, 자동 저장은 CF-349 payload를 그대로 따르고 여기서는 바뀐 부분만 더한다. 구독 endpoint와 키, 실제 공고·프로필 값, 사용자의 직무 선택값, 대화 전문은 기록하지 않는다.

## 받을 직무 저장과 구독 등록 (후보 1)

선택값은 `chrome.storage.local`의 `careerForm.push.roles`(소분류 코드 배열)에 두고 구독 등록 요청 `roles`로 매번 실어 보낸다(빈 배열=미선택). 서버가 "필드 없음=유지"를 지원하지만 확장은 항상 보내 선택 해제도 서버에 반영한다. 꺼짐 상태에서 바꾼 선택은 로컬에만 두었다가 켤 때 재등록으로 반영되고, 끄기는 구독 문서만 지우므로 선택값은 이 브라우저에 남는다. 받을 직무 저장(`PushSubscriptionService.setRoles`)은 구독 재등록 결과를 기다리지 않아 등록 실패 중에도 선택값이 바로 저장되고, 재등록은 기존 재시도 경로가 이어 간다.

## 직무 분류 캐시와 선택기 (후보 2)

`GET /api/v1/notifications/job-categories` 응답을 `careerForm.push.jobCategories`(version·categories·fetchedAt)에 캐시하고, 조회 실패 시 캐시와 오류 코드를 함께 돌려줘 선택기가 저장된 분류로 계속 동작한다(404는 `ENDPOINT_UNAVAILABLE`, 미설정 빌드는 `NOT_CONFIGURED`). 분류에 없는 코드는 서버 응답(오류 없음)일 때만 선택값에서 버린다. 선택기(`RoleSelector.tsx`)는 대분류 tablist(위·아래 방향키, Home·End)와 소분류 체크박스에 대분류 전체 선택 체크박스를 두고 토글 즉시 저장한다(낙관적 draft, 실패 시 되돌림). 오류는 알림 서버 없음, 서버 미지원, 불러오지 못함으로 구분하고 캐시 사용 중임을 알린다.

## 거르기 규칙 (후보 3)

공고 목록과 푸시 payload의 `roles`가 없으면 레거시 공고로 보고 전원에게 보인다. `roles`가 있으면 선택값과 겹칠 때만 새 공고 탭과 알림에 보이고, 미선택이면 직무 있는 공고를 전부 거른다(알림·배지·계측 없이 `filtered`). 새 공고 탭의 미선택 안내("받을 직무를 고르세요")는 분류를 받았거나 직무 있는 공고가 걸러졌을 때만 보여, 분류 API가 없는 구 백엔드 조합에서는 기존 동작이 그대로다. 서버 전환 설정이 꺼진 동안 미선택 구독에도 푸시가 오므로 확장의 거르기가 2중 확인 역할을 한다.

## 계측 (후보 4)

`push_roles_saved` 이벤트에 `role_count`(0 이상 정수)만 싣고 직무 코드는 `events.ts` 허용 속성에서 제외한다. 선택값은 로그·계측·PR 본문 어디에도 코드 값으로 남기지 않고 건수만 적는다.

## 사이드 패널 마감 공고 탭 안내와 패널 발신자 허용 (후보 5)

사이드 패널(그리고 같은 화면을 쓰는 페이지 내 패널)의 마감 공고 탭은 푸시 상태를 읽어, 저장 공고가 없으면 상태별 빈 상태 안내와 행동 버튼 하나를 보인다. 꺼짐은 "새 공고 알림이 꺼져 있어요 · 알림 켜기", 등록 실패·미지원·서버 없음은 "새 공고 알림이 아직 안 와요 · 알림 설정 열기"(구독 상태 한 줄 포함), 등록됨·미선택은 "받을 직무를 골라 주세요 · 받을 직무 고르기", 그 밖에는 "아직 저장한 공고가 없어요 · 새 공고 보기"(미확인 건수 포함)다. 저장 공고가 있으면 꺼짐·미선택·실패에 한해 한 줄 알림 바를 목록 위에 둔다. 등록 확인 중(`status === null`)은 경고 없이 저장 없음 안내로 둔다. 이를 위해 백그라운드 구독 메시지 허용 목록에 `panel` 발신자(sidepanel.html과 콘텐츠 스크립트)를 더하되 `status`·`enable`·`categories`만 허용한다. #369가 콘텐츠 스크립트의 구독 메시지를 막았던 결정의 좁은 완화이며, 콘텐츠 스크립트는 이미 같은 저장 키를 읽을 수 있고 웹 페이지는 확장 메시지를 보낼 수 없어 새로 드러나는 정보는 없고 쓰기는 켜기 하나다. 패널에서 알림 설정 대화상자를 바로 여는 경로는 `options.html#postings/settings` 해시이고 `ManagementApp`이 열자마자 `#postings`로 되돌린다.

## 알림 설정 안내 목록 (후보 6)

알림 설정 대화상자의 안내 목록은 데이터 사실 5줄(마감 알림, 서버 전송, 저장 위치, 확장 삭제 시, 구독 끄기)만 바로 보이고, 문제 해결 4줄(Chrome 종료 중, OS 알림 설정, OS 알림 꺼짐, 놓친 알림)은 `<details>` "알림이 안 보일 때" 안에 접는다. "서버 전송"은 푸시 구독 주소와 받을 직무를 보낸다는 문구로 바뀌었다. 온보딩 시작 화면의 목록은 그대로다.

## 검증 환경 (후보 7)

frontend `format:check`는 develop에서도 fixtures·autofill 151개 파일이 실패하는 기존 상태라 변경 파일 단위로 `prettier --check`를 본다. 로컬 Chromium(Playwright `--load-extension`)에 빌드 확장을 올리고 서비스워커에서 `chrome.storage.local`을 시드하면 옵션 페이지와 사이드 패널을 종단에 가깝게 확인할 수 있고, `VITE_API_BASE_URL`을 로컬 백엔드로 둔 빌드면 분류·공고 조회와 구독 등록(헤드리스 Chromium도 FCM 구독이 만들어져 서버에 등록됨)까지 실제 서버와 맞춰 볼 수 있다. 헤드리스가 만든 구독은 로컬 DB에 남으므로 확인 뒤 지운다. OS 알림 표시와 전환 설정 켜기 같은 사람 확인 항목은 실제 Chrome에서 본다.

## 범위 밖과 후속

서버 쪽 전부(분류 파일, 공고 직무 필수, 구독 `roles` 저장, 대상 발송, 전환 설정, 관리 화면)는 CF-394다. 실제 대분류·소분류 목록 확정, 관심 기업 필터, 필터 변경 뒤 기존 공고의 발송 보충, 전환 설정을 켜는 시점은 사람과 후속 Issue 몫이다. 서버 전환 설정이 켜지면 고르지 않은 사용자의 푸시가 멈추므로 확장 보급이 끝나기 전에 켜지 않는다.
