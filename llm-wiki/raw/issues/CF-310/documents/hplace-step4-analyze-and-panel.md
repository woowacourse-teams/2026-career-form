# 에이치닷 4단계 분석 예외와 결과 패널 집계

이 문서는 2026-10-22에 승인된 CF-310 후보 2와 후보 4를 수집한 기록이다. Approval-Digest는 [승인 후보 스냅샷](approved-candidates-2.md) 전체 UTF-8 바이트의 SHA-256이다. 어댑터 계약을 바꾸지 않는 실행 관측이며, 바꾸지 않은 내용은 Supersedes가 가리키는 [요청 구조 근거](hplace-mrs2-requests.md)를 따른다. 실제 지원값·계정·세션·URL 쿼리·대화 전문은 포함하지 않는다.

## 승인 후보

- 에이치닷 4단계: 수집 필드 0건일 때 분석 API가 `BAD_REQUEST`를 돌려주는 흐름이다.
- 에이치닷 패널 "입력 완료"는 저장 행을 다시 채운 칸까지 세고, 정책 제외 빈 칸은 "확인 필요"에 나오지 않는다.

## 근거

### 4단계 분석 예외

- 2026-10-22 하네스로 다섯 테넌트(abl·careerhyundai·gsenc·gsretail·hankooktire)의 4단계(자기소개서)를 실행했을 때 모두 패널이 예외 상태 "현재 지원서 구조를 분석할 수 없습니다"로 끝났다(`error.code = extension-exception`). 2026-10-21 네 테넌트에서도 같았다.
- 콘솔의 구조 로그 순서는 다섯 곳이 같다. 준비 단계 수집 `collected=11 accepted=0 rejected=11`(에이치닷 섹션 수집기가 모두 `section-missing` 또는 `control-missing`으로 건너뜀) → 필드 단계 수집 `collected=16 accepted=0 rejected=16` → `AUTOFILL_ANALYZE_FIELDS` 호출 → 응답 `error: BAD_REQUEST`.
- 4단계 화면의 컨트롤은 자기소개서 textarea 1–7개뿐이고 프로필 키가 없다. 그래서 입력할 칸이 0개인 단계에서 빈 분석 요청을 보내는 것이 예외의 직접 원인이다.
- 기대 동작은 수락된 필드가 0개면 분석을 부르지 않고 "이 단계에는 자동 입력할 항목이 없어요"를 보여 주는 것이다.

### 결과 패널 집계

- 2026-10-22 1–3단계 15페이지(다섯 테넌트 × 3단계)에서 패널의 "입력 완료"는 실행 뒤 DOM에서 값이 있는 칸 수와 같았다. 사람이 서버의 저장 값을 지우지 않은 지원서에서는 확장이 저장 행의 칸을 같은 값으로 다시 채웠고, 이 칸도 "입력 완료"에 포함된다(예: ABL생명 2단계 70 = 정답 24 + 실행 전 값과 같은 칸 46).
- 같은 15페이지에서 "확인 필요"는 모두 0건이었다. 그 사이 빈 칸은 47개였다. 위키에 의도적 미지원으로 적힌 대학·대학원 계열 13칸, 복수·부전공 주야간 20칸, 어학 응시일 10칸, 주민등록상 주소 3칸과 정책 밖 1칸(한국타이어 2단계 학술논문 발표 여부)이다.
- 즉 패널 수치만으로는 의도적 미지원 칸의 누락을 알 수 없고, 저장 행이 있는 지원서에서는 "입력 완료"가 확장이 새로 쓴 칸 수를 뜻하지 않는다.

## 쓰임

- 제품: 수락 필드 0건이면 분석 호출을 생략하고 안내를 보여 준다. 의도적 미지원 칸은 "직접 입력 필요"로 패널에 노출한다.
- 실사이트 QA: 패널 수치는 항목 단위 참고값으로만 두고, 입력률은 DOM 칸 단위 판정으로 센다. 저장 값이 있는 지원서는 사람이 지운 뒤 측정하는 것이 원칙이며, 지우지 못했으면 실행 전 값과 같은 칸을 `UNVERIFIABLE`로 분리한다.
