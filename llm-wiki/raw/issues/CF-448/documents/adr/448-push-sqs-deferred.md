# 공고 알림 SQS 전환 보류

## 상태

승인됨

## 날짜

2026-11-10

## 관련 Issue

- #448 공고 알림 발송 중 공고 조회 잠금으로 발송이 멈추는 문제 수정
- #445 공고 알림 발송의 SQS 릴레이·워커 방식 추가(구현과 검증 완료, PR #446을 머지하지 않고 닫음)
- #447 공고 알림 SQS 방식의 개발·운영 적용(닫음)
- #441 SQS 전환 전후 비교용 발송 시험 도구
- #348 공고 구독 알림 서버(전달 경로와 발송 보장 ADR)

## 배경

CF-348 ADR은 MongoDB 발송 문서와 스케줄러 선점 구조를 택하고, 2차에서 큐와 별도 워커를 장애 격리와 채널 확장을 이유로 검토하라고 했다. 도입 전후를 같은 숫자로 비교하고 대가를 함께 적으라고도 했다. CF-441이 시험 도구를 만들었고, CF-445가 SQS 방식을 설정으로 켜고 끌 수 있게 구현해 실제 SQS에서 확인했다.

2026-11-10에 확인한 사실이다.

- 실제 규모는 구독자 1,000명 가정(실측 최대 500명), 공고당 푸시 1,000건이다. 서비스 목표는 등록 후 10분 안에 99% 전파다.
- 기존 방식의 약점은 API 서버를 배포하거나 재시작하는 동안 발송이 멈추는 것이다. 운영 배포는 한 달에 5번쯤이고 한 번에 최대 2분이다. 멈춘 발송은 다시 뜬 뒤 이어서 나가고 잃는 알림은 없다.
- 재시도, 재시작 뒤 복구, 중복 방지는 기존 방식이 발송 문서의 선점으로 이미 하고 있다.
- 임시 EC2(t4g.medium, 모든 컨테이너가 한 기계)에서 1,000건을 보낸 진단 실행은 기존 방식 7.9초, SQS 방식 14.4초였다.
- 공용 AWS 계정의 월 비용 한도는 70달러다. 정가로 계산한 지금 구성은 약 78.7달러다. 워커 전용 서버를 두면 약 14달러가 더 든다.
- 운영 앱 서버의 메모리 여유는 543MB이고 워커 JVM은 330~420MB를 쓴다. 개발·스테이징 서버는 여유가 276MB라 워커를 따로 띄울 수 없다.
- 같은 계정의 다른 팀 가운데 워커 전용 서버를 둔 팀은 없었다. Chalkak과 shout-outz는 API와 같은 앱 안에서 큐를 소비하고, Harudle은 SQS를 보류하고 DB를 큐로 쓴다.

## 검토한 대안

### A. SQS 방식을 켠다 (운영 앱 서버 안의 별도 워커 컨테이너)

- 장점: API 서버를 배포하거나 재시작해도 큐에 들어간 발송이 계속 나간다. 로컬 리허설에서 발송 중 API 컨테이너를 재시작해도 유실 0, 중복 0, 수락 공백 0.5초였다. 워커를 늘리거나 다른 채널을 붙일 자리가 생긴다.
- 단점: 큐 6개, 서버 권한, 워커 컨테이너, 배포 절차, 알림을 새로 운영한다. 운영 앱 서버의 메모리가 빠듯해진다. 같은 기계에서 처리가 느려진다. 스테이징에 운영과 같은 형태를 올릴 수 없다. 서버가 죽으면 함께 멈추는 것은 같다.

### B. SQS 코드를 꺼 둔 채 머지한다

- 장점: 필요해지면 설정으로 켤 수 있다.
- 단점: 운영에서 돌지 않는 코드 약 2,900줄과 AWS SDK 의존성을 계속 관리한다. 알림 코드를 고칠 때마다 두 경로를 함께 맞춰야 한다.

### C. 기존 방식을 유지하고 SQS 코드를 머지하지 않는다 (선택)

- 장점: 운영할 것과 코드가 늘지 않는다. 구현과 측정 결과는 PR #446과 브랜치 `CF-445`에 남아 다시 꺼낼 수 있다.
- 단점: 배포 중 최대 2분의 발송 지연이 그대로 남는다. 다시 켜려면 브랜치를 그때의 코드에 맞춰야 한다.

## 결정

대안 C를 택한다.

- SQS로 새로 얻는 것은 배포 중에도 발송이 계속되는 것 하나다. 지금은 그 지연이 최대 2분이고 목표가 10분이라, 새로 운영할 것들과 바꿀 만하지 않다.
- PR #446은 머지하지 않고 닫는다. 브랜치 `CF-445`는 지우지 않는다. 운영 적용 Issue #447은 닫는다.
- 리허설에서 찾은 공고 조회 잠금 문제는 기존 방식에도 있으므로 이 Issue에서 고친다.

## 결과

- 효과: 운영 구성과 코드가 그대로다. 숨어 있던 멈춤 문제가 사라진다.
- 비용: API 서버를 배포하는 동안의 발송 지연(최대 2분)을 계속 받아들인다.
- 다시 볼 조건
  - 선착순처럼 1~2분 지연이 문제가 되는 알림이 생길 때
  - 한 번에 몰리는 발송이 5,000건을 넘게 될 때
  - 이메일 같은 다른 발송 채널을 붙일 때
  - API 서버 장애가 발송에 자주 영향을 줄 때
- 다시 볼 때 참고할 것: PR #446의 구현과 검증 기록, 실제 SQS 확인 결과(공용 역할 `ec2-project`로 큐 조회·보내기·받기·지우기가 됐고 큐 생성은 팀 계정으로 직접 됐다), 워커가 받기를 한 줄로 해서 동시 발송 자리 20개 중 평균 7개만 채웠다는 진단.
