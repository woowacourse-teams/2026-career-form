## 배경

단일 job, 단일 워커로 jsdom 실사이트 fixture 테스트와 V8 커버리지를 실행하면 실행 시간이 테스트 시간 총합과 같아진다. 러너 성능 편차만으로 30초 테스트 제한과 30분 job 제한을 넘어 실패가 반복됐다.

## 검토한 대안

1. 한 러너 안에서 워커 수만 늘린다. 첫 PR 실행에서 4 vCPU 러너의 병렬 jsdom 워커가 무거운 테스트를 2~3배 느리게 만들어 제한 시간을 넘었으므로 채택하지 않는다.
2. 테스트 제한 시간을 늘린다. 단독으로는 실행 시간이 그대로라 채택하지 않는다. shard와 캐시를 적용한 뒤에도 느린 러너에서 30초를 넘는 실사이트 fixture 테스트에 한해, 같은 종류 테스트의 120초로 맞춘다.
3. 제품 DOM 조회를 최적화한다. 근본 비용을 줄이지만 범위가 넓다. 동작을 바꾸지 않는 `genericFormGroups` 읽기 패스 캐시 한 곳만 채택하고 나머지는 후속 후보로 둔다.
5. 테스트 코드만 경량화한다. 타임아웃이 나는 테스트는 화면 상태를 바꿔 가며 분석을 반복하므로 결과 공유로 줄일 수 없어 채택하지 않는다.
4. 고정 개수 shard job으로 나누고 blob 보고서를 병합해 기준을 한 번 검사한다. 러너를 여러 대 쓰면서 기존 기준을 그대로 유지할 수 있어 선택한다.

## 결정

CI는 프론트엔드 테스트를 shard job 8개에서 shard당 워커 1개로 실행한다. 로컬은 Vitest 기본 워커 수를 쓴다. 병합 job에서 커버리지 네 지표 80%와 browser 수집 검사를 적용한다. shard 실행은 커버리지 기준을 검사하지 않는다. 로컬 `npm run coverage`는 한 명령으로 두 프로젝트를 실행한다. `genericFormGroups` 결과는 동기 읽기 패스 안에서만 캐시한다. 30초를 명시한 실사이트 fixture 테스트 6개 파일의 제한은 120초로 맞추고, 그 밖의 제한 시간, 단언, 기대값, 커버리지 기준은 바꾸지 않는다. 보호 영역 workflow 변경은 사용자 선택으로 이 Issue에 포함했고 `harness-change` 라벨과 공유 파일 검사는 유지한다.

## 결과

실행 시간이 가장 느린 shard와 병합 시간으로 줄어든다. shard마다 설치가 반복돼 러너 사용 시간이 늘고 blob artifact를 관리해야 한다. 새 무거운 테스트가 한 shard에 몰리면 shard 수나 파일 배치를 다시 측정해야 한다. 실제 CI 소요 시간은 PR 검증 기록에 남긴다.
