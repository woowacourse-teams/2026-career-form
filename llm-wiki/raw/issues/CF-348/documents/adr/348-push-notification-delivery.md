# 채용 공고 구독 알림의 전달 경로와 발송 보장

## 상태

승인됨

## 날짜

2026-10-25

## 관련 Issue

- #348 공고 구독 알림 서버
- #349 확장의 Web Push 구독과 공고 알림 표시 및 공지함
- #350 Web Push VAPID 시크릿과 알림 기능 배포 설정

## 배경

확장은 사용자가 직접 저장한 공고의 마감만 로컬에서 알린다(#161). 팀은 대기업 공채 공고를 손으로 등록해 구독자에게 알리는 기능을 추가하려 한다. 제품 기준은 로컬 우선과 계정 없음이며, 서버는 지금까지 사용자 데이터를 저장하지 않았다.

요구사항은 2026-10-25 설계 세션에서 다음과 같이 정했다.

- 기능: 팀이 공고를 등록하면 접수 가능 시점(등록 시각과 접수 시작 중 늦은 쪽)에 구독자 전원에게 알린다. 사용자는 공지함에서 진행 중 공고 목록을 언제든 다시 보고, 확인한 공고를 기존 로컬 마감 알림에 저장한다. 1차는 사용자별 필터 없이 전원 발송한다.
- 성능: 등록 후 전파 10분 안에 99%. 가정은 "서류 접수는 선착순이 아니다". 공지함 조회 p99 3초.
- 신뢰성: 등록에 성공한 공고는 공지함에서 사라지지 않는다. 푸시는 FCM 수락 응답까지 재시도한다. 기기 도착과 열람은 서버가 관측할 수 없으므로 책임지지 않는다. 장애당 중복 알림 최대 1건을 허용한다.
- 확장성: 구독자 1,000명(실측 피크 500명의 2배), 하루 등록 공고 5건 이하, 공고당 푸시 1,000건. 자소설닷컴 2026년 10월 채용달력의 접수 시작 건수(전체 기업 평일 약 16건, 최대 30건) 중 팀이 고른 일부라는 가정이다.
- 가용성: 공지함 조회 월 3~4시간(약 99.5%), 푸시 발송 월 7시간 안팎(약 99%). 현재 운영은 EC2 한 대, 컨테이너 하나, MongoDB 한 대이며 운영 배포는 2026년 10월 5회, 회당 끊김 최대 2분이다.

제약은 다음과 같다. 백엔드는 Spring Boot와 MongoDB(단일 노드, 레플리카셋 아님)이고 품질 모듈이 이미 `@Scheduled` 폴링과 Mongo 문서 상태 전이로 Discord 전송을 처리한다. 운영 host는 HTTP 80만 공개한다. AWS 계정의 새 리소스 생성 권한은 확인되지 않았다. 확장은 Manifest V3이고 `alarms`·`notifications` 권한을 이미 가진다. 팀은 다음 주까지 핵심 발송 흐름과 재시도를 완성하고 발표에서 시연하려 한다.

## 검토한 대안

### A. 확장이 당겨오기(폴링)

확장이 chrome.alarms로 10분마다 진행 중 공고 목록을 조회해 처음 보는 공고를 스스로 OS 알림으로 띄운다.

- 장점: 서버는 공고 등록·삭제·목록 세 API만 남고 구독·발송 객체, FCM, VAPID 시크릿이 사라진다. 서버에 사용자 데이터가 전혀 없어 로컬 우선 원칙이 그대로 지켜진다. 트래픽은 1,000명 기준 초당 2건 미만이다. CF-161의 alarms·복구·중복 억제 코드를 재사용한다.
- 단점: 팀의 발송 진행 화면(수락·포기 건수)이 불가능하다. 등록 후 최대 10분 지연이라 시연에서 "누르자마자 뜨는" 장면이 없다. 본 공고 기억, 접수 시작 판단, 재시작 중복 방지가 확장으로 옮겨 간다. 발송 파이프라인(큐, 재시도, 멱등성)을 만들어 보는 학습과 발표 소재가 사라진다. 사용자 수가 수만 명 규모가 되면 빈 응답 트래픽이 발송 비용을 넘어선다.

### B. Web Push + MongoDB 발송 문서 + 스케줄러 선점 (선택)

API 서버가 공고 저장과 함께 구독자 전원에 대한 발송 문서를 "대기"로 만든다. 발송기가 `@Scheduled` fixedDelay(기본 60초)로 예정 시각이 지난 대기 건과 리스가 만료된 발송 중 건을 찾아, FCM 호출 전에 조건부 갱신으로 "발송 중"과 리스 만료 시각을 찍은 뒤(선점), 동시성 20으로 Web Push를 보내고 응답에 따라 수락됨·대기(재시도)·포기로 전이한다.

- 장점: 등록 후 1분 안에 전파된다. 서버가 재시작해도 발송 문서가 남아 다음 주기가 이어 보낸다. 선점이 SQS 가시성 타임아웃과 같은 역할을 해 발송기가 둘이어도 중복이 수백 건으로 번지지 않는다. 품질 모듈의 기존 패턴과 같은 구조라 운영 방식이 익숙하다. 새 인프라 자원이 없고 로컬 개발이 compose만으로 된다. 발송 진행 화면과 FCM 수락률 같은 운영 지표가 생긴다.
- 단점: 서버에 구독 데이터(FCM endpoint와 키)가 저장돼 개인정보 고지와 보호가 필요하다. VAPID 키 쌍을 세 환경 시크릿으로 관리해야 한다. 장애당 중복 최대 1건을 허용한다. 공고당 발송 문서 1,000건이 쌓이므로 보존 정리가 필요하다. 확장 재배포와 Chrome 121 이상이 필요하다.
- 숫자: FCM 호출 1건을 100ms로 가정하면 순차 1,000건은 100초지만 동시성 20이면 5초, 접수 시작이 같은 공고 5건이 겹치는 최악(5,000건)도 25초로 1분 주기 대비 이용률 42%다. 10분 목표를 크게 남긴다. 재시도는 수락(201) → 수락됨, 없는 구독(404·410) → 포기와 구독 삭제, 잠시 후 다시(429·Retry-After) → 응답이 준 시각, 그 밖의 오류 → 지수 백오프 1·2·4·8·16·32·64분, 잘못된 요청(400·403·413) → 포기. 포기 기준은 시도 8회 또는 공고 마감 경과 중 먼저 오는 것이며 백오프 합이 약 4시간이라 푸시 가용성 7시간 안에 든다. TTL은 접수 마감까지 남은 시간으로 준다.

### C. Web Push + Amazon SQS FIFO + 별도 발송 워커 (팀원 제안)

Outbox 문서를 릴레이가 SQS FIFO에 넣고, 별도 워커가 큐에서 꺼내 Web Push를 보내며, 반복 실패는 DLQ로 보낸다. 목표 수치는 30,000건을 5분 안에, 100건/초였다.

- 장점: 내구성 있는 재시도, 가시성 타임아웃, DLQ, 워커 수평 확장을 관리형 서비스가 제공한다. 규모가 100배가 되어도 구조를 바꾸지 않는다.
- 단점: 지금 숫자에서 큐가 푸는 병목이 없다. 대안 B의 선점·재시도·포기 집계가 가시성 타임아웃·재시도·DLQ와 같은 보장을 준다. 비용은 AWS 자격증명과 큐 생성 권한(미확인), 배포 파이프라인의 새 시크릿, 로컬 개발용 큐 대체물, 작은 호스트에 추가 프로세스, 그리고 일주일이라는 시간이다. 30,000건은 "구독자 1,000명이 전원 구독하고 자소설닷컴 최대 일자 30건을 모두 등록"하는 극단 가정에서만 나온다.

## 결정

대안 B를 택한다. 적용 경계는 다음과 같다.

- 서버 책임은 "FCM 수락 응답을 받을 때까지 재시도"까지다. 기기 도착·표시·열람은 책임지지 않으며 확장은 수신 확인을 보내지 않는다. 빈틈은 공지함(진행 중 공고 목록 조회)이 메운다.
- 핵심 객체는 공고(링크가 자연 키), 구독(endpoint가 자연 키), 발송(공고 × 구독 쌍, 재시도·복구의 단위) 셋이다. 사용자 계정은 두지 않는다.
- 같은 링크의 재등록은 거절한다. 수정 API는 두지 않고 삭제 후 재등록으로 대체하며, 그때 전원에게 한 번 더 가는 것을 허용한다.
- 1차는 사용자별 필터 없이 전원 발송한다. 하루 등록 공고가 5건을 넘으면 필터(희망 직무·관심 기업 칸과 확장 측 필터)를 재검토한다.
- 2중화는 하지 않는다. 가용성 목표(99~99.5%)가 한 대 구성으로 충족된다.
- 발송 선택의 솔직한 이유를 남긴다. 핵심 지표(자동 기입 클릭률) 기여는 알림 표시 → 클릭 → 자동 기입 깔때기를 PostHog 이벤트로 측정한다. 발송 파이프라인은 팀 학습과 향후 채널 확장을 위한 선택이며, 그 대가로 서버에 구독 데이터와 시크릿이 생긴다. FCM 수락률과 포기율은 핵심 지표가 아니라 운영 진단 지표다.

## 결과

- 효과: 등록 후 1분 안에 전파, 재시작 복구, 발송기 복수 실행에도 안전한 선점, 발송 진행 화면, 운영 지표. 새 인프라 자원 없이 MongoDB와 기존 스케줄러 패턴으로 구현한다.
- 비용과 후속: 구독 데이터 보호와 개인정보 고지 문구(사람 확정), 세 환경 VAPID 시크릿(`[Infra]`), 확장 재배포와 Chrome 121 하한(`[FE]`), 발송 문서 보존 정리(후속), Grafana 대시보드와 포기율 알림(후속 Infra).
- 남은 한계: 로컬에 저장한 리마인더는 서버 마감 변경을 모른다. Chrome 종료 중이거나 OS 알림이 차단되면 표시되지 않는다. 서버 한 대라 배포마다 최대 2분 끊긴다. 장애당 중복 최대 1건.
- 재검토 조건: (1) 2027-04까지 이메일 등 서버 발송 채널 확장에 착수하지 않았고 FCM 수락률이 운영 진단 외에 쓰이지 않으면 대안 A로 축소를 검토한다. 구독자가 1만 명을 넘으면 더 검토하지 않는다. (2) 공고당 푸시가 1만 건을 넘거나 발송기 한 주기 이용률이 70%를 넘으면 대안 C(큐와 워커 분리)를 검토한다. (3) 가용성 목표를 99.9% 이상으로 올리거나 월 허용 다운타임 초과가 두 달 연속이면 앱 컨테이너부터 2중화한다.
- 대안 A는 대안 B의 부분집합이다. 목록 조회 API와 공지함은 양쪽에 공통이므로, 축소하더라도 버리는 작업은 발송기와 구독 API뿐이다.
- 단계적 도입 경로: 1차는 대안 B로 완성하고 FCM 호출 p50·p99, 1,000건 한 주기 소요, 수락률, 포기율, 배포 중 발송 지연을 실측한다. 2차에서 대안 C(큐와 별도 워커)를 검토하되 이유는 "필요해서"가 아니라 "장애 격리"(배포마다 2분, 백엔드 장애 시 발송 중단 제거)와 "채널 확장"(소비자 추가)이며, 도입 전후를 같은 숫자로 비교하고 대가(AWS 권한, 자격증명 시크릿, 로컬 대체물, 추가 프로세스)를 함께 적는다. 발송기 경계를 유지하므로 되돌리기 쉽다.
- 숫자의 근거: 구독자 1,000명은 PostHog 실측 피크 500명의 2배이며 구독 기본값 켜짐으로 전원 구독을 가정한다. 하루 5건은 팀이 손으로 고르는 대기업 공채 수이며 자소설닷컴 2026년 10월 달력(전체 기업 평일 약 16건, 최대 30건)의 일부다. 최악 5,000건은 하루치 5건의 접수 시작이 같은 분에 겹치는 경우다. FCM 100ms는 실측 전 가정이며 3배 나빠도 동시성 60으로 흡수된다. 큐가 필요해지는 지점은 한 주기 약 8,400건(이용률 70%)부터다.
