# 분석 응답과 품질 관측의 비동기 분리

## 등록과 보고

등록과 보고 분리: 실행당 별도 메모리 등록(201)과 보고 접수(202)를 사용한다. 확장 background가 번호와 토큰을 보관하며 분석과 자동 기입은 등록이나 보고 완료를 기다리지 않는다. 등록 대기는 시작 후 최대30초이고 기존 보고 시점, snapshot 구분과300필드 분할을 유지한다. 서버에는 연결 키와 토큰의 해시만 보관한다. 문맥 소실/만료는401이며 DB에서 권한을 동기 복구하지 않는다.

등록과 보고의 접수 성공은 DB 저장 완료를 뜻하지 않는다. 기존 report 전송 시점과 snapshot 구분은 유지하고, 등록 실패나 지연이 자동 기입 완료를 막지 않게 한다. 구형 확장과 새 서버 조합에서는 분석 JSON과 입력을 유지하되 Receipt 헤더 기반 품질 보고는 빠질 수 있다. 새 확장과 구형 서버 조합에서는 등록 미지원으로 품질 보고만 제외한다.

## 제한된 저장

제한된 최선 노력 저장: 같은 백엔드의 품질 작업자1개가 원본 저장, 집계, 보정을 공유한다. 시험 기본값은 실행/대기/선행정보 작업64개, 직렬화 보관4MiB, 이벤트128KiB, 선행정보 대기30초, 등록 문맥256개/24시간이다. 준비 상태는 메모리로 확인하고 MongoDB를 폴링하지 않는다. 포화 시 새 기록을 거절하고 요청 스레드가 대신 저장하지 않는다. 취소 요청을 실제 종료로 계수하지 않는다. 품질 Mongo 작업별 제한시간은2000ms이며 기존 클라이언트/풀을 공유한다.

## 집계와 운영 한계

지연 집계와 운영 한계: 변경된 원본ID를1024개/24시간까지 보관하고 약60초마다 최신 원본으로 집계한다. 회당64개, 실패 최대3회이며 작업 중 추가 변경을 보존한다. 보정은 원본을 한 건씩 읽고 회당16건/다음 작업 시작 예산1초로 제한한다. 일부 유실과 지연을 허용한다. 위 용량은 초기 시험값으로 JVM 힙/RSS 상한이나143RPS 안전성을 보장하지 않는다. 실제 절감량, 자원 경합과 trace 전파는 dev에서 사람이 검증한다.

## 결정 근거

[승인된 ADR](adr/288-async-quality-observation.md)에 대안과 결정 이유를 기록한다. 기존 품질 판단 기준, 데이터 보존 기간과 자동 입력 정책은 유지한다. 배포와 실제 부하 측정은 사람이 수행한다.
