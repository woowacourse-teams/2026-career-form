# 프론트 회사 어댑터 경계

## 결정

회사별 프론트 코드는 DOM 수집·조건부 동작·특수 입력을 소유한다. 백엔드는 프로필 매핑과 허용 명령을 결정한다. 공통 프론트는 snapshot과 후보 registry, API 통신, 브라우저 로컬 값 결합, 승인과 실행 검사를 유지한다. 초기 분리의 schemaVersion 2와 기존 클라이언트 응답은 유지한다. 후속 SK 주소 검색은 기존 preparation API에서 address-search-v1 지원을 명시한 클라이언트에만 새 명령을 반환한다.

`frontend/src/autofill/adapters/company.ts`에서 host를 소문자로 정규화한 뒤 정확히 비교한다. 미등록 회사에는 일반 처리를 적용하고, 등록 회사의 전용 DOM 예외를 다른 사이트에 적용하지 않는다. 서버 회사 정책의 host/path 및 fingerprint 검증은 별도로 유지된다.

## 실행 책임

| 코드                            | 책임                               |
| ------------------------------- | ---------------------------------- |
| `adapters/collection.ts`        | 회사별 수집 규칙 선택              |
| `adapters/workflow.ts`          | 선행 선택과 재분석 대상 규칙 선택  |
| `adapters/write.ts`             | 회사 특수 입력과 입력 후 보정 선택 |
| `dom/collect.ts`                | 구조 수집과 snapshot/registry 구성 |
| `workflow/AutofillWorkflow.tsx` | API·로컬 프로필·실행 순서 조정     |
| `write/executor.ts`             | 승인·후보 유효성 확인과 표준 입력  |

회사 특수 입력이 `handled: true, written: false`를 반환하면 입력 실패로 종료한다. 일반 writer로 우회하지 않는다. SK 후속 전공 입력도 서버의 `interactionStatus: READY`를 확인한다. 진단 정보는 프로필 값 없이 코드와 개수만 남긴다.

## 승인된 SK 전체 패널 검증 근거

SK 경력의 8개 필드는 exact DOM 조건과 프로필 키를 함께 확인한다. ID가 없는 재직상태 select도 검증된 이름과 제어 종류로만 연결한다. `DERIVED`인 년월 필드는 전체 날짜로 우회하지 않고 `YEAR_MONTH` 계약을 사용하며, 반복 행 수와 대응 프로필 개수가 일치할 때만 입력한다. 재직상태 선행 선택으로 퇴직사유가 나타나면 다시 수집·분석하고, 새 필드도 서버의 `READY` 상태와 해당 경력 항목의 유일한 바인딩을 확인한다.

실제 검증은 공개 fixture를 가져오기 UI로 적용한 뒤 설치된 정적 production 확장의 popup→사이드 패널→자동 기입 경로를 실행하는 방식으로 수행했다. 준비·필드 분석 API 10회가 모두 HTTP 200, `ADAPTER`, `COMPLETE`였고 시험 2행, 자격증 3행, 대학 1행의 선택 결과와 프로필 연결을 확인했다. UI에 표시된 23개 기입 성공과 0개 직접 확인은 writer 집계이며, 선행 선택·미지원·미선택 항목 전체의 성공을 뜻하지 않는다. 테스트 뒤 프로필 키 미존재와 지원서 204개 제어의 값·선택·disabled·readonly 상태를 복원했고, reload로 재생성된 UUID만 정규화해 구조 차이가 없음을 확인했다. 저장·임시저장·미리보기·제출 호환성은 검증하지 않았다.

WXT watcher가 미저장 지원서를 자동 reload할 수 있으므로 브라우저 검증에는 정적 production 빌드를 사용하고, 새로고침 승인은 과거 세션에서 재사용하지 않는다. 도구 연결이 끊겨 메모리 기준이 사라진 경우에도 복구를 보장한다고 확대하지 않는다.

## 새 회사 도입

현재 Issue 계약과 회사 구조 근거를 먼저 확정한다. 확인된 host를 등록하고 표준 수집·입력으로 처리할 수 없는 기능만 회사 모듈로 구현한다. 백엔드 회사 경로, fingerprint, 준비 규칙과 프로필 매핑도 별도로 준비한다. 프론트 어댑터 등록만으로 서버 정책이나 실제 지원 검증이 완료되지 않는다.

어댑터 기준이 없거나 구조를 검증할 수 없으면 추정하지 않고 계약 공백 또는 입력 불가로 처리한다. 코드·비식별 자동화 테스트·회사 문서·지원 현황을 함께 관리한다. 실제 지원서 저장·이동·제출은 사람이 수행한다.

## LG 검색의 후속 경계

이번 변경은 LG 학교 검색을 구현하거나 검증하지 않았다. 후속 구현에는 취소 가능한 비동기 검색, 동일 학력 행의 대상 식별, 후보의 유일성 및 최종 선택 반영 검증이 필요하다. 학교명이 같다는 이유로 첫 결과를 선택하거나 검색 실패를 text 입력으로 우회하지 않는다.

기존 자동 승인 경로, SK 첫 라디오 탐색, 현대 메뉴 탐색 범위와 성공 항목 재실행은 이번 분리로 해결된 것으로 기록하지 않는다. 회사별 실행 경계의 분리와 향후 검색 위젯의 안전성 완성은 별개의 작업이다.

## 현대 주소·국적·학력 경계

현대 정책 v4는 국내 주소 검색, 국적1 대한민국 lookup, 학력 academic 행 준비와 그룹별 날짜·학교·전공·GPA·졸업상태 매핑을 회사 경로로 제공한다. 주소는 유일한 정확 결과만 선택하고 이번 실행이 연 modal만 닫는다. 국적2, 해외 주소, 불명확한 검색 결과와 사용자 변경은 보존한다. 학력은 `itemGroupId` 및 그룹별 `index/count`를 검증하고 종류 변경·취소·stale 후보를 재분석 전 무효화한다.

실제 설치 production smoke는 고교·학사 2행, 주소 실패 modal 정리, 국적1 대한민국/KR과 국적2 불변을 확인했다. 학교는 `data-auto-type=school`, 전공은 `data-auto-type=basic`으로 실제 구조를 교정했으며 학교·전공 검색은 유일한 정확 결과와 유효 코드를 요구한다. API 7회는 HTTP 200/ADAPTER/COMPLETE였고 UI 38/0 집계는 전체 성공이 아니다. toolbar icon 클릭은 검증하지 않았고 `chrome.action.openPopup`으로 popup을 열었다. 실제 대학원·전문학사·박사 및 저장·제출 호환성은 범위 밖이다.

## Greeting 공통 어댑터 경계 (CF-94)

BE는 기존 등록 회사 정책을 우선한 뒤 `site.host`와 지원서 `pathPattern`으로 Greeting 연결을 판정한다. 정확한 Greeting 기본 도메인 또는 제한된 DNS CNAME 조회에서 Greeting으로 이어지는 별칭을 확인하면 하나의 공통 정책을 선택한다. 기업별 자체 도메인 허용 목록은 사용하지 않는다. DNS 조회 시간·동시성·체인 길이·캐시 크기를 제한하며 조회 오류는 차단한다. CNAME 근거가 없다는 결과를 비-Greeting 확정으로 표현하지 않는다.

FE는 SK·현대의 기존 선택 우선순위를 유지하며 유일한 최상위 `basicInformation.name`, `basicInformation.phoneNumber.nationalNumber` 입력과 소유한 Greeting field 구조 등 공통 DOM 속성으로 화면 어댑터를 선택한다. 수집·준비·입력·재검증에서 일관된 선택을 유지하고 DOM 변경 때문에 검증된 Greeting 입력을 범용 실행기로 낮추지 않는다. 정적·범용 분석의 최종 결정은 BE가 담당하며 Greeting 화면에 범용 응답이 오면 입력을 중단한다.

`routingContext`, `executionAdapterId`, Greeting 전용 capability/header와 사용자별 토큰·만료·서버 메모리는 사용하지 않는다. 도메인별 DNS 결과 캐시는 내부 성능 최적화이며 사용자 세션 계약이 아니다. 준비 API → 필요한 준비 동작·재수집 → 필드 매핑 API → 로컬 값 결합·입력 순서를 유지하고, 서버 어댑터 지정을 위한 추가 준비 요청은 만들지 않는다. 기존 주소 검색 capability와 공통 입력 명령은 유지한다. 자세한 결정은 [Greeting ADR](adr/94-greeting-platform-routing.md)을 따른다.

BE는 정확한 DOM name·control·섹션·대학교/대학원 행과 프로필 의미를 매핑한다. FE는 학교·전공의 유일한 선택 코드, 버튼의 실제 선택 상태, 날짜 정밀도, 평점·만점 결합, 조건부 병역·보훈·장애와 기존 값 보호를 실행 직전까지 검사한다. 구조·값·프로필이 바뀌면 해당 필드를 보류하고 범용 매처로 우회하지 않는다. 인증·파일·동의·저장·제출은 실행하지 않는다.

Greeting 이름 없는 이메일 combobox는 단일 소유 라벨 `이메일주소` 또는 `이메일`일 때만 `basicInformation.email`로 수집한다. 두 형태의 칸이 함께 있거나 라벨·행 구조가 모호하면 식별하지 않는다. BE 이메일 의미 매핑은 유지하고 FE는 값 입력과 이메일 확인을 분리한다. 자동 테스트와 메디퀴터스 설치 확장의 비식별 3개 기본 필드 입력을 확인했으며 다른 Greeting 양식 전체의 지원 근거로 확대하지 않는다.

아래 설치 확장 관측은 2026-09-28 라우팅 단순화 이전의 증거다. 기존 필드 지원의 근거로 보존하며 이번 수정의 브라우저 재검증으로 취급하지 않는다. 이후 카카오게임즈 필드 확장의 실화면 관측과 최신 수정본 검증 한계는 별도 후속 절에 기록한다.

## DNS/DOM 자동 판별 검증 구분

이전 설치 확장 관측은 DNS/DOM 자동 판별 이전의 증거다. DNS/DOM 판별은 합성 회귀·정적 검사·빌드와 로컬 서버의 DNS/API 응답으로 검증했다. 이후 필드 확장의 카카오게임즈 설치 브라우저 관측은 별도이며 최신 수정본의 빈 지원서 전체 실행과 재실행은 아직 확정하지 못했다.

## Greeting 필드 확장 후속 경계

고교·대학 추가전공·경력·어학·자격증을 기존 BE 정책과 FE 실행기로 연결했다. 대학 추가전공은 기존 DERIVED 형식의 공통 규칙 목록을 확장하며 준비·필드 API의 필드는 추가하지 않는다. 수집·행 준비·검색 선택·재수집·결과 확인을 함께 검증한다. 최신 설치 브라우저 전체 실행은 확정하지 못했으며 상세 지원 범위와 관측 한계는 Greeting 어댑터 및 필드 현황을 따른다.
