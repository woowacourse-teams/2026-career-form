# Greeting 공통 어댑터

## 판정과 실행 경계

BE는 기존 등록 회사 정책을 우선한 뒤 정확한 Greeting 기본 도메인, 양성 CNAME 또는 명시 등록 근거로 공통 정책을 선택한다. FE는 host나 footer로 Greeting 여부를 판정하지 않는다. 협상된 `greeting-v1` 식별자와 불투명한 `routingContext`를 사용해 일반 수집 뒤 Greeting 구조를 다시 수집하고, 두 번째 준비와 fields에서 같은 판정을 검증한다. 양성 판정 뒤 정책 부재나 구조 불일치는 범용 분석으로 우회하지 않는다. 자세한 결정은 [CF-94 ADR](adr/94-greeting-platform-routing.md)을 따른다.

BE의 정적 규칙은 프로필 의미·명령·행 경계를 담당한다. FE는 현재 DOM의 정확한 이름과 제어 종류, 라벨 소유권, 선택지·코드, 반복 행의 종류와 인덱스, 기존 값을 입력 직전 다시 확인한다. 모호하거나 바뀐 필드는 입력하지 않는다. 프로필과 현재 입력값은 로컬에 두고 분석 요청에 싣지 않는다.

기업 질문, 영문 성·이름 순서가 불명확한 한 칸짜리 영문이름, 파일, 동의, 이메일 확인, 저장·제출은 자동 입력 대상이 아니다. 카카오모빌리티에 없는 프로필 범주를 다른 Greeting 회사에서도 지원한다고 추정하지 않는다.

## 이메일 표시명 호환

이름 속성이 없는 최상위 Greeting `combobox`는 자신이 소유한 라벨을 공백과 필수 표시 `*`를 제거해 읽는다. 정확히 `이메일주소` 또는 `이메일`인 칸이 문서 안에 하나일 때만 `basicInformation.email`로 식별한다. 이름 있는 칸, 반복 행 안의 칸, 다른 라벨, 두 표시명의 중복 칸은 이 경로로 연결하지 않는다. BE의 `contact.contact.email` 정적 규칙과 FE의 이메일 writer는 그대로 사용한다. writer는 값을 입력하되 이메일 확인·인증 버튼은 누르지 않는다.

## 검증 범위

- 비식별 전체 프로필을 적용한 카카오모빌리티 설치 확장 첫 실행에서 48개 입력 완료·확인 필요 0개, 대학 2행·대학원 1행과 기본·민감·학력 핵심 값 유지를 확인했다. 재실행에서 새 입력 0개·확인 필요 0개와 행 중복·값 손실 없음이 관측됐다.
- 현대오토에버 자체 도메인의 공개 지원서에서 이름·이메일·전화 3개 입력 완료·확인 필요 0개를 확인했다. 별도 공고(`238037`)에서 새로 빌드한 설치 확장으로 재검증했고, 재실행에서 세 값 유지·새 입력 0개·확인 필요 0개를 관찰했다.
- 무신사 자체 도메인의 공개 지원서에서 이름·이메일·전화 3개 입력 완료와 영문이름 확인 필요 1개를 확인했다. 한 칸의 영문이름은 조합 순서·구분자가 명시되지 않았다.
- 당근서비스 공개 지원서에서 이름·국적·이메일·전화 4개 입력 완료, 영문이름 확인 필요 1개를 확인했다. 재실행의 새 입력은 0개였다.
- 메디퀴터스 공개 지원서의 `이메일` 라벨·이름 없는 text combobox에서 비식별 프로필의 이름·연락처·이메일 3개 입력 완료와 이메일 값 유지를 확인했다. 기존 `이메일주소`와 새 `이메일`의 수집·입력 및 혼합 중복 거부를 자동 테스트했다.

이 수치는 각각 해당 공개 화면과 시점의 검증 결과다. 다른 Greeting 양식의 전체 필드 지원, 실제 저장·제출 호환성, 운영 정책 배포를 입증하지 않는다.
