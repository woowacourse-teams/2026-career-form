# 기존 API를 유지하는 Greeting DNS·DOM 공통 판별

> Status: Accepted
> Date: 2026-09-28
> Issue: [CF-94](https://github.com/woowacourse-teams/2026-career-form/issues/94)
> Approval-Digest: c2488a72f8044f14f8edd98d8b975422d669e2a1db3a6b15f0a94760985bc71a

## 배경

Greeting 기본 도메인과 기업 자체 도메인은 같은 입력 구조를 사용한다. 기업마다 host를 등록하면 새 채용 홈페이지를 공통 플랫폼으로 지원한다는 목표를 충족하지 못한다. 서버 지정 어댑터·판정 토큰 없이 기존 API를 유지하면서 공통 연결 근거와 화면 구조를 각각 검증한다.

## 검토한 대안

- 서버 지정 어댑터와 판정 토큰: 전용 API 필드·협상·만료·서버 상태가 필요하므로 채택하지 않는다.
- 기업별 자체 도메인 등록: 새 기업마다 FE·BE 수정이 필요하므로 공통 자동 판별로 대체한다.
- FE 텍스트·footer만으로 플랫폼 확정: 화면 표기만으로 BE의 라우팅을 확정하지 않는다.
- BE DNS 연결 확인과 FE 공통 DOM 어댑터 선택: 기존 API에 이미 있는 host/구조 메타데이터를 사용한다. 이 방식을 선택한다.

## 결정

1. BE는 기존 등록 회사 정책을 우선한 뒤 `site.host`와 지원서 `pathPattern`으로 Greeting 연결을 판정한다. 정확한 Greeting 기본 도메인 또는 제한된 DNS CNAME 조회에서 Greeting으로 이어지는 별칭을 확인하면 하나의 공통 정책을 선택한다. 기업별 자체 도메인 허용 목록은 사용하지 않는다. DNS 조회 시간·동시성·체인 길이·캐시 크기를 제한하며 조회 오류는 차단한다. CNAME 근거가 없다는 결과를 비-Greeting 확정으로 표현하지 않는다.
2. FE는 SK·현대의 기존 선택 우선순위를 유지하며 유일한 최상위 `basicInformation.name`, `basicInformation.phoneNumber.nationalNumber` 입력과 소유한 Greeting field 구조 등 공통 DOM 속성으로 화면 어댑터를 선택한다. 수집·준비·입력·재검증에서 일관된 선택을 유지하고 DOM 변경 때문에 검증된 Greeting 입력을 범용 실행기로 낮추지 않는다. 정적·범용 분석의 최종 결정은 BE가 담당하며 Greeting 화면에 범용 응답이 오면 입력을 중단한다.
3. `routingContext`, `executionAdapterId`, Greeting 전용 capability/header와 사용자별 토큰·만료·서버 메모리는 사용하지 않는다. 도메인별 DNS 결과 캐시는 내부 성능 최적화이며 사용자 세션 계약이 아니다. 준비 API → 필요한 준비 동작·재수집 → 필드 매핑 API → 로컬 값 결합·입력 순서를 유지하고, 서버 어댑터 지정을 위한 추가 준비 요청은 만들지 않는다. 기존 주소 검색 capability와 공통 입력 명령은 유지한다.
4. BE는 프로필 의미·정적 정책·준비 계획과 요청된 필드 구조를 검증한다. FE는 로컬 값 결합과 특수 제어를 실행한다. 알려진 Greeting의 정책 부재·구조 불일치는 LLM으로 우회하지 않는다.
5. 이름·전화·국적·학력의 의미 있는 name과 반복 행 인덱스를 사용하고 동적 id/UUID를 고정하지 않는다. 이름 없는 이메일은 combobox 구조, 소유 라벨 이메일주소/이메일, 유일성을 함께 확인한 뒤 합성 domName으로 전달한다. 일부 버튼·라디오는 구조·라벨·선택지를 함께 검증한다.
6. 기존 필드 지원·기존 값 보호·민감정보 개별 확인·최종 선택 코드 검사를 유지한다. 후속 승인에 따라 고교·경력·어학 등 대응 프로필 항목을 같은 정책·API 구조에서 확장한다. 대학 추가전공은 기존 DERIVED 형식의 공통 규칙 목록을 확장하며 별도 라우팅 필드를 추가하지 않는다. 프로필·현재 값·세션은 분석 API에 보내지 않는다. 기업 질문·파일·동의·인증·저장·제출은 실행하지 않는다.

## 결과와 제한

CNAME과 지원 구조를 확인할 수 있는 새로운 자체 도메인은 기업별 등록 없이 Greeting 공통 정책을 사용한다. 현대오토에버·무신사·카카오게임즈에서 Greeting CNAME을 관측했다. 숨겨진 CNAME 사례는 아직 관측하지 않았지만 DNS 근거가 없는 모든 사이트까지 자동 지원한다고 보장하지 않는다. DNS 조회 실패와 양성 근거 부재는 구분한다.

이전 설치 확장 관측은 DNS/DOM 자동 판별 이전의 증거다. DNS/DOM 판별은 합성 회귀·정적 검사·빌드와 로컬 서버의 DNS/API 응답으로 검증했다. 이후 필드 확장의 카카오게임즈 설치 브라우저 관측은 별도이며 최신 수정본의 빈 지원서 전체 실행과 재실행은 아직 확정하지 못했다.

## Greeting 필드 확장 후속 경계

고교·대학 추가전공·경력·어학·자격증을 기존 BE 정책과 FE 실행기로 연결했다. 대학 추가전공은 기존 DERIVED 형식의 공통 규칙 목록을 확장하며 준비·필드 API의 필드는 추가하지 않는다. 수집·행 준비·검색 선택·재수집·결과 확인을 함께 검증한다. 최신 설치 브라우저 전체 실행은 확정하지 못했으며 상세 지원 범위와 관측 한계는 Greeting 어댑터 및 필드 현황을 따른다.
