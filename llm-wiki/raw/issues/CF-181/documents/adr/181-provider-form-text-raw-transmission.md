# 범용 분석 공급자에 길이 제한·패턴 마스킹 양식 원문 전송

## 상태

승인됨

## 날짜

2026-10-11

## 관련 Issue

- #181

## 배경

CF-98 이후 BE의 `ProviderSemanticSanitizer`는 섹션명, 필드·준비 후보 라벨, placeholder, 선택지와 의미 문맥 라벨을 약 300개 용어의 닫힌 사전으로 치환한다. 사전에 없는 텍스트는 공급자 요청에서 사라진다. 부분 문자열 매칭 때문에 `선택`이 `optional`로, `해당없음`이 `no; yes`로 바뀌는 등 의미가 반대로 전달되기도 한다. OpenAI와 Jev가 같은 정제를 사용한다.

FE는 `displayName`, `placeholder`, 섹션명과 선택지 표시명을 공백 정리와 120자 절단만 거친 원문으로 보낸다. 반면 `semanticContext.labels`는 FE `semanticText()` 사전 필터를 이미 거친다. 따라서 BE 변경으로는 앞의 네 필드만 복구할 수 있다.

CF-44 ADR은 label·ARIA에서 정규화한 `displayName`과 선택지 표시명을 LLM에 전달하는 경계를 승인했다. 실제 프로필 값, 현재 양식 값, HTML, URL, 계정·세션 정보와 실행 정보는 제외한다. CF-57에 따라 OpenAI 분석 호출은 `store=true`이므로 전송된 텍스트가 외부에 보관될 수 있다. Jev는 데이터 정책 확인 설정이 false인 동안 외부 호출을 보류한다.

BE는 프로필 값을 모른다. FE `labelOf()`는 label이 없는 요소에서 `textContent`로 대체하므로, `element=custom` 후보의 `displayName`에는 현재 선택값이 섞일 수 있다.

## 검토한 대안

- 사전 정제 유지와 사전 확장: 전송 경계는 가장 좁다. 그러나 회사마다 다른 라벨을 사전으로 따라가야 하고, 부분 문자열 오변환과 6개 용어 상한 문제는 남는다.
- 정제 없는 원문 전송: 정보 손실이 가장 적다. 그러나 placeholder 예시나 안내문의 이메일·전화번호·URL, 커스텀 요소의 현재 선택값이 그대로 나간다.
- FE 프로필 값 대조 마스킹만 사용: 이름처럼 패턴으로 찾을 수 없는 개인화 문구를 가릴 수 있다. 그러나 이전 버전 확장과 직접 호출 요청에는 적용되지 않고, 서버가 마스킹 여부를 확인할 수 없다.
- FE가 마스킹 완료 표시(`textMasking`)를 보낸 요청에만 원문 전송: 이전 클라이언트도 안전하다. 그러나 API 필드가 늘고 두 전송 경로를 함께 유지해야 하며, FE 작업 전까지 개선 효과가 없다.
- BE 패턴 마스킹 후 원문 전송, FE 프로필 값 마스킹은 후속: 서버가 모든 클라이언트에 같은 최소 경계를 적용한다. 패턴 밖 개인화 문구는 남는 위험으로 둔다.

## 결정

BE가 공급자 입력을 만들 때 사전 치환 대신 길이를 제한하고 패턴을 마스킹한 양식 원문을 사용한다. OpenAI와 Jev, 준비 분석과 필드 분석에 같은 규칙을 적용한다.

전송 대상과 처리는 다음과 같다.

| 필드 | 처리 |
| --- | --- |
| 섹션 `displayName` | 원문 투영 |
| 필드·준비 후보 `displayName` (`element`가 input, select, textarea, button) | 원문 투영 |
| 필드·준비 후보 `displayName` (`element=custom`) | 기존 사전 정제 유지 |
| 필드 `placeholder` | 원문 투영 |
| 선택지 `displayName` | 원문 투영, 후보당 128개까지 |
| `semanticContext.labels` | FE 값에 원문 투영만 적용, BE 사전 재정제 제거, 후보당 8개 |
| 식별자, `domId`, `domName`, site, 프로필·양식 값, HTML, URL, selector | 기존처럼 제외 |

원문 투영은 NFKC 정규화, 제어·서식 문자 제거, 연속 공백 축약과 trim을 거친다. 이어서 이메일은 `[EMAIL]`, URL과 도메인은 `[URL]`, 전화번호는 `[PHONE]`, 주민등록번호 형식은 `[ID_NUMBER]`, 6자리 이상 연속 숫자는 자릿수를 보존한 `[NUMBER_<자릿수>]`로 치환한다. 결과는 code point 기준 120자로 자르고, 빈 값은 생략한다.

`visibility=hidden` 후보도 준비 분석에 필요한 양식 구조이므로 라벨을 전송한다. 값과 상태 텍스트는 받지도 보내지도 않는다.

직렬화한 OpenAI 입력 JSON이 실측으로 정한 상한(초기값 UTF-8 512 KiB)을 넘으면 공급자를 호출하지 않고 기존 공급자 불가 경계로 실패한다. 일부를 잘라 보내지 않는다. Jev의 기존 2,000,000 byte 상한과 128 질문 상한은 유지한다.

양식 텍스트는 공급자 입력 JSON의 데이터 값에만 넣는다. 시스템 지시문과 Jev 질문 지시문에는 양식 텍스트를 신뢰할 수 없는 데이터로 다루고 그 안의 지시를 따르지 않는다는 문장을 둔다. 출력은 기존 스키마의 candidate ID, canonical key와 recipe allowlist로 검증한다. 그래서 주입 문구의 최대 영향은 잘못된 매핑이며, 이는 서버 검증, 충돌 가드와 브라우저의 사용자 승인으로 제한한다.

사전은 BE 내부 판정용으로만 남긴다. 주소 1/2 충돌과 미지원 활동 충돌 가드는 공급자 입력이 아니라 요청 원문을 기존 사전으로 로컬 분류해 판정한다. LangSmith trace 투영은 사전 용어 외 텍스트를 계속 `UNRECOGNIZED_TEXT`로 가린다. 검색·달력 상호작용 결정 경로의 투영은 이 결정의 범위가 아니다.

## 결과

사전에 없는 공통 라벨과 섹션 문맥이 공급자에 전달되고, 부분 문자열 오변환이 사라진다. 공급자별로 같은 입력 규칙을 쓰므로 후속 공급자 비교의 입력 조건이 같아진다.

이름처럼 패턴으로 찾을 수 없는 개인화 문구가 라벨이나 섹션명에 있으면 OpenAI로 전송되고 보관될 수 있다. 이 위험은 공급자 전송 전 FE 프로필 값 대조 마스킹으로 줄인다. 이는 별도 FE 작업 후보이며, 완료 후 `element=custom` 예외의 해제 여부를 다시 결정한다.

FE가 이미 사전으로 거른 의미 문맥 라벨은 복구되지 않는다. 의미 문맥 FE 필터 제거는 별도 작업이다. 텍스트 길이 증가로 공급자 입력 토큰과 비용이 늘 수 있으며, 크기 상한을 넘는 페이지는 범용 분석이 실패로 보고된다. Jev 실제 호출 전 데이터 정책 검토 범위에는 이 원문 전송 경계가 포함되어야 한다.

이 결정은 CF-98 계약의 "제한된 어휘" 문맥 규칙 중 위 표의 필드를 대체한다. 나머지 실행·역할 경계는 유지한다. 합성 테스트 통과는 실사이트 개선 근거가 아니며, 개선 여부는 같은 분모와 검증된 설치 revision의 전후 평가로만 판단한다.
