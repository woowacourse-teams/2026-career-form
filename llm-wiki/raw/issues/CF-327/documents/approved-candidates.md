# CF-327 approved candidates

1. [deployment-runbook] 운영 배포 흐름은 workflow 구현이 정본이다. main push는 head ref로 분류한다: release/<ver>→release, hotfix/CF-N→hotfix, revert/<sha>→revert, 그 외는 실패. release는 PR head tree와 main merge tree가 같아야 하고, staging이 push한 <image>:<head sha>의 digest를 재사용하며(재빌드 없음) 그 tag가 없으면 실패한다. 성공 시 annotated v<ver> tag를 만들고 release head가 develop 조상이 아니면 '[Release] <ver> 개발선 동기화' PR을 만든다. hotfix는 main sha로 새 ARM64 이미지를 빌드해 직접 배포하고 main→develop(활성 release가 있으면 main→release) PR을 만들며 tag는 만들지 않는다. revert/* 병합은 image·deploy를 skip해 재배포하지 않는다. deploy.sh는 current-digest로 자동 rollback한 뒤에도 exit 1이라 revert/<main-sha> Draft PR이 생성되고, rollback 실패는 로그 문자열로만 구분된다. 릴리스 점검표: 병합 전(staging 배포 SHA=release head, staging E2E, main 커밋이 모두 release에 포함, 운영 설정 변경 여부, 확장 보급), 병합(Merge Commit만), 병합 후(digest 일치, v<ver> tag, 동기화 PR Merge Commit, 스토어 확장으로 운영 스모크). 근거: .github/workflows/deploy-production.yml, infra/scripts/classify-main-merge.py, infra/scripts/release-sync.py, infra/scripts/deploy.sh, infra/RELEASE.md.

[extension-release] 확장 프로그램 릴리스는 CI 밖의 수동 절차다. frontend-ci는 테스트와 커버리지만 실행하고 빌드·ZIP·Web Store·VITE_API_BASE_URL 단계는 어느 workflow에도 없다. 절차: (1) Web Store 게시본보다 높은 version으로 frontend/wxt.config.ts와 package.json을 올린다 (2) VITE_API_BASE_URL=<환경 origin> npm run zip — origin만 허용되고 값이 manifest host_permissions에 고정되므로 주소가 바뀌면 재빌드·재심사가 필요하다. 로컬 .env*는 gitignore라 빌드 PC 설정이 그대로 들어가며 미지정 빌드는 NOT_CONFIGURED로 동작한다 (3) ZIP의 version, host_permissions, build-info revision을 확인한다 (4) 사람이 업로드·심사·게시한다 (5) 품질 수집의 extensionVersion 분포로 보급을 확인한다. 확장 버전은 릴리스 태그와 독립으로 관리한다. 스테이징 검증용 확장은 스테이징 origin으로 별도 빌드한다(CF-183 선례). 2026-10-23 기준 게시본은 0.4.0이고 소스는 0.1.0으로, 지금까지 업로드 시 로컬에서만 버전을 올려 왔다. 근거: frontend/README.md, frontend/wxt.config.ts, frontend/scripts/assert-zip.mjs, frontend/scripts/assert-release-flags.mjs.

[release-compatibility] 확장과 백엔드는 배포 시점이 다르므로 호환을 설계한다. 현재 장치: /api/v1 경로, X-Career-Form-Capabilities 요청 헤더(address-search-v1, quality-v2), 품질 수집의 extensionVersion, 새 확장이 없는 엔드포인트의 404를 ENDPOINT_UNAVAILABLE로 강등하는 처리. 규칙: 응답 스키마가 바뀌면 경로 버전 또는 capability 협상으로 구 클라이언트에 기존 스키마를 유지하고, 요청 변경은 nullable 추가로 한정하며, 릴리스 PR에 FE/BE 호환 매트릭스를 기록한다. 외부 사용자가 있으면 새 확장 게시 → 보급 확인 → 백엔드 배포 순서를 따른다(CF-177 K39). 1.4.0 사례: Hplace v4 네이티브 정책이 /api/v1/execution-policy 응답 스키마를 버전 표시 없이 바꿔 구 확장이 응답 전체를 거부할 수 있었고(로컬 validator probe 근거, 브라우저 종단 검증 아님), 요청 DTO 변경은 nullable 추가라 호환이었다. 외부 사용자가 있어 확장 0.4.0을 먼저 게시한 뒤 백엔드를 main에 병합했다. 근거: frontend/src/autofill/api/background-handler.ts, frontend/src/autofill/generic/generic-analysis.ts, backend/.../PreparationAnalysisController.java, llm-wiki/raw/issues/CF-177/documents/contract-decisions.md.
4. [adapter-hplace] Hplace 활성 정책 버전은 DB 포인터가 아니라 Spring 속성 careerform.hplace.active-policy-version이며 기본값이 4다. HplaceFormPolicySeeder는 v3·v4 문서를 없을 때만 insert하고, MongoHplacePolicyProvider는 설정값으로 문서를 고른다(4가 없으면 3). application-prod.yml, infra/compose.deploy.yaml, deploy workflow 어디서도 이 값을 전달하지 않아 백엔드 배포 즉시 v4가 활성화되고 운영에서 끌 레버가 없다. 끄거나 v3로 되돌리려면 설정 전달 경로를 추가하는 infra 변경이 필요하다. 기존 raw의 'DB 활성 포인터를 사람이 올린다'는 서술을 이 내용으로 정정한다. 근거: backend/.../MongoHplacePolicyProvider.java, backend/.../HplaceFormPolicySeeder.java, infra/compose.deploy.yaml.
