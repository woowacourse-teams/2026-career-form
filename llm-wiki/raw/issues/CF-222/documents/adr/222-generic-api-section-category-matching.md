# 범용 전용 API 분리와 섹션 분류 기반 범주별 칸 매칭

## 상태

제안됨 (CF-222 초안. 구현 결과를 반영한 확정은 계획 Task17에서 한다)

## 날짜

2026-10-16

## 관련 Issue

- #222

## 배경

공유 API인 /api/v1/fields/analyze와 /api/v1/preparation/analyze는 정적 정책 사이트와 범용 사이트가 함께 쓴다. 사용자는 범용 개선이 정적 어댑터 동작에 영향을 주면 안 된다고 조건을 걸었다(UC1). 현재 범용 매칭에는 세 가지 공백이 있다.

- 섹션 구분: 수집기는 fieldset, section, role=group 조상만 섹션으로 인식한다. 이런 컨테이너가 없으면 페이지 전체가 섹션 하나가 된다(GAP-2).
- 넓은 선택지: 칸마다 프로필 키 약 130개 전체를 선택지로 묻고 배치를 순차로 호출한다(GAP-3).
- 결과 품질: 비교 실험에서 토큰 초과, 학력 칸의 낮은 확신도, 범주를 넘는 오답(예: 국가번호를 국적에, 추천인 연락처를 본인 전화에 매칭)이 함께 나타났다. 세 문제는 모두 선택지가 넓은 데서 비롯된다.

## 검토한 대안

1. 공유 API에 범용 모드 필드나 플래그 추가: 엔드포인트 수가 늘지 않는다. 하지만 공유 요청·응답 계약과 서비스가 바뀌어 정적 경로와 구버전 확장 호환성에 회귀 위험이 생긴다. 폐기한다.
2. 범용 전용 API를 /api/v1/generic/** 아래에 신설(D10): 공유 계약을 건드리지 않고 범용 판단을 독립적으로 바꿀 수 있다. 대신 DTO 일부를 복제하고 배포 순서를 관리해야 한다. 채택한다.
3. 전체 키를 한 번에 묻는 매칭에 배치 크기 조정만 추가: 변경이 작다. 하지만 범주를 넘는 오답과 낮은 확신도는 그대로 남는다. 범주가 확정되지 않은 섹션의 안전망으로만 유지한다(E12).
4. 섹션 분류 뒤 범주별로 좁힌 선택지로 매칭(E7): 세 문제의 공통 원인을 줄인다. 대신 섹션 경계가 틀리면 효과가 사라진다. 안전 실패 규칙을 두고 채택한다.
5. 섹션 단위 정의 비교(E8):
   - 시맨틱 컨테이너만 쓰는 방식(현재): 마크업이 없는 사이트에서 섹션 하나로 뭉친다.
   - 제목만 쓰는 방식: 제목 판정이 사이트마다 흔들린다.
   - 문서 순서상 연속한 입력란 묶음을 단위로 삼고 제목은 보조 근거로 쓰는 방식: 위 두 방식의 약점을 피한다. 채택한다.
6. 반복 행 매핑을 키 접두사만 바꿔 재사용(예: 2행 결과를 3행에 index만 바꿔 적용, E11): 호출 수가 줄어든다. 하지만 변형 블록의 구조가 같다는 근거가 없다. 폐기하고 구조 지문이 완전히 같은 행에 한해서만 결과를 재사용한다.

## 결정

대안 2, 4, 5를 채택한다.

API 경계:
- 범용 전용 API는 /api/v1/generic/** 아래에만 둔다.
  - POST /api/v1/generic/sections/classify: 섹션 범주 분류
  - POST /api/v1/generic/fields/analyze: 섹션별로 범주를 좁혀 칸 매칭
- 두 API는 신규 패키지(com.careerform.formanalysis.generic)와 신규 port(SectionClassifier), 신규 resolver 경로로 구현한다(D14). 기존 JevFieldMappingResolver는 공유 endpoint용으로 남긴다.
- 각 서비스는 FormAnalysisRouter.routeGeneric을 거친다. 정적 정책이 있는 요청은 STATIC_POLICY_PRESENT로 단락하고, 정책을 확인할 수 없는 요청도 기존 단락을 그대로 따른다. 이때 공급자를 호출하지 않는다.

공유 API 불변 범위:
- 다음은 변경하지 않는다.
  - FieldsAnalysisController, PreparationAnalysisController
  - FieldsAnalysisService, PreparationAnalysisService
  - Fields·Preparation DTO
  - FormAnalysisRouter의 ADAPTER 분기
  - FieldInteractionPolicy
- 정적 정책 관련 파일(application/policy, persistence/mongo, dns)과 FE 정적 어댑터·정책 파일도 수정하지 않는다.
- 유일한 예외: Task15·16의 설정과 provider 등록 변경으로 공유 API의 범용 resolver가 OpenAI에서 JEV로 바뀐다. 이 예외도 서비스·DTO 수정이나 정적 경로 변경을 허용하지 않는다. 다음 두 회귀 테스트로 경계를 고정한다.
  - 구버전 요청 JSON에 대해 기존 응답 DTO, 상태 코드, 실패 표현이 유지된다.
  - 정적 정책 요청은 JEV를 호출하지 않는다.

FE 경계:
- 새 판단 로직은 문서 회사 판정이 generic일 때만 실행하는 frontend/src/autofill/generic 모듈에 둔다.
- 공유 파일에는 게이트 분기만 추가한다. 예외는 계획 Task11·12·13·18에 명시한 선택 인자와 결과 전달뿐이다. 인자를 생략한 기존 호출은 종전 동작을 유지한다.
- 범용 코드에는 회사명, 호스트, 회사별 DOM 식별자, 한 사이트에서 유래한 규칙을 넣지 않는다. 범용 규칙은 서로 무관한 사이트 2곳 이상의 fixture로 근거를 갖춰야 한다.

섹션 정의:
- 섹션은 문서 순서상 연속한 입력란 묶음이다.
- 경계 우선순위: 반복 그룹 > 시맨틱 컨테이너(fieldset, section, role=group, table) > 입력란 사이의 제목형 요소 > 공통 조상이 갈라지는 지점
- 제목은 보조 근거다. 라벨 요소는 경계로 쓰지 않는다. 제목이 없는 평면 폼은 섹션 하나로 본다.
- 섹션 분할은 개별 필드 라벨 수집을 대체하지 않는다.

범주와 매칭:
- 범주는 지원 프로필 키 접두사에서 생성한다: PERSONAL, EDUCATION, LANGUAGE, CERTIFICATE, CAREER, PROJECT, PUBLICATION, COMPENSATION, SENSITIVE, NONE, MIXED, ABSTAIN.
- 건강 항목은 범용에서 NONE으로 분류한다.
- 섹션별 질문은 해당 범주 키와 ABSTAIN만 선택지로 쓰고, 상태 정보는 그 섹션과 부모 섹션으로 한정한다.
- 섹션 단위 호출은 제한 병렬로 실행한다(기본 동시 3). 섹션 안 질문은 배치로 나눈다(기본 5). 토큰 초과가 나면 배치를 반으로 나눠 다시 시도한다.

안전 실패:
- 섹션 경계나 범주가 불확실하면 MIXED나 ABSTAIN으로 분류한다. 이런 섹션은 NONE을 뺀 전체 키로 묻고, 결과 등급을 한 단계 낮춘다. 확정 범주처럼 자동 선택하지 않는다.
- 한 섹션의 분류나 매칭이 실패하면 그 섹션만 입력 불가로 처리하고 나머지는 진행한다.

배포 순서:
- 새 BE 엔드포인트를 먼저 운영에 배포한 뒤 이를 호출하는 FE를 배포한다.
- 새 확장이 옛 백엔드에서 404를 받으면 해당 섹션을 BLOCKED(ENDPOINT_UNAVAILABLE)로 처리한다. 배포는 사람이 수행한다.

## 결과

- 범용 판단을 정적 경로와 분리해 바꿀 수 있다. 정적 어댑터 회귀는 모든 후속 Issue의 STATIC-REGRESSION으로 검증한다.
- 선택지가 범주로 좁혀져 토큰 초과와 범주를 넘는 오답이 줄어들 것으로 기대한다. 효과는 범주 확정 커버리지, 틀린 확정 비율, 평가 계약 1.1 지표로 측정한다. 아직 측정 전이므로 기대 효과로만 기록한다.
- 비용: 공유 DTO와 유사한 신규 DTO를 유지해야 하고, 엔드포인트 배포 순서를 관리해야 하며, 섹션 경계 판정이 사이트마다 흔들릴 수 있다.
- 공유 파일에 이미 있는 회사별 분기와 섞인 행 처리 규칙은 범위 밖의 기존 상태로 남긴다. 범용 경로는 이를 확장하거나 호출하지 않는다.
