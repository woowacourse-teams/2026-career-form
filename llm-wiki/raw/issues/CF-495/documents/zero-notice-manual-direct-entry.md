# 0건 안내 문구 레이어의 직접 쓴 값 직접입력

> Issue: [CF-495](https://github.com/woowacourse-teams/2026-career-form/issues/495)
> Collected: 2026-11-19
> Approval-Digest: 95d9a08fb7f050f23358c7ffd4b466ef29f8d9e8d4405fb90840117ce2f73a2e
> Source-Revision: eeb8aaa

[승인 후보 스냅샷](approved-candidates.md)의 후보 1~3을 적는다. 이름+등급 정확 일치는 Supersedes가 가리키는 CF-490 근거를, 직접입력 신호의 0건 인식과 행 저장 연쇄는 CF-488 근거를 그대로 따른다.

## 진입 조건 (후보 1, commit 3cd3d3c)

- 범용 검색에서 결과 0건이 확인되면, 0건 안내 문구로 확인했는지 직접입력 신호로 확인했는지와 상관없이 레이어의 유일한 직접입력 경로로 프로필 원문을 기입하고 확인한다.
- 프로필 값을 카탈로그에서 골랐는지와도 상관없다. CF-488은 0건 안내 문구가 없는 레이어에서만 직접 쓴 값을 허용했다.
- 유지한 안전 조건: 마지막 검색 시도(또는 페이지가 검색어 입력을 교체한 시도), 직접입력 버튼 1개, 버튼을 누른 뒤 새로 보이는 입력칸 1개, 확인 버튼 1개, 결과 1건 이상이면 사용 안 함, legacy 경로 제외.
- 버튼을 눌러도 입력칸이 생기지 않으면 `unverified_search_form`으로 기입하지 않고 레이어가 열린 채 남는다.

## 확인 단계와 후속 칸 대기 (후보 2, commit eaf1afd·eeb8aaa)

- 직접입력 값에는 사이트 코드가 없다. `bindSelectionEffects(..., { directEntry: true })`는 행의 숨은 코드 칸을 묶거나 요구하지 않는다(여러 개여도, 직접입력 뒤 비어 있어도 실패 아님). 같은 행의 숨은 input 변화는 사이트 처리로 보아 불변 검사에서 뺀다.
- 대상 칸 값이 프로필 원문과 같은지, 보이는 다른 칸과 행 밖 칸이 바뀌지 않았는지는 그대로 확인한다.
- `captureSearchFollowUp(..., { directEntry: true })`는 기준 시점에 준비되지 않은(숨은) select를 기다릴 대상으로 두지 않는다. 실제로 바뀐 칸은 준비될 때까지 기다린다.

## 실측과 교훈 (후보 3)

- 진단 빌드, 합성 프로필, 범용 경로 지원서 1곳. 수정 전에는 직접 쓴 값의 0건 검색 5건이 모두 레이어를 닫고 끝났다(기입 47칸).
- 진입 조건만 푼 1차 빌드: 행의 숨은 칸 11개로 `selection_effect_unverified`(직접입력 클릭 전), 직접입력 뒤 빈 코드로 `selection_postcondition_failed`, 뒤 항목 기입이 36칸으로 줄었다. 2차 빌드: 값은 들어갔지만 숨은 select 2개 후속 대기로 `result_pending`.
- 최종 빌드: 5건 모두 직접입력으로 끝났고 기입이 52칸으로 늘었다.
- 교훈: 직접입력 경로는 진입 조건, 결과 코드 검증, 후속 칸 대기 세 단계를 모두 실측으로 확인한다. 한 단계만 고친 빌드는 다음 단계에서 다른 사유로 실패하며, 실패 위치가 바뀌어 뒤 항목 기입이 오히려 줄 수 있다.
