# 도로명주소 검색의 백엔드 프록시와 검색어 개인정보 처리

## 상태

승인됨 (`25240f97b8ef1c28071040dd1ffc96330a753408f2b6756ece4dcda3d216b02c`)

## 날짜

2026-11-04

## 관련 Issue

- #392
- #393 (프로필 화면 연결 후속)

## 배경

프로필 주소가 자유 입력이라 오타나 비표준 표기가 있으면 지원서 사이트의 주소 검색에서 기입이 실패한다. 표준 주소를 고르게 하려면 확장이 주소 검색 결과를 받아야 한다. 행정안전부 도로명주소 검색 API는 승인키가 필요하고 서버 호출을 권장한다. 검색어는 사용자의 거주지를 드러낼 수 있으므로 개인정보로 다룬다. 지금까지 백엔드는 실제 프로필 값을 받지 않았고, 이 API가 그 경계를 처음 넘는다.

## 검토한 대안

- 호스팅 페이지와 카카오 우편번호: 확장 CSP를 피할 수 있고 승인키가 필요 없다. 그러나 운영할 웹 페이지와 확장 사이의 메시지 연결이 새로 생기고, 검색어가 또 다른 제3자에게 가며, 결과 형식을 우리가 통제하지 못한다. 기각한다.
- 확장에서 행정안전부 API 직접 호출: 서버를 거치지 않아 검색어가 우리 서버에 오지 않는다. 그러나 승인키를 확장 번들에 넣어야 하고 번들의 값은 누구나 꺼낼 수 있다. 응답의 CORS 허용 여부와 관계없이 기각한다.
- 확장 페이지에서 카카오 우편번호 스크립트 직접 로드: MV3 CSP와 원격 코드 금지로 쓸 수 없다. 기각한다.
- 백엔드 GET 프록시(`?query=`): 구현은 단순하지만 검색어가 URL에 실려 리버스 프록시 접근 로그, 서버 span의 URL 속성과 브라우저 기록에 남을 수 있다. 기각한다.
- 백엔드 POST 프록시: 승인키를 서버에 두고 검색어를 본문으로만 옮긴다. 채택한다.

## 결정

1. 확장은 `POST /api/v1/address/search`에 JSON 본문 `{query, page}`로 요청한다. URL에 검색어를 싣지 않으려고 POST를 쓴다. 다른 확장 호출 API와 같이 별도 CORS 설정 없이 확장의 host permission으로 접근한다.
2. 백엔드도 외부 API를 폼 본문 POST로 호출해 승인키와 검색어가 외부 호출 URL에 나타나지 않게 한다. 기준 URL은 설정으로 바꿀 수 있고 재전송은 따라가지 않는다.
3. 승인키는 환경 변수 `JUSO_API_KEY`로만 주입한다. 키가 없어도 애플리케이션은 시작하며 검색 요청만 503 `ADDRESS_SEARCH_NOT_CONFIGURED`로 응답한다.
4. 검색어는 공백을 제거한 뒤 1자 이상 80자 이하, 페이지는 1 이상 100 이하만 받고 나머지는 400 `INVALID_INPUT`이다. 특수문자는 변환하지 않고 외부 API 판단에 맡긴다.
5. 외부 API의 HTTP 오류, `errorCode` 오류, 시간 초과, 연결 실패와 형식 위반은 모두 502 `ADDRESS_SEARCH_UNAVAILABLE` 하나로 바꾼다. 외부 메시지를 응답과 로그에 옮기지 않으며, 로그에는 닫힌 사유와 HTTP 상태, 형식이 확인된 오류 코드만 남긴다.
6. 검색어와 승인키는 로그, 지표 태그, 트레이스와 오류 응답에 넣지 않는다. 요청과 응답 객체의 `toString`도 값을 가린다. LangSmith 추적은 이 경로에 연결하지 않는다. 응답은 `Cache-Control: no-store`이고 서버 캐시는 두지 않는다.
7. 기존 백엔드에 요청 제한 정책이 없어 프로세스 메모리의 클라이언트별 고정 창 제한을 둔다. 기본값은 60초당 30회, 추적 클라이언트 10,000개이며 설정으로 바꿀 수 있다. 키는 기존 로그인 제한과 같은 `request.getRemoteAddr()`이고 창이 바뀌면 전체를 비운다. 상한에 닿으면 새 클라이언트는 창이 끝날 때까지 429 `RATE_LIMITED`다.

## 결과

- 승인키가 확장과 저장소 밖에 남고, 확장은 하나의 응답 형식과 오류 코드만 다룬다.
- 사용자가 입력한 주소 검색어가 우리 서버와 행정안전부로 전달된다. 저장하지 않지만 로컬 우선 원칙의 예외이므로 후속 화면(#393)은 사용자가 직접 검색할 때만 호출해야 한다.
- URL에 검색어를 실은 잘못된 GET은 405로 거부하고 기본 로그 수준에서는 남지 않는다. 다만 `org.springframework.web` DEBUG는 요청 URL 전체를 기록하므로 운영에서 켜지 않는다.
- 외부 API의 입력 오류(예: 너무 짧은 검색어)도 502로 보인다. 원인을 구분하지 않는 대신 외부 메시지가 흘러들 경로를 없앤다.
- 제한 상태는 인스턴스별이고 재시작하면 사라진다. 여러 인스턴스로 늘리면 실제 한도는 인스턴스 수만큼 커진다. 창 경계에서는 짧게 두 배까지 허용될 수 있고, 상한이 찬 동안 새 클라이언트는 거부된다.
- 프록시 뒤에서 `SERVER_FORWARD_HEADERS_STRATEGY`가 `none`이면 모든 사용자가 같은 클라이언트로 묶인다. 환경별 값은 운영 설정에서 확인해야 한다.
- 승인키 발급, 배포 설정 전달과 실제 키 호출 확인은 사람이 수행한다.
