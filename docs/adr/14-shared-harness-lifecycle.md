# 공용 하네스 실행 및 CF 스킬 생명주기 표준화

## 상태

승인됨

## 날짜

2026-08-13

## 관련 Issue

- #14

## 배경

공용 하네스는 Windows와 POSIX에서 실행되며 저장소 스킬과 사용자 및 플러그인 스킬이 함께 발견되는 환경을 지원해야 한다. 기존 하네스는 POSIX Python 경로와 Python 파일 직접 실행에 의존했다. 일반적인 스킬 이름과 외부 플러그인 참조, Draft PR 이후 종료 책임 부재도 환경별 실행 편차를 만들었다.

사람의 Issue 계약 승인과 PR 최종 머지는 유지한다. 전체 흐름은 승인 지점에서 멈추고 GitHub 상태를 정본으로 재개할 수 있어야 한다.

## 검토한 대안

- Windows 실행, 템플릿, 스킬과 종료 흐름을 별도 Issue로 나누면 같은 공용 하네스 경계와 검증 경로를 반복 변경한다.
- 팀원의 로컬 중복 스킬을 비활성화하면 개인 환경을 저장소가 통제하게 된다.
- 단계별 스킬을 하나의 파일로 합치면 독립 호출과 단계별 eval을 잃는다.
- `cf-finishing-a-development-branch`에 Project 종료까지 추가하면 범용 Git 통합 선택과 이 저장소의 사람 머지 정책이 충돌한다.

## 결정

1. 하네스는 Windows의 `.venv/Scripts/python.exe`와 POSIX의 `.venv/bin/python`을 인식하는 공통 Python 선택 계약을 사용한다.
2. Issue Form과 PR 템플릿을 본문 생성 원본으로 사용하고 계약 검증기는 독립 안전 기준으로 유지한다.
3. 저장소의 모든 스킬 이름에 `cf-`를 붙인다. 팀원의 개인 스킬을 강제로 비활성화하지 않는다.
4. 단계별 스킬은 독립 호출 가능하게 유지하고 `cf-issue-lifecycle`이 Project draft 기획, Issue 구현, 사람 머지 대기와 머지 후 정리를 연결한다.
5. 고위험 결정이나 중요한 ADR 대안은 `cf-grill-me`, 불명확한 요구사항은 `cf-deep-interview`가 담당한다.
6. 구현은 계획, 실행, TDD, 검증과 리뷰 단계를 실제 호출 관계로 연결한다.
7. `cf-post-merge-cleanup`은 검증된 병합 자원만 멱등적으로 정리한다. `cf-finishing-a-development-branch`는 표준 Issue 생명주기에 사용하지 않는다.
8. 공용 스킬은 Orca와 특정 로컬 플러그인에 의존하지 않는다.
9. 비식별 사용자 프롬프트를 라우팅 eval로 보존하고 중복 스킬 환경의 포함 및 배제 결과를 기록한다. 정적 HTML viewer는 만들지 않는다.

## 결과

- 운영체제와 로컬 플러그인 구성 차이로 인한 실행 및 라우팅 편차가 줄어든다.
- 템플릿, 계약 검증기와 생성 결과의 관계가 구분된다.
- Draft PR 이후 머지 확인과 안전한 정리 책임이 생긴다.
- 스킬 이름과 문서 및 eval을 함께 변경하므로 diff가 크고 외부 upstream 갱신 시 이름과 내부 참조를 다시 맞춰야 한다.
- 원 플로우는 사람의 승인과 머지를 대신하지 않으며 여러 세션에서 원격 상태를 다시 확인해야 한다.
