# PLAN 작업 영역과 ADR 자산화 흐름

## 상태

승인됨

## 날짜

2026-08-13

## 관련 Issue

- #10

## 배경

기존 작업 영역은 구현 책임을 나타내는 `FE`, `BE`, `Infra`, `Harness`만 허용했다.
조사, 요구사항 정리와 문서 기획을 독립된 작업으로 관리할 영역이 없었고, 기획 대화에서
검토한 대안과 장기 결정은 저장소 자산으로 남지 않았다.

기획 단계는 Issue 계약 승인 전이므로 저장소 파일을 수정할 수 없다. ADR을 기획 대화
도중 바로 작성하면 기존 승인 게이트와 충돌한다.

## 검토한 대안

### 구현 영역 안에서 기획 작업 관리

새 영역을 추가하지 않아도 되지만 기획 산출물과 구현 산출물의 책임이 구분되지 않는다.

### 모든 PLAN Issue에 ADR 의무화

모든 기획 결론을 남길 수 있지만 일시적인 조사와 작업 순서까지 ADR로 쌓여 중요한
결정을 찾기 어려워진다.

### 장기 결정이 있는 PLAN Issue만 ADR 작성

구현 전 작업을 넓게 관리하면서 후속 작업에 지속적으로 영향을 주는 결정만 보존할 수
있다. ADR 전문은 승인 전에 검토하고 파일은 승인 후 작업 브랜치에서 작성할 수 있다.

## 결정

- `[PLAN]`은 조사, 요구사항 정리와 문서 기획 같은 구현 전 작업 전반에 사용한다.
- 여러 대안을 검토했고 결과가 후속 작업, 제품 정책, 아키텍처, 보안, 데이터 또는 공용
  워크플로우에 지속적으로 영향을 줄 때만 ADR을 작성한다.
- `status:planning`에서는 ADR 전문과 대상 경로를 Issue 계약과 함께 검토한다.
- 사람이 승인한 뒤 `CF-*` 브랜치에서 ADR 파일을 작성해 같은 PR에 포함한다.
- `[PLAN]`은 기획 자산만 반영하는 작업을 기본으로 한다. 처음 승인된 Issue 계약에
  구현이 포함돼 있으면 같은 Issue에서 구현까지 진행할 수 있다.
- 기획 중 새로 발견된 구현 범위는 별도 Project draft 후보로 제안한다.

## 결과

구현 전 작업을 Project와 Issue에서 추적할 수 있고 장기 결정의 근거를 저장소에서 다시
찾을 수 있다. ADR 작성 여부와 전문은 사람 승인 대상이 되며 승인 전 파일 수정 금지
원칙을 유지한다. 기획 전용과 기획 및 구현 결합 작업을 모두 허용하므로 Issue 계약이
작업 경계를 명확히 밝혀야 한다.
