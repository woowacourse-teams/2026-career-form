# worktree별 워크플로우 체크포인트 도입

## 상태

승인됨

## 날짜

2026-08-20

## 관련 Issue

- #34

## 배경

여러 Skill을 연결한 Issue 작업이 중단되면 AI는 계획, 구현, 검증, Draft PR 생성 중 어느 단계였는지 대화 내용으로 다시 판단했다. 이 방식은 완료한 단계를 반복하거나 현재 HEAD를 검증하지 않고 다음 단계로 넘어갈 수 있다.

사용자는 ESC로 실행을 중단하거나 작업과 관계없는 질문을 한 뒤 같은 작업을 다시 이어갈 수 있어야 한다. 병렬 worktree에서는 각 작업의 진행 상태가 섞이지 않아야 하고, 완료 여부는 실제 Git, 계획 파일, 검증 결과와 Draft PR 상태로 다시 확인해야 한다.

## 검토한 대안

- 환경변수는 세션이 끝나면 사라진다. 병렬 worktree에서는 어떤 작업의 상태인지 구분하기 어렵다.
- `MEMORY.md`는 진행 메모에는 쓸 수 있지만 실제 Git과 검증 결과가 일치하는지 강제하지 못한다. AI가 읽지 않거나 다른 대화 맥락으로 판단할 수도 있다.
- 저장소의 추적 파일은 팀에 불필요한 진행 상태 diff를 만들고 병렬 작업 충돌을 일으킨다.
- worktree 전용 Git 디렉터리는 Git에 커밋되지 않으면서 각 worktree에 별도 경로를 제공한다.

## 결정

1. 체크포인트는 `git rev-parse --git-path cf-workflow/checkpoint.json`으로 구한 worktree 전용 Git 디렉터리에 저장한다.
2. 단계는 `plan`, `implementation`, `verification`, `draft_pr`로 제한한다. 구현 계획 내부 Task와 Step은 기록하지 않는다.
3. 각 단계를 실행하기 전에 `running` 상태와 시작 HEAD를 원자적으로 저장한다. 완료 뒤에는 완료 HEAD와 계획 경로, 구현 commit, 검증 명령, PR 번호처럼 실제 결과를 확인할 근거를 저장한다.
4. 재개 시 체크포인트를 현재 브랜치, HEAD, 계획 파일, worktree 변경과 Draft PR 상태에 대조한다. 완료 근거가 맞는 단계는 반복하지 않고 첫 미완료 단계부터 이어간다.
5. 검증 완료 HEAD와 현재 HEAD가 다르거나 worktree에 커밋되지 않은 변경이 있으면 verification 단계부터 다시 실행한다.
6. Draft PR 생성 전에 현재 HEAD의 검증 완료 근거를 PreToolUse 훅에서 확인한다. 근거가 없으면 `gh pr create`를 차단한다.
7. 실제 Draft PR이 있으면 완료 기록이 없어도 생성하지 않고 기존 PR을 근거로 기록을 보완한다.
8. 작업과 관계없는 질문은 허용하며 체크포인트를 변경하지 않는다. 사용자가 작업 재개를 명시한 경우에만 상태 대조를 시작한다.
9. 체크포인트가 없거나 손상됐거나 Issue와 브랜치가 다르면 대화 맥락으로 진행 지점을 추측하지 않는다.
10. Issue 기획은 계약 초안을 `status:planning`으로 먼저 게시한다. 사용자가 승인한 원격 본문의 SHA-256 digest와 ready 직전 최신 digest가 같은 경우에만 `status:ready`로 전환한다.

## 결과

중단된 작업은 같은 worktree에서 단계 단위로 재개할 수 있다. 현재 HEAD 검증과 실제 PR 존재 여부가 다음 전이의 기준이 되어 완료 단계 반복과 중복 PR 생성을 줄인다. 다른 질문은 제한하지 않으면서 작업 상태는 세션 밖에 남는다.

체크포인트는 삭제한 worktree, 다른 PC와 새 clone으로 이전되지 않는다. 손상 시 자동 복구하지 않으며 현재 상태를 사람에게 보고한다. 구현 계획 내부의 세부 작업 위치는 AI가 계획과 실제 diff를 읽어 판단한다.
