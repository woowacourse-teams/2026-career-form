# 삼성·SK·CJ 지원서 페이지 검증 기록

## 기록 원칙

- 실제 지원서 페이지의 입력값, 레이블 원문, DOM, selector, URL 경로·쿼리와 세션 정보는 기록하지 않는다.
- 사용자가 직접 로그인하고 페이지로 이동한 뒤 읽기 전용 probe를 실행한다.
- fixture 통과는 실제 사이트 검증을 대체하지 않는다.
- 화면에서 사람이 센 입력 후보와 probe의 `totalCandidates`를 대조한다.
- 모든 후보가 `supported`, `review-required`, `unsupported` 중 하나로 분류되어야 `검증 완료`로 표시한다.

## 자동 fixture 검증

| 구조 fixture | 재현한 특성 | 자동 검증 상태 |
| --- | --- | --- |
| Samsung | 중첩 그룹, native input, ARIA combobox | 통과 |

기업 fixture는 기업별 실제 DOM이나 selector를 복사하지 않은 비식별 구조 예시다.

Chrome에서 다섯 섹션을 순서대로 이동한 뒤 입력값·레이블·DOM 원문을 수집하지 않고 구조 수치만 대조했다. 삼성 페이지는 비활성 섹션의 입력 요소도 DOM에 숨겨 둬 전체 후보 수가 현재 화면 후보 수보다 크다. 따라서 섹션별 가시성 대조가 필요하다.

첫 섹션 대조는 현재 렌더링된 범위만 대상으로 했다. 이어서 아래와 같이 자격 입력 행 하나를 생성해 전후 차이를 확인했지만, 다른 동적 입력 영역과 접근 불가 iframe 내부는 확인하지 못했으므로 삼성 전체 검증 완료를 뜻하지 않는다.

### 삼성 자격 입력 동적 생성

- `+자격 추가` 실행 전: 전체 후보 21, 표시 후보 0
- `+자격 추가` 1회 실행 후: 전체 후보 33, 표시 후보 7
- 증가분: 전체 후보 12, 표시 후보 7
- 표시 후보 유형: text 3, 숫자형 키패드 입력 2, combobox 2
- 현재 분류: `supported` 5, `review-required` 2
- 더 넓은 비표준·탭 가능 요소 휴리스틱의 추가 후보: 0
- 저장·다음 단계 이동·제출 없이 빈 자격 입력 행만 생성했다.

이 결과는 숨겨진 후보도 전체 인벤토리에 포함하되, 동적 필드는 안전한 표시 동작 전후의 후보 차이로 별도 발견해야 함을 보여 준다. 숨겨진 후보 수만으로는 아직 DOM에 생성되지 않은 입력 행을 찾을 수 없다.

## 사용자 수동 검증 절차

1. `npm --prefix spikes/page-analysis run build`를 실행한다.
2. Chrome `chrome://extensions`에서 개발자 모드를 켠다.
3. `spikes/page-analysis/dist/extension`을 압축 해제된 확장 프로그램으로 로드한다.
4. 사용자가 해당 기업 지원서 페이지에 직접 로그인하고 이동한다.
5. 화면의 입력 후보 수를 센 뒤 probe의 `현재 탭 분석`을 실행한다.
6. 동적으로 펼쳐지는 영역은 사용자가 직접 펼친 후 다시 실행한다.
7. 위 표에는 비식별 집계와 누락 수만 기록한다.

## 판정

현재 자동 fixture 검증은 완료됐다. 삼성은 다섯 섹션의 현재 표시 후보 대조와 자격 입력 행 1개의 동적 생성 검증까지 수행한 `부분 검증` 상태이며 다른 동적 입력 영역과 접근 불가 iframe 확인이 남아 있다. SK·CJ는 `미검증`이다. 따라서 Issue #8의 실제 기업 검증 인수 조건은 아직 충족되지 않았다.
