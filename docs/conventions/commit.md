# 커밋 컨벤션

## 형식

```text
<type>: <한글 설명>
```

- type은 영문, 설명과 본문은 한글로 작성한다.
- scope는 사용하지 않는다.
- 제목만 읽어도 달라진 동작이나 구조를 알 수 있게 쓴다.
- 문장 끝에 마침표를 붙이지 않는다.
- 한 커밋에는 한 가지 논리적 변경만 담는다.

## Type

| Type | 사용 기준 |
|---|---|
| `feat` | 사용자 또는 운영자가 사용할 기능 추가 |
| `fix` | 잘못된 동작이나 장애 수정 |
| `refactor` | 외부 동작을 바꾸지 않는 구조 개선 |
| `test` | 테스트, Fixture, 평가셋 변경 |
| `perf` | 성능 또는 자원 사용량 개선 |
| `docs` | 문서만 변경 |
| `chore` | 일반 설정, 도구, 유지보수 |
| `ci` | CI/CD 워크플로우 변경 |
| `build` | 빌드 시스템 또는 외부 의존성 변경 |
| `revert` | 기존 변경 취소 |

## 제목 예시

```text
feat: 삼성 채용 사이트 필드 자동 입력을 지원한다
fix: 동일한 필드가 두 번 입력되는 문제를 수정한다
refactor: LLM 응답 파싱 로직을 분리한다
test: 주민등록번호 오분류 회귀 테스트를 추가한다
chore: 스테이징 배포 환경 변수를 설정한다
```

`수정`, `작업`, `업데이트`처럼 대상이 불분명한 표현만 쓰거나 `WIP` 같은 임시 제목을 최종 제목으로 사용하지 않는다. 구현 수단보다 실제 변경 결과를 중심으로 쓴다.

## Breaking Change

하위 호환성을 깨는 변경은 제목의 `!`와 Footer를 함께 사용한다.

```text
feat!: Fill 요청에 schemaVersion을 필수로 추가한다

BREAKING CHANGE: 모든 클라이언트는 요청에 schemaVersion을 포함해야 한다.
```

API 필드 제거, 필수 요청 필드 추가, 호환되지 않는 응답 구조, 저장 데이터 마이그레이션이 여기에 포함된다. 구버전 Extension의 호환 기간 없이 Breaking Change를 운영에 배포하지 않는다.

## 커밋 분리

다음 변경은 가능한 한 분리한다.

- 코드 포맷 정리와 기능 변경
- 대규모 파일 이동과 로직 변경
- API 계약과 각 컴포넌트 구현
- 평가 기준과 제품 로직 변경
- 의존성 업그레이드와 기능 구현

## Squash Merge

작업 브랜치를 `develop`에 합칠 때 Squash Merge를 사용한다. PR 제목이 최종 커밋 메시지가 되므로 PR 제목도 같은 형식을 따른다. `develop`에서 `main`으로 승격할 때는 Squash Merge를 사용하지 않는다.
